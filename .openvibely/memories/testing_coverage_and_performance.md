OpenVibely has a large Go suite. Durable quality work emphasizes broad behavioral coverage, exact-state validation, and production-shaped performance evidence rather than narrow happy paths, raw logs, task-by-task benchmark notes, or transient hosted-check snapshots.

Coverage and fixtures:
- `internal/service` and `internal/handler` are the broadest seams, especially error, pagination, webhook, retry, scheduling, channel, and orchestration paths. `internal/service/llm_service.go` needs controlled caller mocks to avoid flaky tests.
- `NewTestDB` uses isolated in-memory fixtures from an immutable serialized SQLite template with UTC, foreign keys, busy timeout, one connection, migrated schema, seed data, cleanup, and default-agent behavior. Avoid blanket `t.Parallel()` with shared DB setup.
- Generated `*_templ.go` is excluded from coverage summaries while template tests still run. Prefer behavior over granular tests around already-covered code.
- Runtime/action tests cover ownership, authorization, pagination, mode restrictions, malformed JSON, provider-tool-incapable paths, and case-insensitive JSON-field presence. Explicit numeric zero is tested as supplied invalid input rather than omission.
- Breadcrumb tests cover project/schedule/Chat scope, current-first relevance, bounded pages, executable empty-search index plans, and update/delete visibility. Queued-input recovery covers more than 100 IDs independently for Chat and task threads. Attachment tests cover collision-safe allocation, duplicate deletion, multipart limits, and API Chat setup failure through real endpoints.
- Agent/lifecycle tests cover protected controls, enabled/model persistence, Goal disable rejection, UI hydration, startup reconciliation, disabled-hook filtering, configured model IDs, maintenance schedule synchronization, project ownership, modal hydration fencing, and turn-scoped Agent-definition reuse.
- OAuth tests use injected provider callers and protocol-faithful local fixtures, covering duplicate-account isolation, explicit shared OpenAI/Anthropic connection linking, one-refresh-per-connection background coordination, bounded Anthropic background profile-lookup timeout with later-connection continuation, model-preserving singleflight, stale-revision and model-reassignment rejection, cross-process leases, reauthentication, callback-versus-refresh races, disconnect/delete semantics, Analytics connection-bound snapshots, account-ID persistence, response redaction, startup/shutdown refresh, and migration/rollback idempotence.
- Migration `187`/`190` coverage must prove same-provider exact-refresh-token consolidation, distinct-token isolation even with matching provider identity, stale snapshot fail-closed behavior under revision-number collision, rollback/re-upgrade idempotence, and one background refresh per shared connection.
- External-channel coverage should use production-shaped Slack `processIncomingMessageWithHandoff`, Discord `processIncomingMessage`, and Telegram durable-chat paths to verify selected-project deletion fallback, no stale IDs reaching shared ingress, only-project/fresh-service fallback, later switching, selective eviction, Telegram version fencing, failed-deletion preservation, and deterministic cache-miss/overlapping-switch fencing.
- Provider context-window coverage includes trigger math, safe-limit/output-reservation clamping, final-request accounting after runtime/plugin/model preparation, independent history versus pending-input pressure, oversized pending-input externalization/rejection with durable prompt preservation and authorized bounded artifact reads plus cleanup, complete-request preflight across transports, native-first/provider-affine fallback, typed provider-bound error classification, configuration-scoped native capability decisions, checkpoint compatibility, provider-native opaque-state replay, Anthropic compaction blocks, OpenAI WebSocket/HTTP selection and fallback, Mixture route pinning, queued/immediate failed-retry de-duplication, conservative dense tool replay, and non-escalation of write authorization. Generated multi-megabyte/high-line-count fixtures are preferred over private logs.
- Task-thread tests use multi-megabyte/high-line-count output and native Chromium; asynchronous scanners remain bounded by the owning render deadline and failure renders escaped plaintext. `#1183` bounded Task Detail coverage must exercise non-poll initial and earlier-page thread loads and prove `tasks.prompt` is bounded; poll-only compact metadata coverage is insufficient. Bounded thread-loader coverage for `#1185` includes direct invalid/nil input handling, empty/short/exact/multi-page boundaries, offset advancement, equal-timestamp ordering, budget-stop behavior, and paired browser/channel formatting-preservation regressions.
- Pulse blocked-work regressions cover chain and swarm dependency visibility, blocked-to-pending/queued transitions without duplicates, only-blocked empty-state behavior, project/Chat/terminal exclusion, bounded prompt previews, a 200-row blocked projection cap with aggregate blocked counts, unchanged existing sections/counts, compact runtime output, read-only card controls, and `view_pulse` registry documentation for blocked work.
- Production-shaped Analytics regressions cover real repository and handler contracts for project isolation, half-open date boundaries, Workflow Performance denominators/counts across completed, failed, cancelled, skipped, and open invocation statuses, terminal-only duration samples, historical first-terminal attribution, follow-up/rework counting, separate task-goal outcomes, recorded-cost coverage and time scoping, Agent-definition versus model attribution, empty-result JSON, workflow/skill evidence, URL-persisted views, dynamic-content escaping, chart layering/cleanup, and existing usage/skill surfaces. Large-payload Overview and Agents coverage uses file-backed `1W + 1R` fixtures with many tasks, large execution payload blobs, many usage rows, and skill evidence to prove selected dashboard tabs remain bounded; migration-plan coverage must check the actual production Analytics projections and all selected/aggregated columns, not simplified stand-ins that can miss table-row lookups such as `COUNT(id)`.

Browser and realtime evidence:
- Browser process-group cleanup is separate from concurrency control. The machine-wide browser-test lock/slot plumbing was removed; representative Chromium packages may run concurrently. Reintroduce serialization only with repeated A/B evidence of overlap failures.
- Shared composer and Latest-message regressions use real Chromium input for global Chat and Task Thread. They cover whitespace no-side-effects, padded input, intentional scroll-up, appended streaming content, immediate return-to-latest, Thread replacement, and history lifecycle. Synthetic DOM events are supplemental. Environment-level Chrome GPU/network failures must be reported separately from product failures.
- Live-SSE tests use real routing with many scoped clients across projects/task IDs and verify matching delivery, isolation, and deliberate global streams. Streaming tests cover catch-up, UTF-8 offsets, overlap handling, terminal ordering, slow consumers, and cleanup.
- Native browser input is required for behavior evidence around drag/drop, keyboard controls, focus, selection, popovers, file uploads, composer actions, and scroll tracking. Synthetic events can supplement but should not be the only proof for user interaction regressions.

Performance and SQLite evidence:
- Representative file-backed tests use multiple physical `*sql.Conn` handles and real repositories for production `1W + 1R`, pragmas, WAL pressure, atomic writes, busy behavior, bounded lock waits, timeout restoration, claims, leases, attachments, vacuum, startup serialization, and cleanup.
- Timing phases must outlast the approximately 500 ms output ticker; zero-flush short runs are not topology evidence. Every pooled writer/`RETURNING` path needs deadline, cancellation-only, early-cancellation, timeout-restoration, and failure-cleanup cases.
- Projection claims need direct and end-to-end representative small/large cardinalities with latency, allocations, query/wait counts, response bytes, selected/scanned bytes, contention, and rendered-byte parity. Narrow microbenchmarks are insufficient. The `send_message action=list` saved-target pagination/indexing gap `#1206` requires bounded pages and list-order index coverage; related outbound lookup and channel-status issues (`#535`, `#758`) do not cover the unbounded discovery response. Startup OAuth provider-warning projection (`#1213`) also requires target-branch verification before being treated as resolved. Channel `switch_project` compact selection (`#1254`) has PR-local handler-level projection/query-plan/benchmark coverage in `#1267`, and a 2026-09-19 audit-only review found no material implementation issues; verify merge/target-branch state before relying on it as shipped/resolved.
- Warm multi-operation batches stabilize tiny measurements under coverage. For issue-driven performance work, the live PR body is part of acceptance evidence and must report concrete paired results for every required profile and metric; benchmark source or historical task output alone is not reviewable publication evidence.
- Selector/list evidence requires exact/prefix/contains ordering fixtures, boundary pagination, executable query plans, and write/update/delete scope checks. Compact external-channel context, active admission, project capacity, and other projection optimizations must prove bounded queries and response compatibility.
- Email receipt-first tests observe query/exec counts, MIME work, grouped acknowledgement, retry, and contention. Lifecycle regressions use deterministic blocking fake IMAP clients to hold operations across stop, reload, and removal, then assert stale runs produce no `ProcessIncoming`, task/queued-input handoff, receipt, `Store`, or `Seen` side effects; concrete lifecycle invariants should run under `-race` when required.
- Project-capacity projection evidence should compare the real collection handler with the full-row baseline at representative project counts using file-backed `1W + 1R` SQLite fixtures, realistic wide metadata, mixed worker limits, pending-task rows, response-byte parity, selected-project-byte reduction, latency, allocations, SQL counts, and query-plan coverage.

Validation conventions:
- Prefer `make test`, `make test-cover`, or targeted `go test` with `-count=1 -timeout 120s`; use readiness polling instead of fixed sleeps and `testing.Short()` for timing-sensitive cases. Full CI-style coverage uses `OPENVIBELY_SKIP_BROWSER_PERF=1 go test ./... -count=1 -timeout 240s -coverpkg=./...` including `cmd/server`.
- Use `go test -race` only for a concrete production race invariant or explicit requirement, on the smallest deterministic regression. Do not run performance/allocation gates under the detector.
- Preserve generated-file cleanliness, templ coverage exclusions, packaged-update native/E2E matrices, cache identity/action pins, untrusted-cache handling, setup timing artifacts, and Windows rollback-helper cleanup.
- Distinguish touched-scope defects from environment or known baseline failures. Report the narrower passing scope and exact broad failure; local success cannot replace exact-head hosted checks or live publication evidence.
- A failed exact-head check whose logs or annotations cannot establish cause remains unresolved and must not be classified as baseline/transient or cleared as clean. An exact-head hosted check that is failed or pending blocks a clean publication verdict until resolved or a fresh authorized audit establishes acceptable status.
- Strict read-only audits run no build, test, generation, formatting, benchmark, fetch, commit, push, temporary-file redirection, or other write-capable validation commands and must disclose skipped checks.
