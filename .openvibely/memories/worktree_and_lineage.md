Task execution uses isolated Git worktrees in `.worktrees/task_<id>` with task-scoped branches `task/<id_prefix>-<slug>`. Coding changes for assigned tasks belong in the assigned worktree, not the main checkout, unless the user explicitly requests main-checkout changes. Runtime workdir enforcement is authoritative; prompts only orient the model.

Worktree path and lifecycle:
- When `tasks.worktree_path` exists, it is the effective repository root for relative shell/file operations. `LLMService.ExecuteTaskWithAgent` creates the worktree before execution, synchronizes from the selected target/default branch when clean, and handles post-execution merge.
- Startup sync is a real `git merge --no-edit <target>`. `MergeTargetBranch` wins, followed by local `main`, detected default branch, or `main` fallback; local branches are authoritative and remote-tracking branches are not fetched implicitly.
- Setup fails closed. Local commits need no remote, but an unborn repository has no tree for `git worktree add`; never dispatch a coding model in the main checkout when setup fails.
- Auto-merge and Task Changes support merge, fast-forward-only, and squash. Rebase is shown only when both branches have unique commits and no active conflict. Cleanup respects after-merge/keep/manual policies and skips locked, dirty, or unmerged worktrees. Follow-up lineage carries `base_branch`, `base_commit_sha`, and `lineage_depth`.
- Follow-ups to merged, stale, conflict-aborted, or squash-accepted tasks start fresh `task/<id>-followup-*` lineage from the current target; historical branches are read-only lineage. An active dirty/local follow-up worktree may be reused.
- Active managed-worktree Changes resolve the target/task merge base against committed, staged, unstaged, and untracked state. Full Changes, file summaries, lazy cards, live fragments, periodic snapshots, follow-up persistence, and direct file/tab requests must share that resolution.

Sandbox and safety:
- A confirmed incident edited the main checkout when prompt/tool orientation pointed there despite an assigned worktree. The durable fix is one `executionRoot` derived from `tasks.worktree_path`, shared by shell and file resolution for initial runs and follow-ups.
- Writes outside the sandbox require explicit outside-workspace permission/bypass; absolute paths and shell `cd` cannot be trusted to stay within cwd. Intentional project-root writers such as `.openvibely` system agents retain explicit scope configurations, while normal scoped roots resolve against `executionRoot`.
- Automation prompts must not present the main checkout as the operative repository root. Do not add hard containment or deterministic prompt rewriting unless explicitly requested; intentional absolute paths remain a separate policy choice.
- Open security bug `#30`: untracked-file diff synthesis can follow a symlink outside the repo. Skip symlinks and enforce resolved-worktree containment before reading.

Commit, merge, and publication evidence:
- Auto-commit and GitHub publication subjects come from actual worktree diff facts, not conflicting task title/prompt/output. Use concise capitalized imperative language without provider/tool/status boilerplate, task scope, machinery, or `Changed files:` bodies. Do not follow untracked symlinks while collecting snippets.
- Manual merge conflicts are handled outcomes. Changes-tab rebase conflicts abort and guide recovery; an aborted rebase alone must not persist `MergeStatusConflict`. Fast-forward-only merges skip needless rebase when ancestry permits it. When the user requests rebase-only preparation for a fast-forward-only merge, rebase the actual task branch onto the current local target and leave `main` untouched; verify `0 behind / n ahead`, clean status, and no task-side merge commit before handing back. Dirty but non-overlapping target changes are allowed; Git overwrite/refusal without unmerged files is a merge failure.
- Revalidate stale `merge_status` and recover conventional worktree metadata before hiding/rejecting merge actions. A conflict-resolution commit does not itself clear persisted conflict status; a branch is merged only when fully reachable from target. Changes-tab merge failures that leave the branch/worktree recoverable must reload authoritative task/Git state and return a refreshed Changes fragment with failure feedback so retry actions remain available; genuine conflicts instead expose Resolve/Abort recovery controls while ordinary merge actions stay hidden. All Changes action-menu controls use a menu-wide `hx-disabled-elt` guard, and `WorktreeService.MergeBranch` has a canonical repository-path lease with `ErrMergeInProgress`; handler merge requests now re-fetch task state and revalidate eligibility and ancestry through a lease-held validator immediately before Git or task-status mutation, returning `ErrMergeEligibilityChanged` when the state changed. Rebase POSTs use the same complete task/repository/branch/target/status/merged/conflict eligibility gates plus actual two-sided divergence availability. Squash conflicts without `MERGE_HEAD` are restored to retryable failed state using only paths introduced by the squash/conflict, preserving unrelated staged work; legacy no-`MERGE_HEAD` recovery uses task-scoped path restoration instead of unusable `git merge --abort`.
