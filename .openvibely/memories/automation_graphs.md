Automation Graphs is a project-scoped, reviewable orchestration surface built on existing OpenVibely tasks, schedules, workers, queues, Alerts, GitHub services, repositories, and current-graph provenance. It does not introduce a parallel graph executor, queue, worker, or arbitrary-code runtime.

Canonical authoring format (2026-08-07):
- Automation YAML is the sole configuration authoring surface. Template, Describe, Custom, and saved Edit flows serialize to deterministic YAML. Graph mode is interactive for browser-local topology and layout only: add/delete nodes, connect/reconnect/delete edges, and move nodes write the corresponding graph changes back into YAML; node and edge configuration is edited only in YAML and no settings cards are rendered.
- YAML uses schema version 1 and the existing candidate model (`name`, `description`, `automation_type`, `adapter_key`, nodes/configuration/positions, edges/ports/conditions, assumptions, warnings). Strict parsing rejects malformed or multi-document YAML, aliases/anchors, duplicate keys, non-string mapping keys, unsupported fields, and unsupported scalar tags before the existing normalize/validation/compiler path rejects invalid graph topology, configuration, capabilities, provenance, lifecycle, and authorization.
- Existing saved graph-backed Automations are compatible through serialization on read. They are not migrated or silently rewritten, and opening/previewing YAML does not recreate resources or replace point-in-time prompts/configuration.
- Preview/Live YAML is read-only; Edit YAML is browser-local until Save. Save and Preview share the existing validation/compiler path and atomic resource transaction.

Architecture and safety boundaries:
- Supported web creation paths are Template, Describe, and Custom. Custom is the runnable blank builder. New maintained templates are Native SDLC and GitHub SDLC; the internal Vision Driver adapter remains only for already-saved graph reconstruction.
- Each Automation has exactly one current saved graph. There is no retained Automation version history, superseded graph, web-facing draft, staged publication, or failed-publication recovery model. Internal graph revision IDs exist only to isolate stale or currently running execution state; they are not durable Automation or mailbox identities.
- Pending Native alerts and GitHub issues must remain owned by the same logical mailbox after an Automation edit. Durable ownership is keyed by stable Automation identity plus stable logical mailbox identity, not by the replaceable internal graph revision or physical node ID.
- Trigger schedules have exclusive ownership. Worker/inbox resources may be shared only when an adapter explicitly permits it.
- Runtime persistence covers current-graph invocations, leased dispatch, reservations, work items, activities, transitions, live projection, metrics, and health. Replacing a graph deletes runtime projection tied to the old graph.
- Do not discover, infer, migrate, or backfill resources created before Automation Graphs. Existing saved Automations are point-in-time snapshots and registration reruns do not silently rewrite them.
- Human approval and downstream-risk boundaries follow the canonical project-scoped notification contract in `alerts_and_actionable_notifications.md`: approval may authorize the configured implementation handoff, but never merge, release, deployment, destructive remediation, credential changes, or arbitrary execution.
- Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, duplicate keys, unsupported conditions/types, unsafe configuration, foreign-project references, and arbitrary executable behavior fail closed with no resource effects.

Builder, YAML, and Save contract:
- YAML is the canonical Automation authoring format for Template, Describe, Custom, and saved Edit flows. The complete YAML document is browser-local until `Save changes`; refresh or navigation discards unsaved work.
- The canonical YAML schema expresses Automation metadata, nodes (including supported type-specific configuration), edges, schedules, task prompts/goals, agents, models, tools, skills, lifecycle-compatible settings, and maintained-template-specific configuration. Graph-to-YAML serialization is deterministic and readable.
- YAML is decoded through the single strict conversion boundary into the existing canonical graph candidate, then normalized, validated, previewed, and atomically compiled through the existing runtime path. It rejects malformed or multi-document input, duplicate keys, aliases, non-string mapping keys, unsupported or unknown fields, invalid types, unsafe configuration, dangling endpoints, invalid topology, and all other canonical validation failures with no resource effects.
- Graph-backed saved Automations remain compatible through serialize-on-read: reopening or previewing produces YAML from the saved canonical graph without a migration, silent rewrite, prompt replacement, or resource recreation.
- Edit presents an editable YAML document in the same plain code-panel shell as Live's read-only YAML view; it has no `Automation YAML` label, configuration explainer, or standalone `Preview YAML` action. The Graph/YAML selector is the only mode control. The visual graph editor remains browser-local topology and layout editing only: YAML is the sole configuration and submitted/Save source; legacy node-card and edge-settings controls are absent. Every canvas mutation updates YAML. A manually edited YAML document is preserved for Graph/Save; selecting Graph submits it through the strict decode/validate path before applying the topology/layout mutation and returning canonical YAML. Web Preview now calls the compiler's non-persisting `PreviewSave` path, so it matches Save-only capability and agent validation without persistence. Live presents saved YAML and rendered graph read-only.
- Orchestrate Chat creation is direct: an explicit user request to create or save an Automation authorizes one `save_automation` runtime-tool call that generates, validates, and atomically saves through the normal compiler, then returns the Live URL. Plan mode remains read-only, and generation, validation, or Save failure creates no resources.
- Selecting a template loads its embedded canonical YAML through the same strict YAML decoder used for authoring, without creating an Automation, Task, Schedule, graph row, or runtime resource. Native SDLC and GitHub SDLC maintained templates remain editable starting graphs.
- Save submits the complete YAML document, validates its compiled graph, and atomically creates or replaces the current graph and its resource membership under the same Automation identity. Unsupported executable shapes cannot be stored as inert drafts.
- Save uses one database transaction for Automation identity, current graph, Task/Schedule materialization and updates, topology, lifecycle-compatible admission, and old runtime-projection removal. After commit, authoritative pending Active roots that became runnable are submitted.
- Automation Schedule and ordinary Task nodes expose an optional per-node task goal. Saving a non-empty configured goal persists it atomically with the materialized Task; a Native or GitHub implementation projection node carries the configured goal to each runtime-created implementation Task. Goal text is bounded to 2,000 characters. GitHub issue-task creation treats the persisted implementation-node goal as authoritative over a model-supplied `create_task` goal; Native inbox prompts direct the atomic alert implementation-task action to receive the configured goal.
- Preview and Save share the same Task-materialization rules. Schedule-owned and ordinary Task nodes materialize; Native projection-only implementation nodes and GitHub issue-specific configuration Task nodes do not.
- Save preserves Active, Paused, and Archived lifecycle state. Active Automations enable all owned Schedules; Pause and Archive disable them and demote pending Active current-graph work; Resume restores eligible lifecycle-demoted work. Per-schedule enabled intent is not part of the current model.
- New canonical Schedules explicitly use `clear_context_on_start=true`. Trusted Edit/Save preserves an older bound Schedule value when graph metadata omits the key.
- Existing saved Automations are point-in-time prompt snapshots. Registration reruns and ordinary reopen/Edit/Save preserve an existing persisted prompt rather than replacing it with corrected maintained defaults. Adopting a corrected maintained prompt currently requires manually replacing the prompt or recreating the Automation; any automatic maintained-prompt upgrade must be an explicit mechanism with regression coverage that begins from a stale persisted prompt.
- Maintained Native and GitHub SDLC templates are starting graphs, not fixed schemas: every template node may be deleted. The retained graph is authoritative, using the same configuration model as Custom Automation. A producer or Loop Auditor with no action edge is a valid standalone schedule; retained Native/GitHub action and workflow stages determine capability readiness and runtime authorization, not prompt wording or separate metadata. There is no maintained-template `required_capabilities` field or builder checkbox. Validation applies general executable handoff, role/topology, configuration, capability, and safety rules to the nodes and edges that remain, with precise role-specific errors for invalid reduced graphs. Preview and Save materialize only adapter nodes present in the submitted graph. Removing a node removes its owned Schedule/resource membership and only its incident edges, while preserving other producers' edges to a shared action and any durable backing Task required by resource-ownership semantics. Re-adding a maintained node may reclaim only the unique, unbound, unscheduled same-project Task whose durable `automation:<automation-id>:<node-key>` origin exactly matches that Automation and node; ambiguous, cross-Automation, or still-bound candidates fail closed. Both unmodified maintained templates and valid reduced graphs remain saveable.
- The maintained-template Add node modal always offers the allowlisted Custom Automation capabilities as well as explicit `Restore:` choices for deleted canonical nodes. User-added nodes, identified by keys absent from the maintained adapter, use Custom Automation configuration validation, topology/resource materialization, and graph-bound prompt behavior; canonical SDLC nodes retain their specialized configuration and runtime behavior. Template-only `skills` and `source_files` configuration is accepted only for canonical task-configured nodes. On Native/GitHub SDLC builder or Edit submissions, the handler removes only these two obsolete fields from noncanonical nodes after decoding stale legacy `candidate_json`, before validation; canonical fields remain intact and every other unknown custom configuration fails closed. Edges wholly between added nodes use Custom topology rules, while edges touching a canonical node remain subject to maintained-template handoff rules. Vision Driver remains closed to arbitrary added topology.

Runtime and approval contracts:
- Automation execution projects state onto the current graph while using normal Task, worker, Scheduler, Alert, and GitHub runtime paths.
- A protected Goal Agent continuation for an Automation-created implementation Task must recover that Task's trusted current Automation bindings; queued input persists those bindings. Do not infer bindings when the Task has no trusted Automation provenance.
- `Run now` is a manual internal dispatch of each schedule-owned entry Task using its persisted prompt, Agent, model, and tool configuration. It does not mutate Schedule timing, skips queued/running/reserved entries, and rejects Paused or Archived Automations. Refresh generations and Automation identity checks prevent stale Live responses from replacing newer state.
- Native notification handoffs use the canonical actionable-notification lifecycle: explicit approval, lease-based claim, atomic Backlog implementation-task creation/linkage, execution of the exact linked task, then processing completion after execution starts. Inbox processing must collect every stable eligible page before mutations because linkage changes the result set.
- Scheduled Native inboxes derive scope from the persisted caller Task and scan both read states. Automation-origin notification metadata is routing evidence only; durable authorization is separately keyed by project, Automation, artifact, and logical graph identities. Foreign, forged, renamed/removed-mailbox, and untracked artifacts fail closed.
- GitHub assignment to a configured authorized identity is the approval to implement. GitHub issue implementation Tasks are Active and auto-submit; `execute_tasks` is only for reconciled Backlog or failed/cancelled work. Native intentionally creates Backlog work and executes that exact linked Task.
- Every external mutation reloads persisted Task and current Automation context. Automation graph bindings authorize exact downstream actions; visible GitHub tools do not authorize a mutation, and local work does not prove PR publication.
- Loop Auditors are inspect/report-only: their direct task-creation, swarm-creation, and task-execution tool grants are removed based on their durable `automation:<id>:auditor` origin. They retain discovery/reporting capability. The user explicitly deferred further restriction of their alert/claim tool grants.

GitHub repository and duplicate boundary:
- Automations use the selected project's repository identity: explicit `repo_url` first, otherwise a GitHub remote from the local checkout. Automation prompts/tools cannot override it.
- GitHub publication readiness requires usable provider authentication, at least one visible GitHub Authorized User, and a resolvable project repository. Missing readiness fails before creating Automation, Task, or Schedule rows.
- Finder roles use trusted local duplicate state keyed by project, normalized repository, and stable finding idempotency key. Maintained keys derive from role, primary component, and stable symbol/behavior, never run IDs, dates, or random values. Ambiguous provider outcomes fail closed.
- Native notifications and GitHub issues begin with a short nontechnical `Summary`, followed by technical evidence, risk, implementation guidance, acceptance criteria, references, and regression cases. Bug findings require a concrete failure path; optimization findings require measurable evidence; redundancy findings require repeated locations and minimal consolidation.
- GitHub Dev Inbox scans configured authorized users and the PAT identity when available, deduplicates by repository/issue, and creates implementation work only after assignment approval and task/PR reconciliation. It does not carry a persistent completion goal; implementation Tasks do.
- Automation-bound GitHub SDLC turns cannot post issue-status comments. `github_open_pull_request` requires `## Summary`, `## Validation`, and an exact `Closes #<source issue>` reference, with request issue data matching trusted Task provenance. Non-Automation PR behavior remains generic.

Custom graph contracts:
- Describe It and direct Chat Save share the web builder's schema, capability snapshot, normalization, validation, compilation, and atomic Save path. Generation has no mutation tools; only `save_automation` commits a candidate.
- Edges use `from`/`to` with `from_port: right` and `to_port: left`; aliases, invalid ports, dangling endpoints, and invalid geometry fail strict validation. Schedule/Task priority is `1..4`.
- A custom Native mailbox is `Schedule/Task → Create notification → Human approval → Approved inbox → Implementation projection → Outcome`. A custom GitHub mailbox is `Schedule/Task → Create GitHub issue → Human assignment → GitHub inbox → Task projection → Open pull request → Human review → Outcome`. Native and GitHub mailbox stages cannot mix.

UI and current-state facts:
- Saved Edit uses `Automations / [editable automation name]`; unsaved builders retain their separate name field. Saved Edit and Live place primary actions in the breadcrumb header and keep the kebab for lifecycle/template/delete actions only. Saved pages use concise `Edit`, `Run`, and `Save` labels; unsaved builders retain `Save changes`.
- Graph/YAML switching is implemented throughout builder, Edit, and Live. Builder/Edit YAML is the only configuration and submitted Preview/Save source; the editable panel matches Live YAML styling, fills the available builder-card height, and its textarea grows with the panel rather than using a separate resize-driven height. It omits authoring chrome and a separate preview button. Selecting Graph is the non-persisting compiler PreviewSave validation/render transition. Their Graph mode supports browser-local topology and layout editing only: add/delete nodes, connect/reconnect/delete edges, and move nodes, each synchronizing back to YAML. Node and edge configuration remains YAML-only; legacy node/connector settings cards are absent. Live renders both saved YAML and graph read-only.
- Automation detail is one Live graph; historical definition/invocation/work-item/version pages are not product surfaces and return `404`. Portfolio cards show compact adapter/lifecycle/health state and use the shared searchable-card pattern.
- Saved-template revision is nullable. Maintained Native/GitHub templates currently use revision `1`; stale maintained graphs expose destructive `Update to latest template`, which replaces the graph atomically while retaining only the Automation name. Ordinary edits preserve the saved revision.
- Live/portfolio state treats repeated invocation-scoped executions of one Task as retries, using the latest activity sequence for state.
- The YAML editor shell renders a syntax-highlighted overlay layer behind the native textarea: YAML keys are colored with the primary theme color (not warning/amber), string values use the info color, booleans/numbers/null use secondary, and comments are dimmed. Leading indentation is rendered as muted vertical-line and dot guide characters in the overlay (non-editable `pointer-events-none absolute` children over a reserved `relative inline-block` space, not inline text). The textarea has an explicit `caret-color: oklch(var(--bc))` so the cursor remains visible while the text is transparent. The parser-reported error line is underlined with a red wavy squiggle inline in that layer using `text-decoration-color: oklch(var(--er))` (via inline `style`). Word wrap is disabled (`whitespace-pre`, `overflow-auto` for horizontal scroll) so long lines extend horizontally; this sidesteps caret-positioning bugs in multi-section documents. Fold/collapse controls are hidden (`yamlFoldingEnabled = false`, fold-control lane marked `hidden`) — the fold machinery (JS variables, event handlers, range computation) is dormant but preserved for future re-enablement. The gutter width is reduced (`min-width: 3.25rem`, `pr-2`) since no fold-button lane is reserved. The `mouseup` click-correction listener is removed since hanging-indent wrap divergence no longer occurs.
