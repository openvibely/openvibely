Automation Graphs is OpenVibely's project-scoped, reviewable orchestration surface. It compiles visible Tasks, Schedules, Alerts/GitHub handoffs, workers, queues, and current-graph provenance; it is not a parallel graph executor, queue, worker, or arbitrary-code runtime.

Canonical authoring and persistence:
- Automation YAML is the sole configuration authoring surface for Template, Describe, Custom, direct Chat Save, and saved Edit flows. Graph mode is browser-local topology/layout editing only; node and edge configuration stays in YAML.
- YAML uses schema version 1 and the existing candidate model (`name`, `description`, `automation_type`, `adapter_key`, `nodes`, `edges`, `configuration`, `positions`, `assumptions`, `warnings`). Strict decoding rejects malformed or multi-document YAML, aliases/anchors, duplicate keys, non-string mapping keys, unsupported fields/tags, unsafe configuration, invalid topology, unsupported capabilities, and foreign-project references before any resource effects.
- Chat `save_automation` accepts exact canonical Automation YAML through `source: "yaml"` plus `automation_yaml`, uses the same compiler PreviewSave/Save pipeline and project capability validation as the browser builder, and returns the normal saved Automation URL/lifecycle/active response. Malformed, unsafe, unsupported, or project-invalid YAML returns controlled validation errors without creating Automations, Tasks, Schedules, or resources. Raw candidate identity/version payloads remain unsupported model input; handler-side validation rejects stale/raw top-level fields such as `candidate`, `candidate_json`, `automation_id`, `version_id`, `plan_revision`, `token_id`, and `confirming_user_input_id` before YAML decode/save, with no Automation, Task, Schedule, or resource effects.
- Issue `#650` / PR `#663`: Chat Automation lifecycle actions `run_automation_now`, `pause_automation`, and `resume_automation` are Orchestrate-only write actions; Plan mode stays read-only. Runtime execution resolves exact current-project Automation IDs or case-insensitive exact names, returns controlled ambiguity/unknown/archived/foreign-project errors before mutation, reuses `AutomationLifecycleService.RunNow`, `Pause`, and `Resume`, and returns compact prompt-safe results with Automation ID/name/lifecycle state, Live URL, and started invocation IDs for run-now. 2026-08-17 recovery reset the local task branch/worktree from contaminated merge commit `6c30f507b76726a30252bd9d9d59f0635bf2be90` to verified live PR/source head `880eb609bd9a2d8e5f2f26ebeeb4702f87e314b9`, preserving the old tip at `backup/ta[REDACTED]`; the local diff is back to the PR/source scope and excludes `internal/handler/alert_handler.go` and `internal/handler/alert_handler_test.go`. - Draft schedule config validation is shared by custom trigger schedule nodes and maintained adapter schedule resources for `run_at`, `repeat_type`, `repeat_interval`, `enabled`, and `clear_context_on_start`; maintained adapters keep separate `schedule_target` validation.
- Existing graph-backed Automations serialize to YAML on read for compatibility. Opening, previewing, or saving does not silently migrate, rewrite prompts, replace point-in-time configuration, recreate resources, or backfill pre-graph resources.
- Each Automation has exactly one current saved graph. Internal graph revision IDs isolate runtime state but are not durable Automation or mailbox identities.
- In Automation origins and ownership keys, `automation_id` means the saved Automation row's internal `automations.id`, not the adapter/template key, maintained template name, or display name. Human-readable examples like `github-sdlc-automation` are placeholders; real origins look like `automation:<automation-id>:<node-key>`.
- Save atomically persists Automation identity/current graph, materialized Tasks/Schedules, topology, lifecycle-compatible admission, resource membership, and old runtime-projection removal in one database transaction. After commit, eligible Active roots are submitted.
- Automation compiler PreviewSave and Save share the same save-candidate validation helper for normalization, project validation, capability checks, and agent-reference checks. Preview returns the normalized candidate and validation issues; invalid Save fails before persisting Automations, tasks, schedules, or resources.
- Save preserves Active, Paused, and Archived lifecycle state. Active enables owned Schedules; Pause/Archive disable them and demote pending current-graph work; Resume restores eligible lifecycle-demoted work. Per-schedule enabled intent is not separately modeled.
- New canonical Schedules use `clear_context_on_start=true`; trusted Edit/Save preserves older bound Schedule values when graph metadata omits the key.
- Automation Schedule and ordinary Task nodes can carry a per-node task goal bounded to 2,000 characters. Task-execution nodes can carry `model_config_id`; blank, missing, or the sentinel value `default` mean the normal task execution fallback (`Task.AgentID`, then project `DefaultAgentConfigID`, then global default), while explicit configured model IDs materialize into `tasks.agent_id` and therefore use the existing task execution model-selection path. Native SDLC implementation nodes intentionally expose only `goal` plus `model_config_id` in Preview/Edit because runtime task prompt is supplied by the Approved Inbox. GitHub SDLC implementation nodes expose static prompt/category/priority plus optional `model_config_id` because assigned issues create Active implementation Tasks before PR handoff.
- New Native/GitHub SDLC template creation through the web builder or chat `save_automation` template source fills blank or missing task-node `model_config_id` values with the literal sentinel `default`, not the current default model's configured ID. Saved Automation YAML can retain `model_config_id: default`; materializing real Tasks treats it as no explicit model so `tasks.agent_id` remains empty and the current project/global default is looked up dynamically at run time. GitHub SDLC runtime-created implementation tasks pass the same `default` sentinel through generic task creation to suppress model auto-selection. Manually supplied YAML and already-saved Automations keep their persisted or omitted model values.

Maintained templates keep their long prompt text/template-owned configuration, canonical restore-node paths still append nodes from the template palette, and equivalent manually added Native/GitHub inbox nodes now match maintained-template common defaults including `run_at: "10:00"` and `model_config_id: default`. - Existing saved Automations are point-in-time prompt/model snapshots. Registration reruns and ordinary reopen/Edit/Save preserve persisted prompts/model selections; adopting corrected maintained defaults requires the explicit maintained-template update path, manual replacement, or Automation recreation.
- Maintained-template update availability is gated by `CurrentAutomationTemplateRevision(adapterKey)`. Bump the adapter revision when embedded Native/GitHub SDLC template YAML changes so existing lower-revision Automations can show update controls. As of the 2026-08-16 task-node model selector branch, Native SDLC was revision 7 and GitHub SDLC was revision 5. Builder and UI contracts:
- Supported web creation paths are Template, Describe, and Custom; Custom is the runnable blank builder. Native SDLC and GitHub SDLC are maintained starting templates. Vision Driver remains internal for already-saved graph reconstruction.
- Template selection loads embedded canonical YAML through the same strict decoder without creating an Automation, Task, Schedule, graph row, or runtime resource.
- Saved Edit, maintained Template selection, Custom blank creation, and Describe-generated builders use `Automations / [editable automation name]`; the name is edited in the breadcrumb and primary save actions live in the breadcrumb header. Details-view header saves must submit the edited breadcrumb `automation_name` with Details form values.
- Live primary actions live in the breadcrumb header and reserve the kebab for lifecycle/template/delete actions.
- Builder/Edit YAML is browser-local until Save. Selecting Graph validates through non-persisting PreviewSave before applying topology/layout mutations. Live renders saved YAML and graph read-only.
- Live background refreshes may swap the detail fragment, but must preserve the selected Graph/Details/YAML view per visible Automation and reset that memory when the Automation ID changes.
- The Live/read-only YAML panel should visually match the Edit YAML shell for line numbers, syntax highlighting, indentation guides, no word wrap, and horizontal scrolling, while remaining non-submittable and read-only.
- Automation YAML highlighting intentionally keeps string values neutral (`text-base-content/80`) whether quoted or plain so graph-drag reserialization does not visibly change value colors; booleans, numbers, and null values keep scalar coloring (`text-secondary`).
- Fold/collapse controls and word wrap are disabled to avoid correctness bugs. Dormant fold machinery may remain in source, but no fold buttons should render until deliberately re-enabled with regression coverage.
- The visual graph editor can add/delete nodes, connect/reconnect/delete edges, and move nodes. Every canvas mutation updates YAML. Add-node modal edits must not reserialize or discard unsaved manual YAML edits until the dialog is submitted.
- Canvas-generated YAML should use readable block-style YAML for nested maps/arrays rather than inline JSON blobs.
- Details view destructive node/edge controls use icon-only trash buttons with descriptive `aria-label`s.
- Describe-generated Automation review/save pages use the editable breadcrumb/header-save shell. Details-view header saves must preserve breadcrumb renames by submitting synced `automation_name` from `automation-details-form`.
- Maintained Template selection aligns with the saved maintained-template Edit shell for the Add Node modal. Template preview should not show a separate browser-local `Suggested nodes` section.

Maintained templates and custom graph contracts:
- Maintained Native and GitHub SDLC templates are starting graphs, not fixed schemas. Every template node may be deleted, and valid reduced graphs remain saveable.
- As of 2026-08-08, maintained Native and GitHub SDLC templates have five scheduled roles and no Loop Auditor: Vision Suggestions, Bug Finder, Optimization Finder, Redundancy Finder, and the Native/GitHub inbox. Loop Auditor is also absent from canonical restore-node metadata for new maintained templates.
- The retained graph is authoritative: action/workflow stages determine capability readiness and runtime authorization, not prompt wording or separate required-capabilities metadata.
- A producer with no action edge is a valid standalone schedule. Removing a node removes its owned Schedule/resource membership and incident edges while preserving valid shared targets and durable backing Tasks required by ownership semantics.
- Re-adding a maintained node may reclaim only the unique, unbound, unscheduled same-project Task whose durable `automation:<automation-id>:<node-key>` origin exactly matches that Automation and node; ambiguous, cross-Automation, or still-bound candidates fail closed.
- The maintained-template Add Node modal offers Custom Automation capabilities plus explicit `Restore:` choices for deleted canonical nodes. User-added nodes use Custom Automation validation/materialization; canonical nodes retain specialized maintained behavior.
- Custom Native mailbox topology is `Schedule/Task -> Create notification -> Human approval -> Approved inbox -> Implementation projection -> Outcome`.
- Custom GitHub mailbox topology is `Schedule/Task -> Create GitHub issue -> Human assignment -> GitHub inbox -> Task projection -> Open pull request -> Human review -> Outcome`.
- Native and GitHub mailbox stages cannot mix. Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, unsafe configuration, and arbitrary executable behavior fail closed with no resource effects.
- Custom Automation Describe/repair generation follows the runtime contract that open issues assigned to the PAT owner or configured GitHub Authorized Users are eligible even when manually created in GitHub. Generated GitHub inbox prompts should identify connected upstream producer stages as issue sources only, not eligibility limits, and must not rely on producer-branch creation records.

Runtime and approval contracts:
- Runtime projects state onto the current graph while using normal Task, Scheduler, Alert, GitHub, worker, and queue paths.
- Trigger schedules have exclusive ownership. Worker/inbox resources may be shared only when an adapter explicitly permits it.
- Runtime persistence covers current-graph invocations, leased dispatch, reservations, work items, activities, transitions, live projection, metrics, and health. Replacing a graph deletes runtime projection tied to the old graph, so durable authorization for long-lived external handoffs must be keyed independently of graph-version rows when the artifact/task relationship must survive graph replacement.
- Scheduled Automation execution contexts snapshot the schedule owner's graph version and physical trigger node when the occurrence is claimed. If an Automation is saved while that occurrence is already running, the in-flight execution still carries the old binding; external mutations may fail after save unless stale-binding repair explicitly authorizes the same logical action.
- Resolved stale issue-creation authorization class: an already-started Automation execution may keep launch-time `github_create_issue` authority after a graph save when the current graph still contains the same logical producer node connected to the same issue-creation action. Destructive mutations such as branch replacement stay stricter.
- Initial Automation-dispatched GitHub implementation runs mark Automation-created tasks as `OriginTask`, so `github_open_pull_request` can use durable issue-task provenance on first runs as well as follow-ups after graph replacement.
- Native notification durable ownership is keyed by stable Automation identity plus alert artifact in the project, not replaceable graph revision IDs, physical node IDs, automation hashes, or producer/action/approval/inbox topology keys. Native alert owner rows are effectively `project_id + automation_id + artifact_type='alert' + artifact_id`.
- A current active same-project Native inbox for that Automation proves live processing authority, and projection rebinding discovers the current `producer -> create_notification -> native_approval -> native_inbox` role path instead of matching old node keys.
- GitHub issue mailbox-owner mappings were retired on 2026-08-08; assigned GitHub issues are discovered/reconciled by the current inbox scan and exact execution provenance, not `automation_artifact_mailbox_owners` rows.
- GitHub and Native SDLC finder duplicate prevention is trusted-local and existing-work-first, not based on LLM-authored `idempotency_key`. Maintained prompts, embedded templates, bootstrap skills, user guides, and model-facing `github_create_issue` / `create_notification` schemas do not expose `idempotency_key`; missing keys do not fail Automation-bound issue/notification creation, and hidden supplied keys are ignored by SDLC runtime paths. Finders must list existing Automation-owned GitHub issues or Native notifications first, inspect compact metadata, optionally hydrate likely matches, skip covered findings, and create at most one new issue/notification only when no adequate existing work exists. Optional backend/direct-caller idempotency support remains separate for generic tools and unrelated lifecycle/config mutation idempotency. Future duplicate safeguards should derive from stable structured facts such as project, repository, role, component, file/symbol, behavior, and failure mode where possible.
- Runtime work-item projection may lazily repair durable external artifacts across graph replacements only when exact provenance can be mapped through live origin graph versions and stable node keys. Stale discarded-version GitHub issue work items should delete blocking local projection state before re-anchoring to the current graph.
- Human approval follows the canonical Alerts/GitHub contract: approval authorizes configured implementation handoff only, never merge, release, deployment, destructive remediation, credential changes, or arbitrary execution.
- Native notification handoffs use project-scoped actionable notification lifecycle: explicit approval, atomic lease claim, atomic Backlog implementation-task creation/linkage, execution of the exact linked task, and processing completion only after execution starts. Inbox scans must collect all eligible pages before mutation because linkage changes list membership.
- Scheduled Native inboxes derive project scope from the persisted caller Task and scan both read states. Automation-origin metadata is routing evidence only; durable authorization is separately keyed by project, Automation, and alert artifact while current active inbox identity supplies live processing authority.
- Native Approved Inbox Live can legitimately show `Running` from hidden/internal Automation state even when no ordinary Active-column task card is visible. If scheduled inbox Task, inbox activity, active work-item position, and pending queued input are all false while the node still shows `Running`, treat it as a stale-running projection bug.
- GitHub assignment to the PAT owner or a configured Authorized User is approval to implement. GitHub issue implementation Tasks are Active and auto-submitted; `execute_tasks` is only for reconciled Backlog or failed/cancelled work.
- Every external mutation reloads persisted Task and current Automation context. Visible GitHub tools do not authorize mutation by themselves, and local work does not prove PR publication.
- GitHub SDLC implementation tasks with durable issue-task provenance require live verified open/reviewable PR evidence before final task completion. `TaskPullRequestService.openForTask` publishes the branch, records `task_pull_requests.published_head_sha`, ignores closed branch PRs, and creates/persists or reuses an open PR only when live GitHub state is open, on the task branch/repository, and `head.sha` matches the recorded published head. The published-head SHA match is publication evidence for implementation completion, not an Automation graph completion signal.
- Missing PR rows, non-open rows, rows lacking a published head, and live PRs whose head SHA differs from the recorded publication head block completion; the task is finalized failed/backlog with a visible failure message and alert.
- Loop Auditors are inspect/report-only for direct task/swarm/execution creation; those grants are removed based on durable `automation:<id>:auditor` origin. The user deferred further restriction of alert/claim tool grants.
- `Run now` manually dispatches each schedule-owned entry Task using persisted prompt, Agent, model, and tool configuration. It does not mutate timing, skips queued/running/reserved entries, and rejects Paused or Archived Automations.
- Automation start feedback is keyed to successful invocation creation/claim plus dispatchable work, before per-node task activity. Successful manual and scheduled starts publish a project-scoped `automation_invocation_started` event carrying the Automation display name; skipped/busy invocations refresh state without showing a misleading running toast. Automation-start toasts navigate to the Automation Live/detail page when clicked, while deduping by invocation rather than by task.
- Automation scheduled occurrence idempotency is scoped to Automation-owned schedules. Occurrences dedupe by schedule ID plus scheduled time; crash recovery should reuse/recover committed occurrences rather than intentionally starting a second invocation for the same schedule/time.
- If an enabled repeating Automation schedule still points `next_run` at a terminal past invocation for the same scheduled time, the Automation claim path advances `next_run` instead of returning the old invocation forever.
- Automation Live no longer surfaces manual `GitHub state`, Fresh/Stale badge, persisted-update timestamp, or `Refresh GitHub state`. `AutomationReconciler` refreshes stale tracked PR state in the background only while the Automation Live page is recently open/polling, using `AutomationLiveViewTracker`.

GitHub and notification content standards:
- Automations use the selected project's repository identity: explicit `repo_url` first, otherwise a GitHub remote from the local checkout. Automation prompts/tools cannot override it.
- GitHub publication readiness requires usable provider authentication, at least one visible GitHub Authorized User, and a resolvable project repository before creating Automation, Task, or Schedule rows.
- Existing-work listing tools support finder duplicate prevention without preflight prompt injection or post-finder fuzzy dedupe. `github_list_existing_automation_issues` returns compact current-repository issue metadata for PAT-created issues, without body excerpts. `list_existing_automation_notifications` returns compact project/Automation-owned Native notification metadata through durable alert owner rows, without messages, bodies, metadata, or idempotency keys. Maintained finder prompts require calling the appropriate list tool before creation, using metadata first, hydrating similar candidates only when needed, continuing the search after covered findings, creating at most one new issue/notification per run, and reporting no new finding instead of creating a weak duplicate.
- Native notifications and GitHub issues should start with a short nontechnical `Summary`, then provide technical evidence, risk, implementation guidance, acceptance criteria, references, and regression cases. Bug findings require a concrete failure path; optimization findings require measurable evidence; redundancy findings require repeated locations and minimal consolidation.
- Existing-work discovery for duplicate prevention supports pagination, not just the newest page: `github_list_existing_automation_issues` accepts `offset` and returns `next_offset`; `list_existing_automation_notifications` returns `next_offset` and maintained Native finder prompts/templates/docs instruct finders to follow it. Compact list results still exclude GitHub issue body excerpts and Native notification message/body/metadata/idempotency key; finders hydrate only likely matches via `get_alert`.
- GitHub Dev Inbox scans configured Authorized Users and the PAT identity when available, deduplicates by repository/issue, and creates implementation work after assignment approval and task/PR reconciliation. Assigned open issues are eligible even when created manually in GitHub without prior Automation-created/mapping owner rows. Assigned-issue list entries are treated as sufficient for task creation only when explicitly marked complete; incomplete or unknown entries hydrate that specific issue after deduplication to avoid redundant per-issue GitHub fetches.
- Automation-bound GitHub SDLC turns cannot post issue-status comments. `github_open_pull_request` requires `## Summary`, `## Validation`, and an exact `Closes #<source issue>` reference matching trusted Task provenance.
- For Automation-created implementation tasks whose original graph version is no longer current, PR publication is authorized only through durable same-project GitHub issue task provenance plus the current active Automation graph's retained implementation-to-PR policy. Spoofed `created_via` tasks and other stale-origin GitHub writes remain fail-closed.
