Automation Graphs is a project-scoped, reviewable orchestration surface built on existing OpenVibely tasks, schedules, workers, queues, Alerts, GitHub services, repositories, and current-graph provenance. It does not introduce a parallel graph executor, queue, worker, or arbitrary-code runtime.

Architecture and safety boundaries:
- Supported web creation paths are Template, Describe, and Custom. Custom is the runnable blank builder. New maintained templates are Native SDLC and GitHub SDLC; the internal Vision Driver adapter remains only for already-saved graph reconstruction.
- Each Automation has exactly one current saved graph. There is no retained Automation version history, superseded graph, web-facing draft, staged publication, or failed-publication recovery model. Internal graph revision IDs exist only to isolate stale or currently running execution state; they are not durable Automation or mailbox identities.
- Pending Native alerts and GitHub issues must remain owned by the same logical mailbox after an Automation edit. Durable ownership is keyed by stable Automation identity plus stable logical mailbox identity, not by the replaceable internal graph revision or physical node ID.
- Trigger schedules have exclusive ownership. Worker/inbox resources may be shared only when an adapter explicitly permits it.
- Runtime persistence covers current-graph invocations, leased dispatch, reservations, work items, activities, transitions, live projection, metrics, and health. Replacing a graph deletes runtime projection tied to the old graph.
- Do not discover, infer, migrate, or backfill resources created before Automation Graphs. Existing saved Automations are point-in-time snapshots and registration reruns do not silently rewrite them.
- Human approval and downstream-risk boundaries follow the canonical project-scoped notification contract in `alerts_and_actionable_notifications.md`: approval may authorize the configured implementation handoff, but never merge, release, deployment, destructive remediation, credential changes, or arbitrary execution.
- Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, duplicate keys, unsupported conditions/types, unsafe configuration, foreign-project references, and arbitrary executable behavior fail closed with no resource effects.

Builder and Save contract:
- Template, Describe, Custom, and Edit remain browser-local until `Save changes`. Refresh or navigation discards unsaved work.
- Orchestrate Chat creation is direct: an explicit user request to create or save an Automation authorizes one `save_automation` runtime-tool call that generates, validates, and atomically saves through the normal compiler, then returns the Live URL. Chat does not require a separate confirmation-only planning turn. Plan mode remains read-only, and generation, validation, or Save failure creates no resources.
- Selecting a template loads the canonical graph into the builder without creating an Automation, Task, Schedule, graph row, or runtime resource.
- Save submits the complete graph, validates it, and atomically creates or replaces the current graph and its resource membership under the same Automation identity. Unsupported executable shapes cannot be stored as inert drafts.
- Save uses one database transaction for Automation identity, current graph, Task/Schedule materialization and updates, topology, lifecycle-compatible admission, and old runtime-projection removal. After commit, authoritative pending Active roots that became runnable are submitted.
- Automation Schedule and ordinary Task nodes expose an optional per-node task goal. Saving a non-empty configured goal persists it atomically with the materialized Task; a Native or GitHub implementation projection node carries the configured goal to each runtime-created implementation Task. Goal text is bounded to the normal 2,000-character task-goal limit. GitHub issue-task creation treats the persisted implementation-node goal as authoritative over a model-supplied `create_task` goal; Native inbox prompts direct the atomic alert implementation-task action to receive the configured goal.
- Preview and Save share the same Task-materialization rules. Schedule-owned and ordinary Task nodes materialize; Native projection-only implementation nodes and GitHub issue-specific configuration Task nodes do not.
- Save preserves Active, Paused, and Archived lifecycle state. Active Automations enable all owned Schedules; Pause and Archive disable them and demote pending Active current-graph work; Resume restores eligible lifecycle-demoted work. Per-schedule enabled intent is not part of the current model.
- New canonical Schedules explicitly use `clear_context_on_start=true`. Trusted Edit/Save preserves an older bound Schedule value when graph metadata omits the key.
- Existing saved Automations are point-in-time prompt snapshots. Registration reruns and ordinary reopen/Edit/Save preserve an existing persisted prompt rather than replacing it with corrected maintained defaults. Adopting a corrected maintained prompt currently requires manually replacing the prompt or recreating the Automation; any automatic maintained-prompt upgrade must be an explicit mechanism with regression coverage that begins from a stale persisted prompt.
- Maintained Native and GitHub SDLC templates are starting graphs, not fixed schemas: every template node may be deleted. The retained graph is authoritative, using the same configuration model as Custom Automation. A producer or Loop Auditor with no action edge is a valid standalone schedule; retained Native/GitHub action and workflow stages determine capability readiness and runtime authorization, not prompt wording or separate metadata. There is no maintained-template `required_capabilities` field or builder checkbox. Validation applies general executable handoff, role/topology, configuration, capability, and safety rules to the nodes and edges that remain, with precise role-specific errors for invalid reduced graphs. Preview and Save materialize only adapter nodes present in the submitted graph. Removing a node removes its owned Schedule/resource membership and only its incident edges, while preserving other producers' edges to a shared action and any durable backing Task required by resource-ownership semantics. Re-adding a maintained node may reclaim only the unique, unbound, unscheduled same-project Task whose durable `automation:<automation-id>:<node-key>` origin exactly matches that Automation and node; ambiguous, cross-Automation, or still-bound candidates fail closed. Both unmodified maintained templates and valid reduced graphs remain saveable.
- The maintained-template Add node modal always offers the allowlisted Custom Automation capabilities as well as explicit `Restore:` choices for deleted canonical nodes. User-added nodes, identified by keys absent from the maintained adapter, use Custom Automation configuration validation, topology/resource materialization, and graph-bound prompt behavior; canonical SDLC nodes retain their specialized configuration and runtime behavior. Template-only `skills` and `source_files` controls/configuration are declared, rendered, and form-merged only for canonical task-configured nodes. On Native/GitHub SDLC builder or Edit submissions, the handler removes only these two obsolete fields from noncanonical nodes after decoding stale browser-synchronized `candidate_json`, before form merging and validation; canonical fields remain intact and every other unknown custom configuration fails closed. Edges wholly between added nodes use Custom topology rules, while edges touching a canonical node remain subject to maintained-template handoff rules. Vision Driver remains closed to arbitrary added topology.

Runtime and approval contracts:
- Automation execution projects state onto the current graph while using normal Task, worker, Scheduler, Alert, and GitHub runtime paths.
- A protected Goal Agent continuation for an Automation-created implementation Task must recover that Task's trusted current Automation bindings when the lifecycle hook has no ambient graph context. The queued thread input persists those bindings. While it remains pending, Live and portfolio counts project it as running under its causal work-item identity, replacing recent completion immediately; promotion then records the corresponding running `thread_input_execution` activity at the same node without double-counting. Do not infer bindings when the task has no trusted Automation provenance.
- Automation card `Run now` is a manual internal dispatch, not a prompt-generation action: it creates manual invocations and outbox dispatches for every schedule-owned entry Task, then the normal Automation worker runs each Task with its already-persisted prompt, Agent, model, and tool configuration. On Live, Run now submits through the ordered fragment-refresh coordinator; once its POST settles, it must issue a newer authoritative Live GET so a concurrent polling request that captured pre-dispatch state cannot supersede the running-node projection. Newly claimed invocations immediately project their trigger nodes as running until recorded activity takes over without double counting. Manual runs do not advance or otherwise mutate Schedule `last_run`/`next_run`; queued, running, or reserved entries are skipped to prevent duplicate execution, and Paused or Archived Automations reject the action.
- Custom Task fan-out treats queued/running children as branch-local contention, allowing independent siblings to activate once; topology, configuration, lifecycle, and provenance errors remain fail-fast.
- Native notification handoffs reuse the canonical project-scoped actionable-notification lifecycle in `alerts_and_actionable_notifications.md`: explicit approval, lease-based claim, atomic Backlog implementation-task creation/linkage, execution of the exact linked task, and processing completion only after execution starts. Inbox pagination must snapshot every stable page of eligible notification IDs before mutations because linkage removes rows from the filtered result set.
- Scheduled Native inboxes derive project scope from the persisted caller Task and scan both read states; scheduled runtime field restrictions and mutation-safe pagination are canonical in `alerts_and_actionable_notifications.md`.
- Automation-produced notification metadata is routing evidence only. Durable authorization is stored separately and keyed by project, stable Automation identity, artifact identity, and logical producer/action/gate/mailbox identities; current-graph validation and lifecycle mutations fail closed for artifacts outside the caller's matching branch.
- Compatible Automation edits preserve unresolved approved notifications through stable logical mailbox ownership. On the first authorized mutation after replacement, Native processing rebuilds current-graph projection before task linkage; renamed or removed mailboxes, another Automation, forged metadata, and untracked historical artifacts remain rejected.
- GitHub assigned-issue inbox reads apply the equivalent trusted ownership boundary without mutable labels or semantic title/body matching.
- Automation notification idempotency may reuse an Alert only when the same persisted Automation source owns the creation transition; a same-project same-key Alert from another source is rejected. Automation-origin Native `create_notification` calls require a non-empty stable `idempotency_key` and fail closed when it is absent, rather than creating a duplicate-prone alert.
- GitHub assignment to the configured authorized identity is approval to implement. Runtime-created issue-specific implementation Tasks are Active and auto-submit on creation; `execute_tasks` is reserved for reconciled Backlog or failed/cancelled work, never Active-pending, queued, running, or completed Tasks.
- Native differs intentionally: its atomic Alert helper creates a Backlog Task, so the inbox executes that exact task. Generated implementation prompts identify the task as the existing linked implementer, include reviewed context and acceptance criteria, require repository implementation plus tests/validation, and forbid creating or searching for another implementation task or rerunning notification intake.
- Runtime reloads persisted Task and current Automation context before dispatch or external mutation. Every Edit/Save, including configuration-only edits to Native or GitHub SDLC Automations, replaces and deletes the prior graph revision. An execution already running at commit retains its old revision binding and can therefore fail the provenance guard on later protected actions; a fresh scheduled or manual run uses the new revision. Compatible edits still preserve unresolved artifacts through stable Automation and logical-mailbox ownership, but renaming/removing the mailbox intentionally prevents transfer. Delete/recreate is more disruptive because it also changes stable Automation identity.
- GitHub write-tool visibility does not itself authorize mutation: Automation-origin actions require the current graph's complete causal binding to authorize the exact downstream action. Rejection must cause no GitHub mutation and must not be bypassed through direct push or GitHub CLI. Local implementation completion does not prove publication; live PR state and head remain authoritative.
- Cross-invocation GitHub inbox provenance allows issue creation in one producer invocation and later discovery/task creation in another, while still requiring the current Automation/graph, exact inbox topology, canonical issue resource, and exact discovery execution. Creation and discovery need not share one invocation.

GitHub repository and duplicate boundary:
- Automations use the selected project's repository identity: explicit project `repo_url` first, otherwise a GitHub remote from the local checkout. There is no separate Automation repository picker, and Automation-bound prompts/tools cannot override the repository.
- GitHub publication readiness requires usable provider authentication, at least one visible GitHub Authorized User, and a resolvable project repository. Missing readiness fails before creating Automation, Task, or Schedule rows and is surfaced in the builder.
- Offering Manager and Bug, Optimization, and Redundancy finders must not receive or require repository-wide issue bodies, comments, listings, or searches for duplicate detection. Unavailable or incomplete issue search is not a publication gate. Native notifications and GitHub issues from these roles start with a short `Summary` written for a non-technical reader, followed by the full technical evidence, failure paths, risk, implementation guidance, acceptance criteria, file/symbol references, and regression cases needed by an implementation agent. Use `Summary`, not `Human summary`, as the heading.
- Maintained GitHub SDLC issue creation derives visible category labels from the causal finder role even though the four producers share one issue-action node: Vision Suggestions uses `suggestion` plus `feature`, Bug Finder uses `bug`, Optimization Finder uses `performance`, and Redundancy Finder uses `duplication`. Before creating an Automation issue, the GitHub provider reuses or provisions every required label; after fresh creation, the runtime verifies the returned issue contains all required labels and fails closed without completed projection when GitHub omits one. Completed local-dedup reuse remains keyed by the trusted stored issue number: the runtime fetches that exact issue, restores only missing required labels, refetches to confirm them, and fails closed without reporting successful reuse when reading, applying, or confirming labels fails. It does not search/list issues or create a replacement. Custom Automation issue labels remain configuration-driven.
- Bug findings require a concrete correctness failure path; Optimization requires a measurable bottleneck and before/after method; Redundancy requires repeated locations and a minimal consolidation. Native roles create only their matching notification type; GitHub roles create only their matching issue label.
- Duplicate issue prevention uses trusted local state keyed by project, normalized repository, and a normalized stable finding `idempotency_key`; legacy Automation calls without a key fall back to a normalized-title fingerprint. Maintained GitHub SDLC prompts must construct the key from finder role, primary file/component, and stable symbol/behavior, then reuse it across reworded findings and retries without run IDs, dates, timestamps, or random values. Claims move from `reserved` to `dispatched` to `completed`; only definitely pre-dispatch claims may expire or release, while ambiguous provider outcomes remain fail-closed.
- Completed issue identity/projection recovery requires exact trusted project, Task, Automation, graph, source-node, and binding provenance. Cross-Automation, replacement-graph, or missing historical provenance is never inferred or adopted.
- GitHub Dev Inbox prompts are intended to scan both identity sources: configured GitHub Authorized Users through `github_list_assigned_issues` for each user, plus `github_list_my_assigned_issues` when PAT authentication is available. Results are deduplicated by repository plus issue number. Assignment to either identity source is approval to implement. This behavior applies only when the persisted Automation Task contains the corrected prompt; maintained source changes alone do not upgrade an existing saved prompt. New issue Tasks use Active creation as their sole start mechanism; existing eligible work is reconciled before execution. Completed issue discovery waits at the inbox until task handoff instead of leaving the inbox node running; legacy active positions created before explicit waiting semantics are excluded from operational counts.
- GitHub SDLC Automation turns must not post issue status/update comments. Automation-bound runtimes suppress and reject `github_comment_on_issue`, including stale task-follow-up requests, while retaining `github_open_pull_request` so issue-linked PR publication continues. The generic GitHub comment tool remains available to non-Automation contexts. Maintained and bootstrap prompts direct the inbox to keep task/label state current without status comments; existing saved Automation prompts remain snapshots until explicitly updated or recreated.
- `github_open_pull_request` enforces a structured PR body for maintained GitHub SDLC Automation bindings (`internal/service/github_issue_runtime.go`, task `77da04e6fd8381fdc82f90e01d086a8f`, 2026-08-07): the body must contain `## Summary`, `## Validation`, and an exact `Closes #<source issue number>` reference, or the call fails before branch publication/PR creation. Both the request `issue_number` and any supplied `issue_url` must match the implementation Task's canonical source-issue provenance; the runtime derives and persists the canonical URL when omitted, using the selected project repository's validated web host (including GitHub Enterprise), and rejects resource/repository mismatches. Non-Automation callers keep the prior generic concise-title fallback (`TaskPullRequestService.buildCreatePullRequestRequest`) unchanged.

Custom graph and Describe It contracts:
- Describe It and direct Chat Save use the same custom schema, capability snapshot, normalization, validation, compilation, and atomic Save services as the web builder. The model-driven generation step receives schema/capability context but no mutation tools; only the outer `save_automation` runtime action commits the validated candidate.
- Capability context advertises only executable custom node types and surfaced Agent/tool capabilities; it omits project IDs, source files, skills, reusable resources, retired types, and unsupported conditions.
- Edges use `from` and `to` with `from_port: right` and `to_port: left`. Aliases, reversed/same-kind ports, dangling endpoints, and invalid geometry fail strict public validation.
- Schedule/Task priority is integer `1..4`. Browser-authored invalid values fail strictly; generated numeric values may be normalized only within the bounded generation/repair contract.
- Every generated Native `Create notification` action has exactly one outgoing Human approval gate. Generation may deterministically add or route through that gate; manual browser Save remains strict.
- A custom Native mailbox uses `Schedule/Task → Create notification → Human approval → Approved inbox → Implementation projection → Outcome`. Approved inbox is the substantive scheduled Task; Save creates no placeholder implementation Task.
- A custom GitHub mailbox uses `Schedule/Task → Create GitHub issue → Human assignment → GitHub inbox → Task projection → Open pull request → Human review → Outcome`. GitHub inbox is the scheduled mailbox Task and owns its Task/Scheduler; there is no separate relay Schedule and Save creates no issue-specific implementation Task.
- Native and GitHub mailbox stages cannot be mixed in one custom graph.
- Generation/repair receives the schema, capability contract, project snapshot, user description, validation failure, and bounded prior output. Unknown fields remain rejected, and failures create no resources.

- Maintained-node restoration after delete/Save/re-add may reclaim only the unique same-project Task with the exact durable Automation/node origin when it has no graph binding or Schedule, then creates a fresh owned Schedule. Maintained Native alert creation must verify the caller's actual causal `producer → create_notification → native_approval` path inside the alert transaction; disconnected producers fail without alert or runtime-projection residue.
- Automation dispatch submission and model-execution admission are separate durable phases. The dispatcher may reserve and submit outbox work, but the Task stays `pending` and no running Execution is created until `WorkerService` reserves global, project, and model capacity, keeping excess work visibly Queued. Submitted/no-execution dispatches are restart-recoverable and retire cleanly when cancellation or lifecycle demotion makes the Task unrunnable. Capacity-queued work refreshes persisted Task state before claim; the atomic claim returns the authoritative admitted snapshot. Changed model assignments transfer reservation before execution. Cancellation during transfer preserves cancelled semantics, other acquisition failures use failed semantics, and terminal cleanup atomically settles Task, Execution, dispatch, invocation, activity, reservations, and worker counters without allowing persisted `running` state to overwrite terminal fallback.
