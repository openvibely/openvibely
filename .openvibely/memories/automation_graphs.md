Automation Graphs is OpenVibely's project-scoped, reviewable orchestration surface. It compiles visible Tasks, Schedules, Alerts/GitHub handoffs, workers, queues, and graph provenance; it is not a parallel graph executor, queue, worker, or arbitrary-code runtime.

Authoring and persistence:
- Canonical YAML is the only configuration authoring surface for Template, Describe, Custom, direct Chat Save, and saved Edit. Graph mode edits browser-local topology/layout; node and edge configuration remains in YAML.
- YAML schema version 1 strictly rejects malformed/multi-document YAML, aliases/anchors, duplicate/non-string keys, unsupported fields/tags, unsafe configuration, invalid topology/capabilities, and foreign-project references before resource effects.
- Chat `save_automation` accepts `source: "yaml"` plus `automation_yaml` through the browser's PreviewSave/Save pipeline. Orchestrate-only actions are run/pause/resume/template-update/delete; they resolve exact current-project IDs/names and delegate service authorization. Plan is read-only.
- Deletion uses `automation_trigger_owners`, not titles, roles, or categories. It snapshots schedules/tasks, removes owned schedules, and deletes a trigger task only when no surviving schedule or Automation reference remains. Scope and in-flight guards precede mutation; failures roll back metadata/resources; independent/shared/unrelated tasks are preserved.
- Existing graph-backed Automations serialize to YAML on read. Preview/save does not silently migrate, rewrite prompts, replace point-in-time configuration, recreate resources, or backfill old resources. Each Automation has one current graph; graph revision IDs are runtime bindings, not mailbox identities.
- Saved Automation Live exposes the read-only YAML definition with a scoped `Copy YAML` control. Copy uses the exact rendered textarea value, gives accessible success/failure feedback, and does not navigate, edit, save, run, pause, resume, duplicate, delete, or otherwise mutate the Automation.
- Save atomically persists identity/current graph, materialized Tasks/Schedules, topology, admission-compatible resources, and old projection removal. Invalid saves have no resource effects; committed eligible Active roots submit. Active/Paused/Archived state is preserved; only Active schedules are enabled and pending current-graph work is demoted on Pause/Archive.
- New canonical schedules default `clear_context_on_start=true`; trusted edits preserve an omitted older value. Task/schedule nodes support bounded goals and optional `model_config_id`; blank/missing/`default` uses runtime fallback. Agent references resolve through one bounded compact selectable-reference projection per save.
- `DefaultAutomationDraftNodeConfig` owns common category, priority, goal, model, cadence, approval, labels, notification, and PR defaults. Maintained-template updates require `CurrentAutomationTemplateRevision`; current revisions are Native SDLC `11` and GitHub SDLC `15`.

Builder and topology:
- Web creation supports Template, Describe, and Custom; Custom is the runnable blank builder. Native SDLC and GitHub SDLC are maintained starting templates; Vision Driver is internal reconstruction support. Templates load canonical YAML without resource creation; builder YAML remains browser-local until Save.
- Duplicate loads an identity-free browser-local `Copy of <name>` draft and saves independently. Creatable adapters are Custom, Native SDLC, and GitHub SDLC; Vision Driver/unknown/legacy fail closed. Names are normalized, UTF-8-safe, capped at 200 bytes, and deterministically fall back to `Copy 2 of <name>` when needed.
- Add Node offers Custom capabilities and Restore choices for deleted canonical nodes. Canonical nodes retain maintained behavior; user nodes use Custom validation/materialization. The graph includes Vision Suggestions, Bug Finder, Optimization Finder, Redundancy Finder, and Native/GitHub inbox roles, not Loop Auditor.
- The retained graph is authoritative for readiness/authorization. Producers without action edges may be valid. Deleting a node removes owned schedules/resources and incident edges while preserving valid shared targets/tasks; re-add reclaims only a unique unbound unscheduled same-project task with exact origin.
- Custom Native topology is `Schedule/Task -> Create notification -> Human approval -> Approved inbox -> Implementation projection -> Outcome`. Custom GitHub topology is `Schedule/Task -> Create GitHub issue -> Human assignment -> GitHub inbox -> Task projection -> Open pull request -> Human review -> Outcome`. Native/GitHub stages cannot mix; unsafe configuration, executable cycles, duplicate targets, self-edges, dangling endpoints, and arbitrary execution fail closed.
- Describe/repair treats assignment to PAT owner or configured GitHub Authorized Users as eligibility, including manually created issues. Prompts identify producers as sources rather than eligibility limits.

Runtime and handoff:
- Runtime uses normal Tasks, Scheduler, Alerts, GitHub, workers, queues, and `thread_inputs`. Trigger schedules have exclusive ownership; adapters decide when worker/inbox resources are shareable. Durable state includes invocations, leases, reservations, work items, activities, transitions, live projections, metrics, and health. Published Automation health reconciliation pages published rows, batches blocked-position, recent-failure, and external-PR-staleness inputs, excludes unpublished Automations, and only persists newly evaluated or state/reason-changed health rows.
- Scheduled claims snapshot graph version and physical trigger node. In-flight work may retain an old binding after Save; stale-binding repair allows only compatible same-logical actions. Long-lived external authorization is keyed independently of replaceable graph rows.
- Native ownership is `project_id + automation_id + alert_id`; GitHub mailbox mappings are retired and current inbox scans reconcile assigned issues/provenance. Initial GitHub implementation tasks are `OriginTask` and require current policy for PR provenance after graph replacement.
- Duplicate prevention is existing-work-first: list artifacts, hydrate likely matches, skip covered findings, continue searching, create at most one new finding, and report no finding rather than weak duplicates. Model-authored unstable keys/title hashes are not authority; direct-caller idempotency is separate.
- Approval authorizes only configured implementation handoff. Native handoff uses atomic claim, Backlog creation/linkage, exact linked-task execution, and completion-after-start. Automation-owned scheduled tasks remain ordinary generic tasks with shared tools; service authority is decisive. Old Loop Auditors are inspect/report-only.
- Run Now dispatches schedule-owned entry tasks with persisted prompt/Agent/model/tools without changing timing, skips queued/running/reserved entries, rejects Paused/Archived Automations, and uses owned-schedule/occurrence idempotency. Claims/failures are crash-consistent across execution/task/activity/invocation/outbox/reservation; cancellation wins. Eligible failed/completed work may be re-admitted and committed transitions publish project-scoped board updates.
- Resume deduplicates definition/activity-backed Backlog admissions and assigns ranks after the existing Active tail. Automation Live ranks current `node + work_item` projections as `failed > blocked > running > waiting_human > recently_completed`; nonterminal activity does not mask completed work. A running node without backing work is likely stale.

GitHub, notifications, and Chat:
- Automations use selected-project repository identity: explicit `repo_url` first, otherwise a Git remote. Prompts/tools cannot override it. GitHub publication requires usable authentication, visible Authorized User, resolvable repository, matching branch/head, required PR sections, and exact source-issue provenance.
- Assignment is approval to implement; implementation tasks are Active and auto-submitted. `execute_tasks` is for reconciled Backlog or failed/cancelled work. External mutations reload persisted Task and current Automation context; local work does not prove publication.
- Existing-work lists are compact/paginated; detail tools hydrate likely matches. Finder content begins with `## Summary`, then evidence, risk, implementation, acceptance, references, and regressions. Direct web/API and shared channel Chat serialize cards through one `AutomationCardSummary`: `graph_node_count` is saved nodes bound to the published graph version, while `counts` is current operational work.
- Runtime `list_automations` uses a bounded compact page with explicit pagination metadata; runtime `get_automation` uses an exact project-scoped compact lookup with ID-scoped operational count enrichment. Full graph/detail/live/builder paths remain separate from prompt-safe runtime summaries.
- `AutomationGraphService.List` remains for full-card/full-list consumers and combines compact saved-graph cards with one project-scoped operational-count aggregate. Optional project IDs are equality assertions, never overrides. Maintained updates are explicit Orchestrate actions; current/custom/unsupported/foreign Automations are not silently rewritten.

Current gaps:
- External refresh should use project-scoped identity-only `AutomationRepo.Exists` without hydrating graph versions/nodes/edges/resources; background refresh should remain zero-hydration and contention-aware.
- Maintained-template update UX lacks a non-persisting node/YAML/resource diff (`#919`); calendar cards omit `clear_context_on_start` in enabled/disabled states (`#1054`). Task Details lack a valid unambiguous source-issue link (`#1066`).
- Save-during-run must retain active task-backed executions while removing stale graph projection; stale-origin repair must remove queued-input bindings/dependent child work before stale parents. Native inbox state must be checked before marking waiting-human work stale.
- Authoring must not rely on weak per-Automation `skills`/`source_files` hints. Prompts identify sources and Skill Curator routes skills; Vision Suggestions must verify/read root `VISION.md`; Custom child activation recompiles from the saved graph. Empty-goal save currently persists the prior goal (`#1091`); deletion lacks an exact retained/deleted resource preview for shared trigger tasks (`#1093`); and the browser builder calls `PreviewSave` but drops save-impact `effects`/`will_not`, so the pre-save impact summary is tracked in `#1204`.
- Automation graph node model selectors need provider and endpoint/account context to disambiguate recurring task/schedule model choices (`#1251`); related model-card search details for `#1239` are canonical in `provider_architecture.md`.
- Automation Live pages lack a user-facing recent run/work-item/transition history even though runtime services retain invocation, work-item, activity, and transition concepts; GitHub issue `#1261` tracks restoring inspectable lifecycle evidence for saved Automations.
- Edited chained tasks can leave pre-created blocked children stale; the durable chain-materialization contract and `#1228` details are canonical in `openvibely_architecture.md`.
