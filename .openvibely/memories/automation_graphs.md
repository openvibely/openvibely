Automation Graphs is OpenVibely's project-scoped, reviewable orchestration surface. It compiles visible Tasks, Schedules, Alerts/GitHub handoffs, workers, queues, and current-graph provenance; it is not a parallel graph executor, queue, worker, or arbitrary-code runtime.

Canonical authoring and persistence:
- Automation YAML is the sole configuration authoring surface for Template, Describe, Custom, direct Chat Save, and saved Edit flows. Graph mode is browser-local topology/layout editing; node and edge configuration remains in YAML.
- YAML schema version 1 uses strict decoding. It rejects malformed or multi-document YAML, aliases/anchors, duplicate keys, non-string keys, unsupported fields/tags, unsafe configuration, invalid topology/capabilities, and foreign-project references before resource effects.
- Chat `save_automation` accepts canonical YAML through `source: "yaml"` and `automation_yaml`, using the same PreviewSave/Save pipeline as the browser builder and rejecting stale/raw candidate fields before decode. Chat `run_automation_now`, `pause_automation`, `resume_automation`, `update_automation_template`, and destructive `delete_automation` are Orchestrate-only actions with exact current-project ID/name resolution and service-layer authorization; Plan remains read-only. Delete preserves domain Tasks, removes only Automation-owned trigger schedules, and keeps the in-flight guard.
- Existing graph-backed Automations serialize to YAML on read. Open/preview/save does not silently migrate, rewrite prompts, replace point-in-time configuration, recreate resources, or backfill pre-graph resources. Each Automation has one current saved graph; graph revision IDs are runtime bindings, not durable Automation/mailbox identities.
- Save atomically persists Automation identity/current graph, materialized Tasks/Schedules, topology, lifecycle-compatible admission, resource membership, and removal of old runtime projection. Invalid Save fails before any resource persistence; after commit, eligible Active roots are submitted. Active, Paused, and Archived state is preserved; Active enables owned schedules, while Pause/Archive disables them and demotes pending current-graph work.
- Draft schedule validation is shared across custom trigger nodes and maintained schedule adapters, while adapters retain separate target validation. New canonical schedules default `clear_context_on_start=true`; trusted edits preserve older bound values when omitted.
- Task/schedule nodes may carry bounded goals and optional `model_config_id`; blank, missing, or `default` uses runtime fallback, while explicit IDs materialize to `tasks.agent_id`. Native implementation nodes expose goal plus model only because Approved Inbox supplies the prompt; GitHub implementation nodes carry static prompt/category/priority plus optional model.
- `DefaultAutomationDraftNodeConfig` centralizes common category, priority, goal, model sentinel, cadence, approval, labels, notification, and PR defaults. Maintained-template updates are gated by `CurrentAutomationTemplateRevision`; saved Automations are point-in-time snapshots and require explicit update/edit/save or recreation to adopt changed prompts/models. Current maintained GitHub SDLC revision is `15`.

Builder and topology contracts:
- Supported web creation paths are Template, Describe, and Custom; Custom is the runnable blank builder. Native SDLC and GitHub SDLC are maintained starting templates, while Vision Driver is internal reconstruction support.
- Template selection loads embedded canonical YAML without creating resources. Saved Edit, maintained Template, Custom, and Describe builders expose `Automations / [name]` with naming and primary save actions in the breadcrumb/header; lifecycle/template/delete controls are in the kebab menu.
- Builder YAML is browser-local until Save. Selecting Graph validates through non-persisting PreviewSave before layout changes. Live and Builder share Graph/Details/YAML switcher behavior, but Live preserves selected view across background refresh only for the same Automation.
- Add Node offers Custom Automation capabilities plus `Restore:` choices for deleted canonical nodes. User-added nodes use Custom validation/materialization; canonical nodes retain maintained behavior. The graph editor can add/delete/reconnect/move nodes and edges; every canvas mutation updates YAML. Add-node dialogs must not discard unsaved YAML. Generated YAML uses readable block maps/arrays. Destructive node/edge controls are icon-only with descriptive labels.
- Maintained Native and GitHub templates are starting graphs, not fixed schemas: any template node may be deleted and valid reduced graphs remain saveable. Canonical scheduled roles are Vision Suggestions, Bug Finder, Optimization Finder, Redundancy Finder, and the Native/GitHub inbox; there is no Loop Auditor in new maintained templates.
- The retained graph is authoritative for capability readiness and authorization, not prompt wording or separate required-capability metadata. A producer without an action edge is valid; removing a node removes owned schedules/resources and incident edges while preserving valid shared targets and backing tasks. Re-adding may reclaim only a unique, unbound, unscheduled same-project task with an exact `automation:<automation-id>:<node-key>` origin.
- Custom Native topology is `Schedule/Task -> Create notification -> Human approval -> Approved inbox -> Implementation projection -> Outcome`. Custom GitHub topology is `Schedule/Task -> Create GitHub issue -> Human assignment -> GitHub inbox -> Task projection -> Open pull request -> Human review -> Outcome`. Native and GitHub mailbox stages cannot mix; unsafe configuration, executable cycles, duplicate targets, self-edges, dangling endpoints, and arbitrary executable behavior fail closed.
- Describe/repair treats issues assigned to the PAT owner or configured GitHub Authorized Users as eligible, including manually created issues. Generated prompts identify producers as issue sources rather than eligibility limits.

Runtime, handoff, and approval:
- Runtime uses normal Tasks, Scheduler, Alerts, GitHub, workers, queues, and thread inputs. Trigger schedules have exclusive ownership; worker/inbox resources are shareable only where an adapter permits it. Persisted runtime includes invocations, leased dispatch, reservations, work items, activities, transitions, live projection, metrics, and health.
- Scheduled occurrences snapshot schedule-owner graph version and physical trigger node at claim time. In-flight work may retain an old binding after Save; stale-binding repair permits only compatible same-logical actions. Long-lived external authorization must be keyed independently of replaceable graph-version rows.
- Initial Automation GitHub implementation runs mark tasks `OriginTask`, allowing issue-task provenance for PR opening on first runs and follow-ups after graph replacement. Stale-version PR publication is allowed only with durable same-project issue-task provenance and current retained implementation-to-PR policy; branch replacement and other destructive writes are stricter.
- Native notification ownership is `project_id + automation_id + alert_id`, with a current active same-project Native inbox proving live authority. Scheduled inboxes derive project scope from the persisted caller task and scan both read states. GitHub mailbox-owner mappings are retired; current inbox scans and execution provenance reconcile assigned issues.
- Duplicate prevention is existing-work-first, not model-authored idempotency. Finders list existing artifacts, hydrate likely matches only, skip covered findings, continue searching, create at most one new finding per run, and report no finding rather than weak duplicates. A prior duplicate-finder incident came from unstable model keys/title hashes; direct-caller idempotency remains separate.
- Human approval authorizes only configured implementation handoff. It never authorizes merge, release, deployment, destructive remediation, credential changes, or arbitrary execution. Native handoff uses approval, atomic lease claim, atomic Backlog task creation/linkage, exact linked-task execution, and processing completion only after execution starts; inbox scans collect all pages before mutation.
- Automation-owned scheduled tasks remain ordinary generic tasks with the shared tool surface. Missing tools belong in shared allow-lists; excessive authority belongs in service-layer authorization checks. Loop Auditors are inspect/report-only and must not create direct tasks, swarms, or executions.
- `Run now` dispatches each schedule-owned entry task using persisted prompt, Agent, model, and tools without changing timing; it skips queued/running/reserved entries and rejects Paused/Archived Automations. Occurrence idempotency is keyed by owned schedule plus scheduled time, and repeating schedules advance beyond terminal past invocations.
- Queue and board state is crash-consistent: execution-bearing dispatch retry exhaustion terminalizes its bound execution/task/activity/invocation/outbox/reservation atomically while cancellation wins; execution-free failures retain their visible terminal transition. Later claims can re-admit eligible failed/completed tasks and clear stale completion metadata. Committed claims/failures publish project-scoped `task_board_updated` through the shared SSE path.
- Automation Live ranks by current projection identity (`node + work_item`) and current state priority `failed > blocked > running > waiting_human > recently_completed`; nonterminal activity does not mask completed work. For `Run now`, an active claimed/dispatched/running invocation supersedes only the prior terminal activity projection for the same project, Automation graph version, node, owned schedule, and task identity; the current invocation's activities and unrelated task failures retain normal precedence, and an authoritative terminal failure remains red. Hidden/internal Native inbox work may show `Running` without an ordinary Active card, but a running node with no inbox task/activity/work item/pending input is likely stale projection. GitHub and notification content:
- Automations use the selected project's repository identity: explicit `repo_url` first, otherwise a GitHub remote from the local checkout. Prompts/tools cannot override it. GitHub publication requires usable provider authentication, at least one visible Authorized User, and a resolvable repository.
- GitHub assignment to the PAT owner or configured Authorized User is approval to implement. GitHub issue implementation tasks are Active and auto-submitted; `execute_tasks` is for reconciled Backlog or failed/cancelled work. External mutations reload persisted Task and current Automation context; visible GitHub tools do not authorize mutation by themselves, and local work does not prove PR publication.
- Existing-work listing is compact and paginated. GitHub issue lists omit bodies; Native notification lists omit message/body/metadata/idempotency keys; detail tools hydrate only likely matches. Findings start with a short nontechnical `Summary`, followed by evidence, risk, implementation guidance, acceptance criteria, references, and regression cases.
- Chat `list_automations` and `get_automation` expose compact prompt-safe summaries, including maintained-template `template_update_available`, stored `template_revision`, and `current_template_revision` where applicable. Supported web/API and channel runtimes can apply maintained-template updates only through the Orchestrate-only action; current, custom, unsupported, and foreign Automations are not silently rewritten.
- Dev Inbox scans PAT/configured identities, deduplicates by repository/issue, reconciles tasks and PRs, and creates implementation work only after assignment approval. `github_list_assigned_issues` tools return compact pagination metadata and `detail_required` rather than body excerpts; targeted `github_get_issue` is used only for likely task creation.
- Reconciliation is one broad existing-task lookup per issue number/URL with no lifecycle filters. Do not retry with title/fragments or enumerate lifecycle states. GitHub discovery uses runtime GitHub tools, not shell/API substitutes; a successful Active `create_task` is sufficient and should not be rechecked in the same inbox turn.
- Automation-bound GitHub tools use selected-project repository scope, reject cross-host overrides, and cannot post issue-status comments. `github_open_pull_request` requires `## Summary`, `## Validation`, and exact `Closes #<source issue>` provenance.

Current gaps and design constraints:
- External-refresh existence checks should use project-scoped identity-only lookup (`AutomationRepo.Exists`) without hydrating graph versions/nodes/edges/resources; manual refresh may load once, background refresh should remain zero-hydration and contention-aware.
- Maintained-template update gap `#919`: the update UI warns and immediately performs destructive replacement without a non-persisting node/YAML/resource comparison. Existing candidate/preview encoders provide building blocks for a reviewable diff.
- Automation-builder handler duplication issue `#935` is implemented in PR `#943`: `BuildAutomationWeb` and `EditAutomationBuilder` now call private `applySubmittedAutomationBuilderCandidate` for the shared posted-candidate sequence before preview. Non-YAML submissions still discard stale template-only `skills`/`source_files` on custom nodes, apply browser form overrides, and apply requested visual actions; YAML submissions bypass those browser mutations exactly as before. Candidate decoding/YAML fallback, current-definition/template handling, preview context, page metadata, persistence, save, and redirects remain route-specific. Regression coverage exercises create/edit JSON cleanup, overrides, visual actions, and no persistence before explicit save. PR #943 is linked to #935 at published head `8882b32416f34621752a44f48c368742829d50ee`; `go build ./...`, `go vet ./...`, focused handler tests, uncached internal/full suites, and `git diff --check` passed. A separate fresh strictly read-only audit found no material bugs, regressions, missing requirements, scope violations, or publication discrepancies and made no workspace changes.
- Automation Live freshness gap `#895`: expose project-scoped external GitHub freshness/error state and manual refresh. Existing `LastUpdatedAt` is not yet a true refresh-completion timestamp. Live projection compaction remains tracked by `#490`.
- Save-during-run must retain active task-backed executions when old graph-version projection rows are removed. Stale-origin repair must remove queued-input bindings and dependent child work before stale parent work.
- Native inbox ownership is stable across delete/recreate, so an old approved notification can be processed by a new inbox in the same Automation; diagnose alert decision/processing state before treating `waiting_human` as stale projection.
- Authoring should not rely on weak per-Automation `skills` or `source_files` hints; prompts identify sources and Skill Curator routes skills. Vision Suggestions must verify and read the root `VISION.md`. Custom child activation recompiles from the saved published graph so downstream handoff edges remain in generated prompts without creating extra resources.
