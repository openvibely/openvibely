Automation Graphs is a project-scoped, reviewable orchestration surface built on existing OpenVibely tasks, schedules, workers, queues, Alerts, GitHub services, repositories, and current-graph resource provenance. It extends those systems rather than introducing a parallel graph executor, queue, worker, or arbitrary-code runtime.

Architecture and safety boundaries:
- Supported creation paths are Template, Describe It, and Blank. Blank is a runnable custom builder, not an inert diagram editor or preset assembler. Maintained setup registration is restricted to Native and GitHub; Vision Driver remains available through explicit creation/publication.
- Definitions are project-scoped and each Automation has exactly one current saved graph; there is no retained Automation version history or superseded graph. Trigger schedules have exclusive ownership, and worker/inbox resources may be shared only when an adapter permits it.
- Runtime persistence supports the current graph's invocations, leased dispatch outbox, task reservations, work items, activities, transitions, live-position provenance, metrics, and health independent from lifecycle state. Runtime projection tied to a replaced graph is deleted on successful Save.
- Do not add legacy-resource discovery, heuristic inference, confidence scoring, migration, or graph backfill for resources created before Automation Graphs.
- Human approval authorizes only the configured downstream handoff. It never grants merge, release, deployment, or arbitrary execution authority.
- Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, duplicate keys, unsupported conditions/types, unsafe configuration, foreign-project references, and arbitrary executable behavior fail closed with no resource effects.

Builder and publication contract:
- Users may design open-ended graphs in browser memory, but unsupported executable shapes cannot be saved as inert persisted drafts. The normal web flow is `Edit automation`, browser-local changes, then one immediate `Save changes`; refresh/navigation discards unsaved edits.
- Save submits the complete graph, validates it, and atomically replaces the current saved graph under the same Automation identity, including while Automation work is running. There is no web-facing draft, Automation version history, version selection, Review/Apply, separate Publish step, superseded graph, or restorable publication. Successful Save deletes the prior graph and its Automation runtime projection in the same transaction; failure leaves prior behavior active.
- Internal `automation_draft*` and `version_id` names remain implementation terminology for short-lived Save staging/publication journals; they do not define persisted web drafts, retained Automation versions, or pre-Save Automation identity.
- Chat uses `plan_automation_save` followed by later-confirmed `save_automation`. Planning and durable confirmation expose no Automation/version identity or URL, create no Automation or runtime-resource rows, and keep the candidate only in private signed confirmation state. The Automation and graph are staged and applied only after the later exact `save <automation-name>` confirmation.
- Publication plans expose resolved reuse and behavior-affecting dependencies. Replacement task configuration and current-graph switching are atomic, and retry resumes the exact failed journal without duplicating resources.
- Failed web Saves after publication-attempt reservation remain recoverable after browser state loss through a project-scoped `Save needs attention` portfolio item. Reopening restores the exact private candidate, plan revision, and created-resource steps; recovery is separate from saved Automation cards, exposes no selectable version/history, and hides deletion until the exact Save succeeds. Failures before reservation are not recoverable journals and discard their private staging atomically.
- Candidate schema versions are preserved; missing or unsupported versions are rejected or use Describe It's one bounded repair path, never silently downgraded.
- Agent, skill, and source-file references resolve only from the selected project's bounded, secret-free capability snapshot. Missing, ambiguous, unavailable, or foreign-project references are explicit errors.

Executable topology:
- A Schedule node is itself a substantive OpenVibely Task plus a Scheduler row targeting that schedule-owned Task. It owns the prompt, agent, priority, and timing and can run without a connected generic Task; it is not merely trigger metadata attached to another node.
- Automation exposes one generic `Task` node in addition to Schedule nodes. Ordinary Task nodes materialize as stable OpenVibely tasks on Save. Only the exact `GitHub inbox → Task → Open pull request` topology treats that generic Task node as configuration for issue-specific tasks created later.
- Schedule nodes remain available for new graphs. A currently saved graph using the old internal implementation-task role remains runnable until edited; new graphs must not expose separate Agent Task or Implementation Task choices.
- Supported custom shapes use Schedule nodes and generic Task nodes with deterministic paths through supported tasks, actions, human gates, and Outcomes. One task may fan out to multiple children, but each child may have at most one task parent because persisted tasks store one parent.
- `Schedule → Task` is an explicit downstream handoff: scheduled Task A performs its substantive work, then creates, activates, or reuses Task B through normal task/worker machinery. It must never compile as a Scheduler row that directly targets Task B.
- Schedule compilation is generic across Template, Describe It, Blank, and Chat and across supported automation topologies. Every Schedule materializes its own task and Scheduler row; a connected generic Task materializes separately as its downstream child. Unsupported or ambiguous schedule connections fail validation rather than changing those semantics or producing hidden relay tasks. The adapter/compiler publication contract is version 12, invalidating confirmations created under superseded schedule mappings and maintained-template topology.
- Maintained setup registration binds each scheduled loop's Task and Scheduler row to the same node key and rejects a Scheduler row whose target differs from the Task bound to that node. This prevents corrected graph visuals from masking an incorrect scheduled Task.
- Downstream tasks are pre-created blocked, then activated or reused through normal task/worker machinery. Causal handoffs survive restart, are idempotent, and block rather than duplicate busy children.
- Removing or reconfiguring a schedule deletes its obsolete Scheduler row. Confirmed Automation deletion deletes exclusively owned Scheduler rows transactionally while preserving domain tasks; deletion is rejected while dispatch-owned work is in flight.
- Task node settings stay in parity with ordinary tasks and must not expose skill/source-file inputs merely because the task is in a graph. Scheduling must not be represented as a user-authored `scheduled` Task category.

Native Alert and GitHub handoffs:
- Maintained Native and GitHub SDLC templates have parallel scheduled discovery loops for Vision Suggestions, Bug Finder, Optimization Finder, and Redundancy Finder, plus scheduled Inbox and Loop Auditor nodes. Each recurring loop is represented by one Schedule node that owns both its Task and Scheduler row; the templates no longer use empty `*_trigger → Task` relay pairs.
- Their intentional differences begin at the mailbox and delivery boundary. Native uses OpenVibely notifications, human approval, an approved-notification inbox, and visible implementation tasks without opening PRs; GitHub uses issues, assignment approval, a GitHub Dev Inbox, implementation tasks, PR creation, human review, and observed merge completion.
- GitHub's Loop Auditor inspects integration-specific state, while Native's parallel auditor checks stale notifications, failed claims, missing linked tasks, duplicate work, and blocked task state using OpenVibely data.
- A Native Alert graph configures runtime `create_notification`; publication creates no Alert. Multiple valid producers may share one notification action. Human approval may be terminal or branch to approved/rejected Outcomes, and an omitted branch terminates safely.
- Alert/GitHub runtime projection resolves exact project, Automation, current saved graph, node, edge, invocation, and work-item identities. Idempotency cannot adopt an object created outside that Automation.
- GitHub lifecycle graphs preserve human gates: a producer creates an issue, a separate inbox polls assigned issues, assignment is approval, the topology-specific Task performs issue work, PRs wait for human review, and only observed merge reaches Outcome.
- GitHub publication creates only configured producer/inbox tasks and required Scheduler rows. Issues, issue-specific tasks, and PRs arise later through existing GitHub/task services.
- GitHub actions are constrained to the selected project repository and saved labels/settings. Automatic assignees are rejected; assignment, review, merge, release, and deployment remain human-controlled.
- GitHub SDLC publication requires usable provider authentication, an explicit project repository, and an enabled project approval inbox/login.

Describe It and UI contracts:
- Describe It and canonical Chat actions use the same custom schema, capability snapshot, normalization, validation, planning, compilation, and publication services as the web builder. The model receives schema/capability context but no mutation tools.
- `automationDescriptionPrompt` in `internal/service/automation_draft_generation.go` now teaches that every Schedule is its own substantive scheduled Task, that `Schedule → Task` is a downstream handoff to a separate follow-up Task, and that simple recurring work normally needs no extra Task node. Schedule-owned task prompts also tell the model not to recreate or reschedule an explicitly connected child because OpenVibely activates it after successful completion.
- Graph edges use `from` and `to`; aliases such as `source` and `target` remain invalid. Every edge uses `from_port: right` and `to_port: left`, representing source `OUT → IN` target. Missing, reversed, or same-kind port geometry fails strict public validation, while older saved connector metadata normalizes to the canonical directional ports only when reopened through the trusted saved-graph path. Schedule/Task priority is integer `1..4`; generated out-of-range numeric priorities may be clamped before validation, malformed types use one bounded repair, and browser-authored invalid values fail strictly.
- Describe It deterministically enforces the Native Alert approval boundary on generated custom candidates: every `Create notification` action has exactly one outgoing `Human approval` gate. If generation omits the gate, it is added without consuming the model repair; if generation connects the notification directly to an Outcome, that Outcome is routed through approval as the approved branch. Manual browser-authored Save validation remains strict rather than applying this generation-only normalization.
- Repair receives the original schema, capability contract, project snapshot, user description, validation failure, and bounded prior output. Unknown fields remain rejected. Generation/validation failures render visibly and create no Automation, task, or schedule.
- Describe It receives a purpose-built custom-graph capability view rather than the broad builder snapshot: only executable custom node types and roles are advertised, project IDs are omitted, and skills, source files, reusable resources, legacy `implementation`, and unsupported `condition` surface are excluded. Surfaced Agents retain their explicit tool/capability names, while Native/GitHub integration state and safety boundaries remain available.
- Maintained-adapter generation no longer depends on topology guesswork. The prompt includes canonical `native_sdlc`, `github_sdlc`, and `vision_driver` candidates generated through `TemplateCandidate` from the adapter registry, and requires their adapter identity, node keys/types/roles, and edge topology to remain exact.
- The generation and repair contract now states strict validator requirements for graph/name/key/port limits, Task categories, Schedule repeat enums and interval bounds, action field types and lengths, human-gate conditions, and exact GitHub lifecycle cardinalities. If requested external work lacks a compatible surfaced Agent/tool capability, generation must omit `agent_ref`, add an explicit warning that configuration is required, and avoid claiming the operation is executable.
- The canvas supports safe node creation/placement, repeated directed connections, selection/deletion/rewiring, node cleanup, pan/zoom/Fit/Reset, and keyboard controls. Each node renders a visually distinct unlabeled left input handle and right output handle; visible `IN`/`OUT` text is intentionally omitted because direction is apparent, while explicit input/output `aria-label`s remain for assistive technology. New edges and endpoint reconnections must run right output to left input, and output-to-output or input-to-input gestures create no edge. Reverse graph paths and cycles remain possible as separate canonical directional edges. Empty edges serialize as `[]`, connector completion resolves release coordinates despite pointer capture, and foreground SVG geometry remains pointer-transparent.
- Schedule nodes must be labeled `Schedule` in the builder, not the stale `Trigger` label, because each Schedule is itself a substantive scheduled Task rather than an empty trigger.
- Builder node and edge delete controls render their X as symmetric SVG path geometry centered at the control origin, not as a font-dependent `×` text glyph. Server-rendered controls and dynamically created edge controls must use the same geometry so the X remains centered inside its circle at every canvas zoom level.
- Canonical Native SDLC, GitHub SDLC, and Vision Driver template stages use at least 220 graph units of horizontal spacing. With 170-unit node cards, every directed template edge retains at least 50 units of visible connector line instead of collapsing to an arrowhead. Existing saved layouts remain unchanged until edited; newly loaded templates and Reset Layout use the canonical spacing.
- Automation-owned Schedule-page entries display the saved Schedule-node name for the Schedule's own task and Scheduler row.
- Automation detail is a single full-width `Live` graph with no tabs. Automation-facing History, invocation, work-item, Definition, and node-resource pages, handlers, and routes are not product surfaces; those URLs return `404`. The Live page intentionally omits the summary cards for Active invocations, Open work items, Nodes, and Recent since; runtime state remains visible on the graph itself.
- The Live graph fills the remaining viewport height through a full-height flex layout instead of stopping at a fixed canvas height. Its canvas keeps a `34rem` minimum for usability, grows into available desktop space, and relies on normal page scrolling on shorter viewports.
- Schedule and Task nodes with an exact persisted `task` resource binding link directly to that existing project-scoped Task. A Schedule node opens its Schedule-owned Task rather than the Scheduler row. Non-task nodes and Task/Schedule nodes without a task binding remain inert.
- User-facing Automation screens do not expose execution/history pages, version selectors, version detail pages, topology/version badges, visible version numbers, or publication-record terminology. Internal current-graph runtime rows and short-lived Save/Chat staging journals exist only for Live projection, atomic Save rollback/retry, and runtime integrity; they are not retained as selectable or restorable Automation history.
- The Automations portfolio follows the same compact searchable long-card pattern as Models, Agents, Skills, Channels, and Personality: one full-width card per row using standard `font-bold` titles, default card-body padding, a short subdued description, and only adapter, lifecycle, and health badges. The list page omits its explanatory header description plus version, operational counters, health-reason text, timestamps, and linked-resource totals; those details belong on Automation detail views. Shared browser-side search still covers name, description, adapter, lifecycle, and health, and the project-scoped session-persisted helper reapplies active filters after HTMX navigation and swaps.
- Automation portfolio cards use the same plain clickable `<div>` interaction and top-right kebab pattern as Agents/Models. The card click opens Live view; `Edit` opens the browser-local builder, and `Delete` opens the project-scoped native confirmation dialog. Do not add card-level `role="link"`, `tabindex`, keyboard handlers, outline suppression, or `focus-visible` ring classes: making the bordered card wrapper focusable caused the mouse-down border flash the shared management-card pattern avoids. The kebab remains independently focusable and stops propagation so its actions never trigger card navigation.
- The portfolio kebab `Edit` action is a direct `type="button"` handler, not a form-wrapped submit. Its first physical-style click issues exactly one project-scoped HTMX POST to the Automation builder endpoint, closes the dropdown focus state, and opens the editor; browser coverage models the full mouse-down/focus/mouse-up/click sequence and asserts one request.
- Portfolio counts choose one state per node/work-item in precedence order: failed, blocked, waiting, running, recently completed. Graph/resource reads stay project-scoped, bounded, sanitized, and avoid live GitHub calls; reconciliation exposes freshness/staleness.

Publication safety and lifecycle state:
- Compiler-created Tasks are staged in non-admitted Backlog state until Save commits the current graph, exact definition-resource membership, configured Task category, and custom topology. Failed publication cannot submit a root Task or create Automation runtime effects; newly created Active roots are submitted through the existing worker queue only after the publication transaction commits.
- Worker context lookup may resolve exact Task membership from the current saved graph when no causal Automation activity exists, allowing a newly saved standalone/root Task to start with exact Automation, graph, and node provenance. Once causal activity bindings exist, they take precedence so downstream handoffs and shared Tasks retain their runtime-specific invocation/work-item context without extra definition-only bindings.
- Save preserves the Automation lifecycle. Active remains active; paused remains paused with schedules disabled and trigger ownership marked paused; archived remains archived with schedules disabled and no trigger ownership reacquisition. Editing cannot bypass explicit Resume or the archived non-resumable boundary.
