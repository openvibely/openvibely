Automation Graphs is OpenVibely's project-scoped, reviewable orchestration surface. It compiles visible Tasks, Schedules, Alerts/GitHub handoffs, workers, queues, and current-graph provenance; it is not a parallel graph executor, queue, worker, or arbitrary-code runtime.

Canonical authoring and persistence:
- Automation YAML is the sole configuration authoring surface for Template, Describe, Custom, direct Chat Save, and saved Edit flows. Graph mode is browser-local topology/layout editing only; node and edge configuration stays in YAML.
- YAML uses schema version 1 and the existing candidate model (`name`, `description`, `automation_type`, `adapter_key`, `nodes`, `edges`, `configuration`, `positions`, `assumptions`, `warnings`). Strict decoding rejects malformed or multi-document YAML, aliases/anchors, duplicate keys, non-string mapping keys, unsupported fields/tags, unsafe configuration, invalid topology, unsupported capabilities, and foreign-project references before any resource effects.
- Draft schedule config validation is shared by custom trigger schedule nodes and maintained adapter schedule resources for `run_at`, `repeat_type`, `repeat_interval`, `enabled`, and `clear_context_on_start`; maintained adapters keep separate `schedule_target` validation.
- Existing graph-backed Automations serialize to YAML on read for compatibility. Opening, previewing, or saving does not silently migrate, rewrite prompts, replace point-in-time configuration, recreate resources, or backfill pre-graph resources.
- Each Automation has exactly one current saved graph. Internal graph revision IDs isolate runtime state but are not durable Automation or mailbox identities.
- In Automation origins and ownership keys, `automation_id` means the saved Automation row's internal `automations.id`, not the adapter/template key, maintained template name, or display name. Human-readable examples like `github-sdlc-automation` are placeholders; real origins look like `automation:<automation-id>:<node-key>`.
- Save atomically persists Automation identity/current graph, materialized Tasks/Schedules, topology, lifecycle-compatible admission, resource membership, and old runtime-projection removal in one database transaction. After commit, eligible Active roots are submitted.
- Automation compiler `PreviewSave` and `Save` share the same save-candidate validation helper for normalization, project validation, capability checks, and agent-reference checks. Preview keeps returning the normalized candidate and validation issue list, while invalid Save paths fail before persisting Automations, tasks, schedules, or resources.
- Save preserves Active, Paused, and Archived lifecycle state. Active enables owned Schedules; Pause/Archive disable them and demote pending current-graph work; Resume restores eligible lifecycle-demoted work. Per-schedule enabled intent is not separately modeled.
- New canonical Schedules use `clear_context_on_start=true`; trusted Edit/Save preserves older bound Schedule values when graph metadata omits the key.
- Automation Schedule and ordinary Task nodes can carry a per-node task goal bounded to 2,000 characters. Native SDLC implementation nodes intentionally expose only `goal` in Preview/Edit; their runtime task prompt is supplied by the Approved Inbox when it calls `create_alert_implementation_task`. GitHub SDLC implementation nodes expose a static prompt/category/priority because assigned issues create Active implementation Tasks before PR handoff. Preview and Save share task materialization rules.
- Existing saved Automations are point-in-time prompt snapshots. Registration reruns and ordinary reopen/Edit/Save preserve persisted prompts; adopting corrected maintained defaults requires using the explicit maintained-template update path, manual prompt replacement, or Automation recreation.
- The maintained-template update option is gated by `CurrentAutomationTemplateRevision(adapterKey)`: when embedded Native/GitHub SDLC template YAML changes, bump the adapter revision so existing Automations with lower stored `TemplateRevision` see `Update to latest template` on Automation card, Live, and Edit kebab menus. The 2026-08-08 schedule cadence update set Native/GitHub SDLC templates to revision 2; the 2026-08-08 Loop Auditor removal set them to revision 3.

Builder and UI contracts:
- Supported web creation paths are Template, Describe, and Custom; Custom is the runnable blank builder. Native SDLC and GitHub SDLC are maintained starting templates. Vision Driver remains internal for already-saved graph reconstruction.
- Template selection loads embedded canonical YAML through the same strict decoder without creating an Automation, Task, Schedule, graph row, or runtime resource.
- Saved Edit, maintained Template selection, Custom blank creation, and Describe-generated builders use `Automations / [editable automation name]`; the name is edited in the breadcrumb and primary save actions live in the breadcrumb header, not in a separate standalone name/save row. Details-view header saves must submit the edited breadcrumb `automation_name` along with Details form values. Live primary actions also live in the breadcrumb header and reserve the kebab for lifecycle/template/delete actions.
- Builder/Edit YAML is browser-local until Save. Selecting Graph validates through the non-persisting compiler PreviewSave path before applying topology/layout mutations. Live renders saved YAML and graph read-only.
- Live background refreshes may swap the detail fragment, but must preserve the selected Graph/Details/YAML view per visible Automation and reset that memory when the Automation ID changes.
- The Live/read-only YAML panel should visually match the Edit YAML shell for line numbers, syntax highlighting, indentation guides, no word wrap, and horizontal scrolling, while remaining non-submittable and read-only.
- Current YAML editor product choice: fold/collapse controls and word wrap are disabled to avoid fold/wrap correctness bugs. Dormant fold machinery may remain in source, but no fold buttons should render until deliberately re-enabled with regression coverage.
- The visual graph editor can add/delete nodes, connect/reconnect/delete edges, and move nodes. Every canvas mutation updates YAML. Add-node modal edits must not reserialize or discard unsaved manual YAML edits until the dialog is submitted.
- Canvas-generated YAML should use readable block-style YAML for nested maps/arrays rather than inline JSON blobs.
- Details view destructive node/edge controls use icon-only trash buttons with descriptive `aria-label`s.

Maintained templates and custom graph contracts:
- Maintained Native and GitHub SDLC templates are starting graphs, not fixed schemas. Every template node may be deleted, and valid reduced graphs remain saveable.
- As of 2026-08-08, maintained Native and GitHub SDLC templates have five scheduled roles and no Loop Auditor: Vision Suggestions, Bug Finder, Optimization Finder, Redundancy Finder, and the Native/GitHub inbox. Loop Auditor is also absent from canonical restore-node metadata for new maintained templates.
- The retained graph is authoritative: action/workflow stages determine capability readiness and runtime authorization, not prompt wording or separate required-capabilities metadata.
- A producer with no action edge is a valid standalone schedule. Removing a node removes its owned Schedule/resource membership and incident edges while preserving valid shared targets and durable backing Tasks required by ownership semantics.
- Re-adding a maintained node may reclaim only the unique, unbound, unscheduled same-project Task whose durable `automation:<automation-id>:<node-key>` origin exactly matches that Automation and node; ambiguous, cross-Automation, or still-bound candidates fail closed.
- The maintained-template Add Node modal offers Custom Automation capabilities plus explicit `Restore:` choices for deleted canonical nodes. User-added nodes use Custom Automation validation/materialization; canonical nodes retain specialized maintained behavior.
- Custom Native mailbox topology is `Schedule/Task -> Create notification -> Human approval -> Approved inbox -> Implementation projection -> Outcome`.
- Custom GitHub mailbox topology is `Schedule/Task -> Create GitHub issue -> Human assignment -> GitHub inbox -> Task projection -> Open pull request -> Human review -> Outcome`.
- Native and GitHub mailbox stages cannot mix. Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, unsafe configuration, and arbitrary executable behavior fail closed with no resource effects.

Runtime and approval contracts:
- Runtime projects state onto the current graph while using normal Task, Scheduler, Alert, GitHub, worker, and queue paths.
- Trigger schedules have exclusive ownership. Worker/inbox resources may be shared only when an adapter explicitly permits it.
- Runtime persistence covers current-graph invocations, leased dispatch, reservations, work items, activities, transitions, live projection, metrics, and health. Replacing a graph deletes runtime projection tied to the old graph, so durable authorization for long-lived external handoffs must be keyed independently of graph-version rows when the artifact/task relationship must survive graph replacement.
- Scheduled Automation execution contexts snapshot the schedule owner's graph version and physical trigger node when the occurrence is claimed. If an Automation is saved while that occurrence is already running, the in-flight execution still carries the old binding; GitHub issue creation (`github_create_issue`) requires every causal binding to be current-active and may fail after the save instead of rebinding mid-run.
- Fix direction from 2026-08-10 authorization incidents: already-started Automation executions should keep safe launch-time authorization, or carry durable execution/origin proof, instead of losing GitHub issue/PR mutation authority merely because the Automation was saved mid-run. This must not become a broad GitHub-tool bypass; destructive mutations such as `github_replace_pull_request_branch` stay stricter.
- Open GitHub SDLC dispatch gap diagnosed on 2026-08-10: initial Automation-dispatched implementation runs can still carry only stale graph bindings because the dispatch envelope context sets `Bindings` without `OriginTask`. The durable issue-task provenance fallback for `github_open_pull_request` is available in task-thread follow-ups that mark Automation-created tasks as `OriginTask`, but not necessarily in the first dispatched run; if the Automation is saved mid-run, PR publication can still reject despite valid issue-task provenance.
- Native notification durable ownership is keyed by stable Automation identity plus alert artifact in the project, not replaceable graph revision IDs, physical node IDs, automation hashes, or producer/action/approval/inbox topology keys. Native alert owner rows in `automation_artifact_mailbox_owners` are effectively `project_id + automation_id + artifact_type='alert' + artifact_id`; migration 146 collapses old duplicate topology-key variants and blanks the historical node-key columns. A current active same-project Native inbox for that Automation proves live processing authority, and projection rebinding discovers the current `producer -> create_notification -> native_approval -> native_inbox` role path instead of matching old node keys. GitHub issue mailbox-owner mappings were retired on 2026-08-08; assigned GitHub issues are discovered/reconciled by the current inbox scan and exact execution provenance, not `automation_artifact_mailbox_owners` rows. Migration 145 deletes existing `artifact_type='github_issue'` owner rows while preserving alert owner rows.
- Runtime work-item projection may lazily repair durable external artifacts across graph replacements only when exact provenance can be mapped through live origin graph versions and stable node keys. Stale discarded-version GitHub issue work items should delete blocking local projection state before re-anchoring to the current graph.
- Human approval follows the canonical Alerts/GitHub contract: approval authorizes configured implementation handoff only, never merge, release, deployment, destructive remediation, credential changes, or arbitrary execution.
- Native notification handoffs use project-scoped actionable notification lifecycle: explicit approval, atomic lease claim, atomic Backlog implementation-task creation/linkage, execution of the exact linked task, and processing completion only after execution starts. Inbox scans must collect all eligible pages before mutation because linkage changes list membership.
- Scheduled Native inboxes derive project scope from the persisted caller Task and scan both read states. Automation-origin metadata is routing evidence only; durable authorization is separately keyed by project, Automation, and alert artifact while current active inbox identity supplies live processing authority.
- GitHub assignment to the PAT owner or a configured Authorized User is approval to implement. GitHub issue implementation Tasks are Active and auto-submitted; `execute_tasks` is only for reconciled Backlog or failed/cancelled work.
- Every external mutation reloads persisted Task and current Automation context. Visible GitHub tools do not authorize mutation by themselves, and local work does not prove PR publication. GitHub SDLC implementation tasks with durable issue-task provenance require live verified open/reviewable PR evidence before final task completion. As of the 2026-08-10 publication-head fix, `TaskPullRequestService.openForTask` publishes the branch, records `task_pull_requests.published_head_sha`, ignores closed branch PRs, and creates/persists or reuses an open PR only when live GitHub state is open, on the task branch/repository, and `head.sha` matches the recorded published head. The published-head SHA match is publication evidence for successful implementation task completion only; it does not decide, authorize, or mark Automation graph completion. Completion blocks missing PR rows, non-open rows, rows lacking a published head, and live PRs whose head SHA differs from the recorded publication head; when blocked, the task is finalized as `status=failed`, moved to `category=backlog`, emits a visible failure message, and creates an alert.
- Loop Auditors are inspect/report-only for direct task/swarm/execution creation; those grants are removed based on durable `automation:<id>:auditor` origin. The user deferred further restriction of alert/claim tool grants.
- `Run now` manually dispatches each schedule-owned entry Task using persisted prompt, Agent, model, and tool configuration. It does not mutate timing, skips queued/running/reserved entries, and rejects Paused or Archived Automations.
- Automation scheduled occurrence idempotency is scoped to Automation-owned schedules, not ordinary recurring task schedules or GitHub-only behavior. Occurrences dedupe by schedule ID plus scheduled time, so separate Automation schedules remain distinct even when configured for the same clock time, and repeated occurrences of one schedule remain distinct across times. Scheduled-time identity primarily exists for runtime dedupe/recovery, preventing duplicate side effects when scheduler claim/startup crashes or retries; Automation UI/history/audit rendering is a secondary benefit. On app restart while an Automation schedule is queued/running, the scheduler may rediscover the same due time, but Automation should reuse/recover the existing occurrence: create it only if nothing committed before crash, re-lease/resubmit queued or prepared dispatch work, or finalize an already-terminal execution. It should not intentionally start a second invocation for the same schedule/time. If an enabled repeating Automation schedule still points `next_run` at a previously completed, failed, cancelled, or skipped invocation for the same scheduled time, the Automation claim path advances `next_run` instead of returning the old invocation forever. This prevents past schedule edits or stale rows from suppressing later hourly/daily occurrences while avoiding duplicate dispatch and preserving the original `last_run`; ordinary recurring task schedules continue through the generic scheduler `MarkRan` path after submission.
- Automation Live no longer surfaces the manual `GitHub state` panel, Fresh/Stale badge, persisted-update timestamp, or `Refresh GitHub state` button. Stale tracked GitHub PR state still contributes to automation health, but as of 2026-08-08 `AutomationReconciler` refreshes stale tracked PR state in the background through `AutomationExternalStateService` only while the Automation Live page is recently open/polling. The lightweight `AutomationLiveViewTracker` marks `GetAutomationLive` page loads and HTMX polls, and the reconciler skips stale external-state refresh when no recent Live view exists. Background refresh updates stored PR status/URL and reconciles merged PRs to completed review outcomes or closed PRs to failed review outcomes without requiring manual interaction. The backend refresh endpoint may remain available even though the UI does not expose it.

GitHub and notification content standards:
- Automations use the selected project's repository identity: explicit `repo_url` first, otherwise a GitHub remote from the local checkout. Automation prompts/tools cannot override it.
- GitHub publication readiness requires usable provider authentication, at least one visible GitHub Authorized User, and a resolvable project repository before creating Automation, Task, or Schedule rows.
- Finder roles use trusted local duplicate state keyed by project, normalized repository, and stable finding idempotency key. Maintained keys derive from role, component, and stable symbol/behavior, never run IDs, dates, or randomness.
- Native notifications and GitHub issues should start with a short nontechnical `Summary`, then provide technical evidence, risk, implementation guidance, acceptance criteria, references, and regression cases. Bug findings require a concrete failure path; optimization findings require measurable evidence; redundancy findings require repeated locations and minimal consolidation.
- GitHub Dev Inbox scans configured Authorized Users and the PAT identity when available, deduplicates by repository/issue, and creates implementation work after assignment approval and task/PR reconciliation. Assigned open issues are eligible even when created manually in GitHub without prior Automation-created/mapping owner rows.
- Automation-bound GitHub SDLC turns cannot post issue-status comments. `github_open_pull_request` requires `## Summary`, `## Validation`, and an exact `Closes #<source issue>` reference matching trusted Task provenance. For Automation-created implementation tasks whose original graph version is no longer current, PR publication is authorized only through durable same-project GitHub issue task provenance plus the current active Automation graph's retained implementation-to-PR policy, even when stale or review-node causal bindings are still attached to the execution context; production follow-up context preparation marks durable Automation-created tasks as `OriginTask` while preserving any stale/review bindings. Spoofed `created_via` tasks and other stale-origin GitHub writes remain fail-closed.

Current gaps and incidents to remember:
- Open Automation UI scanability gaps from 2026-08-08/2026-08-09 suggestion discovery: Automation cards should surface already-populated next/last run, active work, counts, and resource summaries; Automation Live Details should expose linked resources, resource URLs/statuses, status counts, and task links equivalent to canvas task drill-downs.
- 2026-08-10 incidents: a GitHub SDLC Optimization Finder run gathered publishable performance evidence but `github_create_issue` was rejected as unauthorized after the Automation was saved mid-run. The run started on the old graph binding, the save published a new current graph before the tool call, and the issue tool rejected the now-stale binding even though the new graph retained `optimization_finder -> issue`; the next run should use the updated schedule owner binding unless another save happens mid-run. A later `#416` implementation run initially could not publish a reviewable PR because `github_open_pull_request` was rejected by Automation authorization, but the publication blocker was resolved on 2026-08-10 by opening PR `#435` for issue `#416` at head SHA `b0f86374d936c54960838626e2f0cd212bf46144`; its old blocked-goal/publication-blocker text could remain stale after the successful retry, so successful later PR publication should clear or refresh prior publication blockers. A later `#396` implementation run also reported passing validation but could not open a PR because `github_open_pull_request` was rejected by Automation authorization. Future failures without mid-run graph edits may need Automation graph/tool-grant remediation; unpublished performance targets remain tracked in `testing_coverage_and_performance.md`.
- Open gap `#387`: newly added custom Automation Schedule/Task nodes omit `skills` and `source_files` config defaults, so Details view does not show Skills or Source files selectors even though the compiler/runtime supports those fields when present; users must hand-edit YAML first to configure them.
- Stale-origin GitHub SDLC implementation tasks can publish PRs after graph replacement only when durable graph-independent issue-task provenance proves the Automation-created task/source-issue relationship. The mapping survives graph edits/replacements and old graph-version deletion, is cleaned up only when the owning OpenVibely task or Automation is deleted, and is not cleaned up by GitHub issue closure or PR merge. `github_open_pull_request` may use the current active graph's retained PR policy with that provenance even if stale/review bindings remain on the execution; branch replacement, spoofed `created_via` tasks, and other stale-origin GitHub writes remain blocked. A corrected incident diagnosis found that review-node causal bindings can block PR publication even when durable issue-task provenance is valid; authorization must distinguish implementation-to-open-PR policy from review-node bindings.
- Resolved 2026-08-10 publication-evidence gap: GitHub SDLC Automation implementation tasks with durable issue-task provenance are not marked completed unless PR publication is live-verified as open/reviewable and current enough for review, including `task_pull_requests.published_head_sha` matching the live PR `head.sha`.
- Describe-generated Automation review/save pages use the editable breadcrumb/header-save shell. Details-view header saves must preserve breadcrumb renames by submitting the synced `automation_name` from `automation-details-form`.
- Maintained Template selection aligns with the saved maintained-template Edit shell for the Add Node modal. Template preview should not show a separate browser-local `Suggested nodes` section.
- Custom Automation Describe/repair generation follows the runtime contract that open issues assigned to the PAT owner or configured GitHub Authorized Users are eligible even when manually created in GitHub. Generated GitHub inbox prompts should identify connected upstream producer stages as issue sources only, not eligibility limits, and must not rely on producer-branch creation records.
- Existing custom Automation snapshots require explicit Edit/Save or recreation to receive corrected generated prompts. Already-created Backlog tasks are not retroactively started and require manual execution.
- Stale-version repair coverage should include queued input bindings and dependent child work items so they are removed before deleting a stale parent work item.
- Native alert/notification mapping to Automations follows the Automation-owned model: `project_id + automation_id + alert_id` owns the notification, and a current same-project Automation inbox proves live processing authority. Stable node-key chains plus current graph topology are not durable ownership inputs; deleting and recreating a Native inbox inside the same Automation can allow old approved notifications to be processed by the new/current inbox.
