Automation Graphs is OpenVibely's project-scoped, reviewable orchestration surface. It compiles visible Tasks, Schedules, Alerts/GitHub handoffs, workers, queues, and graph provenance; it is not a parallel graph executor, queue, worker, or arbitrary-code runtime.

Authoring and persistence:
- Canonical YAML is the only configuration authoring surface for Template, Describe, Custom, direct Chat Save, and saved Edit. Graph mode edits browser-local topology/layout; node and edge configuration remains in YAML.
- YAML schema version 1 uses strict decoding. It rejects malformed/multi-document YAML, aliases/anchors, duplicate/non-string keys, unsupported fields/tags, unsafe configuration, invalid topology/capabilities, and foreign-project references before resource effects.
- Chat `save_automation` accepts canonical `source: "yaml"` plus `automation_yaml` through the same PreviewSave/Save pipeline as the browser. Orchestrate-only actions `run_automation_now`, `pause_automation`, `resume_automation`, `update_automation_template`, and destructive `delete_automation` resolve exact current-project IDs/names and delegate service authorization; Plan is read-only.
- Deletion uses `automation_trigger_owners`, not titles, roles, or categories. It snapshots tasks linked to owned schedules, removes those schedules, and deletes a candidate trigger task only when no surviving schedule or Automation reference remains. Scope and in-flight-dispatch guards precede mutation; failure rolls back metadata, schedules, and tasks, while success publishes Automation/task-board invalidations. Independent domain, implementation, outcome, issue-created, shared, and unrelated Tasks are preserved.
- Existing graph-backed Automations serialize to YAML on read. Preview/save does not silently migrate, rewrite prompts, replace point-in-time configuration, recreate resources, or backfill old resources. Each Automation has one current graph; graph revision IDs are runtime bindings, not durable mailbox identities.
- Save atomically persists identity/current graph, materialized Tasks/Schedules, topology, admission-compatible resources, and removal of old projection. Invalid saves have no resource effects; committed eligible Active roots submit. Active/Paused/Archived state is preserved, with schedules enabled only for Active and pending current-graph work demoted on Pause/Archive.
- New canonical schedules default `clear_context_on_start=true`; trusted edits preserve an omitted older value. Task/schedule nodes support bounded goals and optional `model_config_id`; blank/missing/`default` uses runtime fallback. Agent references are resolved in one save-scoped bounded compact selectable-reference projection, with zero Agent queries when no references exist. The 50-row bound, scope/filtering, ordering, invalid/foreign handling, and atomic materialization are part of the contract.
- `DefaultAutomationDraftNodeConfig` owns common category, priority, goal, model sentinel, cadence, approval, labels, notification, and PR defaults. Maintained-template updates require `CurrentAutomationTemplateRevision`; saved Automations are snapshots. Current maintained revisions are Native SDLC `11` and GitHub SDLC `15`.

Builder and topology:
- Web creation supports Template, Describe, and Custom; Custom is the runnable blank builder. Native SDLC and GitHub SDLC are maintained starting templates; Vision Driver is internal reconstruction support.
- Templates load embedded canonical YAML without resource creation. Builder YAML remains browser-local until Save; Graph selection runs non-persisting PreviewSave. Live and Builder share Graph/Details/YAML views, while Live retains the selected view only for the same Automation.
- Eligible saved Automation cards and Live actions expose project-scoped Duplicate. It loads the current candidate into an identity-free browser-local `Copy of <name>` draft; Save creates independently owned resources and leaves the source unchanged. Duplicate eligibility is an explicit allowlist: Custom, Native SDLC, and GitHub SDLC are creatable; Vision Driver and unknown/legacy adapters fail closed. Names are normalized, UTF-8-safe, capped at 200 bytes, and deterministically fall back to `Copy 2 of <name>` when needed.
- Add Node offers Custom capabilities and Restore choices for deleted canonical nodes. User nodes use Custom validation/materialization; canonical nodes retain maintained behavior. Canvas mutations update YAML and preserve unsaved YAML. Maintained templates are starting graphs rather than fixed schemas and include Vision Suggestions, Bug Finder, Optimization Finder, Redundancy Finder, and Native/GitHub inbox roles, not Loop Auditor.
- The retained graph is authoritative for capability readiness/authorization. Producers without action edges can be valid; deleting a node removes owned schedules/resources and incident edges while preserving valid shared targets/tasks. Re-add may reclaim only a unique unbound unscheduled same-project task with exact `automation:<automation-id>:<node-key>` origin.
- Custom Native topology is `Schedule/Task -> Create notification -> Human approval -> Approved inbox -> Implementation projection -> Outcome`. Custom GitHub topology is `Schedule/Task -> Create GitHub issue -> Human assignment -> GitHub inbox -> Task projection -> Open pull request -> Human review -> Outcome`. Native/GitHub mailbox stages cannot mix; unsafe configuration, executable cycles, duplicate targets, self-edges, dangling endpoints, and arbitrary execution fail closed.
- Describe/repair treats assignment to PAT owner or configured GitHub Authorized Users as eligibility, including manually created issues. Prompts identify producers as sources rather than eligibility limits.

Runtime and handoff:
- Runtime uses normal Tasks, Scheduler, Alerts, GitHub, workers, queues, and `thread_inputs`. Trigger schedules have exclusive ownership; adapters decide when worker/inbox resources are shareable. Durable state includes invocations, leased dispatch, reservations, work items, activities, transitions, live projections, metrics, and health.
- Scheduled claims snapshot graph version and physical trigger node. In-flight work may retain an old binding after Save; stale-binding repair allows only compatible same-logical actions. Long-lived external authorization is keyed independently of replaceable graph rows.
- Native ownership is `project_id + automation_id + alert_id`. GitHub mailbox mappings are retired; current inbox scans and execution provenance reconcile assigned issues. Initial GitHub implementation tasks are `OriginTask`, allowing issue-task PR provenance after graph replacement only under current policy.
- Duplicate prevention is existing-work-first: list artifacts, hydrate likely matches, skip covered findings, continue searching, create at most one new finding per run, and report no finding rather than weak duplicates. Model-authored unstable keys/title hashes are not authority; direct-caller idempotency is separate.
- Approval authorizes only configured implementation handoff. Native handoff uses the atomic claim, Backlog task creation/linkage, exact linked-task execution, and completion-after-start contract in `alerts_and_actionable_notifications.md`. Automation-owned scheduled tasks remain ordinary generic tasks with shared tools; authority is enforced at the service layer. Loop Auditors in old graphs are inspect/report-only.
- `Run now` dispatches schedule-owned entry tasks with persisted prompt/Agent/model/tools without changing timing, skips queued/running/reserved entries, and rejects Paused/Archived Automations. Occurrence idempotency uses owned schedule plus scheduled time; repeating schedules advance beyond terminal past invocations.
- Claims/failures are crash-consistent across execution/task/activity/invocation/outbox/reservation; cancellation wins. Eligible failed/completed work may be re-admitted, stale completion metadata is cleared, and committed transitions publish project-scoped `task_board_updated`. Resume deduplicates definition/activity-backed Backlog admissions and assigns consecutive ranks after the existing Active tail.
- Automation Live ranks current `node + work_item` projections as `failed > blocked > running > waiting_human > recently_completed`; nonterminal activity does not mask completed work. A current Run-now invocation supersedes only the matching prior terminal projection. Hidden Native inbox work may show Running without an ordinary Active card; a running node with no backing work is likely stale.

GitHub, notifications, and Chat:
- Automations use selected-project repository identity: explicit `repo_url` first, otherwise a Git remote. Prompts/tools cannot override it. GitHub publication requires usable authentication, a visible Authorized User, and a resolvable repository.
- GitHub assignment is approval to implement; implementation tasks are Active and auto-submitted, while `execute_tasks` is for reconciled Backlog or failed/cancelled work. External mutations reload persisted Task and current Automation context; local work does not prove PR publication.
- Existing-work lists are compact/paginated: GitHub omits bodies, Native omits message/body/metadata/idempotency keys, and detail tools hydrate likely matches only. Finder prompts/findings begin with `## Summary`, then evidence, risk, implementation, acceptance, references, and regressions.
- Direct web/API Chat and shared channel/scheduled Chat serialize prompt-safe Automation cards through one service-level `AutomationCardSummary`. `graph_node_count` is the count of saved nodes bound to the published graph version, while `counts` is reserved for current operational work (`running`, `waiting`, `blocked`, `failed`, `completed_recently`). Surface authorization, lookups, errors, and envelopes remain local.
- `AutomationGraphService.List` combines the compact saved-graph card projection with one project-scoped operational-count aggregate. Optional `project_id` inputs are equality assertions against the caller's current project, never project-selection overrides. Maintained updates are explicit Orchestrate actions; current, custom, unsupported, and foreign Automations are not silently rewritten.
- Reconciliation uses one broad task lookup per issue URL/number without lifecycle filters. `github_open_pull_request` requires `## Summary`, `## Validation`, and exact `Closes #<source issue>`.

Current constraints and gaps:
- External refresh should use project-scoped identity-only `AutomationRepo.Exists` without hydrating graph versions/nodes/edges/resources; background refresh should remain zero-hydration and contention-aware.
- Maintained-template update UX still replaces destructively without a non-persisting node/YAML/resource diff (`#919`). Calendar cards omit `clear_context_on_start` in enabled and disabled states (`#1054`).
- GitHub SDLC records trusted project-scoped source-issue provenance, but Task Details does not expose a valid unambiguous issue link (`#1066`).
- Capability-backed and fallback validation share candidate reference filtering and availability reporting, but retain separate catalog acquisition and no-reference query guards. `model_config_id` validation and save-time Agent materialization remain separate.
- `AutomationGraphService` owns shared project-scoped Automation-card ID/name selection: normalization, ID precedence/conflict rejection, case-insensitive name matching, deterministic ambiguity reporting, and exact-ID refresh.
- Save-during-run must retain active task-backed executions while removing stale graph projection, and stale-origin repair must remove queued-input bindings/dependent child work before stale parents. Native inbox ownership is stable across delete/recreate, so alert decision/processing state must be checked before marking `waiting_human` stale.
- Authoring must not rely on weak per-Automation `skills` or `source_files` hints. Prompts identify sources and Skill Curator routes skills; Vision Suggestions must verify/read root `VISION.md`. Custom child activation recompiles from the saved graph so downstream handoff edges remain in prompts.
- The editor accepts an emptied task goal, but atomic save currently persists the prior nonempty goal (`#1091`). Deletion confirms owned trigger schedules/tasks but does not preview exact retained/deleted resources when trigger tasks are shared (`#1093`).
