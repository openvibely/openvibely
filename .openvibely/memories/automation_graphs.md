Automation Graphs is a project-scoped, reviewable orchestration surface built on existing OpenVibely tasks, schedules, workers, queues, Alerts, GitHub services, repositories, and current-graph resource provenance. It extends those systems rather than introducing a parallel graph executor, queue, worker, or arbitrary-code runtime.

Architecture and safety boundaries:
- Supported creation paths are Template, Describe It, and Blank. Blank is a runnable custom builder, not an inert diagram editor or preset assembler. New template creation and maintained setup registration are restricted to Native and GitHub SDLC; both templates include scheduled Vision Suggestions. The internal Vision Driver adapter remains only to preserve editing and runtime support for already-saved Vision Driver graphs, without migration or backfill.
- Definitions are project-scoped and each Automation has exactly one current saved graph; there is no retained Automation version history or superseded graph. Trigger schedules have exclusive ownership, and worker/inbox resources may be shared only when an adapter permits it.
- Runtime persistence supports the current graph's invocations, leased dispatch outbox, task reservations, work items, activities, transitions, live-position provenance, metrics, and health independent from lifecycle state. Runtime projection tied to a replaced graph is deleted on successful Save.
- Do not add legacy-resource discovery, heuristic inference, confidence scoring, migration, or graph backfill for resources created before Automation Graphs.
- Human approval authorizes only the configured downstream handoff. It never grants merge, release, deployment, or arbitrary execution authority.
- Unsupported handoffs, executable cycles, ambiguous duplicate targets, self-edges, dangling endpoints, duplicate keys, unsupported conditions/types, unsafe configuration, foreign-project references, and arbitrary executable behavior fail closed with no resource effects.

Builder and publication contract:
- Template, Describe It, Blank, and Edit are browser-local until `Save changes`. Selecting `Use template` loads the canonical maintained graph into the same builder without creating an Automation, Task, Schedule, graph row, or runtime resource; users may review or customize it, and refresh/navigation discards it. Only `Save changes` validates and atomically creates the Automation and required resources, then redirects to Live.
- Users may design open-ended graphs in browser memory, but unsupported executable shapes cannot be saved as inert persisted drafts. For user-authored graphs, the normal web flow is `Edit automation`, browser-local changes, then one immediate `Save changes`; refresh/navigation discards unsaved edits.
- Save submits the complete graph, validates it, and atomically replaces the current saved graph under the same Automation identity, including while Automation work is running. There is no web-facing draft, Automation version history, version selection, Review/Apply, separate Publish step, superseded graph, or restorable publication. Successful Save deletes the prior graph and its Automation runtime projection in the same transaction; failure leaves prior behavior active.
- Save-time persistence must use one SQLite transaction that creates or updates Tasks and Schedules, replaces the current graph and bindings, and commits before normal workers or schedulers can act. Any error or pre-commit crash rolls back the whole Save and leaves prior behavior active.
- Do not retain persisted Save journals, staged Automation versions, publication-attempt resource-step tracking, `Save needs attention` recovery, `PlanRevision`, or `automationCompilerContractVersion`. Failed-Save recovery is unnecessary because all Save-time resources are local database rows and GitHub issues/PRs are created only at runtime, not during Save.
- Chat uses `plan_automation_save` followed by later-confirmed `save_automation`. Planning exposes no Automation/version identity or URL and creates no Automation or runtime-resource rows. It needs only private signed confirmation state tied to the exact displayed graph; the later exact `save <automation-name>` confirmation applies that graph through the same atomic Save path.
- Candidate schema versions are preserved; missing or unsupported versions are rejected or use Describe It's one bounded repair path, never silently downgraded.
- Agent, skill, and source-file references resolve only from the selected project's bounded, secret-free capability snapshot. Missing, ambiguous, unavailable, or foreign-project references are explicit errors.

Executable topology:
- A Schedule node is itself a substantive OpenVibely Task plus a Scheduler row targeting that schedule-owned Task. It owns the prompt, agent, priority, timing, enabled intent, and `clear_context_on_start`; it can run without a connected generic Task and is not merely trigger metadata attached to another node.
- Automation exposes one generic `Task` node in addition to Schedule nodes. Ordinary Task nodes materialize as stable OpenVibely tasks on Save. Only the exact `GitHub inbox → Task → Open pull request` topology treats that generic Task node as configuration for issue-specific tasks created later.
- Schedule nodes remain available for new graphs. A currently saved graph using the old internal implementation-task role remains runnable until edited; new graphs must not expose separate Agent Task or Implementation Task choices.
- Supported custom shapes use Schedule nodes and generic Task nodes with deterministic paths through supported tasks, actions, human gates, and Outcomes. One task may fan out to multiple children, but each child may have at most one task parent because persisted tasks store one parent.
- `Schedule → Task` is an explicit downstream handoff: scheduled Task A performs its substantive work, then creates, activates, or reuses Task B through normal task/worker machinery. It must never compile as a Scheduler row that directly targets Task B.
- Schedule compilation is generic across Template, Describe It, Blank, and Chat and across supported automation topologies. Every Schedule materializes its own task and Scheduler row; a connected generic Task materializes separately as its downstream child. Unsupported or ambiguous schedule connections fail validation rather than changing those semantics or producing hidden relay tasks.
- Chat's signed confirmation state must bind the later confirmation to the exact graph that was displayed. This is an integrity check only; web Saves do not need candidate/resource-operation hashes, and Chat confirmation does not create Automation versions, publication journals, or retryable resource-step state.
- Maintained setup registration binds each scheduled loop's Task and Scheduler row to the same node key and rejects a Scheduler row whose target differs from the Task bound to that node. This prevents corrected graph visuals from masking an incorrect scheduled Task.
- Downstream tasks are pre-created blocked, then activated or reused through normal task/worker machinery. Causal handoffs survive restart, remain idempotent, and block rather than duplicate busy children. Activation transactionally verifies the Automation is still on the same current graph and Active. Pause and Archive demote every pending Active root or entered child, including activity-created Tasks, to Backlog; final dispatch admission rejects lifecycle races; Resume admits eligible Paused work once from exact durable admission intent; and Archive remains non-resumable.
- Removing or reconfiguring a schedule deletes its obsolete Scheduler row. Confirmed Automation deletion deletes exclusively owned Scheduler rows transactionally while preserving domain tasks. Deletion rejects scheduler in-flight work and ordinary running Task executions linked through exact Automation activity resources, then permits deletion once those executions are terminal. Stale invocation rows with no surviving dispatch or execution remain safely deletable.
- Task node settings stay in parity with ordinary tasks and must not expose skill/source-file inputs merely because the task is in a graph. Scheduling must not be represented as a user-authored `scheduled` Task category.

Native Alert and GitHub handoffs:
- Maintained Native and GitHub SDLC templates have parallel scheduled discovery loops for Vision Suggestions, Bug Finder, Optimization Finder, and Redundancy Finder, plus scheduled Inbox and Loop Auditor nodes. Each recurring loop is represented by one Schedule node that owns both its Task and Scheduler row; the templates no longer use empty `*_trigger → Task` relay pairs.
- Their intentional differences begin at the mailbox and delivery boundary. Native uses OpenVibely notifications, human approval, an approved-notification inbox, and visible implementation tasks without opening PRs; GitHub uses issues, assignment approval, a GitHub Dev Inbox, implementation tasks, PR creation, human review, and observed merge completion.
- GitHub's Loop Auditor inspects integration-specific state, while Native's parallel auditor checks stale notifications, failed claims, missing linked tasks, duplicate work, and blocked task state using OpenVibely data.
- A Native Alert graph configures runtime `create_notification`; publication creates no Alert. Multiple valid producers may share one notification action. Human approval may be terminal or branch to approved/rejected Outcomes, and an omitted branch terminates safely.
- Alert/GitHub runtime projection resolves exact project, Automation, current saved graph, node, edge, invocation, and work-item identities. Idempotency cannot adopt an object created outside that Automation.
- GitHub lifecycle graphs preserve human gates: a producer creates an issue, a separate inbox polls assigned issues, assignment is approval, the topology-specific Task performs issue work, PRs wait for human review, and only observed merge reaches Outcome.
- GitHub publication creates only configured producer/inbox tasks and required Scheduler rows. Issues, issue-specific tasks, and PRs arise later through existing GitHub/task services.
- The maintained Native SDLC Automation template owns self-contained prompts in Automation service code for Vision Suggestions, the three finder roles, Notification Inbox, and Loop Auditor. The prompts require notification-only discovery with stable idempotency keys, focused project-area rotation, approved-notification claiming and atomic implementation-task linkage, safe failure/release recovery, and approval-gated auditing. Template execution does not depend on bundled skill files. Existing saved Automations remain unchanged; corrected defaults apply only to newly created or explicitly saved templates, while bootstrap registration snapshots exact bound Task prompts.
- Native and GitHub create implementation work through intentionally different prompt paths. GitHub's Dev Inbox composes each issue-specific Task from the trusted configuration-only Implementation-node prompt plus assigned issue content, so an empty node prompt is invalid. Native's Approved Inbox does not copy the graph Implementation-node prompt; its maintained inbox instructions require the agent to pass a focused prompt, reviewed notification context, acceptance criteria, notification identity, and approval limits to `create_alert_implementation_task`, which atomically creates and links the Task. Therefore the repaired GitHub empty-Implementation-node defect did not affect Native SDLC.
- `AutomationRegistrationService.Register` returns whether an existing registration was reused; completion telemetry reports creation as the inverse of that value.
- Builder form overlays preserve explicitly empty names and malformed numeric values so strict validation rejects them rather than silently retaining valid values from hidden candidate JSON. Final browser Save also treats an unchecked Schedule `clear_context_on_start` control as explicit `false`, while browser-local intermediate actions preserve omitted values.
- Maintained Native and GitHub public guidance and bootstrap skills must stay aligned with their six scheduled roles, canonical cadences/node keys, approval boundaries, and selected-project repository rules. The templates themselves own their runtime prompt bodies and do not depend on bootstrap skill files.
- The maintained GitHub SDLC Automation template owns explicit prompt bodies in Automation service code for Dev Inbox, the configuration-only issue-specific Implementation Task, Offering Manager, the shared finder roles, and Loop Auditor. Each runtime issue-specific Task composes the trusted template Implementation prompt with the assigned GitHub issue title/body supplied by Dev Inbox: the issue content says what to solve, while the template prompt controls how the agent may work. Runtime must not execute from external, untrusted issue content alone. The Implementation prompt requires focused issue work, relevant build/tests, PR creation through `github_open_pull_request`, and no approval, merge, release, or deployment on a human's behalf. Template creation does not import `builtinskills`, read or parse a bootstrap `SKILL.md`, depend on skill support files, or require the bootstrap skill to remain installed. Cadences remain daily discovery, hourly Dev Inbox, and weekly Loop Auditor. Existing saved Automations are not silently rewritten; these prompts apply when the GitHub SDLC template is created or explicitly saved. The separate bundled bootstrap setup path must nevertheless keep its Task-prompt guidance consistent with the same repository boundary because registration copies exact bound Task prompts into the saved graph.
- Initial setup intentionally differs: the bootstrap skill requests an immediate first Offering Manager run before attaching its daily schedule, while saving the GitHub SDLC Automation template normally follows the configured schedule unless the user manually runs that Task.
- Initial maintained registration hydrates graph node configuration from canonical maintained defaults plus the exact bound Task and Schedule rows, including prompt, category, priority, cadence, configured enabled state, `clear_context_on_start`, action settings, and approval method, without mutating the bound Task prompt. New Automation schedules default `clear_context_on_start=true`; when an older saved graph omits that key, trusted Edit/Save preserves the exact persisted Schedule value rather than silently changing it. Registration reruns never repair, rehydrate, rename, migrate, or replace an existing published graph, including older graphs with `{}` node configuration; they preserve the saved point-in-time snapshot exactly. Trusted Edit reconstruction may fill only absent canonical keys in an older maintained snapshot in browser-local state so explicit Save remains possible, without overwriting stored values or writing before Save. While Paused or Archived, physical Schedules remain disabled until explicit Resume restores the enabled/disabled intent already saved in the current graph.
- Required GitHub boundary: Automations use the selected OpenVibely project's repository identity, resolving the explicit project `repo_url` first and otherwise resolving a GitHub remote from the project's local checkout. The Automation has no separate repository picker, never infers a repository from the GitHub account, and ignores model-supplied repository overrides across issue creation/reads, assigned-issue lists, comments, labels, PR-feedback forwarding, task-scoped pull-request operations, source-issue provenance, and external-state refresh. Save readiness, issue tools, issue-specific Task creation, PR open/replace, and external refresh use this same URL-first/local-remote rule so Save cannot accept a repository that runtime later rejects. Idle web, queued/channel, and failed-retry follow-ups with surviving causal or current-definition bindings load both the Task and causal Automation context before runtime composition, and the hardened Automation executor takes precedence over generic/channel executors for overlapping GitHub tool names. Automation-origin Tasks whose prior graph/projection has been replaced remain Automation-bound through durable Task identity, including narrowly repaired prior feature-created issue Tasks with exact provenance; stale queued bindings are revalidated before GitHub writes. Issue creation, implementation-Task creation, PR opening, and guarded branch replacement require every causal binding to belong to the current active graph and authorize the action; task-scoped PR mutations target the exact causal caller Task. Ordinary non-Automation Chat retains the generic tools' explicit-repository capability.
- Offering Manager and the three finder roles must not receive repository-wide issue lists, search results, titles, bodies, or comments for duplicate detection because that expands the prompt-injection surface. Their prompts must not require model-visible repository-wide issue search, and Automation-bound `github_create_issue` must not read existing GitHub issues at all for duplicate detection. Duplicate prevention uses only trusted local state: a durable record keyed by project, normalized repository, and normalized-title fingerprint serializes creation and stores only the issue number OpenVibely itself created plus an IDs-only OpenVibely projection-source snapshot. Claims transition from `reserved` to `dispatched` immediately before the provider call and to `completed` when the returned issue number is durably stored. Only definitive pre-dispatch failures may release a claim; post-dispatch ambiguity remains permanently fail-closed. Successful issue identity and projection are persisted independently of caller cancellation. A completed claim may repair missing projection only for the same project, Task, Automation, graph, and source-node binding set; a different Automation or replacement graph fails closed, while a later execution of the same stable source remains eligible. Successful repair must prove every expected issue and assignment projection was recorded. Concurrent equivalent runs must create at most one issue. Duplicate/reuse responses may expose only the locally recorded issue number and a trusted same-repository URL. The Dev Inbox remains a separate narrow path limited to explicitly assigned issues because assignment is the human approval gate for implementation.
- GitHub SDLC publication requires usable provider authentication, at least one visible GitHub Authorized User for approval/inbox identities, and a project repository resolvable from either `repo_url` or a GitHub remote in the local checkout. It does not require a hidden legacy `github_project_inboxes` row. Missing readiness fails before creating Automation, Task, or Schedule rows. A web `Save changes` attempt remains in the builder, renders a prominent `Save did not apply` error, automatically expands the setup-item list, and names the missing public prerequisites instead of appearing inert. The maintained template's canonical GitHub action fields `instructions`, `labels`, `base`, and `draft` are valid Save configuration and receive the same strict type, required-value, length, label-count, and forbidden-label-prefix checks as equivalent custom action nodes.

Describe It and UI contracts:
- Describe It and canonical Chat actions use the same custom schema, capability snapshot, normalization, validation, planning, compilation, and publication services as the web builder. The model receives schema/capability context but no mutation tools.

Schedule-owned task prompts also tell the model not to recreate or reschedule an explicitly connected child because OpenVibely activates it after successful completion.
- Graph edges use `from` and `to`; aliases such as `source` and `target` remain invalid. Every edge uses `from_port: right` and `to_port: left`, representing source `OUT → IN` target. Missing, reversed, or same-kind port geometry fails strict public validation, while older saved connector metadata normalizes to the canonical directional ports only when reopened through the trusted saved-graph path. Schedule/Task priority is integer `1..4`; generated out-of-range numeric priorities may be clamped before validation, malformed types use one bounded repair, and browser-authored invalid values fail strictly.
- Describe It deterministically enforces the Native Alert approval boundary on generated custom candidates: every `Create notification` action has exactly one outgoing `Human approval` gate. If generation omits the gate, it is added without consuming the model repair; if generation connects the notification directly to an Outcome, that Outcome is routed through approval as the approved branch. Manual browser-authored Save validation remains strict rather than applying this generation-only normalization.
- Repair receives the original schema, capability contract, project snapshot, user description, validation failure, and bounded prior output. Unknown fields remain rejected. Generation/validation failures render visibly and create no Automation, task, or schedule.
- Describe It receives a purpose-built custom-graph capability view rather than the broad builder snapshot: only executable custom node types and roles are advertised, project IDs are omitted, and skills, source files, reusable resources, legacy `implementation`, and unsupported `condition` surface are excluded. Publication safety and lifecycle state:
- Save uses one repository/database transaction for Automation identity, the complete current graph, exact resource membership, Task creation/updates/topology, Schedule creation/updates/deletion, lifecycle-compatible admission state, and removal of prior runtime projection. After commit it submits every authoritative pending Active root that became runnable, whether newly created, changed from Backlog to Active, or reset from a terminal state; schedulers cannot observe unpublished enabled rows.
- The atomic Save implementation has replaced the prior multi-step compiler/publication staging path. Publication-attempt/step persistence, candidate hashing, plan revisions, compiler contract versions, staged-Save recovery, and failed-Save recovery UI are not part of the current contract.
- Worker context lookup may resolve exact Task membership from the current saved graph when no causal Automation activity exists. Definition-only root provenance creates an execution-scoped work item and carries that causal binding through terminal Live projection; existing causal activity bindings take precedence for downstream or shared Tasks.
- Ordinary worker-queue entries are Task-ID admission hints. Dispatch atomically reloads the full persisted Task, resolves current Automation context, and claims the Task in one SQLite immediate transaction, preventing a concurrent Save from mixing old prompt, Agent, or topology with replacement graph identity. Prepared Automation dispatches retain their immutable envelope and pre-created execution.
- Save preserves Active, Paused, and Archived lifecycle state. Paused and archived schedules stay disabled. Pause and Archive demote all pending Active current-graph Tasks, including exact activity-created children, to non-admitted Backlog. A durable paused-admission row distinguishes work demoted by lifecycle from intentionally Backlog work, allowing Resume to restore eligible Paused Tasks once. Delayed handoffs and ordinary dispatch recheck the current graph and lifecycle transactionally; Archive clears paused admission and remains non-resumable.
- Archive retains disabled trigger-owner provenance so later archived edits or deletion can find and remove obsolete exclusively owned Scheduler rows while preserving domain Tasks.
- Automation Graphs documentation is maintained in `docs/specs/automations/`, root `README.md`, and the standalone `docs/automations-user-guide.md` linked from `docs/user-guides.md`. Documentation must describe the one-current-graph, direct-Save, Live-only model.
