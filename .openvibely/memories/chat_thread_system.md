Interactive Chat intentionally bypasses worker capacity. Task-thread follow-ups use `processStreamingResponse` with `IsTaskFollowup=true` and respect global, project, and model capacity.

Queueing, steering, and attachments:
- Normal Send during an active Chat/task-thread run queues the next input; explicit steering applies only at OpenVibely-owned provider/model-step boundaries; Stop cancels the current execution. Durable `thread_inputs` represent queued/steering input; `executions` represent real model runs.
- Promotion claims pending input while creating the next execution/task and preserves FIFO. Task-thread follow-ups resolve current model assignment at promotion; queued Chat inputs retain per-input model selection. Follow-up executions stay `queued` until worker admission, then become `running`.
- Attachment sessions live on queued/steering rows. Chat rows use `run_execution_id` without `task_id`; task-thread rows use `task_id`. Repeated drops append, browser-name collisions get unique pending names, and the three-files-per-message limit spans repeated drops.
- Text attachments enter prompt context, images become model attachments, and large text remains attached without inlining. Steering attachment discovery after a provider call/deferred completion is requeued as a normal next message, never committed to a completed user bubble. Failed submissions preserve drafts/sessions for retry; rollback retires unowned sessions.
- Attachment persistence writes and renames atomically before metadata. Multipart limits are endpoint-specific and checked before full parsing/side effects. Per-task destinations reserve existing and same-request names, fail closed when listing existing rows fails, and delete physical bytes only when no remaining metadata row references them.
- Effective Active runtime task creation persists Backlog until conversion succeeds, then activates by request index. Storage roots vary by local, hosted/Docker, and desktop configuration; broken metadata may be reconciled, missing file bytes cannot.

Admission, lifecycle, and history:
- Follow-up admission is serialized with scheduler/worker claims and Automation reservations. Browser pending-input, queued-to-steering, and cancel routes are project-scoped. Active-lane reservation/order and lifecycle handoff fences are canonical in `openvibely_architecture.md`.
- Startup and update-drain recovery use stable bounded keyset pages, per-task FIFO, exactly-once promotion, sparse indexes, and guards for active Chat/terminal executions. Chat and task-thread recovery share pagination mechanics but retain distinct queries, callbacks, diagnostics, and list-error policies.
- HTTP acceptance remains lightweight; full context setup occurs after durable acceptance. Setup failure performs terminal cleanup and may promote queued input. Thread pagination renders execution history, not an unrecorded `tasks.prompt`.
- After-complete hooks receive only the latest normalized input/response. Provider history is rebuilt from `executions.PromptSent` and cleaned `Output`, with at most 20 prior task-thread turns after filtering the current execution.
- Immediate follow-ups load the newest 21 executions, honor context boundaries, and hydrate context only after queued admission. Manual failed-execution retries exclude both the new retry and failed source while preserving other relevant history; queued retries persist `retry_source_execution_id`, and promotion applies the same exclusion so the failed prompt is sent exactly once. Execution-scoped oversized-input artifacts are cleaned after the provider loop.
- Execution History and Task Thread share a canonical light page loader with project/task filters, descending timestamp/rowid ordering, cursor adjacency, and bounded pages. Global Chat follows the same chronological window contract; handler consolidation remains `#1059`.
- Web/API and external-channel Chat `view_task_thread` paths share `service.LoadBoundedTaskThreadExecutions` for zero-limit chronological history loading. The helper owns 20-row batching, caller-provided transcript-budget stopping, empty/short-page termination, and returned-row offset advancement; lookup, counting, ownership, positive-limit reads, errors, and browser/channel formatting stay surface-specific. Detailed `#1185` coverage expectations live in `testing_coverage_and_performance.md`.
- Task Detail non-poll thread windows must use bounded UTF-8-safe projections: `tasks.prompt` capped to a 4 KiB preview with truncation state; execution prompt/error previews capped at 4 KiB and output previews at 24 KiB. Poll-only compact metadata coverage is insufficient; the non-poll `GetTaskThread` path must not reload the full prompt. Preserved-terminal polling remains on the compatibility path, and full execution content is lazy, exact-execution scoped, task-plus-project ownership checked, and rendered through the shared task-thread bubble/hydration contract.

Composer and realtime contract:
- Shared `ChatInputForm` owns send/queue/steer markup and behavior. Enter sends/queues, Meta/Ctrl+Enter steers while active and sends once while idle, Shift+Enter inserts a newline. Platform hints are `⏎ sends or queues · ⌘+⏎ steers` on Apple and `Enter sends or queues · Ctrl+Enter steers` elsewhere. The textarea remains accessible and required, but `novalidate` suppresses browser validation UI.
- Task-thread and API Chat trim at the admission boundary, reject normalized-empty messages with `400 message is required` before task lookup, agent/model selection, attachment, queue, or execution side effects, and preserve padded nonempty input. Web task-thread coverage must exercise valid configured-agent idle and active admission paths as well as invalid-agent ordering.
- Accepted sends clear text/session only after acceptance; a lost `409` steer retries once as a normal send. The active primary action becomes a same-styled Stop with a square icon; server OOB state is authoritative and carries a fresh execution ID immediately. In-flight counters start at `htmx:beforeRequest` so native validation cannot strand them.

Modes and runtime actions:
- `/chat` is the global/project Orchestrate surface; Task Detail Thread is task-specific. Plan is read-only; Orchestrate mutations require authorized runtime tools. Tool-incapable providers receive no bracket-marker fallback; legacy markers such as `[CREATE_TASK]` are inert prose.
- Web Orchestrate Chat alone exposes provider-agnostic `request_user_input`, accepting 1–3 questions with 2–3 options, project-scoped SSE, one-time in-memory answers, and a ten-minute TTL. It must precede ambiguous writes. Definition filtering and execution both reject it on task-thread follow-ups. Pending requests are not durable across restart; reload/SSE recovery and expired-card UX gaps are `#1104` and `#1110`.
- Orchestrate-only actions include model/personality/Agent/project/task/Automation mutations, cancellation, and destructive deletes. Read-only discovery includes channels, tasks, schedules, Pulse, usage, system update, and Automations where supported. Actions resolve exact IDs or unambiguous names, enforce current-project ownership, validate before side effects, and preserve protected records. Agent create/update runtime tools share service-level strict JSON decoding and tool-list normalization; preserve create/update-specific allowed fields, create default tools for omitted or all-blank tool lists, update explicit-empty tool lists, target selectors, error prefixes, and nested `scoped_files` key rejection.
- `create_task` and `create_swarm_task` share normalized service input, compact model loading, validation, and summaries across web/API/channels. `list_tasks` is bounded, current-project, read-only discovery excluding Chat category, with filters, deterministic pagination, compact summaries, and guarded identical exhausted-empty calls. It lacks several rich Task Detail fields.

Goals, cancellation, schedules, and swarms:
- Plan handoff uses completed Plan responses containing `<proposed_plan>`. Goals are durable `task_goals`; continuation uses queued task-thread follow-ups rather than inline work. There is no direct peer-to-peer task chat; coordination uses durable state and runtime tools.
- Manual follow-up on an achieved goal reactivates it; system continuation does not. Persisted cancellation wins over provider output, and streaming rechecks cancellation immediately before dispatch. Stop pauses an active goal with `stopped by user`; cancellation preserves terminal statuses and does not rewrite history. Public pause can currently rewrite terminal goals (`#1029`). Browser task-goal HTTP routes share the `handleTaskGoalRoute` preflight/response path for service availability, project ownership, mutation error translation, and HTMX/JSON refresh behavior; this is intentionally separate from runtime-tool goal handling (`#333`) and the pause correctness bug (`#1029`).
- Task cancellation records pre-update category/status, cancels only work that originated Active, persists cancellation before category changes, pauses active goals, cleans capacity, publishes SSE, and preserves requested category. Task Thread Stop does not bulk-cancel queued follow-ups; broader task cancellation may cancel pending inputs.
- Schedule due selection uses `next_run <= now`, excludes disabled rows, clears one-time `next_run`, advances repeating rows, and clamps monthly recurrence to its anchor. Runtime schedule mutation tools should share the schedule-action service while preserving operation-specific behavior; verify the target branch before assuming a PR-only helper is on main. Calendar gaps include local Pause/Resume (`#1146`) and Run Now (`#1151`), plus older LastRun/drag/goal/attachment/cue/context gaps.
- Capacity cleanup releases all reservations on terminal paths. Follow-up waiting is cancellable and does not consume `worker_timeout`; model-blocked reservations may still occupy global capacity (`#44`). Failed tasks retry latest failed follow-up history when reactivated.
- Swarm parents own child templates and guarded assignments. Runtime creation supports goals, priority, tags, explicit model/Agent, reviewer/merger, merge target, and two independent default-off auto-merge triggers. Child cancellation records intent before callbacks. Shared isolation inheritance remains an open planner issue (`#502`); Swarm Overview lacks human reviewer/merger rerun controls (`#1006`); swarm child detail pages can expose the parent only as a raw task ID rather than a title/status summary (`#1211`).
