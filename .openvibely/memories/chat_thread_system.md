Interactive Chat intentionally bypasses worker capacity. Task-thread follow-ups use `processStreamingResponse` with `IsTaskFollowup=true` and respect global, project, and model capacity.

Queueing, steering, and attachments:
- Normal Send during an active Chat/task-thread run queues the next input; explicit steering applies only at OpenVibely-owned provider/model-step boundaries; Stop cancels current execution. Queueing and steering use durable `thread_inputs`; `executions` represent real model runs, not parked composer state.
- Promotion claims pending input while creating the next execution/task and preserves FIFO. Promoted task-thread inputs resolve current model assignment at promotion time; queued Chat inputs retain per-input model selection. Follow-up executions remain `queued` until worker admission and become `running` only after a slot is acquired.
- Attachment sessions are stored on queued/steering rows. Chat rows have no `task_id` and use `run_execution_id`; task-thread rows use `task_id`. Repeated drops append, duplicate browser names receive unique pending names, and the three-files-per-message limit spans repeated drops.
- Text attachments enter prompt context, images become model attachments, and large text remains attached without being inlined. Steering attachment discovery after a provider call or during deferred completion is requeued as a normal next message, never committed to the completed user bubble. Failed submissions preserve drafts/sessions for retry; rollback retires unowned sessions.
- Shared attachment persistence writes a temporary destination, applies permissions, flushes/renames atomically, syncs the directory, then stores metadata. Metadata is removed before files on rollback; files remain if metadata deletion fails. Multipart limits are endpoint-specific and enforced before full parsing or side effects. Valid totals such as two 6 MB files are allowed when each file is within its endpoint cap.
- Browser/API prompt assembly shares finalized file-fact helpers, while handlers retain movement, metadata, rollback, session cleanup, and response ownership. Direct attachment routes enforce current/requested project ownership before content read/delete or upload side effects. Runtime task attachment listing remains an inspection gap (`#427`); metadata only is the intended scope, not downloads.
- Effective Active runtime task creation persists Backlog until conversion succeeds, then activates by request index. Upload/session storage follows configured local, hosted/Docker, and desktop roots; broken metadata can be reconciled, missing file bytes cannot.

Admission, lifecycle, and history:
- Follow-up admission is serialized with scheduler/worker claims and Automation reservations. It atomically reserves a direct execution or appends durable FIFO input. Browser pending-input refresh, queued-to-steering, and cancel routes are project-scoped and do not leak or mutate foreign rows.
- Startup reclaims interrupted follow-ups and promotes recoverable inputs through stable keyset pages with per-task FIFO and exactly-once promotion. Chat recovery and update-drain reopening use sparse indexed keyset paging, promote each eligible project once per page, skip active Chat executions, and filter guarded terminal executions.
- After-complete hooks receive only the latest normalized input/response; prior provider history can influence the answer but is not copied into lifecycle transcript. Future provider history is rebuilt from `executions.PromptSent` and cleaned `Output` as plain turns, with at most 20 prior task-thread turns after filtering the current execution.
- HTTP send/acceptance stays lightweight; full context setup runs after durable acceptance. Deferred setup failures still perform terminal cleanup and can promote queued input. Thread pagination renders execution history, not an unrecorded `tasks.prompt`. Runtime `view_task_thread` uses repository count/page projections and the existing 80 KiB transcript budget without hydrating payloads unnecessarily.
- Issue `#981` identified duplication between Execution History and Task Thread pagination: the history path and the no-cursor task-thread path repeated the same light execution projection, task filter, descending timestamp/rowid order, limit-plus-one sentinel, cursor handling, and older-page detection. The implementation in PR `#1003` consolidates that contract into one handler loader and canonical repository page query; Execution History reverses the shared chronological result for newest-first cards while Task Thread retains chronological rendering. Regression coverage protects route boundaries, cursor adjacency, equal-start-time rowid tie-breaking, invalid/default limits, empty/short/exact histories, and active polling. The PR remains open and unmerged as of 2026-09-05.
- Lifecycle activity belongs in the Lifecycle tab; task-thread follow-ups still run normal lifecycle routing before the model call. Canonical lifecycle and ownership details are in `agent_lifecycle_and_skills.md` and `openvibely_architecture.md`.

Composer and realtime behavior:
- Shared composer markup lives in `web/templates/components/chat_shared.templ` and uses one `ChatInputForm` contract. Apple hints are `⏎ sends or queues · ⌘+⏎ steers`; other platforms use `Enter sends or queues · Ctrl+Enter steers`; Shift+Enter inserts a newline.
- Enter sends/queues; Meta/Ctrl+Enter steers while active and falls back to one normal send while idle. Modifier-click on the primary button steers when an active turn is resolvable. Accepted sends clear text/session only after acceptance and only clear a matching visible attachment session. A lost `409` steer race retries once as normal send.
- The active primary button becomes a same-styled Stop with a square icon; server OOB state is authoritative. OOB fragments carry a new execution ID immediately so immediate steering can target it. If steering races an in-flight send before an ID exists, the draft/session is deferred and flushed after execution creation; failed/nonaccepted sends discard it. In-flight counters begin at `htmx:beforeRequest` so native validation cannot strand them.
- `activeTurnID()` prefers authoritative running/queued transcript rows, then the composer guard; the guard clears when idle. Chat/task-thread rendering batches DOM updates and performs a final flush. Terminal reconciliation uses persisted status/output regardless of event order and replaces loading indicators with the assistant result.
- Queued/steering inputs remain compact composer rows, not transcript bubbles. Promoted runs remove pending rows, append authoritative execution fragments, and attach streams. Streams must not be replaced by page reloads on start/input-applied events.

Modes and runtime actions:
- `/chat` is the global/project orchestrator; Task Detail Thread is task-specific. Plan is read-only; Orchestrate mutations require authorized runtime tools. Capabilities are canonical in `internal/chatcontrol/registry.go`; tool-incapable providers receive no textual bracket fallback. Legacy markers such as `[CREATE_TASK]` are inert prose.
- Orchestrate-only actions include `set_default_model`, `save_custom_personality`, `update_agent`, `cancel_task`, `create_project`, `update_project_settings`, task/Automation mutations, and destructive deletes. They resolve exact IDs or unambiguous names, enforce current-project ownership, validate before side effects, preserve protected/built-in records, and are not advertised/executable in Plan. Custom personality save reuses browser name/prompt validation, rejects duplicate/blank keys, missing custom targets, built-in prompt mutation, and partial activation before save. `list_channels`, `list_tasks`, `list_schedules`, `view_pulse`, `view_usage_analytics`, `view_system_update`, `list_automations`, and `get_automation` are read-only where supported in both modes.
- `create_task` and `create_swarm_task` share normalized service input, compact model loading, title/prompt/priority validation, and summaries across web/API and channels; surfaces retain attachment, project, Automation, and channel callbacks. `create_project` is GitHub-backed only, rejects local path/directory behavior, clones through the normal project service, rolls back clearly on failure, and may switch project through channel persistence. Project worker limits are any positive integer, must not exceed a finite global limit, and must be checked before persistence/clone/setup.
- `update_project_settings` can set/clear safe metadata, select a default model, and set/clear a worker cap; it rejects repository rebinding, credential, and deletion fields and triggers dispatch when capacity increases. `switch_project` remains informational in web/API runtime within the same model turn (`#734`); channel persistence is separate.
- `update_agent` may patch bounded user-managed fields including prompt, description, model inherit/override, safe tools, scoped-file grants, enabled state, and primary selectability. It rejects protected/archived/foreign/ambiguous agents, duplicate enabled/selectable names, unknown tools, malformed scoped files, and unsupported keys without partial save.
- `list_tasks` is bounded, current-project, read-only discovery with one substring query, title/category/status filters, deterministic pagination, compact summaries, and `category=chat` exclusion. Omitted filters mean all visible categories/statuses. Exhausted identical empty calls return a guarded `duplicate_noop`; callers should not repeat the same query merely to change echoed filters. Task discovery still lacks several Task Detail fields such as assigned Agent, tags, goals, merge/PR state, diffs, review comments, lifecycle evidence, and attachments.
- Automation actions resolve project-scoped targets and preserve point-in-time template revisions. Details belong in `automation_graphs.md`; integration action behavior belongs in `integrations_and_channels.md`. Channel handlers take precedence over generic runtime handlers while preserving prompt-safe readiness summaries.
- Status parsing accepts only a complete final standalone `[STATUS: SUCCESS]`, `[STATUS: FAILED | reason]`, or `[STATUS: NEEDS_FOLLOWUP | reason]`. Malformed, inline, fenced, or non-final examples remain visible/inert. Output cleaning preserves examples in Markdown code.
- Known runtime gaps include task-thread current-task resolution for PR tools (`#536`), `execute_tasks` (`#423`), channels (`#326`), and goal tools (`#338`), plus scheduled capability advertisements exceeding executor support (`#341`). Chat inspection gaps include specific Agent config/capabilities (`#595`), plugin state (`#790`), Agent creation (`#732`), linked PR state (`#765`), skill catalog (`#621`), worker pressure (`#604`), and Insights (`#624`).

Goals, cancellation, schedules, and swarms:
- Plan handoff uses completed Plan responses containing `<proposed_plan>`. Goals are durable `task_goals` managed by `TaskGoalService`; orchestration can create explicit/implicit goals, and continuation uses normal queued task-thread follow-ups rather than inline work.
- Tasks coordinate through durable state and tools such as `send_to_task`, `view_task_thread`, child tasks, schedules, dynamic wakeups, goals, and `thread_inputs`; there is no direct peer-to-peer task chat. Task identity is project-scoped and there is no cross-project view/switch capability.
- Manual follow-up on an achieved goal reactivates it; system continuation does not. Stop pauses an active goal with `stopped by user`; restarting resumes only that pause reason. Persisted cancellation wins over provider output, and `processStreamingResponse` rechecks cancellation immediately before dispatch. Cancellation must preserve terminal statuses, require cancellable executions, and not rewrite history (`#477`).
- Task cancellation/category transitions use pre-update category/status, cancel only work that originated Active, persist cancellation before category changes, pause active goals, clean capacity, publish SSE, and preserve requested category. Explicit CancelTask retains its Backlog behavior. Task Thread Stop cancels the active run/capacity wait without bulk-cancelling queued follow-ups; broader task cancellation may cancel pending inputs. Task Detail still lacks Stop/Cancel replacement for Run Now on running/queued tasks (`#235`).
- Schedule mutations share `ScheduleActionService`; due selection uses `next_run <= now`, disabled rows are excluded, one-time rows clear `next_run`, repeating rows advance, and monthly recurrence clamps to its anchor. Schedule gaps include missing LastRun (`#88`), past one-time drag behavior (`#270`), goal/attachment creation (`#342`, `#353`), card cues (`#354`), and current-task context (`#312`).
- Capacity cleanup releases global/project/model reservations on every terminal path. Follow-up wait is cancellable and does not consume `worker_timeout`; model-blocked reservations can still occupy global capacity (`#44`). Failed tasks retry latest failed follow-up history when reactivated, not blindly `tasks.prompt`. Zero-model guards offer an Open Models action.
- Swarm parents own child templates and assignment changes are guarded. New swarms persist resolved child models; runtime creation supports goals, priority, tags, explicit model/Agent, reviewer/merger, and merge target. `view_swarm` is compact and project-scoped. Child cancellation marks in-process intent before status/callback work. Planner application still rejects inherited `shared` isolation when entries omit worker isolation (`#502`).
