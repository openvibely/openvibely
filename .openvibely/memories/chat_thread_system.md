Interactive Chat intentionally bypasses worker capacity limits. Task-thread follow-ups use `processStreamingResponse` with `IsTaskFollowup=true` and respect global, project, and model limits.

Queueing and steering facts:
- Queueing, steering, and explicit stop are distinct product behaviors. Normal Send during an active Chat or task-thread response queues a next-turn input; steering is an explicit in-progress action applied only at OpenVibely-owned provider-call/model-step boundaries; the active composer Stop action cancels the current execution instead of queueing input.
- Queueing and steering use durable `thread_inputs`; `executions` represent real model runs, not parked composer state.
- Queued input promotion claims the pending input while creating the next execution/task and keeps FIFO ordering durable.
- Queued messages with attachments store the pending upload `attachment_session_id` on the durable `thread_inputs` row; final execution attachment records are created when the queued input is promoted and the attachment session is processed. Production queued Chat rows intentionally have no `task_id` and identify the active run through `run_execution_id`, while task-thread rows use `task_id`; cleanup and ownership queries must handle both shapes.
- Chat and task-thread composers share pending attachment upload behavior: repeated file/screenshot drops append into the current `attachment_session_id`, duplicate browser filenames are preserved with unique pending filenames, and the existing three-files-per-message limit applies across repeated drops.
- Staged attachment-session rollback covers queued Chat, queued task-thread, direct Chat task/create/claim/execution failures, direct task-thread execution creation failures, and stale task-thread not-found submissions without an ownership check-to-delete race. Durable session retirement and database triggers reject later `thread_inputs` owners; rollback atomically retires only an unowned session before directory removal, and task deletion retires captured sessions transactionally. Upload, rollback, and deletion cleanup coordinate through a per-session fence and check retirement before creating or appending files, so stale retired session IDs cannot repopulate unowned directories. Sessions referenced by another task/project remain preserved.
- `ChatSteer` (Chat steering) intentionally does NOT clean up/delete the pending attachment session on failure (including `ErrNoActiveTurn`/`ErrActiveTurnChanged`), matching `TaskThreadSteer`: the composer preserves the draft and `attachment_session_id` after a failed/conflict steer response so the user can retry with the same files. Only queued-input (Chat/task-thread) and direct-publication failures retire/delete the pending session.
- Chat-to-task conversion preserves filenames byte-for-byte, including spaces and `U+202F`; Unicode normalization was not the reported screenshot failure. Attachment publication now copies to a temporary destination file, applies permissions, flushes the inode, atomically renames, synchronizes the destination directory, and only then persists metadata. Batch rollback deletes metadata before files and retains files whenever metadata deletion fails; pending-session sources survive until the batch commits, duplicate destination names are disambiguated, and definitively missing historical metadata is reconciled before task execution.
- Attachment-bearing runtime-tool task requests resolve their effective category before creation. Effectively Active requests are persisted as Backlog until conversion succeeds, then activated by original request index rather than title; conversion failure leaves them Backlog. Failure to load Chat attachment metadata aborts task creation instead of being treated as an empty attachment set. Lifecycle diagnostics identify stage, execution/session, source, destination task/path, and error without file contents.
- Deferred Active Chat-created tasks track attachment publication readiness independently, so successfully published siblings activate while failed siblings remain Backlog; creation summaries must reflect activation per task ID and partial-failure notices identify only affected tasks.
- Deferred Active-task category transitions are rollback-safe: `TaskService.UpdateCategory` restores prior category/status after post-write reload, promotion/retry hook, status-reset, or submission errors, and uses a non-cancelled compensation context. Existing active executions are treated as handled so repeated activation cannot reset a task to Pending or resubmit its original prompt.
- Known deferred-activation rollback gap tracked in `openvibely/openvibely#23`: `TaskService.UpdateCategory` resumes the separately persisted task goal before follow-up promotion/retry succeeds, but its compensation restores only task category/status. A later activation failure can therefore leave a task shown as stopped while its goal remains active and lifecycle automation can continue it.
- The attachment lifecycle behavior is rooted in the configured uploads directory and applies equally to local `$HOME/.openvibely`, `OPENVIBELY_APP_DATA_DIR` overrides, and mounted hosted/Docker storage. Existing broken metadata rows can be removed during definitive-missing reconciliation, but missing file contents cannot be recovered and must be reattached.
- Task-thread sends made while a task execution is running, including before first assistant output or while initial lifecycle routing/hooks are still running, queue as next-turn input rather than running inline or duplicating messages.
- Direct task-thread follow-up admission is serialized with scheduler/worker claims and Automation reservations in the database. `ExecutionRepo.CreateDirectTaskFollowupOrQueue` atomically either reserves a direct execution or appends durable FIFO input when another admission owner exists. Scheduler claims and queued promotion honor running executions, reservations, and pending inputs while preserving first-turn dispatch for truly fresh tasks. Startup recovery reclaims interrupted follow-ups and drains recoverable pending inputs through stable keyset pages with per-task FIFO and exactly-once promotion.
- `after_complete` lifecycle hooks receive only the latest normalized user input and the assistant response completed for that input. Prior thread history may be used by the provider to answer the turn, but it is not copied into the lifecycle `conversation_transcript`.
- Steering rows target an active execution with an `expected_turn_id` guard and use two-phase consumption so failed/cancelled provider steps can recover input.
- Current merged steering instruction formatting passes through the user's steering text trimmed, without wrapping it in additional “latest user instruction” wording.
- Prepared/in-flight steering clears `expected_turn_id` while the row can still have `input_status='pending'`; pending-list queries and UI should exclude those rows until committed, restored, or requeued.
- `ChatSteer` does not clean up/delete the pending attachment session on a failed steer, including the expected `ErrNoActiveTurn`/`ErrActiveTurnChanged` race, matching `TaskThreadSteer`: draft and `attachment_session_id` survive for retry. Regression: `TestHandler_ChatSteer_FailurePreservesAttachmentSessionForRetry`.
- Shared Chat/task-thread composer shortcuts (`web/templates/components/chat_shared.templ`, used identically by `/chat` and task-thread): hint/tooltip is concise and platform-aware — `⏎ sends or queues · ⌘+⏎ steers` on Apple platforms, `Enter sends or queues · Ctrl+Enter steers` elsewhere — with no `Shift+Enter`/click wording advertised. Plain `Enter` sends/queues; `Shift+Enter` inserts a newline. `Meta+Enter` (Apple) / `Ctrl+Enter` (other) steers via the guarded `data-steer-endpoint` with expected-turn guard when active, with idle fallback to one normal send when steering is unavailable. `Meta+click`/`Ctrl+click` on the primary Send/Stop button also steers (undocumented). Steering responses render into `#pending-thread-inputs`, not the transcript. Apple-platform detection prefers `navigator.userAgentData.platform` with `navigator.platform`/UA fallback, recognizing `Mac|iPhone|iPad|iPod|iOS`.
- `activeTurnID()` resolution order: the transcript's authoritative `[data-execution-pair="true"][data-exec-status="running"|"queued"]` rows first, then the `data-composer-running`/`expected_turn_id` guard as fallback — because the OOB primary-action Send→Stop swap can lag slightly behind execution start. The guard field itself is actively cleared via `clearExpectedTurnIDWhenIdle()` (driven by a `MutationObserver` on the form) whenever `data-composer-running` is not `"true"`, so a stale turn ID cannot be reused after the composer returns to idle. Modifier-click does not hard-gate on `aria-label === "Stop response"`; it attempts steering whenever the platform modifier is held and a turn ID is resolvable, for either Send or Stop button state.
- `submitComposer` increments its in-flight counter (`normalRequestInFlight`) from the `htmx:beforeRequest` listener rather than at call time, so a native HTML5 `required`-validation-blocked empty submit (no request emitted) cannot strand the counter and misroute later shortcuts.
- The OOB primary-action fragment (`ChatComposerActionButtonOOB`) takes an explicit `activeTurnID` parameter threaded through `ChatSend`/`ChatComposerAction`/`TaskThreadSend`/`TaskThreadComposerAction` so the running-action fragment exposes the new execution's turn ID immediately after a send, before any transcript execution-pair row exists; this lets an immediate post-send Meta/Ctrl+Enter or modifier-click resolve and steer instead of falling back to a duplicate send or bypassing into cancellation. The Stop icon also visually swaps to Send while the platform modifier key is held.
- Immediate post-send steering race: if the steer shortcut fires while an earlier normal send from the same composer is still in flight (no execution-pair row and no resolvable turn ID yet), the draft/attachment-session is captured as a `deferredSteer` payload instead of double-sending, and a `MutationObserver`-driven flush submits it as a real guarded steer once the first send's execution-pair row appears. Submitted-message/attachment-session tracking is per-request (on the request's own XHR object), not shared mutable form state, so a slower first response cannot clear a newer draft/session the user has already typed. A failed/non-accepted normal send discards any pending deferred steer.
- Lesson: this composer-shortcut/steering-race area has repeatedly defeated audit-only review (stale guard, lagging Send-button, immediate post-send, and a validation-counter strand were all found only through direct interactive testing after an audit reported no material issues). Treat audit-only review here as necessary but not sufficient; require direct interactive reproduction of shortcut usage at each timing boundary (idle, active, immediately post-send, mid-request).
- Task-thread pending composer rows are reconciled from authoritative server-side pending-input fragments on relevant live task/execution/input events.
- Provider failure requeues prepared steering; retry restore returns it to guarded steering. Durable cleanup/finalization writes use non-cancelled contexts where needed so pending steering and executions are not stranded after request cancellation.
- Chat/task-thread success defers completion when pending steering exists; if follow-on steering preparation fails or finds no claimable steer, pending steering for that execution is requeued before terminal failure.
- Thread history for future calls is rebuilt from `executions.PromptSent` and cleaned `executions.Output` as plain turns rather than provider-native tool-use messages.
- Failed task executions remain visible terminal history rows. When no replayable assistant output exists, replay preserves the prompt with explicit failure metadata rather than leaving a trailing user-only turn.
- Initial task executions that report final `[STATUS: FAILED | ...]` persist assistant failure transcript/output while marking execution and task failed, so follow-up context can replay the failed turn chronologically.
- Task failure finalization does not clear execution diff output; diff capture/update is a separate post-processing path.

Routes, modes, and runtime actions:
- `/chat` is the global/project-level orchestrator; the task detail Thread tab is task-specific.
- `/chat` supports Orchestrate and Plan modes. Plan is read-only; Orchestrate mutations require authorized runtime tools/actions.
- Canonical chat capabilities live in `internal/chatcontrol/registry.go`.
- `list_tasks` is the canonical bounded read-only current-project task discovery action. It is available in Plan and Orchestrate modes across web/API Chat, supported channel runtimes, task-thread follow-ups, and generic initial/scheduled task runs with executable handlers. It supports partial title plus optional existing category/status filters, deterministic limit/offset pagination, excludes internal `category=chat` rows and cross-project results, and returns compact identity/status summaries including task ID, title, category, status, priority, updated time, and parent/swarm role when applicable. Existing write-action mode restrictions remain unchanged.
- Known task-discovery merge-state gap tracked in `openvibely/openvibely#129`: task records already load merge state, but `list_tasks` omits it from model-visible summaries, so Chat cannot identify pending, merged, conflicted, or failed review-boundary work without opening tasks individually.
- Known Chat inspection gap tracked in `openvibely/openvibely#114`: product guidance says Chat can inspect task changes, but `list_tasks` exposes only lifecycle summaries and `view_task_thread` formats prompts, output, and errors without `Execution.DiffOutput`. The proposed bounded read action should be project-scoped and reuse the Changes UI's live-worktree diff with preserved-execution fallback; review mutations, merge/PR actions, unrestricted file reads, and new persistence are out of scope.
- Known task-discovery gap tracked in `openvibely/openvibely#113`: `list_tasks` does not include the assigned Agent identity in its compact results, limiting Chat's ability to distinguish or coordinate tasks by ownership. The suggested slice adds assigned Agent identity to bounded task discovery without broadening task mutation behavior.
- Legacy bracket-based Chat mutation markers such as `[CREATE_TASK]`, `[EDIT_TASK]`, `[EXECUTE_TASKS]`, `[SEND_TO_TASK]`, and `[SCHEDULE_TASK]` are not an executable model-output channel. Prompts do not advertise them, response processing does not dispatch them, and marker-looking model prose is preserved as ordinary inert text across Chat, task-thread, queued channel, mixture, and initial-task paths.
- Chat runtime-tool handlers decode typed JSON inputs and invoke direct action/service paths without constructing or parsing bracket-marker strings. Legacy Chat mutation parser APIs and their supported-behavior tests have been removed; model-emitted marker-looking prose remains inert.
- The open-PR and replace-PR-branch runtime actions share one private target resolver for task selector resolution, current-project task ownership, project loading, and Automation repository validation. Their executors retain JSON decoding, mutation-specific options/service calls, and response formatting; branch replacement validates `confirm_history_rewrite` before target resolution and preserves its explicit confirmation and lease-guard SHA.
- Runtime-tool-incapable provider/auth paths receive no native tool definitions and no textual marker fallback. Ordinary Orchestrate Chat, task-followup, and initial-task prompts surface the capability limitation plainly; Plan remains read-only.
- Status-marker parsing recognizes only complete canonical final standalone controls: `[STATUS: SUCCESS]`, `[STATUS: FAILED | <non-empty reason>]`, and `[STATUS: NEEDS_FOLLOWUP | <non-empty reason>]`. Failed/follow-up reasons cannot contain another `|` delimiter; extra-delimiter variants such as `[STATUS: FAILED | reason | extra]` and `[STATUS: NEEDS_FOLLOWUP | reason | extra]` remain inert and visible. Incomplete, empty-reason, misclosed, or otherwise malformed forms remain inert and visible. Literal marker text in prose, code spans, code fences, bullets, quotes, examples, or lines with trailing explanatory text must not classify an execution. Fenced status examples remain protected until a closing delimiter uses the same backtick/tilde character and a run at least as long as the opening delimiter; mixed characters and shorter runs do not close the fence.
- Status cleaning follows the same exact grammar as classification: only a complete canonical control on the original final standalone non-empty line is stripped. History cleaning, server display, workflow-chain handoff, browser raw cleaning, streaming rendering, DOM hydration, and generated templates preserve extra-delimiter variants, status-like prose, bullets, quotes, code-fence/inline examples, lines with trailing explanatory text, formatting variants, and non-final status lines.
- Chat output cleaning preserves status, tool, and thinking controls, including `[Thinking]...[/Thinking]`, `[Using tool: ...]`, and `[Tool ... done/error ...]` result controls, inside inline backtick code spans and Markdown code fences while stripping or rendering real controls outside code. History cleaning, workflow-chain handoff, browser-side `cleanTranscriptControls`, and server-rendered `CleanDisplayContent` use Markdown-code-aware replacement; streaming control-segment parsing ignores examples inside backtick or tilde fences and inline code; and post-Markdown DOM cleanup skips `code`/`pre` descendants. Provider/client `<thinking>...</thinking>` and malformed tool-invoke alias normalization applies Markdown inline/fenced code protection before persistence, history/server cleaning, workflow-chain handoff, browser raw cleanup, and streaming rendering. Markdown inline code spans may cross line endings and close only on a backtick run exactly matching the opening run; an unmatched backtick run remains literal and does not prevent a later independently valid inline code span, including one with a different delimiter length, from being protected. Outside code, a contiguous odd backslash count escapes the first backtick of a run, leaving any remaining backticks eligible as an opener; an even count leaves the full run eligible; inside an open code span, backslashes are literal and an exact raw run still closes it. These are the intended Marked-compatible delimiter semantics for control recognition. Multiline coded provider/client aliases, status/tool/thinking controls, `[TASK_ID:...]`/`[TASK_EDITED:...]` metadata, and `Created`/`Edited` summaries remain visible and inert across persistence, history/server cleaning, workflow-chain handoff, browser raw cleanup, streaming rendering, DOM hydration, direct loads, and generated templates. Real aliases and canonical controls outside the matching closer continue to normalize, classify, clean, render, hydrate, or deduplicate normally. Overlap-safe scanning ensures a coded partial alias or control cannot mask a later real alias or control. Legacy single-line tool-result matching is delimiter-bounded so a code example cannot mask a later real control on the same line. Block tool-result controls accept both same-line payloads such as `[Tool name done]payload[/Tool]` and LF/CRLF/bare-CR multiline payloads consistently across provider history, server/browser cleaning, workflow-chain handoff, streaming segmentation, DOM/direct-load hydration, and generated templates; coded inline/fenced examples remain visible and inert, overlap-safe scanning still discovers later real blocks, and real blocks are cleaned or rendered normally. `[TASK_ID:...]` and `[TASK_EDITED:...]` remain non-executable result metadata emitted by successful typed runtime actions; they are not model-output mutation channels. Backend history and channel-display cleaning removes actual task-result metadata where no link hydration occurs but preserves literal metadata and complete task-result summary examples inside inline or fenced Markdown code; workflow-chain handoff retains both actual and coded metadata as child context. On browser-capable surfaces, metadata-to-link converters live in the shared Chat/task-thread rendering script, so direct loads, hard refreshes, streaming completion, HTMX hydration, and tool-card rendering convert actual metadata outside code without prior `/chat` navigation; the converters skip `code`/`pre` descendants so literal inline/fenced examples remain visible and inert. Real metadata in raw tool-output `pre` blocks remains convertible unless its raw text is itself inside an inline or fenced Markdown-code range. Task IDs are URL-encoded before link, HTMX, fetch, or history use. Server and browser task-summary deduplication ignores `Created`/`Edited` summaries inside inline or fenced Markdown code, removes only earlier real structured summary blocks, and preserves coded examples plus unrelated prose between duplicate real summaries.
- Large task-thread tool-output rendering uses lazy vertical-overflow OUT rows and line-bounded, code-aware task links in expanded raw output (`web/templates/components/chat_shared.templ`, `web/templates/layout/base.templ`). Vertically overflowing OUT rows start collapsed with a bounded standard preformatted preview (first six logical lines, capped at 4 KiB) but without the full pre/scroller; expansion materializes only that complete OUT subtree, while collapse removes it and restores the preview. State is keyed by enclosing execution-pair ID, stable tool render ID, and row kind across streaming rerenders and HTMX morphs, preventing completed executions with identical output prefixes from sharing expand/collapse/scroll state. Overflow prediction counts LF, CRLF, and bare CR without double-counting CRLF. Create/edit task metadata uses line-bounded captures, trimmed non-empty IDs, Markdown-code protection, and URL encoding, so valid one-line runtime metadata hydrates while multiline source and inline/fenced examples remain inert. Cooperative large-output insertion normalizes adjacent 64 KiB text nodes inside the scoped raw tool-output `pre` before conversion, preserving complete marker and Markdown-code context across chunk boundaries. Short and horizontally overflowing one-line OUT values remain expanded; the Show/Hide control stays below visible output; and IN text uses the same preformatted typography. `resolveToolOutputLineCapacity` applies `.stream-tool-output-text` to its measurement `pre`, keeping near-capacity decisions aligned with rendered line-box typography.
- Known gap tracked in `openvibely/openvibely#40`: the Go-side `CleanChatOutput`/`CleanChatOutputForDisplay` cleaner (`internal/llm/output/cleaner.go`) lacks the "tool boundary crosses Markdown code range" protection present in the JS live-render pipeline (`excludeToolBlockCodeRanges` in `web/templates/components/chat_shared.templ`). A stray backtick inside raw tool output can form a phantom Markdown code span that crosses a `[/Tool]` boundary and shields a real `[Thinking]...[/Thinking]` marker, causing it to be silently dropped rather than stripped as internal reasoning or preserved as literal code. This feeds LLM history replay context and outbound Slack/Discord/Telegram/Email display text.
- Final Markdown rendering, missing/failing-Marked fallback behavior, and shared CommonMark line-ending semantics across persistence/history/streaming/DOM paths are canonical in `realtime_and_frontend_patterns.md`.
- Failed-task history replay and terminal-marker fixes are provider-neutral shared-layer behavior, not provider-specific fixes.
- Task creation can happen through authorized runtime action surfaces or local app APIs. Runtime task creation should use the attached `create_task` contract; non-running/backlog task creation should set `"category": "backlog"`.
- Known product gap tracked in `openvibely/openvibely#12`: web Chat-created tasks currently return task links but do not durably retain the originating Chat turn or post terminal completion/failure/cancellation evidence back into that conversation. The proposed first slice is durable task-to-Chat provenance plus one deduplicated compact lifecycle entry, without a model call, automatic follow-up, or full output dump; task detail remains the surface for logs, diffs, and full thread history.
- Chat task creation distinguishes Agent definitions from model configs: `agent` names a selectable/enabled Agent, while `agent_id` is internal model-config selection.
- Chat-control task/schedule automation should respect schema semantics: task `priority` uses `1=Low`, `2=Normal`, `3=High`, `4=Urgent`; scheduled task `days` values are short weekday keys; `edit_task` needs a real task ID; `schedule_task` moves the target task into `scheduled`, so bootstrap flows needing immediate work should schedule then explicitly execute when appropriate.
- Task-thread follow-up runtime filters intentionally expose visible bootstrap controls such as `create_task`, `create_swarm_task`, `schedule_task`, `delete_schedule`, and `modify_schedule` alongside thread, goal, GitHub, and `list_capabilities` tools when runtime tools are supported. This lets standalone bootstrap skills selected by task lifecycle routing create/update visible tasks and schedules from the task thread instead of stopping with missing scheduling support.
- `send_message` is an Orchestrate-mode write runtime tool for sending outbound Slack, Telegram, Email, and Discord messages through configured project channel targets. Normal task execution and task-thread follow-ups expose/advertise a narrow default `send_message` runtime only when the selected provider/auth path supports runtime tools, so tasks can send completion messages without requiring an explicit agent-tool grant. Runtime-tool-incapable provider/auth paths cannot call it and receive no textual fallback.

Swarm task facts:
- Swarm tasks are parent/child orchestration with planner, worker, reviewer, and merger children plus parent summaries, task-detail swarm panels, Active kanban parent/child aggregation, and a `create_swarm_task` runtime tool.
- The swarm parent normally does not execute an LLM call; it is an orchestration/state container. Planner, worker, reviewer, and merger children perform the model work. Parent task-thread follow-ups route into swarm coordination rather than ordinary parent execution.
- `integrator` was renamed to canonical `merger` on 2026-07-04. Legacy persisted `integrator` roles/config/form/API aliases remain intentionally supported and display as Merger; no data migration was required.
- Planner completion parses the latest completed planner output as JSON, tolerates surrounding transcript/tool text, and applies output idempotently so duplicate callbacks do not create duplicate workers. `ParsePlannerOutputJSON` scans fenced/balanced candidates in true text order and accepts the last valid object with non-empty `workers`.
- Swarm child `swarm_status` is API-visible durable coordination metadata, not cosmetic. Successful children terminalize to role-appropriate values: planner `planned`, worker `completed`, reviewer `reviewed`, merger `integrated`.
- Failed worker/reviewer children persist failure-specific coordination states (`failed` or `followup_failed`). A follow-up that repairs a failed prerequisite stays in the current swarm generation rather than advancing it, so completed siblings remain fresh and still-running siblings continue to gate downstream work. Failed-follow-up retries transition `followup_failed` back through `followup_pending`; completion, follow-up, and reconciliation coordination is serialized to prevent duplicate reviewer/merger submission.
- `RecomputeParentStatus` durably recovers missed terminal child callbacks by replaying worker, reviewer, and merger transitions in prerequisite order under the orchestration lock. It stamps missing completion generations, preserves failure and running-sibling gates, activates downstream roles exactly once under concurrent/repeated reconciliation, recovers merger result finalization, and distinguishes current-generation completion awaiting reconciliation from intentional stale-generation reruns.
- Reviewer and worker completion auto-submit downstream merger/reviewer children as active/pending so the worker queue cannot prune them. Auto-start and finalization paths must guard against stale child completions overriding fresher pending/running work.
- All four reviewer/merger enabled/disabled lifecycle combinations are intended to reach a terminal completed parent state: reviewer+merger, reviewer-only, merger-only, and worker-only.
- Parent task-thread follow-ups affect swarm coordination: affected workers can be targeted, unaffected completed workers carry forward, and reviewer/merger phases rerun when needed.
- Swarm child follow-ups are role-specific: worker follow-ups advance generation and require review/merge, reviewer follow-ups invalidate merge only, and merger follow-ups invalidate final merge/result only.
- Explicit reviewer/merger reruns reject while the role child is pending/queued/running or has an active execution. Accepted reruns reactivate the parent and child, move completed role children back to Active, set pending before submission, and invalidate freshness.
- Deferred swarm creation is supported through the `Autonomous planner` UI toggle and chat runtime `start_immediately:false`; omitted/default values still start immediately. Visible generic `/tasks/:id/run` detects swarm parents and starts/resumes the planner instead of submitting the parent as an ordinary task.
- Slack, Telegram, Discord, and Email channel runtimes handle advertised `create_swarm_task` through shared channel action handling, create real swarm parents with channel origin/context metadata, and use the active authorized channel project rather than caller-supplied `project_id`.
- Active kanban/drop-zone rendering should visually aggregate runnable swarm child activity into the parent card. Only child `pending`, `queued`, and `running` states count as runnable work that promotes a blocked/non-terminal parent to Active/In Progress; blocked parents with no runnable children should normalize/render as Backlog/blocked rather than Active/Queued.
- `AttachSwarmChildren` should be idempotent and applied before kanban rendering paths that need parent/child aggregation, including HTMX board refreshes and full-page/main-content routes.
- Multiple swarm workers may independently solve the same root bug. Reviewers should audit actual branch diffs, accept the single best/most-complete overlapping branch, and reject redundant ones rather than merging duplicates.
- Reviewer/merger prompts currently rely partly on task/worktree/git discovery rather than a generated inline worker-ID/branch manifest. This is a non-blocking reliability gap for git-capable roles, but remains worth revisiting for channel-origin or non-git-capable swarm roles.
- Merger enforcement of reviewer accept/reject decisions is soft/prompt-based: there is no structured persisted accepted/rejected-worker contract or hard branch/diff gate. A more robust design would store reviewer `accepted_worker_ids`/`rejected_worker_ids` and inject only accepted branch/diff data into merger prompts.
- If a merger is cancelled by a human, the parent can appear stuck in needs-merge/blocked even though planner/workers/reviewer completed; distinguish this from orchestration bugs.
- Historical detached terminal swarm children can be repaired only through the guarded `POST /api/tasks/{id}/swarm/reconcile-detached` application path. It rejects linked or nonterminal tasks and derives canonical coordination metadata from terminal task status and swarm role rather than accepting caller-supplied status.
- Swarm-parent deletion intentionally retains children through `ON DELETE SET NULL`, and was previously fixed (commit `62b40a1e`) to terminalize unfinished direct planner/worker/reviewer/merger/legacy-integrator descendants atomically as `completed/cancelled/cancelled` with active child workers receiving cancellation. Regression tracked in [GitHub #278](https://github.com/openvibely/openvibely/issues/278) (filed 2026-08-07) found that fix absent from the codebase's then-current state. Reinstated 2026-08-07 in PR [#282](https://github.com/openvibely/openvibely/pull/282) (pending human review/merge): `TaskDeletionManifest` gained `SwarmChildTaskIDs`, `deleteWithCleanupManifest` records direct planner/worker/reviewer/merger/integrator children of a `swarm_parent` before deleting it and updates any non-terminal child (`pending`/`queued`/`running`/`blocked`) to `status=cancelled`, `swarm_status=cancelled`, `category=completed` (terminal children untouched), and `TaskService.deleteTask`'s `prepareDelete` hook now calls `CancelRunningTask` for each returned child ID in addition to the parent's own. A strictly read-only audit-only review (2026-08-07) confirmed all three acceptance criteria and both required regression tests (repo-level and service-level) with no material findings; it noted one benign non-material nuance where the UPDATE sets `category='completed'` unconditionally (not gated by the same non-terminal-status guard as `status`/`swarm_status`), which only matters for a `failed` child still sitting in `category='active'` and is harmless because `normalizeActiveTerminalTasks` already relocates such active-terminal tasks to completed elsewhere in the system.
- Known swarm-card UI gap: the accordion container can be too narrow relative to the task card, and the accordion should default collapsed rather than open.

Task-thread, goals, and cancellation facts:
- Plan handoff is driven by completed Plan-mode responses containing `<proposed_plan>`.
- Task-thread follow-ups use chronological execution history rather than reinjecting the original task prompt.
- Task-thread follow-up HTTP send/acceptance should stay lightweight and must not synchronously load/render full execution history, rebuild full transcripts, resolve worktrees, or build model-only context before responding; model-call setup runs in the background after the user message/execution is durably accepted.
- Task-thread model replay history is bounded to the provider context window: background follow-up, queued-promotion, and failed-followup retry paths query only enough latest task executions to preserve up to 20 prior replay turns after filtering the current execution.
- Task-thread composer model selection follows task assignment semantics, not interactive-chat Auto semantics: explicit `Task.AgentID`, then project default model config, then global default. New swarms persist the resolved assigned model for children; legacy nil-agent rows resolve the same effective model at render time.
- Explicit non-`""`/non-`"auto"` task-thread model selections (including `"default"`) persist to `Task.AgentID` via `TaskRepo.UpdateAgentID`, both on send (`TaskThreadSend`) and immediately on dropdown change without sending (`POST /tasks/:taskId/thread/model` / `Handler.TaskThreadSelectModel`, wired via `data-model-select-endpoint`), matching task-assignment semantics; `"auto"`/empty selections never overwrite the existing assignment. The Chat page is unaffected since it persists model selection client-side via localStorage keyed by `ProjectID`, not `Task.AgentID`. Both persistence paths return early via `HandleParentFollowup`/an explicit `SwarmRoleParent` guard before touching `Task.AgentID` on swarm parent threads, so dropdown changes there cannot mutate `parent.AgentID` (the template for planner/worker/reviewer/merger child creation) outside swarm's own `resolveAssignedAgentID` resolution. Queued `thread_inputs` capture `AgentConfigID` from the already-resolved agent at enqueue time, so queued/steering follow-ups and swarm children are unaffected by races with this persistence step.
- Deferred task-thread setup failures after durable acceptance should still run normal terminal/finalization cleanup that can promote the next queued input.
- The Task Thread transcript/pagination renders `executions` history; `tasks.prompt` may not appear as the oldest paged thread item unless also recorded as an execution prompt.
- Task-thread follow-ups run normal task lifecycle routing before the follow-up model call; selected skill/memory semantics are canonical in lifecycle and managed-memory memories.
- Interactive Chat uses narrower recall-only memory preparation rather than full Skill Curator routing. It currently does not receive lifecycle-selected standalone skills or scoped `skill_view` context; this Chat-to-reusable-workflow gap is tracked in `openvibely/openvibely#19`. The proposed first slice routes relevant standalone skills into ordinary web Chat turns while preserving Plan-mode read-only controls and avoiding learning/memory writes.
- Lifecycle-agent activity belongs in the task Lifecycle tab rather than the main Thread tab.
- Known task-thread run-inspection gap tracked in `openvibely/openvibely#149` and related suggestion `#225`: individual task-thread runs have a detail page, but thread turns do not link to that execution-specific view, identify the model used for the run, or expose execution history directly from task detail, limiting review of prior runs.
- Task goals are durable `task_goals` records managed by `TaskGoalService`. Chat orchestration supports explicit and implicit task-goal creation.
- Goal continuation uses normal task-thread follow-ups through `thread_inputs`; it does not start work inline.
- Tasks do not support direct peer-to-peer chat. Coordination is mediated through app state and control-plane mechanisms such as `send_to_task`, `view_task_thread`, chain-created child tasks, schedules, dynamic wakeups, persisted goals, and durable `thread_inputs`.
- A durable “inbox task” pattern is a canonical task thread, not an automatic mailbox.
- Goal status writes use stale `goal_id` plus active-status guards. Goal status tools can be granted to agents beyond Goal Agent, but ungranted/default agents do not see or execute them.
- Manual/user follow-ups on achieved goals reactivate the same goal before prompt context and lifecycle evaluation; Goal Agent/system-agent continuations do not reopen achieved goals.
- Manual stop/cancel signals implicitly pause the active task goal with reason `stopped by user`, preserving the goal for intentional resume. Starting a task again resumes only goals paused with that reason; explicit/manual goal pauses remain explicit-resume-only.
- Global Chat stop uses the active Chat execution’s backing task and reuses task cancellation semantics while preserving `category=chat` so Chat history remains visible.
- Task cancellation and Global Chat stop share one private handler helper that owns running-execution row cancellation, best-effort repository-error handling, cancellation count logging, and terminal SSE publication for every returned execution ID. Each endpoint retains its own surrounding behavior, including Chat category preservation, pending-input cancellation, swarm handling, goal pausing, redirects, and HTMX responses.
- `processStreamingResponse` must re-check persisted task/execution cancellation after registering runtime cancellation and before model/provider preparation, and check the runtime context immediately before provider dispatch to avoid early-cancel races.
- Task Thread composer Stop posts to the task cancel path with composer-stop semantics so it cancels the active run/capacity-wait without bulk-cancelling queued follow-up rows. Broader task cancel controls may still cancel pending thread inputs.
- Known task-operational-control gap tracked in `openvibely/openvibely#235`: the Task Details page replaces `Run Now` with a disabled control for running or queued tasks, despite the task cancellation endpoint and Thread composer already supporting cancellation. Operators therefore cannot stop work from the primary Details surface; the focused proposal is to expose the established Stop/Cancel action there, preserving existing cancellation behavior for pending inputs, active executions, status publication, active goals, and swarms.
- Streaming task-thread cancellation finalization for normal tasks must not leave `tasks.category='active'` with terminal `failed`/`cancelled` status; normal active terminal rows are normalized to Backlog, while Chat tasks preserve `category=chat` so Chat history remains visible.
- Direct task-thread cancel and Active-to-Backlog/Completed moves cancel queued/running execution, pause the active goal, and preserve the user's requested target category. `TaskService.UpdateCategory` must use the pre-update category/status for stop semantics.
- Goal Agent `send_to_task` re-checks active goal state and execution freshness before queueing continuations, preventing stale lifecycle hooks from restarting stopped or superseded work.

Task execution and scheduling facts:
- Active tasks auto-submit to the worker pool on creation or when moved to Active.
- Scheduled tasks run when `next_run <= now`; one-time schedules clear `next_run`, while repeating schedules compute the next occurrence.
- Schedules have durable enabled/disabled state. Disabled schedules are excluded from due-run selection until re-enabled; toggling off preserves `next_run`, while toggling on recomputes stale/past `next_run` to the next valid future occurrence.
- Browser/HTMX and JSON API schedule toggles intentionally share one handler-level transition operation that owns schedule lookup, enabled-state inversion, persistence, stale `next_run` recomputation on re-enable, and final schedule retrieval. HTTP status mapping, logging, HTMX rendering/redirects, and JSON serialization remain transport-specific; parity coverage locks the disable/re-enable semantics across both endpoints.
- Dynamic task-loop wakeups are schedule rows with wakeup metadata and replacement semantics. When due, the scheduler enqueues normal task-thread follow-ups through durable `thread_inputs`; wakeups are blocked for stopped goal states and failures should be visible on the task timeline/event stream.
- Chat control-plane schedule modification supports `enabled: bool` and must stay consistent with HTTP/API toggling semantics.
- Web/API Chat and channel Chat schedule mutations (`schedule_task`, `modify_schedule`, and `delete_schedule`) share one service-level implementation. The core owns time parsing, recurrence mapping, interval validation, weekly-day calculation, `NextRun`, persistence, project ownership, and linked task category/status transitions; wrappers retain surface-specific batching, response formatting, and logging. Cross-project task/schedule references are rejected, and deleting a task's final schedule recategorizes it consistently.
- Runtime schedule create and modify validation is strict and mutation-safe: times must exactly match supported `HH:MM` grammar, recurrence values must be supported, and weekly day tokens must use `sun` through `sat`. Invalid values are rejected before repository mutation, including trailing time text, seconds, unsupported recurrence, unknown weekdays, and non-empty weekly lists with no valid day.
- `list_schedules` is the canonical bounded, read-only current-project schedule discovery action. It is available in Plan and Orchestrate modes across web/API Chat, supported channel runtimes, task-thread follow-ups, and generic initial/scheduled task runs. Its result contract includes schedule and task IDs, task title, enabled state, recurrence type/interval/days, next run, and clear-context-on-start state; every result always includes `days` (an empty string when inapplicable) and `next_run` (`null` when absent). It supports optional task ID, partial title, and enabled filters; defaults to 20 results with a maximum of 50; and provides offset pagination with a total and `has_more`. Repository lookup joins schedules to tasks under the requested project, preventing cross-project IDs, and orders deterministically by non-null `next_run` ascending, then `created_at` descending and schedule ID ascending. Returned schedule IDs are accepted by the existing modify/delete schedule actions without changing scheduler or recurrence semantics.
- Known schedule-discovery evidence gap tracked in `openvibely/openvibely#131`: schedule records carry `LastRun`, but `list_schedules` exposes only the next run, so Chat cannot distinguish never-run automation from schedules with execution history.
- Monthly recurrence uses consistent anchor-aware month clamping in backend scheduling and schedule-calendar projection. Advancement preserves the original `RunAt` day, clamps only when a target month lacks that day, and recovers the anchor in later months, so January 31 advances to February 28/29 and then March 31 without skipping the configured interval. Calendar rewind uses the same anchor and clamped arithmetic.
- Known scheduled-occurrence loss bug tracked in `openvibely/openvibely#88`: the scheduler marks an occurrence consumed after placing it only in the in-memory worker queue. If the process exits before worker claim, a one-time schedule can have `next_run = NULL` while its task remains `scheduled/pending`; startup recovery reads only `active/pending`, so the occurrence is never recovered. Existing scheduler tests cover enqueue plus `MarkRan` but not restart between those operations.
- Known drag-to-reschedule bug tracked in `openvibely/openvibely#270`: dragging a one-time (`RepeatOnce`) scheduled task to a past calendar slot via `RescheduleTask` leaves `NextRun` in the past, defeating the handler's own documented safety guard, so `ScheduleRepo.ListDue` immediately treats the task as due and the scheduler re-executes it right after the drag.
- Known multi-day weekly recurrence bug tracked in `openvibely/openvibely#281`: a weekly schedule configured with multiple `Days` (e.g. Mon/Wed/Fri) only ever recurs on the single stored weekday, because `Schedule` persists only one `RunAt` timestamp and `ComputeNextRun` never re-consults the `Days` list when computing the next occurrence. Confirmed with a reproducing test showing six consecutive `ComputeNextRun` calls all landing on the same weekday.
- Schedule rows own timing state; the linked task owns execution assignment. Primary Agent selection is persisted on `tasks.agent_definition_id`, while model configuration remains the separate task `agent_id` field, and scheduler execution uses those task-owned assignments.
- Schedule `Clear context on start` is a non-destructive replay boundary applied only when that schedule invokes an ordinary or swarm run: the scheduled run starts without prior task turns, while stored executions, thread history, lifecycle, goals, diagnostics, and audit evidence remain intact. A later manual user follow-up does not clear context again; it replays from the latest scheduled boundary, including that scheduled run and subsequent follow-ups while excluding older turns. The value survives worker Task refresh and reaches the persisted execution, including a newly created or reused swarm planner child; manual/unscheduled planner starts preserve context. Existing schedules retain legacy `false`, newly created schedules default to `true`, timing-only edits preserve the stored choice, and Automation Edit/Save preserves omitted legacy values from the bound Schedule while defaulting new Automation schedules to `true`.
- Schedule create/add/edit forms expose a server-rendered project-scoped `Primary Agent` selector with explicit `No Agent`; choices exclude disabled, archived, protected, non-selectable, and cross-project Agent definitions. Edit hydration uses the persisted task assignment, explicit form submissions may clear it, and timing-only legacy/API updates leave assignment unchanged. Schedule-origin task creation preserves both transport modes: HTMX submissions return the refreshed `ScheduleContent` fragment, while native form submissions return `303 See Other` to `/schedule?project_id=<active-project>` after persisting the task and schedule.
- Schedule context policy is owned by schedule-specific create/add/edit surfaces, not the Task Details Edit Task form. Task Details renders no `Clear context on start` controls or sentinels, and ordinary task updates ignore even forged schedule-policy fields so linked schedules retain their persisted values. New schedules still default the option to `true`, while existing schedules change it only through a schedule surface; underlying persistence, execution-boundary behavior, and Automation preservation remain intact.
- Promoted queued task-thread follow-ups move the task back to Active during the queue-claim/promotion transaction before the follow-up execution is exposed.
- Reactivating a failed task with no queued input should retry the latest failed follow-up using its `PromptSent` and chronological history, not blindly resubmit `tasks.prompt`; older failed follow-ups are ignored if a later execution succeeded.
- Zero-model guardrails block task execution and Chat send surfaces with an `Open Models` action.
- Channel-origin runs follow the same queueing, steering, and task-thread rules where supported.
- Worker dispatch capacity uses global/project/model counters. Cleanup after slot acquisition is centralized so completion, provider errors, cancellation, claim failures, and provider panics release slots, clear pending/cancel state, and trigger redispatch.
- Prepared-Automation setup failure after claim must not let a persisted `running` execution overwrite failed or cancellation-derived terminal fallback. Model lookup/default-resolution failure or model removal while queued must converge Task, Execution, dispatch, invocation, activity, reservation, and worker counters to consistent terminal state without a provider call.
- Task-thread follow-up admission atomically reserves global and project capacity under the worker mutex before acquiring model capacity. Finite global limits queue follow-ups until capacity opens; canonical `0` remains unlimited. Cancellation interrupts global/project capacity waits, and deferred release restores global/project/model counters and triggers redispatch exactly once.
- Known capacity-accounting gap tracked in `openvibely/openvibely#44`: a task-thread follow-up reserves global/project capacity before polling for model capacity, so model-blocked follow-ups continue to count as globally running and can occupy every global slot, preventing otherwise runnable queued work on another model from dispatching.
- Task-thread follow-up slot waiting is not charged against `worker_timeout`; follow-ups wait for project/model slots with a cancellable no-deadline queue context, then start turn-processing timeout after slots are acquired. Capacity-waiting follow-ups are cancellable while `queued`.
- Tasks legitimately run/dispatch while `category` is either `active` or `scheduled`; stale-running recovery must not treat scheduled-category running executions as inactive.
- Direct task-thread follow-up startup on completed/inactive swarm children must reactivate the owning task and insert the running follow-up execution atomically. Otherwise concurrent stale recovery can mark the execution failed while the background runner keeps streaming. `ExecutionRepo.CreateDirectTaskFollowup` is the durable fix pattern for direct-start paths; queued promotion was already atomic.
- True inactive/orphaned child executions should still be recovered.
