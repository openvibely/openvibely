Interactive Chat intentionally bypasses worker capacity limits. Task-thread follow-ups use `processStreamingResponse` with `IsTaskFollowup=true` and respect global, project, and model capacity limits.

Queueing, steering, and attachments:
- Queueing, steering, and Stop are distinct product behaviors. Normal Send during an active Chat/task-thread run queues the next input; explicit steering applies only at OpenVibely-owned provider-call/model-step boundaries; Stop cancels the current execution instead of queueing input.
- Queueing and steering use durable `thread_inputs`. `executions` represent real model runs, not parked composer state.
- Queued input promotion claims pending input while creating the next execution/task and preserves FIFO ordering.
- Promoted queued task-thread inputs resolve the current task model assignment at promotion time, so model changes after queueing or a failed run take effect on rerun. Interactive Chat queued inputs keep their existing per-input model selection behavior.
- Queued and steering rows with attachments store `attachment_session_id` on `thread_inputs`. Chat queued rows intentionally have no `task_id` and identify the active run through `run_execution_id`; task-thread rows use `task_id`.
- Steering attachments are one-shot: the pending session is included in the next outer-model provider step when claimed and committed as `ChatAttachment` records after successful execution. Text attachments enter prompt context, image attachments are sent as model attachments, large text files stay attached but are not inlined, and multiple/oversized attachments are covered. Text-only provider-loop steering must skip attachment-bearing rows until an outer-model step can process them. Attachment-bearing steering discovered after the active provider call has returned or during final/deferred completion is requeued as the next normal queued message; it must not be committed to the completed execution/user bubble.
- Chat and task-thread composers share pending attachment behavior: repeated drops append into the current session, duplicate browser filenames are preserved with unique pending filenames, and the three-files-per-message limit applies across repeated drops.
- Failed Chat/task-thread steering preserves drafts and pending attachment sessions so the user can retry; publication/queued-input failures retire/delete unowned sessions through rollback paths.
- Responses WebSocket transport failures during task-thread follow-ups are terminal for that execution: prepared steering must not be requeued, pending inputs tied to the failed execution are cancelled, live cancellation events remove stale rows, and queued-turn promotion is suppressed. Ordinary non-transport provider failures retain the older steering recovery behavior.
- Attachment publication copies to a temp destination, applies permissions, flushes, atomically renames, syncs the destination directory, then persists metadata. Batch rollback deletes metadata before files and retains files if metadata deletion fails.
- Resolved issue `#418` / PR `#433`: API queued-chat attachment failure rollback now uses the shared unpublished pending-session cleanup helper instead of directly removing pending upload directories. The shared path validates and locks the session, skips already-owned queued input sessions without deleting or retiring them, and retires/deletes unowned pending sessions with a `retired_attachment_sessions` tombstone.
- Known attachment inspection gap `#427`: Chat/runtime actions can edit attachment IDs on tasks but cannot list the attached-file metadata already shown on Task Detail and backed by `AttachmentRepo.ListByTask`; suggested scope is metadata-only listing, not download/content access.
- Attachment-bearing runtime-tool task requests resolve effective category before creation. Effective Active requests persist as Backlog until conversion succeeds, then activate by request index; conversion failure leaves them Backlog.
- Deferred Active task transitions are rollback-safe for category/status, but known gap `openvibely/openvibely#23` remains: goal resumption during failed activation can leave goal state active while task is stopped.
- Upload/session lifecycle is rooted in the configured uploads directory and applies to local, env-overridden, Docker/hosted, and desktop storage. Existing broken metadata can be reconciled; missing file contents cannot be recovered.

Task-thread admission and lifecycle:
- Task-thread sends made while execution is running, including before first assistant output or during initial lifecycle hooks, queue as next-turn input rather than running inline or duplicating messages.
- Direct task-thread follow-up admission is serialized with scheduler/worker claims and Automation reservations in the database. It atomically either reserves a direct execution or appends durable FIFO input.
- Startup recovery reclaims interrupted follow-ups and drains recoverable pending inputs through stable keyset pages with per-task FIFO and exactly-once promotion.
- `after_complete` hooks receive only the latest normalized user input and assistant response for that input. Prior provider history may influence the answer, but it is not copied into lifecycle `conversation_transcript`.
- Thread history for future provider calls is rebuilt from `executions.PromptSent` and cleaned `executions.Output` as plain turns rather than provider-native tool-use messages.
- Task-thread follow-ups use chronological execution history, not reinjection of the original task prompt. Replay history is bounded to preserve up to 20 prior replay turns after filtering the current execution.
- Task-thread HTTP send/acceptance stays lightweight; full transcript/model-context setup runs in the background after durable acceptance.
- Deferred setup failures after durable acceptance should still run terminal/finalization cleanup that can promote queued input.
- Task-thread transcript/pagination renders `executions` history; `tasks.prompt` may not appear as the oldest paged item unless also recorded as an execution prompt.
- Lifecycle-agent activity belongs in the Lifecycle tab rather than the main Thread tab. Task-thread follow-ups run normal task lifecycle routing before the model call.

Composer shortcuts and steering races:
- Shared composer hint is platform-aware: Apple `⏎ sends or queues · ⌘+⏎ steers`, other platforms `Enter sends or queues · Ctrl+Enter steers`.
- Plain Enter sends/queues; Shift+Enter inserts newline; Meta/Ctrl+Enter steers via guarded endpoint when active and falls back to one normal send when idle. Meta/Ctrl-click on the primary button also steers when a turn is resolvable.
- Accepted steer submissions, active-turn queue submissions, and ordinary idle sends clear the submitted composer textarea after acceptance; they clear the submitted attachment session only when the visible session still matches the submitted one, and explicit user clearing remains honored.
- `activeTurnID()` resolves from authoritative running/queued transcript rows first, then the composer guard. The guard is cleared whenever the composer is idle so stale turn IDs are not reused.
- OOB primary-action fragments carry the new execution turn ID immediately after send so immediate steering can target the new turn before transcript rows appear.
- If steering fires while a normal send is still in flight and no turn ID exists yet, the draft/session is captured as deferred steering and flushed once the execution row appears. Failed/non-accepted sends discard the deferred steer.
- If an explicit steer loses the race because the active model completed first and the steer endpoint returns `409`, the composer retries the same message and attachment session once through the normal send/queue path so the input is not dropped.
- `submitComposer` increments in-flight counters from `htmx:beforeRequest`, not call time, so native HTML validation cannot strand counters.
- This area has repeatedly defeated audit-only review; direct browser reproduction of idle, active, immediately-post-send, mid-request, validation-blocked, keyboard, and modifier-click states is required when changing it.

Routes, modes, and runtime actions:
- `/chat` is the global/project orchestrator; Task Detail Thread is task-specific.
- `/chat` supports Orchestrate and Plan. Plan is read-only; Orchestrate mutations require authorized runtime tools/actions.
- Canonical Chat capabilities live in `internal/chatcontrol/registry.go`.
- `list_tasks` is the bounded read-only current-project task discovery action across web/API Chat, supported channel runtimes, task-thread follow-ups, and generic initial/scheduled task runs. It supports partial title and category/status filters, deterministic pagination, excludes `category=chat`, and returns compact identity/status summaries.
- Known task-discovery gaps: merge state omitted from `list_tasks` (`#129`), assigned Agent omitted (`#113`), tags and goal badges omitted from Chat task creation/discovery despite web task forms/cards exposing them (`#415`), compact goal state omitted from `list_tasks` despite the task board already projecting `has_goal` (`#419`), bounded diff/run inspection absent from Chat (`#114`; consolidated task diffs, review comments, and lifecycle evidence suggestion `#417`), task changes/review-comment inspection absent from Chat despite Task Detail Changes rendering persisted `diff_output` and `review_comments` (`#389`, suggestions `#411`, `#421`, and latest `#424`), consolidated read-only Chat task-evidence snapshots for attachments, changes, review comments, and related metadata are absent despite Task Detail already loading those surfaces (`#430`), task lifecycle activity inspection absent from Chat (`#394`, latest suggestion `#410`), and saved Automation state inspection is absent from Chat despite Chat exposing Automation creation/save actions (`#348`).
- `list_schedules` is the bounded read-only current-project schedule discovery action across supported runtimes. It supports task ID/title/enabled filters, deterministic pagination, and returns schedule IDs accepted by modify/delete actions.
- Legacy bracket markers such as `[CREATE_TASK]`, `[EDIT_TASK]`, `[EXECUTE_TASKS]`, `[SEND_TO_TASK]`, and `[SCHEDULE_TASK]` are inert model prose. Runtime-tool handlers decode typed JSON and invoke direct service paths; runtime-tool-incapable providers receive no native tools and no textual fallback.
- Status-marker parsing recognizes only a complete canonical final standalone control: `[STATUS: SUCCESS]`, `[STATUS: FAILED | reason]`, or `[STATUS: NEEDS_FOLLOWUP | reason]`. Malformed, extra-delimiter, quoted, fenced, inline-code, non-final, or prose examples remain visible/inert. Cleaning follows the same exact grammar.
- Chat output cleaning preserves control-looking examples inside Markdown inline code and fences while stripping/normalizing real provider controls outside code. Fenced and inline-code semantics intentionally match Marked-compatible delimiter behavior.
- Open/replace PR runtime actions share target-resolution logic for task selectors, project ownership, project loading, and Automation repository validation.
- Known task-thread runtime action gap `#423`: `execute_tasks` is exposed in task-thread follow-ups but treats `task_id="current"` as a literal task ID instead of resolving it through current-task context, so rerun/resume attempts can fail with `task current not found` without submitting work.
- Known channel task-thread runtime gap `#326`: channel-provided Slack/Telegram/Discord/Email runtimes have the caller task ID available but do not use it to resolve `task_id="current"` or omitted task references, so channel follow-ups can fail for tools that work in web task threads.
- Known web task-thread runtime goal-tool gap `#338`: task-goal tools in persisted task-thread follow-ups resolve explicit `task_id="current"` but reject omitted task identity with `task_id is required`, despite current-task context being available. `send_to_task` and `view_task_thread` already have omitted-current-task regressions; the missing coverage is for the other task-goal tools.
- Known scheduled task-control runtime gap `#341`: loop-auditor scheduled tasks filter task-creation and implementation-linking tools out of their executable runtime definitions, but `list_capabilities` still renders the broader web/orchestrate capability registry and can advertise tools the executor will reject.

Task goals, continuations, and cancellation:
- Plan handoff is driven by completed Plan-mode responses containing `<proposed_plan>`.
- Task goals are durable `task_goals` records managed by `TaskGoalService`; Chat orchestration supports explicit and implicit goal creation.
- Goal continuation uses normal task-thread follow-ups through `thread_inputs`; it does not start work inline.
- Tasks do not support direct peer-to-peer chat. Coordination is through app state and control-plane tools such as `send_to_task`, `view_task_thread`, chain-created children, schedules, dynamic wakeups, goals, and `thread_inputs`.
- A durable “inbox task” pattern is a canonical task thread, not an automatic mailbox.
- Goal status writes use stale `goal_id` plus active-status guards. Goal tools can be granted beyond Goal Agent, but ungranted/default agents do not see or execute them.
- Resolved issue `#333` / PR `#370`: the seven task-goal runtime tools share one service-level runtime action builder for request decoding, `TaskGoalService` calls, assistant actor strings, post-mutation goal reloads, and JSON response serialization. Web/API construction still supplies `Handler.resolveTaskIDForTool` and goal-status authorization, while channel construction supplies the project-owned channel task resolver.
- Manual/user follow-ups on achieved goals reactivate the same goal before prompt context and lifecycle evaluation; Goal Agent/system continuations do not reopen achieved goals.
- Manual Stop/cancel implicitly pauses the active goal with reason `stopped by user`. Starting again resumes only goals paused with that reason; explicit/manual pauses require explicit resume.
- Resolved issue `#298` / PR `#308`: web/API/lifecycle task-goal tools and `send_to_task` now validate raw task IDs and resolved `current` aliases through the project-scoped task resolver before reading goals, mutating goal status, or queueing `thread_inputs`. Title-based task resolution remains project-scoped, `task_id="current"` remains limited to task-thread follow-ups, and channel runtime isolation remains equivalent.
- Global Chat Stop uses the active Chat execution's backing task and task cancellation semantics while preserving `category=chat`.
- Task cancellation and Global Chat stop share handler logic for running-execution cancellation, best-effort repo-error handling, cancellation logging, and terminal SSE publication.
- `processStreamingResponse` must re-check persisted task/execution cancellation after registering runtime cancellation and immediately before provider dispatch.
- Initial worker runs and task-thread follow-ups must not finalize as success merely because a provider returns output after user cancellation has reached durable task/execution state; persisted cancellation wins and required cancellation finalization remains authoritative.
- Task Thread composer Stop posts to task cancel with composer-stop semantics, cancelling the active run/capacity wait without bulk-cancelling queued follow-ups. Broader task cancel controls may still cancel pending inputs.
- Known task-control gap `#235`: Task Details replaces Run Now with disabled state for running/queued tasks instead of exposing established Stop/Cancel behavior.
- Streaming cancellation for normal tasks must not leave `category=active` with terminal failed/cancelled status; normal active terminal rows normalize to Backlog, while Chat preserves `category=chat`.
- Direct cancel and Active-to-Backlog/Completed moves cancel queued/running executions, pause active goal, and preserve requested target category. `TaskService.UpdateCategory` must use pre-update category/status for stop semantics.
- Lifecycle-origin `send_to_task` must re-check active goal state, execution freshness, and cancelled source/destination task state before queueing continuations so stale lifecycle hooks cannot restart stopped, cancelled, or superseded work. It also rejects source/destination tasks with an in-process cancellation request during the task-cancellation window after pending `thread_inputs` are cancelled but before `tasks.status` is persisted as `cancelled`. Legitimate task activation, queued/failed task-thread follow-up promotion, scheduled task creation/reactivation, schedule edit pending resets, due scheduled task submission, and legitimate swarm restart/follow-up paths clear stale cancellation-request markers so stopped tasks can later run user-approved work without remaining blocked as lifecycle-cancelled. Timeout/deadline failures such as `context.DeadlineExceeded` are ordinary failures for lifecycle purposes and should run after-complete hooks with `execution_error`; only explicit user cancellation/Stop suppresses optional after-complete work. Resolved 2026-08-09: task-thread streaming deadline finalization no longer lets a later persisted `cancelled` task status make detached after-complete preflight skip ordinary timeout/deadline failures, and lifecycle-origin `send_to_task` can queue a same-source continuation for an ordinary non-cancel failure even when timeout finalization persisted `status=cancelled`. Cancelled destinations, explicit Stop/Cancel source tasks, in-process cancellation markers, and stale lifecycle source runs still reject continuations.

Task execution and scheduling:
- Open task-board attribution gap `#306`: task cards should surface source badges for channel-origin and Automation-created tasks using existing origin/provenance fields, so users can distinguish web-created work from integration/Automation work without opening each task.
- Active tasks auto-submit on creation or when explicitly moved to Active through execution/category activation paths.
- Task Detail `PUT /tasks/:id` saves are metadata-only: editing title, prompt/model/priority, category fields, or goals on a completed task must not create executions, enqueue `thread_inputs`, reset status to pending, or submit the stored `tasks.prompt`. Explicit `/tasks/:id/run`, board/drag category activation, schedules, follow-ups, and lifecycle continuations remain the execution paths.
- Scheduled tasks run when `next_run <= now`; one-time schedules clear `next_run`, repeating schedules compute the next occurrence.
- Schedules have durable enabled state. Disabled schedules are excluded from due selection; toggling off preserves `next_run`, toggling on recomputes stale/past `next_run`.
- Browser/HTMX and JSON API schedule toggles share one handler-level transition operation.
- Dynamic loop wakeups are schedule rows with wakeup metadata and replacement semantics. Due wakeups enqueue normal task-thread follow-ups through durable `thread_inputs` and are blocked for stopped goal states.
- Chat/control-plane schedule mutations (`schedule_task`, `modify_schedule`, `delete_schedule`) share service-level time parsing, recurrence mapping, interval validation, `NextRun`, persistence, project ownership, and linked-task category/status transitions across web/API and channels.
- Schedule create/modify validation is strict: times must match supported `HH:MM`, recurrence values must be supported, and weekly schedules accept at most one weekday from `sun` through `sat`.
- Known schedule gaps: `list_schedules` omits `LastRun` (`#131`), due one-time occurrence can be lost on process exit between enqueue and `MarkRan` (`#88`), drag-to-past one-time schedule can rerun immediately (`#270`), Schedule page new-task creation omits the optional task Goal field even though normal task creation and the backend schedule create path support goals (`#342`; latest suggestion `#379` on 2026-08-09), New Scheduled Task omits attachment upload support (`#353`), Schedule calendar cards lack lightweight task status/goal cues for scanability (`#354`), and remaining task-thread schedule/runtime current-task context gaps are tracked in `#312`.
- Monthly recurrence uses anchor-aware clamping, preserving original configured day when later months support it.
- Schedule rows own timing; linked tasks own execution assignment. Primary Agent is `tasks.agent_definition_id`; model configuration remains task `agent_id`.
- `Clear context on start` is schedule-owned and non-destructive. Scheduled ordinary/swarm runs start without prior turns, while stored history/evidence remain intact; later manual follow-ups replay from the latest scheduled boundary. New schedules default true; existing schedules retain stored value.
- Schedule create/add/edit surfaces expose project-scoped Primary Agent selection and own `Clear context on start`; Task Details Edit Task does not expose or mutate schedule context policy.
- Promoted queued task-thread follow-ups move the task back to Active during queue-claim/promotion before exposing the execution.
- Reactivating a failed task with no queued input retries the latest failed follow-up from `PromptSent` and chronological history, not blindly `tasks.prompt`.
- Zero-model guardrails block execution and Chat send surfaces with an Open Models action.
- Worker dispatch capacity uses global/project/model counters. Cleanup after slot acquisition is centralized so completion, provider errors, cancellation, claim failures, and panics release slots and trigger redispatch.
- Known capacity gap `#44`: task-thread follow-ups reserve global/project capacity before model capacity, so model-blocked follow-ups can occupy global slots and block runnable work on other models.
- Capacity waiting for follow-ups is cancellable and not charged against `worker_timeout`; timeout begins after slots are acquired.
- Tasks legitimately run while category is active or scheduled; stale-running recovery must not treat scheduled-category running executions as inactive.
- Direct task-thread startup on completed/inactive swarm children must reactivate the task and insert the execution atomically; true inactive/orphaned children should still be recovered.

Swarm and parent-thread notes:
- Swarm parent follow-ups and dropdown changes guard before touching parent `Task.AgentID`; parent assignment remains the template for child creation.
- New swarms persist resolved assigned model for children; legacy nil-agent rows resolve the same effective model at render time.
- Swarm child cancellation/deletion paths should cancel running child work when deleting/cancelling parent context. Swarm cancellation marks parent/child in-process cancellation intent before invoking runtime cancel callbacks or persisting cancelled status, preventing lifecycle-origin continuations from slipping through the pre-status race. Legitimate swarm restarts/follow-ups after `CancelSwarm` clear stale cancellation markers on reused parent/planner/child tasks before resumed work can run lifecycle hooks. Known UI gap: swarm-card accordion can be too narrow and should default collapsed.
