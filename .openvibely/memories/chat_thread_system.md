title: Chat and Task-Thread Behavior

Interactive Chat intentionally bypasses worker capacity. Task-thread follow-ups use `processStreamingResponse` with `IsTaskFollowup=true` and respect global, project, and model capacity.

Queueing, steering, and attachments:
- Normal Send during an active Chat/task-thread run queues the next input; explicit steering applies only at OpenVibely-owned provider/model-step boundaries; Stop cancels current execution. Queueing and steering use durable `thread_inputs`; `executions` represent real model runs, not parked composer state.
- Promotion claims pending input while creating the next execution/task and preserves FIFO. Promoted task-thread inputs resolve current model assignment at promotion time; queued Chat inputs retain per-input model selection. Follow-up executions remain `queued` until worker admission and become `running` only after a slot is acquired.
- Attachment sessions are stored on queued/steering rows. Chat rows have no `task_id` and use `run_execution_id`; task-thread rows use `task_id`. Repeated drops append, duplicate browser names receive unique pending names, and the three-files-per-message limit spans repeated drops.
- Text attachments enter prompt context, images become model attachments, and large text remains attached without being inlined. Steering attachment discovery after a provider call or during deferred completion is requeued as a normal next message, never committed to the completed user bubble. Failed submissions preserve drafts/sessions for retry; rollback retires unowned sessions.
- Shared attachment persistence writes a temporary destination, applies permissions, flushes/renames atomically, syncs the directory, then stores metadata. Metadata is removed before files on rollback; files remain if metadata deletion fails. Multipart limits are endpoint-specific and enforced before full parsing or side effects. Valid totals such as two 6 MB files are allowed when each file is within its endpoint cap. Browser task creation, editing, and the dedicated upload route allocate collision-free per-task destinations, reserving existing names and names allocated earlier in the same request while preserving the established basename/suffix convention. Allocation fails closed when existing task attachments cannot be listed, so a stale or missing-file row cannot cause a reused destination to be allocated. Each accepted attachment has an independent metadata path; deletion removes the physical file only when no remaining task-attachment row references it. Copy or metadata failure removes only the new destination and cannot overwrite or remove an existing attachment. The chat-to-task copier and ordinary task uploads therefore share the same collision/ownership invariant.
- API Chat multipart admission persists the task/execution before creating `uploads/chat/<executionID>`. If directory/setup fails after persistence, the existing bounded failure contract removes partial storage, terminalizes the execution/task, clears active-turn lookup, and allows queued input promotion; real multipart regression coverage for issue `#1128` is published in PR `#1141`.
- Effective Active runtime task creation persists Backlog until conversion succeeds, then activates by request index. Upload/session storage follows configured local, hosted/Docker, and desktop roots; broken metadata can be reconciled, missing file bytes cannot.

Admission, lifecycle, and history:
- Follow-up admission is serialized with scheduler/worker claims and Automation reservations. It atomically reserves a direct execution or appends durable FIFO input. Browser pending-input refresh, queued-to-steering, and cancel routes are project-scoped and do not leak or mutate foreign rows. Ordinary Active-lane reservation and ordering are canonical in `openvibely_architecture.md`.
- Lifecycle-owned Active-lane moves carry the browser-observed category/status as an expected-state fence into the owner’s first durable mutation; a changed terminal, category, or ownership state returns a controlled lane conflict instead of falling through to ordinary promotion/retry. The transaction and durable-reservation invariants are canonical in `openvibely_architecture.md`.
- Startup reclaims interrupted follow-ups and promotes recoverable inputs through stable keyset pages with per-task FIFO and exactly-once promotion. Chat recovery and update-drain reopening use sparse indexed keyset paging, promote each eligible project once per page, skip active Chat executions, and filter guarded terminal executions. `RecoverQueuedInputs` and `RecoverQueuedTaskThreadInputs` share a private 100-item callback-driven pagination/promotion helper while retaining distinct repository queries, ID meanings, promotion callbacks, diagnostics, and Chat-versus-task list-error continuation. Startup and update-drain recovery ordering remain preserved.
- The Chat input request-list and answer endpoints share a private `requireChatInputProject` preflight for repository availability, project lookup, error propagation, and missing-project handling. Endpoint-local parsing, blank-ID `400`, answer validation, broker ownership, exactly-once resolution, SSE events, and response shaping remain separate.
- After-complete hooks receive only the latest normalized input/response; prior provider history can influence the answer but is not copied into lifecycle transcript. Future provider history is rebuilt from `executions.PromptSent` and cleaned `Output` as plain turns, with at most 20 prior task-thread turns after filtering the current execution. Every immediate task-thread follow-up, including direct review submission, loads only the newest 21 executions through `ListByTaskChronologicalLimit` before chronological filtering. Filtering excludes the newly created/current and running executions and honors a `starts_new_context` boundary within that window. Queued review admission returns before context hydration; its later promotion retains the same bounded policy.
- HTTP send/acceptance stays lightweight; full context setup runs after durable acceptance. Deferred setup failures still perform terminal cleanup and can promote queued input. Thread pagination renders execution history, not an unrecorded `tasks.prompt`. Runtime `view_task_thread` uses repository count/page projections and the existing 80 KiB transcript budget without hydrating payloads unnecessarily.
- Execution History and Task Thread pagination share one handler loader and canonical light repository page query, preserving task filters, descending timestamp/rowid ordering, cursor adjacency, limit-plus-one detection, and chronological thread rendering. Execution History reverses the shared result for newest-first cards. This removes the duplication tracked by `#981`.
- Global `/chat` independently implements the same chronological conversation-window contract as the Task Thread loader: `limit + 1` retrieval, initial versus `before`-cursor selection, sentinel trimming, and an older-page flag. Handler-level consolidation is tracked by `#1059`; route-specific lookup, error, and rendering behavior should remain local.
- Lifecycle activity belongs in the Lifecycle tab; task-thread follow-ups still run normal lifecycle routing before the model call. Canonical lifecycle and ownership details are in `agent_lifecycle_and_skills.md` and `openvibely_architecture.md`.

Composer and realtime behavior:
- Shared composer markup lives in `web/templates/components/chat_shared.templ` and uses one `ChatInputForm` contract. Apple hints are `⏎ sends or queues · ⌘+⏎ steers`; other platforms use `Enter sends or queues · Ctrl+Enter steers`; Shift+Enter inserts a newline. The visible shortcut hint is not duplicated as a textarea `title` tooltip; the textarea keeps explicit accessible naming with `aria-label="Message"` while retaining the visible platform-aware hint.
- The shared `ChatInputForm` sets `novalidate` to suppress browser and HTMX native constraint-validation UI such as “Please fill this out” on both Chat and task-thread composers. The textarea retains `required` semantics. Normal task-thread sends now enforce boundary validation consistently: `TaskThreadSend` trims at entry, rejects normalized-empty input with `400` and `message is required` before task/model/admission side effects, and uses the normalized value through admission, persistence, and rendering; the shared submit guard treats trim-empty drafts as a no-op. Issue `#1147` is implemented in PR `#1157`, with idle/active no-side-effect and padded-success regressions. API Chat now applies the same trim-empty admission boundary independently: `POST /api/chat/message` returns `400` with `message is required` before project/model lookup, attachment staging, task/execution creation, or queued `ThreadInput` insertion while preserving accepted padded message text verbatim; spaces, tabs, newlines, mixed URL-encoded/multipart input, active-turn state, attachment-session non-staging, provider non-invocation, and padded-success behavior are covered by issue `#1153` regressions in PR `#1163`.
- Enter sends/queues; Meta/Ctrl+Enter steers while active and falls back to one normal send while idle. Modifier-click on the primary button steers when an active turn is resolvable. Accepted sends clear text/session only after acceptance and only clear a matching visible attachment session. A lost `409` steer race retries once as normal send.
- The active primary button becomes a same-styled Stop with a square icon; server OOB state is authoritative. OOB fragments carry a new execution ID immediately so immediate steering can target it. If steering races an in-flight send before an ID exists, the draft/session is deferred and flushed after execution creation; failed/nonaccepted sends discard it. In-flight counters begin at `htmx:beforeRequest` so native validation cannot strand them.
- The shared Chat/Task Thread transcript controls include an accessible `Latest message` button for `#chat-messages` and `#task-thread-messages`. It is shown only when the existing `ChatScrollTracker` records that the reader intentionally left the bottom; activation calls the tracker’s `returnToLatest(false)`, advances the same intent revision used by streaming fences, clears the parked state, and immediately jumps to the latest message. The controller observes scroll, row/layout mutation, and resize changes, and is installed, rebound, and destroyed across initial render, lazy/pagination/HTMX/SSE updates, and history restoration rather than maintaining a separate scroll policy.

Modes and runtime actions:
- `/chat` is the global/project orchestrator; Task Detail Thread is task-specific. Plan is read-only; Orchestrate mutations require authorized runtime tools. Capabilities are canonical in `internal/chatcontrol/registry.go`; tool-incapable providers receive no textual bracket fallback. Legacy markers such as `[CREATE_TASK]` are inert prose.
- Web Orchestrate Chat also exposes the provider-agnostic `request_user_input` approval tool only on that surface. It accepts 1–3 questions with 2–3 options each, publishes a project-scoped `chat_user_input_requested` event, waits for validated answers, and returns the selected answers to the same model run so an affirmative response can authorize a later mutation. Pending requests use generated IDs, are in-memory with expiry/cancellation semantics, and answer resolution is project-owned and exactly once; they are not durable across restart. The server exposes `input_request.expires_at` and enforces a ten-minute TTL, but the Chat card does not currently surface expiration, so an expired question can remain apparently actionable until submission returns a generic error; suggestion `#1110` tracks showing expired status and disabling or otherwise closing the stale action. While a provider is waiting, page reload or SSE reconnect can also lose the one-shot request because Chat rebuilds from persisted executions and the live stream does not replay it, leaving the run blocked; open bug `#1104` tracks this recovery gap. Model guidance requires this tool before ambiguous writes such as task creation and never treats assistant prose or bracket markers as authorization. Definition filtering hides it from task-thread follow-ups, and execution now enforces the same boundary: `executeRequestUserInputTool` rejects `IsTaskFollowup=true` before validation, broker creation, SSE publication, or waiting. Focused regression coverage proves a provider-emitted hidden call on a web task-thread run returns an error without creating a pending request or SSE event.
- Orchestrate-only actions include `set_default_model`, `save_custom_personality`, `update_agent`, `cancel_task`, `create_project`, `update_project_settings`, task/Automation mutations, and destructive deletes. They resolve exact IDs or unambiguous names, enforce current-project ownership, validate before side effects, preserve protected/built-in records, and are not advertised/executable in Plan. Custom personality save reuses browser name/prompt validation, rejects duplicate/blank keys, missing custom targets, built-in prompt mutation, and partial activation before save. `list_channels`, `list_tasks`, `list_schedules`, `view_pulse`, `view_usage_analytics`, `view_system_update`, `list_automations`, and `get_automation` are read-only where supported in both modes.
- `create_task` and `create_swarm_task` share normalized service input, compact model loading, title/prompt/priority validation, and summaries across web/API and channels; surfaces retain attachment, project, Automation, and channel callbacks. `create_project` is GitHub-backed only, rejects local path/directory behavior, clones through the normal project service, rolls back clearly on failure, and may switch project through channel persistence. Project worker limits are any positive integer, must not exceed a finite global limit, and must be checked before persistence/clone/setup.
- `update_project_settings` can set/clear safe metadata, select a default model, and set/clear a worker cap; it rejects repository rebinding, credential, and deletion fields and triggers dispatch when capacity increases. `switch_project` remains informational in web/API runtime within the same model turn (`#734`); channel persistence is separate.
- `update_agent` may patch bounded user-managed fields including prompt, description, model inherit/override, safe tools, scoped-file grants, enabled state, and primary selectability. It rejects protected/archived/foreign/ambiguous agents, duplicate enabled/selectable names, unknown tools, malformed scoped files, and unsupported keys without partial save.
- `list_tasks` is bounded, current-project, read-only discovery with one substring query, title/category/status filters, deterministic pagination, compact summaries, and `category=chat` exclusion. Omitted filters mean all visible categories/statuses. Exhausted identical empty calls return a guarded `duplicate_noop`; callers should not repeat the same query merely to change echoed filters. Task discovery still lacks several Task Detail fields such as assigned Agent, tags, goals, merge/PR state, diffs, review comments, lifecycle evidence, and attachments.
- Automation actions resolve project-scoped targets and preserve point-in-time template revisions. Details belong in `automation_graphs.md`; integration action behavior belongs in `integrations_and_channels.md`. Channel handlers take precedence over generic runtime handlers while preserving prompt-safe readiness summaries.
- Status parsing accepts only a complete final standalone `[STATUS: SUCCESS]`, `[STATUS: FAILED | reason]`, or `[STATUS: NEEDS_FOLLOWUP | reason]`. Malformed, inline, fenced, or non-final examples remain visible/inert. Output cleaning preserves examples in Markdown code.
- Known runtime gaps include current-task resolution for PR tools, `execute_tasks`, channels, and goal tools; scheduled capability advertisements must not exceed executor support. Chat inspection remains intentionally compact and lacks several Agent, plugin, PR, skill, worker-pressure, and Insights details. Project tools currently expose metadata and task counts but no bounded, read-only way for Chat to inspect the repository's authoritative root `VISION.md`; suggestion `#1114` tracks adding project-scoped vision inspection without arbitrary file I/O or changes to existing memory, skills, Insights, or Automation actions. `view_pulse` exposes project-scoped active pending/queued work with bounded, deterministic, prompt-safe agenda summaries; it excludes Chat, terminal, and blocked placeholders. Pulse and `view_pulse` do not project durable task-goal state, even though it determines automatic continuation and human-attention needs; read-only goal-state visibility is tracked by suggestion `#1073`.

Goals, cancellation, schedules, and swarms:
- Plan handoff uses completed Plan responses containing `<proposed_plan>`. Goals are durable `task_goals` managed by `TaskGoalService`; orchestration can create explicit/implicit goals, and continuation uses normal queued task-thread follow-ups rather than inline work.
- Tasks coordinate through durable state and tools such as `send_to_task`, `view_task_thread`, child tasks, schedules, dynamic wakeups, goals, and `thread_inputs`; there is no direct peer-to-peer task chat. Task identity is project-scoped and there is no cross-project view/switch capability.
- Manual follow-up on an achieved goal reactivates it; system continuation does not. Stop pauses an active goal with `stopped by user`; restarting resumes only that pause reason. A known goal-state invariant bug allows public pause to rewrite terminal `achieved` or `cleared` goals to `paused`, after which resume makes them active and clears achievement metadata (`#1029`); the pause mutation needs an atomic source-status guard. Persisted cancellation wins over provider output, and `processStreamingResponse` rechecks cancellation immediately before dispatch. Cancellation must preserve terminal statuses, require cancellable executions, and not rewrite history (`#477`).
- Task cancellation/category transitions use pre-update category/status, cancel only work that originated Active, persist cancellation before category changes, pause active goals, clean capacity, publish SSE, and preserve requested category. Explicit CancelTask retains its Backlog behavior. Task Thread Stop cancels the active run/capacity wait without bulk-cancelling queued follow-ups; broader task cancellation may cancel pending inputs. Task Detail still lacks Stop/Cancel replacement for Run Now on running/queued tasks (`#235`).
- Schedule mutations share `ScheduleActionService`; due selection uses `next_run <= now`, disabled rows are excluded, one-time rows clear `next_run`, repeating rows advance, and monthly recurrence clamps to its anchor. Schedule gaps include missing LastRun (`#88`), past one-time drag behavior (`#270`), goal/attachment creation (`#342`, `#353`), card cues (`#354`), current-task context (`#312`), calendar-local Pause/Resume controls (`#1146`), and a calendar-local `Run Now` action that leaves cadence unchanged (`#1151`).
- Capacity cleanup releases global/project/model reservations on every terminal path. Follow-up wait is cancellable and does not consume `worker_timeout`; model-blocked reservations can still occupy global capacity (`#44`). Failed tasks retry latest failed follow-up history when reactivated, not blindly `tasks.prompt`. Zero-model guards offer an Open Models action.
- Swarm parents own child templates and assignment changes are guarded. New swarms persist resolved child models; runtime creation supports goals, priority, tags, explicit model/Agent, reviewer/merger, merge target, and independent default-off auto-merge settings for successful execution completion and goal achievement. Runtime task `create_task` accepts both settings; `edit_task` uses nullable values so omitted settings are retained while explicit `false` disables the selected trigger. `view_swarm` is compact and project-scoped. Child cancellation marks in-process intent before status/callback work. Planner application still rejects inherited `shared` isolation when entries omit worker isolation (`#502`). The parent Swarm Overview currently exposes child links and statuses but not human-triggered reviewer/merger rerun controls; suggestion `#1006` tracks status-aware controls without changing scheduling or retry semantics.
