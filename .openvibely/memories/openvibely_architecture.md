OpenVibely is an open-source Go application for scheduled tasks and AI execution. The backend uses Echo v4, SQLite through `modernc.org/sqlite`, goose migrations, and a channel-based worker pool. The UI is server-rendered with HTMX, templ, Tailwind CSS, and DaisyUI.

Server, desktop, and storage:
- `internal/server.Start(ctx, cfg)` wires the shared backend and returns address, base URL, and shutdown handle. Desktop and server share `internal/server`; backend forking is not intended.
- The Handler owns the synchronized current X service. Shutdown and reconfiguration operate on the installed service, with configuration-generation fencing preventing stale pollers from handling mentions or completing handoffs.
- Local/server storage defaults to `$HOME/.openvibely`; desktop uses the platform application-data directory; hosted/Docker uses explicit env-driven storage under mounted `/data`. Desktop uses `ModeDesktop`, `PORT=0`, local repos, and a Wails WebView. `OPENVIBELY_APP_DATA_DIR` is literal, `DATABASE_PATH` still wins for the database, and `OPENVIBELY_RUNTIME_DIR` is only a deprecated `start.sh` alias.
- Packaged desktop binaries load `config.env` from the OS config directory unless `OPENVIBELY_DESKTOP_CONFIG_FILE` overrides it. Desktop startup constructs its own environment because shell `PATH` is unreliable. Safe external links use runtime markers and `/open-external`; native dialogs are preferred when WebView uploads are unreliable.

SQLite and runtime state:
- File-backed production SQLite uses a dedicated `1W + 1R` topology after serialized bootstrap: one pooled writer and one query-only reader. Isolated `:memory:` fixtures use one shared connection. Each file-backed connection receives foreign keys, a five-second busy timeout, UTC datetime behavior, and preserved caller query/pragma parameters; WAL permits readers beside the writer.
- Bootstrap and goose migrations run through the held writer before opening the reader. Startup failure unregisters mappings and closes both handles, including late failures. Initial auto-vacuum conversion may require a warned pre-context `VACUUM`.
- Bounded writer and `RETURNING` helpers are cancellation/deadline-aware, restore and verify timeouts, classify retries, clean up, and discard poisoned physical connections. Transaction-owned executors remain caller-scoped. Task-goal updates and attachment creation follow this writer invariant.
- High-cardinality deletion uses ownership indexes for alerts, lifecycle parents, task/execution attachments, and pending-upload sessions. Project deletion snapshots and revalidates its cleanup manifest inside the relational transaction, moves files only after commit/runtime cancellation, quarantines ordinary attachments and pending uploads, and returns a committed-deletion warning if post-commit cleanup fails. Managed clones are removed only under the recognized managed root plus project ID; user-owned repositories are retained while validated task worktrees/branches and Git metadata are cleaned. Pending-session locks and retirement tombstones protect late uploads.
- Local storage migration preserves databases, SQLite sidecars, repos, uploads, and runtime directories; release binaries never use checkout-relative storage. Migration 177 removes the obsolete `memory_consolidation_schedules` table whose dangling foreign key could break project cascades.

Workers, tasks, and schedules:
- `worker_settings.max_workers=0` means unlimited and the API/UI display `Unlimited`. Global, project, and model reservations are atomic and released on completion, failure, cancellation, claim failure, or panic. Project caps are positive, independent limits that cannot exceed a finite global limit; malformed values fail before side effects. Lowering the global limit blocks new admissions without cancelling running work, and increasing capacity triggers dispatch.
- Project capacity list/detail handlers share a canonical response mapper for identity, running workers, capacity state, zero-clamped available slots, and queue count. The project-capacity collection API uses `ProjectService.ListWorkerCapacityProjects` and its compact `id`/`name`/`max_workers` projection; the single-project detail route retains its full project read and existing capacity check.
- Repeat intervals are positive `1..365` for every recurrence unit across browser, repository, Automation, runtime, and channel paths. Direct schedule-handler coercion of malformed/overflow intervals or unsupported recurrence types remains open as `#116`.
- Scheduled-task creation has an orphan risk in `#947`: invalid or missing `run_at` can persist a task without a schedule row. Validation must reject before task persistence and cover both no-task and no-schedule side effects.
- Schedule timing belongs to schedule rows; execution assignment belongs to linked tasks. `tasks.agent_definition_id` selects the primary Agent persona and `tasks.agent_id` selects the model config. `clear_context_on_start` is schedule-owned and non-destructive; new schedules default true. `ScheduleActionService.CreateForTask` is the normalization boundary. `ScheduleActionService.Toggle` atomically pauses/resumes schedules, preserves the occurrence when pausing, repairs stale recurring `next_run` on resume, and rejects already-fired one-time schedules rather than inventing a cadence.
- Grouped schedule movement is one project-scoped atomic request: reload enabled rows in the writer transaction, validate ownership/disabled members, reconstruct local wall-clock fields across DST, change only `run_at`/`next_run`, and roll back on mismatch/error. Single-card rescheduling uses task ownership checks.
- Automation claim/failure transitions are crash-consistent across execution, task, activity, invocation, outbox, reservation, and cancellation state. Committed transitions publish project-scoped board invalidations; eligible failed/completed Automation work may be reset during later admission.
- Active-lane board moves use one immediate project-scoped transaction. The persisted tail is shared by every writer and is calculated from every card rendered in In Progress, including running scheduled Automation cards. Browser moves include pre-drag category/status; the repository rejects duplicate, foreign, missing, or stale rows before writing. Every genuine entry path appends at the common tail, and already-active cards already in the requested pending/running lane are true no-ops.
- Active scheduler admission scans retain the compact `ListActivePendingAdmissions` projection and use migration 184's partial composite SQLite index for `category='active' AND status='pending'`, keyed by `priority DESC, display_order ASC, created_at ASC`. The actual file-backed `1W + 1R` production query plan avoids `USE TEMP B-TREE FOR ORDER BY` and keeps the five-second cadence, worker submission, swarm-parent routing, authoritative worker claim, and exclusion fences unchanged.

OAuth, hosted deployment, and Docker:
- OAuth origins prefer `APP_BASE_URL`, then forwarded/request host. `OAUTH_REDIRECT_MODE` controls callback URIs; hosted workspace provisioning forces `localhost_manual` for built-in OpenAI/Anthropic OAuth.
- OAuth refresh is lifecycle-owned as well as request-time: after successful listener binding, a periodic service refreshes expiring OpenAI and Anthropic configs independently, using per-config durable leases and revision-conditional persistence. Permanent refresh failures persist per-config reauthentication state, and shutdown cancels and joins the refresher before database closure. Built-in OpenAI and Anthropic callback persistence atomically saves credentials, clears `oauth_needs_reauth`, and advances `oauth_config_revision`, so stale refresh success or `invalid_grant` writes cannot overwrite a successful reconnect. Analytics account/workspace grouping is display/snapshot aggregation only and never a credential-sharing boundary. A strict audit found that a failed or reauthentication-required first config could suppress a healthy sibling's account-limit fetch when `refreshAccountSnapshots` marked the shared display key seen before fetch success; repair commit `eede5d32` now defers failure persistence and deduplication until a usable cached or successful sibling result, without sharing credentials or reauthentication state. The exact merged candidate was `acf292c1` (first parent `eede5d32`, current `main` second parent). A fresh strict read-only audit then found a cooldown-path defect: when `latestAccountSnapshotForConfig` returned `shouldRefresh=false` for a recent shared-account failure snapshot, `refreshAccountSnapshots` marked the grouping key seen and suppressed a later healthy sibling. Repair commit `9dc42d5e` scopes failure cooldowns to the originating OAuth config in both snapshot selection and traversal. A subsequent fresh strict read-only audit of exact HEAD `9dc42d5e99ba1706074eb3a68f58c4ba38e560ee` found a persisted-history precedence defect where a newer failure snapshot from one config could replace a still-fresh healthy cached sibling during account-view merging. Repair commit `b47f844d` makes error-free account views outrank config-scoped failures for the same account while preserving timestamp ordering within each result class; OpenAI/Anthropic regression coverage verifies no provider fetch, healthy limits, and independent credential/reauthentication state. Validation passed through a clean committed worktree. A fresh strictly read-only audit of exact HEAD `b47f844d238ab1179be65ceca281a584292c0d3f` found a stale-account-identity race: a rejected revision-conditional account-ID write could leave Analytics using a stale in-memory config, allowing a still-fresh stale token to reach usage fetch and snapshot persistence. Repair commit `56b48f9d` makes rejected identity writes reload the authoritative config; reconnects continue only with current OAuth credentials, provider/auth edits become ineligible, reload failures abandon the candidate, and Anthropic profile results that lose a reconnect race are discarded before usage fetch or snapshotting. Production-shaped OpenAI/Anthropic regressions cover reconnect and model-edit races plus Anthropic profile-request interleaving. Build, vet, template no-drift generation, full service tests, callback race coverage, focused regressions, and all-package coverage validation passed; the unchanged `TestValidateRepoPathsProjectionProductionPerformance` timing gate passed three isolated runs but was skipped under broad load. Repair commit `f7508b68` fences newly produced Analytics account snapshots: successful and deferred-failure snapshots are inserted only inside an immediate SQLite transaction that verifies the producing config ID, OAuth revision, provider, and OAuth auth method; superseded OpenAI or Anthropic candidates are skipped. Production-shaped regressions cover reconnect and model-edit interleavings after identity resolution for both providers. Build, vet, zero-update template generation, repository and service suites, callback race coverage, focused Analytics regressions, and the CI-style all-package coverage suite passed with only the unchanged `TestValidateRepoPathsProjectionProductionPerformance` timing gate excluded. The worktree was clean. A fresh strict read-only audit of exact HEAD `f7508b68a2713e5ba1e78e9b3663921b9ea8fd22` nevertheless found a material historical-snapshot identity/generation defect: persisted snapshots have no OAuth generation binding, so after reconnecting from principal A to B, a fresh snapshot can be suppressed when identity is unavailable by config-ID fallback, or an old A snapshot can be remapped to B when the current identity is known; rendering checks only that the config remains OAuth-connected. The next repair must prevent prior-generation snapshots from being reused or attributed to a new principal, with OpenAI and Anthropic regressions for unavailable and changed identities. The audit changed no workspace state and ran no validation commands; separate repair, validation, and another fresh strict read-only audit remain required.
- Callback state is consumed once and tokens are written only when provider, method, target, and config revision still match. Manual completion handles provider-denial callbacks with `error` and `state` but no `code` before success-code validation, consumes the pending state once, returns sanitized application-owned denial text, and rejects replay. Hosted SSO is server-only with canonical-origin/HMAC validation and process-local pending state, so one replica per workspace is required.
- Hosted cookies are centralized with `HttpOnly`, `SameSite=Lax`, configured `Secure`, and remain separate from local-auth cookies. Hosted deployments use Compose under `/docker/<project>/docker-compose.yml`, Traefik, and persistent `/data`.
- Local login rejects raw or encoded backslashes in `next` values. Authentication cookies are versioned with subsecond expiry while legacy token verification remains supported.
- One server/coding-agent Docker image is intentional. It runs as UID/GID `10001:10001`; mounted `/data` must already be writable by that identity. It includes common Go, Node.js, Python, Rust, Java, Ruby, and C/C++ toolchains but is not a complete sandbox.

Reflection, ownership, and handlers:
- Reflection `hour`, `day`, and `week` are rolling windows; `day` means the last 24 hours. Change statistics prefer app-produced `task_commit_stats` and use Git only for the true pre-stats range. Shared bounded NUL-safe numstat parsing covers task output, safety, dirty-worktree, merge/squash, conflict, rebase, and GitHub publication paths; fast-forward merges add no extra row.
- `internal/handler` is the Echo boundary: `handler.go` owns dependencies/routes while feature files own task, project, chat, model, auth, integration, SSE, worktree, HTMX, and API behavior.
- Lifecycle hook repository list reads share one private row-lifecycle helper for query execution, closing, `scanHook` decoding, and iteration errors; `HooksByAgent` and `HooksForWhen` retain their distinct projections, filters, ordering, and method-specific query-error context.
- Queued-input recovery pagination and promotion use one private callback-driven bounded keyset helper: batch size 100, empty-cursor initialization, page loading, per-ID callbacks, short-page termination, and last-ID advancement are shared while Chat/task-thread callers retain scoped loaders, promotion callbacks, diagnostics, and list-error policies.
- Browser task attachment create, update, and upload routes share a handler-private bounded multipart-admission helper using canonical aggregate/per-file limits. Parser-originated HTTP errors are preserved; generic parser failures map to `400 failed to parse form`; ownership-before-parse and endpoint-specific checks remain local.
- GitHub-backed project updates normalize repository identity before side effects. Equivalent URLs preserve the managed checkout, canonical stored URL/path, untracked files, and local-only branches; genuinely different repositories or local-to-GitHub transitions re-clone and persist normalized values.
- Compact project-aware projections serve polling, metrics, detail lists, upcoming work, selectors, task cards, API projects, repo-path validation, project switching, scheduler admission, and channel Chat context. Rich Agent/model/task reads remain limited to deliberate detail, execution, lifecycle, skills, plugins, MCP, and management paths. Project list and selector projections retain scope, deterministic ordering, response compatibility, and query-free behavior where required. The channel-specific `get_current_project` action uses a typed `ProjectIdentity` (`id,name`) projection through a parameterized primary-key lookup; generic web/API current-project and rich project callers remain on `GetByID`.
- Task breadcrumb selection uses a compact `(id,title)` projection. Title searches retain current-task, exact, prefix, contains, recency, and ID relevance ordering; empty searches split the current-task lookup from bounded recency retrieval so current-first ordering does not impose a full-project temporary sort. Migration 174 adds the partial `(project_id, updated_at DESC, id ASC)` discovery index for non-Chat tasks. Results remain project/schedule scoped and bounded.
- Browser execution, review, lifecycle, goal, Insights, and configuration endpoints enforce project ownership before reading or mutating data and return controlled non-success responses without leaking prompts, outputs, skills, memory, events, goals, or analytics. Task-goal browser routes require an explicit non-empty `project_id` or selected-project boundary.
- Direct Insights reports share only private project/default-Agent resolution; each report retains its own gathering, prompt, parser, persistence, unavailable-AI, and repository-path behavior. Explicit task ID/title resolution is centralized in `internal/service/task_reference_resolver.go`; web/channel `current` normalization remains adapter-owned.

Diagnostics and development:
- The repository targets Go `1.27.1`, canonicalized by `go.mod` and CI. Docker/dev images and README source-build requirements use the same patch version. Air is pinned to `v1.67.4`; `make dev` delegates to Air, and templ/Tailwind/Swagger freshness checks are conservative and shared by build/run targets.
- Uncached broad suites have recurring baseline failures, including server-bootstrap protected-agent/read-only-database setup and schema-version migration assertions. Report exact failures with the narrower passing scope rather than claiming the broad suite passed.
- `internal/applog` uses `Infof` for operational events and debug-gated `Debugf` for raw LLM/user content and high-frequency stream/SSE/diff/poll/provider traces. `internal/util/json.go` centralizes fenced/balanced JSON candidate extraction; callers retain schema validation and repair.
- External-channel first-turn compact context, realtime details, theming, provider behavior, worktrees, integrations, alerts, Automations, analytics, and testing contracts live in their specific topic files.
