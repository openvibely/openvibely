OpenVibely is an open-source Go application for automated task scheduling and AI-powered execution. The backend uses Echo v4, SQLite through `modernc.org/sqlite`, goose migrations, and a channel-based worker pool. The frontend is server-rendered with HTMX, templ, Tailwind CSS, and DaisyUI.

Server, desktop, and storage architecture:
- `internal/server.Start(ctx, cfg)` wires the shared backend and returns a server instance with bound address, base URL, and shutdown handle. Server and desktop share `internal/server`; backend forking is not intended.
- Local web/server binaries default database, repos, uploads, and runtime state to `$HOME/.openvibely` unless overridden. Desktop uses OS application-data directories: macOS `~/Library/Application Support/OpenVibely`, Windows `%LOCALAPPDATA%\OpenVibely` with `%APPDATA%` fallback, and Linux `$XDG_DATA_HOME/openvibely` with `~/.local/share/openvibely` fallback.
- Hosted/Docker deployments use explicit env-driven storage under mounted `/data` where applicable. Desktop uses `config.LoadWithMode(ModeDesktop)`, ephemeral `PORT=0`, local repo paths, and a Wails WebView pointed at the server base URL.
- `OPENVIBELY_APP_DATA_DIR` overrides the local app-data root and is literal, with no shell `~` expansion. `DATABASE_PATH` still overrides the database path. Packaged desktop binaries load environment variables from `config.env` in the OS config directory, overridden by `OPENVIBELY_DESKTOP_CONFIG_FILE`.
- Desktop/Wails GUI launches may not inherit shell `PATH`; task execution relies on centralized environment/PATH construction. Authoritative server runtime markers plus `/open-external` handle safe external links, and native dialogs are preferred where WebView upload features are unreliable.

SQLite and runtime-state contracts:
- File-backed production SQLite now uses a dedicated `1W + 1R` topology after serialized bootstrap, auto-vacuum initialization, and goose migrations. `database.NewReadWrite` keeps one writer pool connection (`MaxOpenConns(1)`) and one reader connection whose physical connection uses `query_only=ON`; isolated `:memory:` fixtures return one shared handle and remain single-connection. Server repositories use the reader handle for ordinary reads, while bounded repository mutations, write-with-`RETURNING` paths, read-write transactions, and incremental vacuum route to the writer; read-then-write transactions remain entirely on the writer. This reserves reader capacity under writer contention, and missed reader-side writes fail instead of silently mutating through the read pool. Duration-based production-shaped benchmarks at active workloads `1/4/10`, including 500 ms stream flushes, selected `1W+1R` over `1W+2R`: active-1 reads were effectively tied, while active-4 and active-10 read/mixed throughput favored one reader; all mixed samples recorded positive flushes and zero SQLite busy errors. Every physical file-backed connection still receives `foreign_keys=ON`, `busy_timeout=5000`, and UTC datetime behavior while preserving caller query/pragma parameters. WAL permits readers alongside SQLite's single writer, and incremental auto-vacuum remains enabled.
- Bootstrap, auto-vacuum initialization, and goose migrations run through the writer while it is held to one connection; the query-only reader pool opens only after successful initialization. Startup error paths unregister the writer mapping and close both handles, including late failures after registration; the confirmation-secret initialization regression proves this cleanup contract. Initial `auto_vacuum=INCREMENTAL` transition may require a full pre-context `VACUUM`, so startup should warn before a potentially long rebuild. Later reclamation uses short bounded batches.
- Repository-wide SQLite writer-routing helpers live in the package-level `internal/repository/sqlite_write.go`, not in thread-input code: `RegisterDedicatedWriter`, `writeDatabase`, `execBoundSQLite`, `queryRowBoundSQLite`, `beginImmediateTx`, `beginImmediateConn`, shared executor interfaces, `manualTx`, and the shared `withImmediateTx(ctx, db, fn)` callback lifecycle. Connection-level cancellation and `busy_timeout` mechanics are shared from `internal/database/sqlite_busy.go`. These generic helpers centralize connection selection, bounded writes/`RETURNING`, transaction handling, and begin/callback/commit/cleanup behavior to prevent repository duplication and future drift. `TaskRepo` and `ThreadInputRepo` no longer define duplicate transaction wrappers, and unrelated repositories call the package helper directly rather than constructing `ThreadInputRepo` solely for transaction infrastructure.
- Pooled repository writes and write-with-`RETURNING` reads must use bounded same-connection helpers; transaction-owned executor variants stay caller-scoped. Cancellation-only contexts use short busy-handler slices and retry only ordinary `SQLITE_BUSY`; deadline contexts respect the deadline, and permanent errors are not retried. Temporary timeout changes must restore and verify `busy_timeout=5000` before pool release or discard the connection.
- `AttachmentRepo.Create` routes task-attachment `INSERT ... RETURNING` through the bounded writer-routing helper, so browser/server construction through the query-only reader handle persists correctly on file-backed databases; a public split-pool regression covers creation and readback.
- The previous repository/vacuum timeout-handling drift is resolved: both use `internal/database/sqlite_busy.go` for cancellation-aware timeout binding, restoration verification, idempotent cleanup, retry classification, bounded restore contexts, and physical-connection discard. Future SQLite lock-wait changes should stay on this shared boundary and retain cross-package held-lock/cleanup regressions.
- The bounded-writer invariant now covers repository mutations and write-with-`RETURNING` paths, including task-goal updates. Held-writer regressions cover deadline expiry, cancellation-only contexts, early cancellation, and timeout restoration; transaction-owned executor variants remain caller-scoped. A fresh read-only audit found no remaining task-goal lock-wait defect.
- High-cardinality deletion paths keep indexes for `alerts.execution_id`, lifecycle parent references, task/execution attachments, and pending-upload session IDs. Single-task deletion, bulk deletion, Chat clearing, and non-default project deletion share per-task cleanup; default-project deletion remains blocked.
- Attachment cleanup ownership is captured in the same transaction as cancellation/cascading deletion. Filesystem cleanup occurs only after relational commit. Pending publication and retirement use a process-wide session fence plus durable `retired_attachment_sessions` tombstones; retired client sessions return HTTP 409.
- Local storage migration preserves existing database, SQLite sidecars, repos, uploads, and runtime directories in `$HOME/.openvibely` when no override is set; `OPENVIBELY_DISABLE_LEGACY_STORAGE_MIGRATION` skips it. `OPENVIBELY_RUNTIME_DIR` is a deprecated `start.sh` alias only. Release binaries must not use checkout-relative paths such as `./openvibely.db` or `./repos`.

Worker and scheduling contracts:
- Unlimited global capacity is persisted as `worker_settings.max_workers = 0`; dispatch and follow-up admission treat it as unbounded, API serialization preserves `0`, and Settings displays “Unlimited.” Existing finite limits are not migrated to zero. There is no environment override.
- Follow-ups reserve global and project capacity atomically before provider execution. Browser project-limit saves reject malformed, negative, nonnumeric, and out-of-range values; omitted/empty/`0` deliberately clears a project-specific cap. Chat/channel `create_project` and `update_project_settings` enforce project limits `1..10` before side effects or persistence.
- Repeat intervals have the bounded-positive `1..365` contract for every recurrence unit across browser, repository, Automation, runtime, and channel paths. Open bug `#116` remains for direct schedule handlers that coerce malformed/overflow intervals or surface unsupported recurrence types as repository errors instead of controlled HTTP 400 responses.
- Schedule creation is normalized through `ScheduleActionService.CreateForTask`; browser routes use absolute-time forms while runtime/channel methods retain HH:MM contracts. A one-time schedule for a terminal task resets it to pending unless it is running; newly created schedules initially use `NextRun=RunAt`, including past recurring `run_at` values.
- Schedule rendering uses compact `LLMConfigRepo.ListBadgeOptions`; full model hydration is reserved for execution, editing, credentials, and persistence. Browser/API/runtime schedule mutations enforce project ownership and shared redirects preserve project scope. Capacity response fields use one canonical mapper while endpoint-specific inputs remain explicit.

OAuth and hosted deployment:
- OAuth initiate/callback URLs resolve absolute origins from `APP_BASE_URL` first, then forwarded/request host. `OAUTH_REDIRECT_MODE` controls provider callback URI, not browser launch; `auto`, `hosted`, and `localhost_manual` retain distinct semantics. Hosted workspace provisioning forces `localhost_manual` because built-in OpenAI/Anthropic OAuth clients require localhost callbacks.
- OAuth callback completion is centralized, consumes pending flow state once, and persists tokens only when provider, OAuth method, target, and config revision still match. Hosted SSO is server-only, uses explicit `hosted_sso`, validates canonical origins/instance/HMAC key, and requires one app replica per workspace while pending state is process-local.
- Hosted cookie construction is centralized with `HttpOnly`, `SameSite=Lax`, and configured `Secure` policy. Local-auth cookies retain their separate session-cookie contract. Hosted deployments use Docker Compose under `/docker/<project>/docker-compose.yml`, Traefik routing, and persistent `/data`; live Compose/image state must be checked before rollout.
- Local login `sanitizeNext` rejects raw backslashes and encoded `%5c` sequences before `Location` emission, preventing browser-normalized authority redirects while preserving ordinary internal paths.

Docker image direction:
- One server-and-coding-agent image is intentional because the server executes coding agents. It includes common Go, Node.js, Python, Rust, Java, Ruby, and C/C++ toolchains and excludes Podman/Buildah.
- The runtime user is `10001:10001`; mounted `/data` must already be writable by that UID/GID. `sudo` and setuid/setgid bits are removed after package installation. Non-root execution is defense in depth, not a complete sandbox.

Reflection and history:
- Reflection `hour`, `day`, and `week` are rolling windows based on current time; `day` means the last 24 hours, not a calendar day.
- Project changes prefer app-produced `task_commit_stats`; Git history is a fallback only for the true pre-stats range, merged with DB stats so early history is not dropped. Stats use scalar totals, newest-10 commit projections, capped category examples, and streamed changed-file scanning; malformed full JSON arrays contribute zero file/type counts.
- App-created commit recording covers task output, post-execution safety, dirty-worktree, merge/squash, conflict-resolution, rebase, and GitHub API publication commits. Fast-forward merges create no extra stat row. Generated artifacts or app-recorded commits later absent from the maintained branch are metric pollution, not source churn.
- Normal and GitHub-publication numstat paths share one parser for trimming, malformed/binary filtering, tab parsing, insertion/deletion conversion, path extraction, and scanner errors while retaining caller-specific deduplication and metadata.

Handlers, diagnostics, and local development:
- `internal/handler` is the Echo HTTP boundary; `handler.go` owns shared dependencies and route registration while feature files own task, project, chat, model, auth, integration, SSE, worktree, HTMX, and API behavior.
- Task Detail status polling uses a targeted project-aware Agent `id/name` projection and skips the lookup when no Agent is assigned. Full Agent hydration remains for initial forms, execution, lifecycle, skills, plugins, and MCP. Task-detail metrics use scalar `GetTaskExecutionMetrics` projections; deliberate history/detail paths keep full executions.
- Browser execution detail, review submission, lifecycle activity, and task-goal reads/mutations enforce task/project ownership and return controlled non-success responses without leaking prompt, output, error, selected-skill, memory, event, or foreign-goal data. Browser task-goal GET, set, pause, resume, and clear routes require a non-empty explicit `project_id` or selected-project boundary, resolve the task before invoking `TaskGoalService`, reject known tasks with neither context as `400`, and reject foreign or unknown tasks without goal leakage or mutation. Internal task-owned service workflows retain their task-ID contracts. Swagger is generated with `swag init` into `docs/`; user-facing guides generally live under `docs/`.
- `make dev` delegates to `air` and does not provide browser hot reload without `.air.toml`. Editing `.templ` requires `templ generate` or a watcher; Tailwind changes require a separate build/watch process.
- `make build`, `make build-desktop`, and `make run` share incremental generated-output freshness checks. Clean checkouts may seed missing stamps without running generators; malformed state, relevant source changes/additions/removals, missing outputs, or generator-version changes regenerate conservatively. Swagger freshness includes annotated API files, non-test model/viewmodel files, all non-test `internal/update` files, and the execution-repository schema. The uncached broad suite has a known baseline failure in `internal/handler.TestHandler_Schedule_NoViewportHeightOverflow` that also reproduces on clean `main`; validation must disclose it rather than claim the broad suite passed.
- Logging uses `internal/applog`: `Infof` for operational events and debug-gated `Debugf` for raw LLM/user content, high-frequency stream/SSE/diff/poll/routing traces, and provider diagnostics. `internal/util/json.go` centralizes fenced/balanced JSON candidate extraction and duplicate suppression; callers retain schema validation and repair.
