OpenVibely is an open-source Go application for automated task scheduling and AI-powered execution. The backend uses Echo v4, SQLite through `modernc.org/sqlite`, goose migrations, and a channel-based worker pool. The frontend is server-rendered with HTMX, templ, Tailwind CSS, and DaisyUI.

Server, desktop, and storage:
- `internal/server.Start(ctx, cfg)` wires the shared backend and returns the bound address, base URL, and shutdown handle. Server and desktop share `internal/server`; backend forking is not intended.
- The Handler owns the synchronized current X service. Shutdown and X reconfiguration must operate on the currently installed service; configuration-generation fencing prevents stale pollers from handling mentions or completing durable handoffs.
- Local web/server binaries default database, repos, uploads, and runtime state to `$HOME/.openvibely`; desktop uses `~/Library/Application Support/OpenVibely` on macOS, `%LOCALAPPDATA%\OpenVibely` with `%APPDATA%` fallback on Windows, and `$XDG_DATA_HOME/openvibely` with `~/.local/share/openvibely` fallback on Linux. Desktop uses `config.LoadWithMode(ModeDesktop)`, ephemeral `PORT=0`, local repo paths, and a Wails WebView pointed at the server base URL; hosted/Docker deployments use explicit env-driven storage under mounted `/data`.
- `OPENVIBELY_APP_DATA_DIR` is a literal override with no shell expansion; `DATABASE_PATH` still overrides the database path. `OPENVIBELY_RUNTIME_DIR` is only a deprecated `start.sh` alias. Packaged desktop binaries load `config.env` from the OS config directory, overridden by `OPENVIBELY_DESKTOP_CONFIG_FILE`.
- Desktop/Wails launches may not inherit shell `PATH`; centralized environment construction is authoritative. Safe external links use runtime markers and `/open-external`, and native dialogs are preferred when WebView upload behavior is unreliable.

SQLite and runtime state:
- File-backed production SQLite uses a dedicated `1W + 1R` topology after serialized bootstrap, incremental-auto-vacuum initialization, and goose migrations. The writer has one pooled connection; the reader is query-only. Isolated `:memory:` fixtures use one shared single-connection handle.
- Every physical file-backed connection receives foreign keys, a 5-second busy timeout, UTC datetime behavior, and preserved caller query/pragma parameters. WAL permits readers beside the single writer.
- Bootstrap and migrations run through the held writer before the reader opens. Startup failures unregister mappings and close both handles, including late failures; initial auto-vacuum conversion may require a warned pre-context `VACUUM`.
- Repository write and write-with-`RETURNING` paths use bounded same-connection helpers with cancellation/deadline-aware busy handling, timeout restoration verification, cleanup, retry classification, and physical-connection discard. Transaction-owned executor variants remain caller-scoped.
- The bounded-writer invariant includes task-goal updates and attachment creation.
- High-cardinality deletion retains ownership indexes for alerts, lifecycle parent references, task/execution attachments, and pending-upload session IDs. Relational attachment cleanup commits before filesystem cleanup, with session fences and retirement tombstones protecting late uploads.
- Local storage migration preserves databases, SQLite sidecars, repos, uploads, and runtime directories under `$HOME/.openvibely`; `OPENVIBELY_DISABLE_LEGACY_STORAGE_MIGRATION` skips it. Release binaries must not use checkout-relative storage paths.

Workers and schedules:
- Unlimited global capacity is persisted as `worker_settings.max_workers = 0`; dispatch and follow-up admission treat zero as unbounded and the API/UI display `Unlimited`. Global, project, and model capacity reservations are atomic and released on completion, failure, cancellation, claim failure, or panic.
- Project worker limits are `1..10`; malformed, negative, nonnumeric, and out-of-range browser/runtime values fail before side effects. Empty or zero clears a project-specific cap and capacity increases trigger dispatch; there is no environment override.
- Repeat intervals are bounded positive values `1..365` for every recurrence unit across browser, repository, Automation, runtime, and channel paths. Open bug `#116` remains for direct schedule handlers that coerce malformed/overflow intervals or mishandle unsupported recurrence types instead of returning controlled `400` responses.
- Open bug `#947` covers scheduled-task creation accepting an invalid or missing `run_at`: `parseScheduleForm` returns a raw `time.ParseError`, while `CreateTask` only aborts on `*echo.HTTPError`, so it can persist a task as `scheduled` without a schedule row, log the parse failure, and follow the normal success/redirect path. The schedule calendar's left join can expose the orphan as an unscheduled entry. The fix should reject the request before task persistence and add invalid/missing-`run_at` regressions proving no orphaned task or schedule is created; this is distinct from #116, #169, and #357.
- Schedule creation is normalized through `ScheduleActionService.CreateForTask`; browser routes use absolute-time forms while runtime/channel methods retain HH:MM contracts. A one-time schedule resets a terminal linked task to pending unless it is running, and new schedules initially use `NextRun=RunAt`, including past recurring `run_at` values.
- Grouped schedule movement is one project-scoped atomic request. It reloads current enabled rows inside the writer transaction, validates ownership and disabled members before writing, reconstructs local wall-clock fields across DST, changes only `run_at`/`next_run`, and rolls back on mismatch/error. Single-card rescheduling uses task-scoped ownership checks.
- Schedule rows own timing; linked tasks own execution assignment. `tasks.agent_definition_id` is the primary Agent and `tasks.agent_id` is the model config. `clear_context_on_start` is schedule-owned and non-destructive; new schedules default true.
- Automation claims/failures are crash-consistent: execution-bearing retry exhaustion terminalizes the bound execution, task, activity, invocation, outbox, and reservation atomically while cancellation remains authoritative; execution-free failures retain the visible terminal transition. Committed claims/failures publish project-scoped board invalidations through the shared SSE path. Eligible failed/completed Automation tasks may be reset during later admission.

OAuth, hosted deployment, and Docker:
- OAuth origins use `APP_BASE_URL` first, then forwarded/request host. `OAUTH_REDIRECT_MODE` controls provider callback URI; hosted workspace provisioning forces `localhost_manual` for built-in OpenAI/Anthropic OAuth.
- Callback completion consumes pending state once and writes tokens only when provider, method, target, and config revision still match. Hosted SSO is server-only with canonical-origin/HMAC validation and process-local pending state, requiring one replica per workspace.
- Hosted cookies are centralized with `HttpOnly`, `SameSite=Lax`, and configured `Secure`; local-auth cookies remain separate. Hosted deployments use Compose under `/docker/<project>/docker-compose.yml`, Traefik, and persistent `/data`.
- Local login rejects raw or encoded backslashes in `next` values before redirect emission. Authentication cookie format is versioned with subsecond expiry while legacy token verification remains supported.
- One server-and-coding-agent Docker image is intentional. It runs as UID/GID `10001:10001`; mounted `/data` must already be writable by that identity. The image includes common Go, Node.js, Python, Rust, Java, Ruby, and C/C++ toolchains and is not a complete sandbox.

Reflection, handlers, and ownership:
- Reflection `hour`, `day`, and `week` are rolling windows; `day` means the last 24 hours. Project-change stats prefer app-produced `task_commit_stats`, use Git only for the true pre-stats range, and scan changed files through shared numstat parsing with bounded projections. App-recorded commits cover task output, safety, dirty-worktree, merge/squash, conflict-resolution, rebase, and GitHub publication; fast-forward merges add no extra row, and generated artifacts later absent from the maintained branch are metric pollution.
- `internal/handler` is the Echo boundary: `handler.go` owns dependencies and route registration while feature files own task, project, chat, model, auth, integration, SSE, worktree, HTMX, and API behavior.
- Status polling, task metrics, detail lists, and the Schedule primary-Agent selector use compact project-aware projections where summaries suffice; deliberate execution/history/detail paths retain full hydration. The Schedule selector projection returns only `id`, `name`, and `model`, applies enabled/selectable/non-archived/generated/project-or-global availability predicates in SQL, and serves initial Schedule rendering, week-refresh HTMX responses, and schedule-origin task-create refreshes. Task Detail and configuration consumers retain full Agent reads.
- Active-task scheduler admission follows the same boundary: `SchedulerService.checkActiveTasks` reads compact `TaskRepo.ListActivePendingAdmissions` rows and submits routing metadata, while `WorkerService.dispatchNext` performs the authoritative full-task refresh. The projection preserves the existing exclusions, ordering, and swarm-parent routing; it does not change worker claim semantics.
- `UpcomingRepo` Pulse-list consolidation is implemented: `ListRunningTasks`, `ListPendingActiveTasks`, and `ListUpcomingScheduledTasks` retain explicit filters, ordering, schedule clauses, and method-specific error context while sharing canonical task/agent projections and a private query/close/scan helper. Bounded prompt previews, schedule hydration, and the `/upcoming`/`view_pulse` response shapes are unchanged. The change shipped for issue `#925` in PR `#929`.
- Browser execution, review, lifecycle, and goal endpoints reject foreign ownership without leaking prompt, output, error, skill, memory, event, or goal data. Task-goal browser routes require an explicit non-empty `project_id` or selected-project boundary before invoking `TaskGoalService`; internal task-owned workflows retain task-ID contracts. Swagger is generated with `swag init` into `docs/`.
- Insights project isolation is part of the analytics/control-plane contract; status/deletion ownership and `resolved_at` behavior are canonical in `usage_analytics.md`.
- Explicit task ID/title resolution is centralized in `internal/service/task_reference_resolver.go`: trimmed ID first, project-filtered title search, controlled missing/repository/foreign-project/empty-input semantics, and a schedule-only empty-project allowance. Web/channel `current` normalization remains adapter-owned.
- Lifecycle activity is project-scoped and prompt-safe, with keyset cursors, deterministic `(started_at DESC, id DESC)` ordering, a task/start index, compact single-execution rehydration, and durable `task_lifecycle_execution_changed` publication. Browser pagination/reconnect behavior and bounded gap continuation belong to `realtime_and_frontend_patterns.md`.

Diagnostics and development:
- The repository targets Go `1.27.0`. `go.mod` is the canonical module and CI version source (`go-version-file: go.mod`); the active explicit pins are `1.27.0` in `Dockerfile`, `Dockerfile-dev`, and the README requirement. There is no `go.work`, `.go-version`, `.tool-versions`, mise, or devcontainer Go pin in the checkout. The external Air development tool is pinned to `v1.67.4` in `Makefile` and `Dockerfile-dev`.
- `make dev` delegates to `air`; templ and Tailwind changes need their generators/watchers. `make build`, `make build-desktop`, and `make run` share conservative generated-output freshness checks, including Swagger inputs.
- Uncached broad-suite runs have recurring baseline failures such as server-bootstrap protected-agent/readonly-database setup and a clean-main schedule viewport test. Report exact failures with the narrower passing scope instead of claiming a broad suite passed.
- `internal/applog` uses `Infof` for operational events and debug-gated `Debugf` for raw LLM/user content and high-frequency stream/SSE/diff/poll/provider traces. `internal/util/json.go` centralizes fenced/balanced JSON candidate extraction; callers retain schema validation and repair.
