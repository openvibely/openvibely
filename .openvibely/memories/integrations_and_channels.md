OpenVibely integrates with GitHub, Slack, Telegram, Discord, Email, X, generic inbound webhooks, and outbound message targets. UIs separate discovery/add flows from management cards, show explicit configured/running/connected states, and use confirmed `Delete` actions. Configured provider cards participate in shared selection/removal; Outbound Target cards remain separate and non-selectable.

Shared channels:
- Channels bulk removal uses one `/channels/bulk` request. The server validates every selected provider and project-owned webhook, resets provider settings, deletes webhooks, and clears system-level Discord authorization in one transaction. Runtime teardown occurs after commit; failure rolls back without partial deletion or stale UI.
- `internal/service/channel_chat_ingress.go` owns reusable inbound flow for Slack, Discord, Telegram, Email, and X: attachments, compact model selection, active-Chat queueing, first-turn task/execution creation, reply context, broadcasts, history, runner invocation, and queued promotion. `chat_action_runtime.go` owns generic channel task/project/goal/thread/schedule/personality/model/Pulse/alert/capability actions; channel-specific handlers win by name.
- Inbound Chat uses compact text/vision model rows, hydrates only the selected full config before provider execution, and queues active-turn inputs with the selected ID. Channel Chat/task-thread behavior follows web/API queueing, steering, cancellation, goals, Agent, memory, and swarm contracts.
- `list_channels` returns compact prompt-safe status without credentials. Tool-incapable provider/auth paths receive no channel tools or bracket-marker fallback. Email and Slack receipts use atomic deduplication and durable execution/queued handoff.
- External-channel first-turn context uses a project-scoped compact task projection with bounded prompt previews and recursive chain fields, preserving filtering, ordering, tags, parent annotations, assigned model names, and schedule formatting without per-task queries. Active projected tasks with terminal failed/cancelled status normalize to Backlog through one guarded transaction, batch-cancel queued ordinary executions, publish category events, and reload only when rows moved.
- External-channel project selection is cached in live Slack, Discord, and Telegram services. Project deletion emits a post-commit observer notification that selectively evicts matching live cache entries; failed deletions preserve caches. Slack and Discord fence cache-miss population and overlapping successful switches with a service-wide generation plus serialized mutation publication. Telegram combines selective eviction with per-user version and service-wide deletion-generation fencing and serialized explicit switches. Startup- and settings-created Telegram services both receive durable selector-repo and project-deletion wiring. PR `#1267` implements compact selector resolution for the shared channel `switch_project` path (`#1254`) while preserving `list_projects` descriptions and switch persistence; a 2026-09-19 audit-only review found no material implementation issues, but verify merge/target-branch state before treating the gap as shipped/resolved.

Webhooks:
- Create/update/delete/rotate/test are project-scoped and validate ownership before side effects. Agent pickers include global and enabled/selectable same-project project Agents; foreign, unknown, disabled, archived, or non-selectable IDs fail closed.
- Create/update/test share normalized name, enabled, instructions, priority, template, and ordered Agent assignment. Omitted Enabled preserves disabled state; accepted true values include `true`, `1`, and `on`. Disabled endpoints return `403` without creating work. Zero-row delete/rotate returns controlled not-found without secret output.
- Compact cards omit prompts/templates, secrets, and Agent assignments; authorized dialogs lazy-load detail and disable Save until hydration. Webhook card order is SQLite `name COLLATE NOCASE`, then original name and ID; browser appends use the same ASCII-folded comparator. The supporting index must match both sort directions.
- Open gaps include review-gated Backlog intake (`#349`), webhook-as-Automation triggers (`#665`), selected-project ownership for all webhook routes (`#373`), spaced placeholder substitution (`#622`), and bounded evidence of the latest accepted inbound trigger/task (`#1034`).

X:
- X is a first-class X API v2 channel using OAuth 1.0a user-context credentials. It verifies `/2/users/me`, polls authenticated mentions, and posts replies/outbound messages only when credentials/account/API access permit. Incomplete credentials, unsupported operations, invalid targets, and provider errors fail closed.
- X persistence is project-scoped and stores authorized users, selected project, mention cursor, reply/origin metadata, originating account, and lease-based mention receipts with ownership tokens. Stale pollers cannot complete/release reclaimed leases. Omitted-category tasks use `created_via='x'` and complete `XTaskContext` before Active admission; explicit Backlog remains deferred.
- Settings use write-only OAuth fields; blank submissions preserve secrets. Candidate account/mention-read access is verified before one coherent commit. Cursor compare-and-set is guarded by account ID; configuration-generation fencing protects replacement/removal and shutdown.
- Mention identity and conversation metadata remain immutable through queueing, `send_to_task`, promotion, and streaming. Missing `tweet.author_id` fails closed before authorization/receipt handling. Mention removal is case-insensitive with full-handle boundaries. URL/length handling follows pinned `twitter-text` weighted behavior. Project-wide author lookup performance remains `#946`.
- Reply delivery uses durable `pending -> posting -> sent` state and structured outcomes. Stored reply text is retried without rerunning execution; provider-confirmed posts whose sent state fails remain non-retryable `posting`. Startup alerts on durable `posting` rows without reposting; missing context/unavailable services/persistence failures create actionable alerts.

Outbound targets:
- `send_message` is a project-scoped runtime tool for Slack, Telegram, Discord, Email, and X and records send audits. X uses `x:me`, rejects thread IDs, enforces 280 weighted characters, and uses stored task context for reply completion.
- Default policy requires a saved target or home target; arbitrary explicit targets require `send_message_allow_explicit_targets`. Targets are project-owned, support channel/user/chat/email kinds, reject duplicate platform/kind/destination/thread rows, and allow at most one Home per platform. Draft changes stage until Save; per-target Test is immediate and non-mutating.
- Home is a platform/project default destination, not inbound authorization or credential configuration. Cross-project IDs fail closed. Saved-target discovery and Channels outbound-target card refresh summaries should remain bounded/paginated while preserving send-mode resolution; verify target-branch state before treating implementation branches for `#1206` or `#1231` as resolved. Remaining gaps include delivery-history UI (`#853`), shared target form/test/runtime normalization (`#296`, `#496`), indexed lookup (`#535`), Discord target-kind collisions (`#667`), inherited explicit-target policy (`#1071`), and cancellation handling (`#183`, `#162`, `#195`).

GitHub:
- Trusted task PRs parse strictly as `https://{host}/{owner}/{repo}/pull/{number}` and must match selected host and persisted number. Enterprise references use the selected API base; repository identity comparison is case-insensitive.
- Chat and Automation share issue-action service core for inbox, authorization, reads/comments/labels, PR-associated and assigned-issue operations. GitHub runtimes use runtime tools rather than shell/API substitutes. Assigned-issue discovery requires Authorized Users or PAT owner, returns compact pages without bodies, hydrates likely candidates, searches existing work broadly, skips covered findings, and creates at most one new finding.
- Assignment to PAT owner/configured Authorized User is approval to implement; labels, existing PRs, and Automation mappings are not substitutes. The current project GitHub inbox is configured for Authorized Users `dubee` and `openvibely`; the PAT owner scan identifies `openvibely` as the PAT owner. Implementation tasks are visible Active work. PR creation/reuse requires matching repository, branch, head SHA, required `## Summary`/`## Validation` sections, and exact `Closes #<source issue>` provenance. Branch replacement validates the authoritative live linked PR is open before provider replacement or success persistence; closed, merged, missing, or otherwise non-open PRs preserve `published_head_sha` and `needs_republish`. Publication verifies live head/base/files/checks, issue linkage, review state, and `published_head_sha` before completion claims.
- Automation-bound tools cannot override selected project/host or post issue-status comments. GitHub workflow labels are unprefixed, such as `task-created`, `in-progress`, `blocked`, `needs-human`, and `pr-opened`; do not use `openvibely:`-prefixed labels. Branch replacement/destructive writes require current graph authorization. Review-feedback forwarding caches authorization only within one pass, filters self/bots first, and stops on lookup errors. Default plugin marketplace name/source pairs should stay centralized in `internal/agentplugins/plugins.go` so seeding and reset consume the same catalogue (`#1230`); verify target-branch state before relying on branch-local behavior. Remaining gaps include forwarding wrappers (`#167`, `#302`), ordinary versus Automation entry points (`#203`), plugin source normalization (`#425`), duplicate repository resolution (`#561`), title-only matching (`#741`), stale PR reconciliation (`#233`), remote pagination (`#1028`), GitHub inbox exact-provenance `create_task` dropping advertised auto-merge/target fields (`#1216`), reused task PRs missing the default closing issue body (`#1248`), and issue `#1215` title-collision reconciliation lacking a safe task ID/status after the constrained lookup path.

Provider behavior:
- Slack is allow-by-default without an authorized-user list. OAuth callback persistence validates bot/team identity before one coherent snapshot; post-token failures preserve prior manual-token configuration. Configured user-project writes commit before cache updates.
- Discord is deny-by-default and project-scoped. DMs and bot-mentioned guild/channel/thread messages are supported; REST token validity is not readiness, Gateway running/error is authoritative. Delete clears project authorized users.
- Telegram advances offset only after terminal handling or durable handoff; failed handoff is retryable and blocks later batch updates. Authorization is system-wide despite project selection. Rich Messaging V2 falls back from escaped MarkdownV2 to plain text only for known rejection; ambiguous errors stop to avoid duplicates. Do not restore the rejected Telegram Desktop macOS table fallback without renewed approval.
- Email is deny-by-default and project-scoped with IMAP/SMTP presets, authorized senders, attachments, and shared runner/queueing. Reply sessions use normalized sender/thread headers then subject hash; headers are sanitized within RFC limits and blank secret saves preserve credentials.
- Email receipt-first polling retains UID identity, bounded existence queries, grouped acknowledgement, durable handoff, and fail-closed retries. The poller uses an explicit run completion/generation fence: Stop cancels and waits for exit before teardown, reload starts a replacement only after the prior run exits, and cancellation is preserved through processing. Stale runs are rejected immediately before task/queued-input/receipt handoff and Store, with best-effort active-connection termination when supported.
- Filename-bearing inline MIME parts are attachments before body selection and are omitted from both body and attachment output when skipped.
