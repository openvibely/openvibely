OpenVibely has channel integrations for GitHub, Slack, Telegram, Discord, Email, and generic inbound webhooks. Integration UIs separate discovery/add flows from management cards, render explicit connection states, and keep destructive action language consistent as `Delete` with confirmation.

Durable channel direction:
- Supported channel integrations keep task-goal controls at parity with web/API chat where the surface supports them.
- Channel-origin Chat and task-thread behavior stays aligned with shared lifecycle, queueing, steering, cancellation, task-goal, agent-resolution, selected-memory, and swarm child follow-up routing rules. Canonical shared semantics live in `chat_thread_system.md` and `managed_memory.md`; this file stores integration-specific facts only.
- `internal/service/channel_chat_ingress.go` owns the reusable production inbound Chat flow for Slack, Discord, Telegram, and Email, including attachment staging/linking, model selection after downloaded/sniffed attachment classification, active-chat lookup/queue branching, first-turn task/execution creation, reply-context persistence, Chat Page broadcast, context/history assembly, runner invocation, and queued-chat promotion.
- Shared generic channel image validation, pending-session ID generation, unique temp filenames, MIME sniffing, and decoder imports belong in neutral channel ingress code rather than Slack/Discord/Telegram/Email-specific files.
- `internal/service/chat_action_runtime.go` centralizes generic channel runtime handlers for task creation/edit/execution, task goals, task thread viewing/sending, project switching/listing, schedule/personality/model/project utilities, channel completion, and shared alert/capability formatting. Its shared channel context/mode builder supplies repository-backed `get_current_project`, fixed orchestrate-only `get_chat_mode`, and channel-named unsupported `set_chat_mode` handlers for Slack, Telegram, Discord, and Email; each channel still owns its `switch_project` authorization and active-project persistence callback.
- GitHub issue #229 is complete: `internal/chatcontrol.DecodeRuntimeToolInput` is the one production decoder for empty/whitespace normalization, JSON unmarshalling, and the exact `invalid tool input JSON: ...` wrapper across in-scope web Chat, automation Chat, channel, GitHub runtime, outbound `send_message`, `list_tasks`, and `list_schedules` action paths. Action-specific validation, authorization, response formatting, and intentionally separate provider-native, scoped-file, and bootstrap tool contracts remain outside this chat-action decoder boundary. Focused web, channel/service, and discovery regression coverage locks blank, whitespace, valid, and malformed inputs.
- Telegram, GitHub, Slack, Discord, and Email removal handlers share one ordered settings-reset helper. Required reset failures return a controlled server error without a successful Channels refresh/redirect, while each handler retains its explicit reset list and existing stop/disconnect and authorization lifecycle behavior. Slack removal preserves `SlackSettingBotTokenSource=oauth`. Discord removal always runs its explicit helper-based reset after local disconnect, whether the Discord service is present or unavailable, and clears the current project's authorized-user allowlist.
- Slack, Discord, Telegram, and Email authorization forms share two templ primitives: one owns the authorization fragment's container ID, empty/list branch, row/remove layout, confirmation, and modal-scoped target/swap wiring; the other owns hidden `project_id`, primary/display-name inputs, and Add wiring while deriving the Add target from that same container ID. Wrappers remain channel-specific for copy, identity formatting, endpoints, input semantics, parsing, validation, and repository behavior. Keeping the container ID in the shared list shell as the single source prevents Add/Remove target drift and ensures fragment swaps stay inside the open modal.
- Telegram, Slack, Discord, and (as of GitHub issue #252, PR #260) Email authorized-user/sender handlers delegate project-ID validation, list/load error mapping, create/delete orchestration, deletion project fallback, and post-mutation reload to a private handler-level `authorizedUserCRUD[T]` helper (`internal/handler/channel_authorized_users_handler.go`). Narrow channel callbacks retain transport-specific parsing and validation, model/repository adaptation, display-name defaults, error messages, routes, fragments, and templ rendering; this helper is intentionally not a broad cross-channel domain abstraction. Email's adaptation preserves `repository.NormalizeEmailAddress`, the `authorized_email_address` form field, and `components.EmailAuthorizedSendersList` while reducing `ListEmailAuthorizedSenders`/`AddEmailAuthorizedSender`/`RemoveEmailAuthorizedSender` to channel-specific dependency checks and identity parsing/validation callbacks.

Channel-specific handler maps, `Surface`, authorization, and active-project persistence callbacks remain at each integration; Email intentionally retains its partial handler-map filtering path. - Slack and Telegram runtime goal actions are wired through durable `TaskGoalService` behavior rather than surface-specific stubs.

The intended scope is one shared formatter while routing, settings, hydration, persistence, and transport delivery remain channel-specific, with parity tests across all four paths.
- Channel-origin `switch_project` must run through channel-specific runtime tools, not only the generic chat runtime, so project selection persists under the correct channel identity. Slack, Telegram, Discord, and Email pass channel runtime tools into shared channel Chat ingress; these tools authorize the target project, persist active project for the channel user/sender, and return same-turn semantics where the current turn continues in its already-selected project context while future messages use the new selection.

This ensures channel-specific actions such as Email `switch_project` persist under the correct channel identity.
- `send_message` is a first-class outbound channel runtime tool for Slack, Telegram, Email, and Discord. It sends through existing channel configuration/services, not duplicate credentials, and is backed by project-scoped saved outbound targets plus structured send-audit rows.

Outbound target facts:
- Outbound channel targets are distinct from inbound authorization allowlists. The default policy requires saved targets or a saved home target; arbitrary explicit targets require the project-scoped `send_message_allow_explicit_targets` setting.
- Saved outbound targets have durable `target_kind` values: `channel`, `user`, `chat`, or `email`. Slack/Discord user-DM destinations are first-class saved targets and route via `slack:user:<id>` / `discord:user:<id>` without depending on inbound Authorized Users.
- Backward compatibility remains: project-authorized Slack and Discord user IDs can still be used as outbound direct-message targets for that same project when no saved target exists, but non-authorized user IDs do not become outbound DM targets. A Slack/Discord user ID authorized in a different project must fail closed with a project-authorization error rather than falling through to explicit raw channel sending, even when explicit targets are enabled.
- In the Outbound Message Targets UI, `Home` marks a saved target as the default destination for that platform/project when a `send_message` request names the platform but not a specific saved target; it does not authorize inbound users or configure channel credentials.
- Outbound Message Targets is a permanent, always-visible safety-net card at the top of the Channels page. It behaves like other channel cards by opening editable controls when clicked, but the card itself must not expose delete/remove actions.
- The Outbound Message Targets edit dialog should match other channel dialogs with explicit Cancel and Save Settings footer actions. Dialog edits are staged: policy toggles, Add Target, and per-row Delete must not persist until Save Settings; Cancel, X, backdrop close, and ESC discard draft changes by reloading persisted state.
- The add-form target-type control should be platform-aware: Slack/Discord expose `Channel` and `User DM`, Telegram is fixed/labeled as chat/channel, and Email is fixed/labeled as email.
- Save Settings submits the full staged outbound-target list plus policy, reconciles it atomically for the project, closes the dialog on success, and refreshes the top card summary. Direct immediate add/delete outbound-target routes should not be exposed because they bypass the settings-dialog save contract.
- Per-target Test remains immediate and non-mutating. Draft targets can be tested before saving through a non-persisting draft-test path that sends only the fixed OpenVibely test message. Test progress/completion belongs inside the Test button rather than separate row banners or raw transport JSON.
- Outbound target names are optional. Multiple unnamed targets for the same project/platform are valid, while duplicate non-empty names remain invalid per project/platform and duplicate destinations remain invalid per project/platform/target-kind/target/thread.
- Outbound target reconciliation deletes omitted rows before upserting submitted rows so users can delete/save and later re-add the same destination without unique-constraint failures.
- Outbound Message Targets modal mutation fragments must stay modal-only and must not return the top-level card or `hx-swap-oob` card markup; the permanent top safety card refreshes separately after Save Settings.
- The shared Channels `htmx:afterRequest` JavaScript drives channel modal close behavior, webhook modal close behavior, and Outbound Message Targets close/reset behavior; request-path extraction must run before webhook/outbound branches and normalize query-bearing paths.
- The normal outbound-target save path enforces at most one Home target per project/platform by clearing existing homes before saving the new one. If duplicate homes are introduced outside the app path, `send_message` resolves the most recently updated home target.
- Outbound Message Targets handlers must enforce project ownership for saved target IDs. Save/update, delete, and test-send actions should only operate on targets owned by the resolved request project and should deny cross-project target IDs without dispatching messages or moving targets between projects.
- Outbound Message Targets per-target actions should preserve the displayed project context by including the displayed `project_id`, matching Delete/Add/Save/card refresh.

GitHub facts:
- Stored open task PRs are routed using a strictly parsed persisted `https://{selected-repository-host}/{owner}/{repo}/pull/{number}` URL; its host must match the selected project repository host and its embedded number must match the persisted PR number. Malformed, foreign-host, query/fragment-bearing, unsupported, or number-mismatched records are skipped without blocking later valid records. Parsed Enterprise PR references inherit the selected project's custom `APIBaseURL`. Fetch, repository-scoped deduplication, and persistence use each record's repository identity rather than the project's current owner/repository. Repository identities compare case-insensitively, and new identities are canonicalized to lowercase while remaining compatible with pre-existing mixed-case rows.
- `CreateIssue`, `GetIssue`, `CommentOnIssue`, and `AddLabelsToIssue` share one private authenticated JSON request helper that applies common GitHub headers and conditionally applies JSON content type; operation-specific validation, endpoints, payloads, and response handling remain at each call site.
- Interactive Chat handlers and task/Automation runtime services share a canonical GitHub issue-action request contract and a service-level core for common inbox, authorization, issue read/comment/label, PR-associated listing, and assigned-issue operations. Surface-specific decoders and task resolution remain in wrappers; Automation-only filtering/recording, trusted duplicate prevention, issue creation, PR handling, topology enforcement, and feedback forwarding remain outside the shared core.
- `GitHubIssueActionCore` uses shared private helpers for canonical request decoding, repository resolution across applicable issue actions, and optional assigned-issue postprocessing across both assigned-list paths. Preserve assignee validation order and repository input when changing this path.
- GitHub issue #233 tracks stale task-PR state: ordinary task PR records are not reconciled with GitHub after creation, unlike the Automation-only refresher. A PR closed or merged remotely can therefore still receive forwarded review feedback and be reported as reusable; the fix must refresh/reject stale closed PR records before feedback forwarding or reuse, with regression coverage for both paths.
- GitHub issue #167 tracks duplicated PR-feedback forwarding workflow assembly across interactive and Automation runtimes: both decode the request, resolve the repository, construct and invoke the forwarder, deduplicate forwarded task IDs, trigger task-promotion callbacks, and serialize the same result. The smallest safe consolidation is a shared service-level forwarding action core while retaining surface-specific authorization and adapter concerns; parity coverage should lock forwarding, deduplication, and promotion behavior on both paths.
- `github_open_pull_request` and `github_replace_pull_request_branch` runtime executors share one private target-resolution helper for task selectors, current-project ownership, project loading, and Automation repository validation while retaining mutation-specific decoding, destructive confirmation order, service options, and response shaping.
- GitHub issue #203 tracks redundant ordinary and Automation service entry points for opening pull requests and replacing pull-request branch heads: each Automation method is only an alias to the same private implementation, while runtime code branches on Automation context solely to choose between behaviorally identical names. The bounded consolidation is one service entry point per operation while preserving adapter-specific authorization and projection behavior.
- Shared GitHub paginated JSON reads in `internal/service/github_service.go` cover PR issue comments, reviews, review comments, assigned issues, and issue-to-PR cross-reference lookup. They own authenticated headers, API-error decoding, same-origin `Link` traversal, and cycle prevention; later-page errors fail the whole read rather than returning partial results, while endpoint callers retain mapping, filtering, and feedback sorting.
- `ListPullRequestFeedback` fetches PR issue comments, reviews, and review comments concurrently using one shared cancellable context and exactly three source goroutines. Each source retains independent pagination; empty reviews remain filtered; successful results are merged in fixed source order and stably sorted by `CreatedAt`; the first source error cancels outstanding requests and returns no partial feedback.
- The scheduled GitHub Dev Inbox treats assignment to the PAT owner or a configured GitHub Authorized User as approval to begin implementation; it does not require an `approved` label or an existing PR. Every run scans all configured Authorized Users and also scans the PAT owner when PAT authentication is available, then deduplicates by repository and issue number. It skips closed, duplicate, explicitly blocked/non-actionable, unexpectedly assigned, and already-active issues, and maintains one visible implementation task per actionable issue.
- Before creating implementation work, GitHub Dev Inbox runs must query the current project's `list_tasks` discovery action by issue number or URL and reconcile current issue-to-PR association evidence. Task state and issue labels alone do not prove whether work is active or integrated; task creation must wait until both task and PR evidence have been checked.
- The Dev Inbox orchestrator forwards authorized feedback from linked PRs before polling assigned issues and must not carry its own persisted task goal. Persisted completion goals belong on dispatched implementation tasks and continue through code changes, relevant build/tests, and opening or reusing the issue-linked PR.

- `resolveGitHubRuntimeTask` (in `internal/service/github_issue_runtime.go`, used by the hardened Automation-bound GitHub tool executors including `github_open_pull_request` and `github_replace_pull_request_branch`) resolves `task_id: "current"` to the trusted caller task ID from `AutomationExecutionFromContext`, failing closed with `task_id current requires Automation task execution context` when no execution context is bound. Reuse must reconcile stored records against live PR state and head, genuinely reopen or create/update a replacement linked PR, and never report success from stale stored state.
- `github_replace_pull_request_branch` is a separate destructive runtime tool for explicitly approved cleanup of a linked task PR's polluted ancestry; ordinary `github_open_pull_request` never rewrites history. Replacement requires the exact expected 40-character remote head SHA plus `confirm_history_rewrite:true`, an existing linked PR, a clean worktree checked out on the exact task branch, and uses the configured short-lived PAT/App operation token with one atomic `git push --force-with-lease=<ref>:<expected_sha>` of local `HEAD`. Before pushing, the service fetches the stored PR number from the resolved current-project GitHub repository and requires its live `head.repo.full_name` and `head.ref` to exactly match the resolved project repository and task worktree branch; lookup errors, missing PRs, fork/repository mismatches, and branch mismatches fail closed. A failed lease is never retried with an unguarded force push. The tool is exposed on web/API, task-thread, and initial/scheduled runtime paths but is not a Task Changes UI action.

- For API-backed PR publication, synthesize the remote branch commit from the task worktree's net diff against the remote GitHub base branch SHA/tree fetched via the Git refs/API, not the local base branch SHA. Genuine changes remain parented on the latest remote task-branch SHA and updated with `force:false`; after a non-fast-forward race, refresh the remote tip and repeat the tree-equality check before synthesizing another commit. First-publication races also require reconciliation: if concurrent publishers both observe an absent branch and one loses `POST /git/refs` with GitHub `422 Reference already exists`, refresh the newly created remote tip, compare its tree with the desired tree, and either succeed idempotently or fast-forward a genuine update. When there are no local changes and the remote task branch already exists, reuse the existing branch rather than synthesize a reset-to-base commit; first publication with no changes may create the absent branch at the remote base SHA, and a losing concurrent create must confirm the branch now exists and succeed without commits, ref updates, force, or history rewriting.
