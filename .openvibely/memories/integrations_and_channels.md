OpenVibely integrates with GitHub, Slack, Telegram, Discord, Email, X, generic inbound webhooks, and outbound message targets. Integration UIs separate discovery/add flows from management cards, show explicit configured/running/connected states, and use consistent confirmed `Delete` actions.

Shared channel contracts:
- Status badges share configured/running/connected classes and labels across providers, with intentional provider wording differences. Configured wins over a stored connected installation when the integration is not actually configured.
- `internal/service/channel_chat_ingress.go` owns reusable inbound flow for Slack, Discord, Telegram, Email, and X: attachments, model selection, active-Chat queueing, first-turn task/execution creation, reply context, broadcasts, history, runner invocation, and queued promotion. `chat_action_runtime.go` owns generic channel task/project/goal/thread/schedule/personality/model/Pulse/alert/capability actions; channel-specific handlers win by name.
- Shared channel code owns image validation, MIME sniffing, pending session IDs, unique temporary filenames, and decoder imports. Channel-origin Chat/task-thread behavior follows the web/API lifecycle, queueing, steering, cancellation, goals, Agent resolution, memory, and swarm contracts in `chat_thread_system.md`.
- Slack, Telegram, Discord, and Email support project-aware project creation/switch-after-create through active-project persistence. The fallback project is default, then first project, then empty; each channel retains its own authorization, cache, persistence, versioning, and error handling.
- `list_channels` returns compact prompt-safe status for GitHub, Slack, Telegram, Discord, Email, X, inbound webhooks, and outbound targets without credentials. It prefers aggregate auth counts and grouped target summaries. `view_pulse` is available to Slack/Telegram/Discord and not advertised to Email without explicit support. Tool-incapable provider/auth paths receive no channel tools or bracket-marker fallback.
- Email and Slack receipts use atomic deduplication and durable execution/queued handoff while retaining channel-specific identity and retry semantics. Channel task-creation callback assembly should stay shared while preserving platform callbacks.

Webhooks:
- Webhook create/update/delete/rotate/test operations are project-scoped and must validate ownership before side effects. Webhook Agent pickers include global Agents and enabled/selectable same-project project Agents; foreign, unknown, disabled, archived, or non-selectable IDs fail closed. Create/update/test share normalized name, enabled, instructions, priority, template, and ordered Agent assignment logic.
- Inbound and Settings `Test` should share task create/assign/submit logic while retaining separate authentication/parsing and UI responses. Compact cards omit prompts/templates, secrets, and Agent assignments; authorized edit dialogs lazy-load detail and disable Save until hydration.
- Missing/omitted Enabled preserves disabled state; enabled values include `true`, `1`, and `on`. Disabled endpoints reject authenticated inbound requests with `403` without creating work. Zero-row delete/rotate returns controlled not-found responses rather than a successful refresh or secret output.
- Open gaps: review-gated Backlog intake for less-trusted events (`#349`), webhook-as-Automation trigger resources (`#665`), selected-project ownership for all webhook routes (`#373`), and spaced placeholder substitution such as `{{ event_type }}` (`#622`).

X channel:
- X is a first-class X API v2 channel using OAuth 1.0a user-context credentials. It verifies `/2/users/me`, polls authenticated mentions, and posts replies/outbound messages only when credentials/account/API access permit. Incomplete credentials, unsupported operations, invalid targets, and provider errors fail closed.
- X persistence adds one unreleased `172_x_channel.sql` migration directly after public schema `171`. It stores project-scoped numeric authorized users, selected-project state, mention cursor, reply/origin metadata, originating account, and lease-based mention receipts with ownership tokens. Queued/first-turn ingress and receipt completion are atomic; stale pollers cannot complete/release reclaimed leases.
- Settings use write-only OAuth fields; blank submissions preserve secrets. Candidate account and mention-read access are verified before committing a coherent snapshot, and activation makes no second fallible provider call. Cursor compare-and-set is guarded by authenticated account ID; configuration-generation fencing protects replacement/removal and shutdown drains the installed poller. Same-account receipt overlap is retryable without cursor advance; polling failures mark disconnected with an error and successful polls restore readiness.
- Authorized mentions retain immutable author identity, conversation/reply metadata, account, and identity-sensitive runtime tools through queued inputs, `send_to_task`, promoted runs, and shared streaming. Missing immutable `tweet.author_id` fails closed before authorization/receipt handling and leaves the cursor retryable. Mention text removal is case-insensitive with full-handle boundaries and preserves prefixes, repeated mentions, punctuation, ordinary at-signs, and unusable usernames.
- X URL/length handling matches the pinned `twitter-text` behavior: URL entities use provider weighted length, preserve original text/ranges, account for Punycode expansion, split outer labels on ASCII `.`, normalize RFC 3490 separators within each label, and handle inner `xn--` labels, protocol-less paths, ports, and queries without overcounting. The open performance gap `#946` remains: unresolved mention authors scan every project and authorization index instead of using a user-keyed lookup, and do not persist the fallback selection.
- The X IDNA helper preserves empty inner segments produced by leading, consecutive, or trailing RFC 3490 separators within an ASCII-dot-delimited outer label, matching pinned `twitter-text`/`punycode.toASCII`; literal empty outer labels remain rejected and the complete normalized outer label remains subject to the provider length check. Regression coverage spans all three separator code points, URL entity ranges, direct outbound rejection, and completion truncation.

Outbound targets:
- `send_message` is a first-class project-scoped runtime tool for Slack, Telegram, Discord, Email, and X and records send audits. X uses configured OAuth account target `x:me`, rejects thread IDs, enforces the 280 weighted-character limit, and uses stored task context for reply completion.
- Saved targets are distinct from inbound authorization. Default policy requires a saved target or home target; arbitrary explicit targets require `send_message_allow_explicit_targets`. Kinds are `channel`, `user`, `chat`, and `email`; Slack/Discord user DMs are first-class and compatible same-project IDs may work without saved targets. Cross-project IDs fail closed.
- `Home` is a platform/project default destination, not inbound authorization or credential configuration. Targets are project-owned, optional names permit multiple unnamed rows, and duplicates are rejected by project/platform/kind/destination/thread. At most one Home exists per platform. Add/edit/delete/policy changes stage in the modal until Save; cancel/reload discards drafts. Per-target Test is immediate and non-mutating, including for draft targets using the fixed test message.
- Open gaps include delivery-history/read UI (`#853`), shared target form/test/runtime/persistence normalization (`#296`, `#496`), indexed home/name/target-thread lookup (`#535`), and Discord typed target-kind collisions (`#667`). Outbound cancellation contexts remain defective for Discord (`#183`) and SMTP (`#162`); attachment transfer does not honor context for Telegram (`#195`).

GitHub and autonomous SDLC:
- Stored task PRs are trusted only when strictly parsed as `https://{host}/{owner}/{repo}/pull/{number}`, matching the selected repository host and persisted number. Enterprise references use the selected API base; repository identity comparisons are case-insensitive.
- Chat and Automation share the issue-action service core for inbox, authorization, reads/comments/labels, PR-associated and assigned-issue operations. Automation retains filtering, provenance, duplicate prevention, and PR-specific behavior. GitHub runtimes use runtime tools rather than shell/API substitutes.
- Assigned-issue discovery requires configured Authorized Users or PAT owner, returns compact pages without bodies, hydrates only likely candidates, and reconciles existing work with one broad current-project task lookup per issue number/URL without lifecycle filters. Finder scans collect all stable pages, skip covered findings, continue searching, and create at most one new finding per run; labels alone are not implementation evidence.
- Assignment to PAT owner/configured Authorized User is approval to implement; no approved label, existing PR, or Automation mapping is required. GitHub implementation tasks are visible Active work. PR opening publishes the branch, records remote head SHA, verifies live open PR rows before reuse, ignores closed branch PRs, and requires matching branch/repository/head SHA.
- Direct/Automation tools share repository selection. Automation-bound tools cannot override the selected project or cross-host endpoint, and cannot post issue-status comments. PR creation requires `## Summary`, `## Validation`, and exact `Closes #<source issue>` provenance. PR publication is the only stale-origin mutation allowed after graph replacement; branch replacement/destructive writes require current graph authorization.
- Open gaps include review-feedback forwarding/wrappers (`#167`, `#302`), ordinary versus Automation PR entry points (`#203`), GitHub plugin source normalization (`#425`), duplicate repository resolution (`#561`), title-only task matching (`#741`), stale ordinary PR reconciliation (`#233`), and GitHub `list_tasks`/task discovery coverage. Live PR target/head/files/checks and issue closure must be revalidated before reuse or completion claims.

Provider-specific behavior:
- Slack is allow-by-default when no authorized-user list exists; removal preserves OAuth bot-token source while clearing other configured state. Shared Markdown completion duplication remains `#81`.
- Discord is a project-scoped deny-by-default bot/gateway integration. DMs and bot-mentioned guild/channel/thread messages are supported; non-DM messages must mention the bot. `channel` targets represent channel/thread IDs and `user` targets represent DMs. REST token validity is not connected readiness; Gateway running/error is authoritative. Delete clears the project's authorized users.
- Telegram polling advances offset only after terminal handling or durable handoff; failed handoff remains retryable and stops later batch updates. Messages without `From` are acknowledged/ignored. Project switches and `/start` persist before cache updates; generation fencing prevents stale cache writes. Authorization is system-wide despite project selection, username-only lookup uses a lowercased unknown-ID index, and attachments are cleaned on failure and byte-sniffed when MIME is vague. Rich Messaging V2 is default-on; rejection falls back to escaped MarkdownV2 then plain text, but ambiguous errors stop to avoid duplicates. The user rejected automatic table fallback for Telegram Desktop macOS 12.8 crashes; do not add it without renewed approval.
- Email is a project-scoped deny-by-default IMAP/SMTP channel with provider presets, authorized senders, attachments, and shared runner/queueing. Reply sessions use normalized sender plus thread headers, falling back to subject hash; `In-Reply-To`/`References` are sanitized and folded within RFC limits. Project switching revalidates mailbox authorization; preset app-password whitespace is normalized while custom-password internal spaces are preserved; blank password saves preserve the secret. Authorized senders are added only through explicit Add, not Save settings. Outbound new mail has app-owned `Message-ID`/optional subject and no reply headers; reply aliases allow `In-Reply-To`-only responses to resolve to the originating session. Receipt-first polling and grouped acknowledgement preserve retry, attachment, and handoff semantics. Inbound polling currently re-reads the configured mailbox address from SQLite once per unread message during self-address filtering even though `EmailRuntimeConfig` already holds it; issue `#983` tracks reusing the loaded value while preserving direct `ProcessIncoming` freshness/reload behavior.
