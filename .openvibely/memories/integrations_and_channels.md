OpenVibely integrates with GitHub, Slack, Telegram, Discord, Email, X, generic inbound webhooks, and outbound message targets. Integration UIs separate discovery/add flows from management cards, show explicit configured/running/connected states, and use consistent confirmed `Delete` actions. Configured provider cards can participate in shared selection/removal; Outbound Target cards remain a separate, non-selectable management surface.

Shared channel contracts:
- Channels bulk removal uses one `/channels/bulk` request. The server validates every selected provider and project-owned webhook, then immediately resets provider settings, deletes webhooks, and clears system-level Discord authorization in one transaction. Runtime teardown happens only after commit, so failures roll back without partial deletion or stale UI.
- `internal/service/channel_chat_ingress.go` owns reusable inbound flow for Slack, Discord, Telegram, Email, and X: attachments, model selection, active-Chat queueing, first-turn task/execution creation, reply context, broadcasts, history, runner invocation, and queued promotion. `chat_action_runtime.go` owns generic channel task/project/goal/thread/schedule/personality/model/Pulse/alert/capability actions; channel-specific handlers win by name.
- Shared ingress uses compact text/vision model rows, hydrates only the selected full configuration immediately before a provider turn, and queues active-turn inputs with the effective selected ID without a full lookup. Channel-origin Chat/task-thread behavior follows the web/API lifecycle, queueing, steering, cancellation, goals, Agent, memory, and swarm contracts.
- `list_channels` returns compact prompt-safe status for GitHub, Slack, Telegram, Discord, Email, X, inbound webhooks, and outbound targets without credentials. Tool-incapable provider/auth paths receive no channel tools or bracket-marker fallback. Email and Slack receipts use atomic deduplication and durable execution/queued handoff.
- External-channel first-turn Chat context uses a project-scoped compact task projection with bounded prompt previews and recursive chain fields instead of full task hydration. Slack, Discord, Telegram, Email, and X preserve filtering, ordering, tags, parent annotations, assigned model names, and schedule formatting with two project-scoped reads and no per-task queries. The SQL reconstruction matches Go `ParseChainConfig`/`encoding/json`, including case-insensitive keys, invalid scalar types, nested child chains, and duplicate-null semantics. Active projected tasks with terminal `failed`/`cancelled` status are normalized to Backlog through one guarded project-scoped transaction: candidate order uses the full-list `display_order, created_at` contract, backlog positions are assigned in that order, queued ordinary executions are batch-cancelled, and category events are published. A compact reload occurs only when rows moved, and regression coverage protects model-facing byte/order parity and absence of per-task update fan-out. On 2026-09-13, the exact issue #1112 candidate was narrowed to the five implementation/test files by removing unrelated sidebar source/generated changes, paired 20/300-task performance evidence was added, and a fresh strictly read-only audit of commit `45222801` found no material implementation, workspace, or requirement issues. PR/publication state was not established by that audit and remains separate evidence.

Webhooks:
- Webhook create/update/delete/rotate/test operations are project-scoped and validate ownership before side effects. Agent pickers include global Agents and enabled/selectable same-project project Agents; foreign, unknown, disabled, archived, or non-selectable IDs fail closed. Create/update/test share normalized name, enabled, instructions, priority, template, and ordered Agent assignment logic.
- Inbound and Settings `Test` share task create/assign/submit logic while retaining separate authentication/parsing and UI responses. Compact cards omit prompts/templates, secrets, and Agent assignments; authorized edit dialogs lazy-load detail and disable Save until hydration.
- Missing/omitted Enabled preserves disabled state; enabled values include `true`, `1`, and `on`. Disabled endpoints reject authenticated inbound requests with `403` without creating work. Zero-row delete/rotate returns controlled not-found responses rather than a successful refresh or secret output.
- Webhook card pages order by SQLite `name COLLATE NOCASE`, then original name and ID. Browser appends use the same ASCII-only folded key, original UTF-8 name, and stable identity; do not use Unicode/locale casing. The supporting index must match the filter and tie-break collations in both sort directions.
- Open gaps include review-gated Backlog intake (`#349`), webhook-as-Automation triggers (`#665`), selected-project ownership for all webhook routes (`#373`), spaced placeholder substitution (`#622`), and bounded evidence of the latest accepted inbound trigger/task (`#1034`).

X channel:
- X is a first-class X API v2 channel using OAuth 1.0a user-context credentials. It verifies `/2/users/me`, polls authenticated mentions, and posts replies/outbound messages only when credentials/account/API access permit. Incomplete credentials, unsupported operations, invalid targets, and provider errors fail closed.
- X persistence is project-scoped and stores authorized users, selected project, mention cursor, reply/origin metadata, originating account, and lease-based mention receipts with ownership tokens. Queued/first-turn ingress and receipt completion are atomic; stale pollers cannot complete or release reclaimed leases. Omitted-category runtime tasks persist `created_via='x'` and complete `XTaskContext` before Active admission; explicit Backlog remains deferred.
- Settings use write-only OAuth fields; blank submissions preserve secrets. Candidate account and mention-read access are verified before committing one coherent snapshot. Cursor compare-and-set is guarded by authenticated account ID; configuration-generation fencing protects replacement/removal and shutdown drains the installed poller. Same-account receipt overlap is retryable without cursor advance.
- Authorized mentions retain immutable author identity, conversation/reply metadata, account, and identity-sensitive tools through queued inputs, `send_to_task`, promoted runs, and streaming. Missing `tweet.author_id` fails closed before authorization/receipt handling. Mention removal is case-insensitive with full-handle boundaries and preserves ordinary at-signs and punctuation.
- X URL/length handling follows pinned `twitter-text` weighted URL behavior, including Punycode and RFC 3490 separators. The open performance gap `#946` is the project-wide author lookup across authorization indexes without a user-keyed index or persisted fallback.
- X reply delivery uses durable `pending -> posting -> sent` state and structured outcomes. Stored reply text is retried without rerunning execution; provider-confirmed posts whose sent-state persistence fails remain non-retryable `posting`. Startup reconciliation alerts on durable `posting` rows without reposting. Missing delivery context, unavailable services, and persistence failures create actionable alerts.

Outbound targets:
- `send_message` is a project-scoped runtime tool for Slack, Telegram, Discord, Email, and X and records send audits. X uses `x:me`, rejects thread IDs, enforces the 280 weighted-character limit, and uses stored task context for reply completion.
- Default policy requires a saved target or home target; arbitrary explicit targets require `send_message_allow_explicit_targets`. Targets are project-owned, support channel/user/chat/email kinds, reject duplicate platform/kind/destination/thread rows, and allow at most one Home per platform. Draft add/edit/delete/policy changes stage until Save; per-target Test is immediate and non-mutating.
- `Home` is a platform/project default destination, not inbound authorization or credential configuration. Cross-project IDs fail closed. Open gaps include delivery-history UI (`#853`), shared target form/test/runtime normalization (`#296`, `#496`), indexed lookup (`#535`), Discord target-kind collisions (`#667`), and effective inherited explicit-target policy (`#1071`). The latter must make display, status, and draft saving agree with runtime inheritance and avoid silently persisting a false override. Discord/SMTP cancellation contexts and Telegram attachment cancellation remain open (`#183`, `#162`, `#195`).

GitHub and autonomous SDLC:
- Stored task PRs are trusted only when strictly parsed as `https://{host}/{owner}/{repo}/pull/{number}`, matching the selected repository host and persisted number. Enterprise references use the selected API base; repository identity comparison is case-insensitive.
- Chat and Automation share the issue-action service core for inbox, authorization, reads/comments/labels, PR-associated and assigned-issue operations. GitHub runtimes use runtime tools rather than shell/API substitutes. Assigned-issue discovery requires configured Authorized Users or PAT owner, returns compact pages without bodies, hydrates likely candidates, reconciles with one broad current-project task lookup per issue number/URL without lifecycle filters, skips covered findings, and creates at most one new finding per run.
- Assignment to PAT owner/configured Authorized User is approval to implement; approved labels, existing PRs, and Automation mappings are not substitutes. Implementation tasks are visible Active work. PR opening/reuse requires matching repository, branch, and head SHA; publication records and revalidates live head/base/files/checks, issue linkage, review state, and `published_head_sha` before claims of completion. Provider-specific behavior:
- Slack is allow-by-default when no authorized-user list exists. OAuth callback persistence validates bot/team identity before committing one coherent settings snapshot containing token, OAuth source, bot/team identity, connection time, state cleanup, and conditional default-response setting; post-token failures preserve the prior manual-token configuration. Configured user-project persistence commits before mutex-protected cache update, so failed writes cannot leave a misleading cache.
- Discord is deny-by-default and project-scoped. DMs and bot-mentioned guild/channel/thread messages are supported; REST token validity is not readiness, and Gateway running/error is authoritative. Delete clears the project's authorized users.
- Telegram advances offset only after terminal handling or durable handoff; failed handoff remains retryable and blocks later batch updates. Authorization is system-wide despite project selection, with lowercased username lookup. Rich Messaging V2 falls back to escaped MarkdownV2 then plain text only for known rejection; ambiguous errors stop to avoid duplicates. Do not add the previously rejected Telegram Desktop macOS table fallback without renewed approval.
- Email is deny-by-default and project-scoped with IMAP/SMTP presets, authorized senders, attachments, and shared runner/queueing. Reply sessions use normalized sender plus thread headers, then subject hash; headers are sanitized/folded within RFC limits. Blank secret saves preserve credentials. Receipt-first polling uses bounded sequential 500-key existence queries and grouped acknowledgement while retaining UID identity, durable handoff, no-store behavior, and fail-closed retries. Filename-bearing inline MIME parts, including `text/*`, are attachments before body selection and are omitted from both body and attachment output when skipping incoming attachments. Issue #1139 is implemented in open PR #1149: each poll run has shutdown/lifecycle fencing, cancellation checks, production IMAP transport teardown when supported, and the poll context is preserved through inbound processing so stale work released from blocked IMAP operations cannot reach processing, receipt, queue/task handoff, or `STORE` side effects. `Start`, `Stop`, and reload transitions are serialized; every `Stop` fences and drains the captured run before publishing `running=false`, so concurrent `Stop` callers cannot return early and `Start` cannot install a replacement before the old run is fenced. Deterministic blocking-IMAP regressions cover stop, reload to a new account, removal, concurrent Stop, and Stop-versus-Start; focused ordinary and race tests plus `go build ./...` pass.
