OpenVibely integrates with GitHub, Slack, Telegram, Discord, Email, X (formerly Twitter), generic inbound webhooks, and outbound message targets. Integration UIs separate discovery/add flows from management cards, render explicit connection states, and use consistent destructive `Delete` language with confirmation.

Generic inbound webhooks:
- Open review-gated intake gap `#349`: inbound webhooks can create and submit Active tasks but lack a Backlog-for-human-review mode for less-trusted events.
- Open Automation-trigger gap `#665`: inbound webhooks are Channels integrations that create standalone Active tasks, but are not Automation trigger nodes/resources.
- Open project-boundary defect `#373`: webhook update/delete/rotate/test routes must enforce selected-project ownership for webhook IDs.
- Webhook Agent pickers return global Agents plus enabled/selectable same-project project-scoped Agents. Webhook create/update and shared inbound/Test task creation apply the same project-aware availability rules before mutation or task creation; foreign, unknown, disabled, archived, and non-selectable IDs fail closed without changing assignments. Legacy incompatible endpoint assignments cannot create tasks, while valid assignments preserve order and populate primary/complete task assignment rows.
- Webhook delivery and Settings `Test` should share private webhook task create/assign/submit logic while retaining separate inbound authentication/parsing and UI rendering. Create/update saves should share normalization for name, enabled, system instructions, default priority, prompt templates, and ordered Agent IDs.
- Webhook compact cards keep sensitive/detail-only fields, prompts/templates, secrets, and Agent assignments out of card attributes. Edit modals lazy-load authorized detail and disable Save until hydration succeeds.
- Open template substitution bug `#622`: webhook templates replace tight placeholders such as `{{event_type}}` but leave spaced forms such as `{{ event_type }}` verbatim.
- Resolved issue #914: the webhook create form's unchecked or omitted `Enabled` value is preserved by `parseWebhookEndpointForm`/`applyWebhookEndpointForm`; `HandleWebhookCreate` no longer overwrites it before persistence, so disabled endpoints render Disabled and reject authenticated inbound requests with `403` without creating or submitting work. Regression coverage also preserves enabled creation for `true`, `1`, and `on` values alongside existing CRUD, rendering, and inbound behavior.
- Resolved issue `#917`: `WebhookRepo.Delete` and `WebhookRepo.RotateSecret` inspect affected-row counts and return exported `ErrWebhookNotFound` for zero-row mutations; `HandleWebhookDelete` and `HandleWebhookRotateSecret` map it to controlled `404` responses, suppressing successful HTMX refreshes and rotate-secret output. Existing successful deletion/rotation behavior and project-scoped ownership remain unchanged. Regression coverage covers fabricated IDs, stale deleted endpoints, HTMX responses, and secret persistence; the fix was published in PR `#930`.

Shared channel direction:
- Channel Settings status badges use one shared configured/running/connected class/label contract across GitHub, Slack, Discord, Telegram, Email, and X, while provider adapters retain intentional wording differences. Configured state wins over a stored connected installation when the integration is not actually configured.
- Channels has a mixed replacement root: fixed provider and Outbound Targets cards are rendered beside the paginated webhook list. The root now opts into replacement-card scope across `[data-channel-type]`, so HTMX refresh snapshots and restores focus/anchors for fixed cards as well as webhooks, while webhook pagination counts, offsets, appends, and deduplication remain list-scoped to `#webhook-card-list`. The production-shaped Channels regression covers a focused GitHub `Disconnect` action through the root refresh path.
- X (formerly Twitter) is a first-class channel implemented against the X API v2 with OAuth 1.0a user-context credentials. It verifies the authenticated account through `/2/users/me`, polls authenticated mentions, and posts replies/outbound messages only when the supplied credentials and account/API access permit those operations; incomplete credentials, unsupported/unavailable provider operations, invalid targets, and provider failures fail closed. It reuses shared channel ingress, runtime-action, task/thread, and outbound-message contracts rather than using an isolated client path.
- X channel persistence is one unreleased `172_x_channel.sql` directly after public schema `171`; no X migration had been applied, so no hypothetical `172`–`174` repair chain is retained. It creates project-scoped numeric authorized users, revalidated project selection, reply context, durable mention cursor, reply metadata and originating-account binding on queued inputs/task context, and lease-based mention receipts with ownership tokens. Queued/first-turn ingress commits durable work and receipt completion atomically; stale workers cannot complete or release reclaimed leases.
- X settings use write-only OAuth credential fields with blank submissions preserving stored secrets; the Channels UI exposes explicit configured/running/connected status, connection testing, removal, polling interval, response-notification control, and project-scoped authorized mention authors. Candidate credentials/account and mention-read access are verified before a coherent settings snapshot is committed, and activation performs no second fallible provider call. Receipt leases have ownership tokens, queued/first-turn durable ingress and receipt completion are atomic, and server shutdown stops the currently installed service, including dynamically replaced pollers. Cursor advancement uses an atomic compare-and-set guarded by the authenticated account ID, so an in-flight poll from a replaced account cannot commit a stale cursor; a same-account lost cursor race is benign because receipt deduplication makes handoffs safe and the winning cursor remains authoritative. An overlapping same-account replacement poller that encounters an active receipt lease now treats the overlap as retryable without advancing the cursor or degrading the healthy replacement's readiness; account changes still fail closed. Routine same-account edits preserve the cursor even when it is intentionally empty, while first setup or an account change baselines safely. Polling failures mark X disconnected and retain an error while the poller remains live; successful polling restores readiness and clears the stale error. `TestConnection` verifies both `/users/me` and mention-read access, and configured-service failures render provider failure feedback rather than “not configured.”
- X settings use write-only OAuth fields with blank submissions preserving secrets. Candidate credentials/account and mention-read access are verified before committing a coherent settings snapshot; activation makes no second fallible provider call. Cursor CAS is guarded by authenticated account ID, same-account lease overlap is retryable, and replacement/removal is protected by a persisted configuration-generation fence. Poller failures mark X disconnected with an error; successful polling restores readiness. Immediate `send_to_task` and promoted task-thread runs carry identity-sensitive `RuntimeTools` through the shared channel runner. Missing immutable `tweet.author_id` fails closed before authorization/receipt handling and leaves the cursor retryable. Configure/remove installs verified candidates before polling, and receipt completion/handoff is fenced against stale pollers.
- Resolved issue `#941` in PR `#948`: `XService.processMention` now removes only the authenticated account's full-handle mention case-insensitively with handle boundaries, preserving longer/prefix handles, repeated mentions, punctuation, ordinary at-signs, and all text when the username is empty or unusable. Production-path `pollOnce`/handoff regressions assert prompt/message content plus one-task durable-receipt and cursor behavior; authorized handoff semantics remain unchanged. A fresh strictly read-only audit of published head `7112bf795faa8e2f9eef5020d3bd5c2cfdf3a1f3` found no material bugs, regressions, missing requirements, or scope violations; local `edd0cc5cf5bbf095ae2867ef69db415ba21a58bf` and the PR tree were identical, and no build or tests were rerun because the audit boundary was strictly read-only.
- Open performance issue `#946`: when an X mention has no cached project selection, `processMention` resolves the author by listing every project and issuing one authorization query per project. A disposable SQLite probe at 1,000 projects measured up to 1,002 SQL statements and about 898 microseconds per unresolved-user resolution; the fallback does not persist the selected project, so repeated mentions can repeat the fan-out. The issue proposes a user-keyed repository lookup while preserving explicit selection and fallback ordering; it is distinct from Telegram/Slack/Discord channel-auth findings.
- Channel-origin Chat and task-thread behavior stays aligned with web/API lifecycle, queueing, steering, cancellation, task goals, Agent resolution, selected memory, and swarm follow-ups. Canonical task/thread semantics live in `chat_thread_system.md`.
- `internal/service/channel_chat_ingress.go` owns reusable inbound Chat flow for Slack, Discord, Telegram, Email, and X, including attachment staging/linking, model selection, active-chat lookup/queue branching, first-turn task/execution creation, reply context, broadcasts, history assembly, runner invocation, and queued promotion.
- Shared generic channel image validation, pending session IDs, unique temp filenames, MIME sniffing, and decoder imports belong in neutral channel ingress code.
- `internal/service/chat_action_runtime.go` centralizes generic channel runtime handlers for task creation/edit/execution, goals, task-thread viewing/sending, project/list utilities including GitHub-backed `create_project`, schedules, personalities, models, Pulse, completion, alerts, and capabilities. Channel-provided handlers take precedence by name over generic fallbacks.
- Slack, Telegram, Discord, and Email channel runtimes support GitHub-backed `create_project` and `switch_after_create` through active-project persistence. The shared `fallbackProjectID(projects []models.Project) string` rule is default project, otherwise first project, otherwise empty; each channel retains its own saved-selection validation, authorization, cache, persistence, versioning, and error handling.
- The read-only `list_channels` action provides compact prompt-safe readiness for GitHub, Slack, Telegram, Discord, Email, X, inbound webhooks, and outbound targets without exposing credentials. Aggregate auth counts and grouped outbound-target summaries are preferred to materializing allowlists; webhook status may list endpoint names/IDs.
- Resolved issue #904: Web/API Chat and channel/scheduled Chat `list_channels` now delegate `ChannelTargetProjectSummary` mapping to shared `service.OutboundTargetStatusSummaryFromRepoSummary`; both preserve `total`, `configured`, initialized empty `by_platform`, nested `home`, `named`, and `by_kind`, while policy fields remain surface-local. Direct and channel regression coverage covers multi-platform/multi-kind and empty summaries; provider/status aggregation and the channel materialized-target fallback remain separate.
- Email and Slack inbound receipts share atomic receipt/deduplication and durable execution-or-queued-handoff mechanics while retaining channel-specific identity keys, polling behavior, and retry semantics.
- Channel task-creation callback assembly should stay DRY across Slack, Discord, and Telegram while preserving platform-specific callbacks.
- Slack, Telegram, and Discord advertise and execute read-only `view_pulse` through the shared service path; Email does not advertise it unless explicit handler support is added. Runtime-tool-incapable provider/auth paths receive no channel action tools and no bracket-marker fallback.
- `internal/chatcontrol.DecodeRuntimeToolInput` is the production decoder for chat-action JSON across web Chat, Automation Chat, channels, GitHub runtime, outbound `send_message`, `list_tasks`, and `list_schedules`.
- Open channel task-thread runtime gap `#326`: Slack/Telegram/Discord/Email runtimes receive a caller task ID but do not resolve `task_id="current"` or omitted task references through it. Open scheduled capability gap `#341`: scheduled tasks can advertise broader tools through `list_capabilities` than the executor allows.

Outbound message targets:
- `send_message` is a first-class outbound runtime tool for Slack, Telegram, Discord, Email, and X. It uses existing channel services/configuration and records project-scoped send audits.
- X outbound targets route through the configured OAuth user context, use the account target (`x:me`), reject thread IDs, enforce the provider's 280-character post limit, and use stored X task context for reply-to-tweet completion responses.
- Open visibility gap `#853`: send attempts persist project, destination, caller, preview, result, error, and timestamp, but Channels exposes only transient feedback and no project-scoped delivery-history/read path.
- Outbound targets are distinct from inbound authorization allowlists. Default policy requires saved targets or a saved home target; arbitrary explicit targets require `send_message_allow_explicit_targets`.
- Saved target kinds are `channel`, `user`, `chat`, and `email`. Slack/Discord user-DM destinations are first-class saved targets. Backward-compatible Slack/Discord user IDs work for same-project outbound DMs when no saved target exists; cross-project IDs fail closed.
- `Home` marks a platform/project default destination for platform-only calls. It does not authorize inbound users or configure credentials.
- Outbound Message Targets is a permanent Channels card. Its edit dialog stages policy toggles, Add Target, and per-row Delete until Save; cancel/X/backdrop/ESC discard drafts by reloading persisted state.
- Resolved issue `#902`: every saved outbound target has a per-row `Edit` action that hydrates the existing staged form, retains the persisted `target_row_id`, and stages friendly name, destination, thread/topic, Home, and default subject changes. Edited rows use the draft-test path until `Save Settings`; cancel/reload, add/delete, project ownership, normalization, duplicate validation, and one-Home-per-platform semantics remain unchanged.
- Per-target Test is immediate and non-mutating. Draft targets can be tested without persistence using only the fixed OpenVibely test message.
- Target names are optional; multiple unnamed targets are valid. Duplicate non-empty names and duplicate destinations per project/platform/kind/target/thread are invalid. Reconciliation deletes omitted rows before upserting submitted rows and enforces at most one Home per project/platform.
- Per-target actions must enforce project ownership and preserve displayed `project_id`. Open consolidation gaps `#296`/`#496` cover saved-target form, test-send, runtime resolution, and persistence normalization; `#535` covers indexed home/name/target-thread resolution; `#667` covers Discord typed target-kind collisions.

GitHub integration:
- Stored task PRs are routed only from strictly parsed persisted `https://{host}/{owner}/{repo}/pull/{number}` URLs. Host must match the selected project repository host and the embedded number must match persisted PR number; malformed, foreign, query/fragment, and number-mismatched records are skipped.
- Enterprise PR references inherit the selected project's custom API base URL. Fetch, dedupe, and persistence use repository identity case-insensitively.
- GitHub issue reads/comments/labels share authenticated JSON request helpers; operation-specific validation, endpoints, and payloads stay at call sites.
- Interactive Chat and Automation runtimes share the canonical issue-action service core for inbox, authorization, reads/comments/labels, PR-associated listing, and assigned-issue operations. Automation-only filtering, provenance, duplicate prevention, and PR behavior remain outside the generic core.
- Model-facing `github_create_issue` does not advertise `idempotency_key`. Manual tasks that reference existing issues use ordinary task/PR flow and do not need Automation issue-task provenance.
- Assigned-issue discovery requires configured GitHub Authorized Users or the PAT owner, returns compact paginated records without bodies, and hydrates only likely candidates through `github_get_issue` before creating work. Existing-work reconciliation uses one broad `list_tasks` lookup per issue number/URL with lifecycle filters omitted; maintained Automation snapshots require explicit update/edit/save or recreation to adopt corrected prompts.
- PR-filtered assigned-issue pagination validates page arguments before provider calls, removes PR-less issues before slicing, and exposes stable `returned`, `total`, `offset`, `next_offset`, and `truncated` metadata. Open discovery gap `#741` remains title-only `list_tasks` matching.
- Scheduled GitHub Dev Inbox treats assignment to the PAT owner or configured Authorized User as approval to implement; it does not require an approved label, existing PR, or prior Automation mapping. Workflow labels remain unprefixed, such as `task-created`, `in-progress`, `blocked`, `needs-human`, and `pr-opened`.
- Assigned-issue scans affected by truncation or unintended lifecycle filters must be reconciled against live GitHub/OpenVibely state. Workflow labels alone are not evidence of a usable implementation-task mapping.
- Open stale-PR gap `#233`: ordinary task PR records are not reconciled with GitHub after creation, so closed/merged remote PRs can still receive forwarded feedback or be reported reusable. Verify live GitHub PR/issue state and current task records before continuing or deduplicating inbox issues.
- Open duplication gaps include PR-feedback forwarding assembly (`#167`), PR-feedback runtime wrappers (`#302`), ordinary versus Automation open/replace entry points (`#203`), GitHub plugin source normalization (`#425`), and duplicate repository resolution before `TaskPullRequestService.OpenForTask` (`#561`).
- Direct and Automation GitHub tools share repository selection for explicit repo URL, selected project repo, endpoint scoping, and Automation-bound behavior. Automation-bound tools ignore model-supplied repo overrides for the selected project, allow same-host Enterprise repositories, and reject cross-host endpoint overrides.
- PR opening publishes the branch, records the published remote head SHA, live-verifies stored open PR rows before reuse, ignores closed branch PRs, and creates/reuses only when the live PR is open on the task branch/repository and `head.sha` matches the recorded published head.
- PR publication is the only stale-origin GitHub mutation allowed to use durable Automation issue-task provenance after graph replacement. Branch replacement and other writes require current graph authorization. Publication/review state is volatile: verify live target, PR head/file list/checks, issue closure, and task publication evidence before claiming completion.
- `github_open_pull_request` accepts `pr_body` on create, but existing-PR reuse may ignore it. Re-read the authoritative body after reconciliation; stale validation or benchmark claims are a handoff blocker. If no authorized body-only operation exists, report it rather than attempting unsafe publication or API mutation.

Slack:
- Slack uses shared channel ingress/runtime behavior and project-aware active-project persistence. Removal preserves `SlackSettingBotTokenSource=oauth` while resetting other configured channel state.
- Slack authorization is allow-by-default when no authorized-user list exists, unlike Email and Discord deny-by-default. Open duplication gap `#81` covers similar Markdown completion payloads in Slack and Telegram.

Discord:
- Discord is a first-class bot/gateway integration with Settings configure/test/delete UI, migrations, docs, and `discordgo`. Authorized-user enforcement is project-scoped and deny-by-default; entries use numeric Discord user IDs.
- Inbound Discord supports DMs and bot-mentioned guild/channel/thread messages. Non-DM messages must mention the bot; default channel IDs, free-response allowlists, and require-mention toggles are unsupported/ignored.
- Discord project switching persists active project per user. Failed persistence preserves prior cache/default state; nil repository path is in-memory-only. Attachments use shared channel flow with trusted CDN/media validation, image persistence, distinct duplicate filenames, and queued pending sessions.
- Discord replies preserve channel/thread/message/user metadata for queued promotion and completion callbacks. Outbound targets use `channel` for channel/thread IDs and `user` for DMs; thread IDs are destination channels, not reply message IDs.
- Open cancellation defect `#183`: outbound APIs discard accepted contexts, so pre-cancel/mid-send cancellation may not stop transport calls. Bare numeric targets resolve only as saved targets or authorized user DMs; unsaved explicit channels require typed `discord:channel:` syntax when enabled.
- REST token validation proves token validity only; connected status should require Gateway running and surface the last Gateway start error when configured but offline. Deleting Discord clears the current project's authorized-user list; modal Add/Delete controls update only the modal fragment.

Telegram:
- Telegram attachment and command behavior is project-aware and uses shared runner/queued task-thread paths. Startup-created and Settings-created services need equivalent shared-runner, AgentRepo, and queued-promoter wiring.
- Polling advances update offset only after terminal handling or durable execution/queued-input handoff succeeds; failed handoff remains retryable and stops later updates in the batch. Messages without `Message.From` are acknowledged and ignored before authorization/project selection.
- Active-project cache is synchronized; per-user generations prevent slow DB/default cache population from overwriting newer explicit switches. `/project`, natural-language switching, and runtime `switch_project` should share selection logic while preserving formatting.
- Explicit switches and `/start` default initialization persist before cache updates; failed persistence leaves persisted/cache selection unchanged. Authorization is system-wide despite active project selection; repository errors fail closed. Username-only authorization uses the lowercased unknown-ID index while retaining numeric-ID authorization and username backfill.
- Telegram cleans temporary attachments on post-download failures and byte-sniffs vague image bytes. Outbound `send_message` supports saved chat IDs plus optional topic/thread IDs.
- Telegram `Start`/`Stop` are nil-safe and serialized by one operation mutex; relaunch waits for old poller drain. Rich Messaging V2 is default-on; blank existing settings resolve enabled unless explicitly saved false. Disabled Rich V2 uses escaped MarkdownV2 then raw plain-text fallback; rich delivery falls back only on clear rich rejection, while ambiguous errors stop to avoid duplicates.
- Telegram Desktop for macOS 12.8 can crash on Rich V2 payloads beginning with GitHub-style pipe tables. The user rejected automatic table fallback; do not assume it without re-approval.
- Open attachment-ingress cancellation defect `#195`: attachment transfer uses `http.Get` instead of the processing context.

Email:
- Email is a first-class channel with IMAP polling, SMTP replies, provider presets, Settings UI, project-scoped authorized senders, inbound attachments, and shared runner/queueing behavior.
- Email reply context is durable: queued inputs and Email-origin Chat tasks preserve message/thread headers so SMTP responses remain threaded after async promotion/completion. Sessions are scoped by normalized sender plus thread root/message ID, falling back to subject hash when headers are absent.
- Inbound parsing captures `In-Reply-To` from IMAP envelope and MIME headers. Session keys prefer `References`, then `In-Reply-To`, then current `Message-ID`/subject. Authorization is project-scoped and deny-by-default. Address normalization is centralized in `repository.NormalizeEmailAddress`.
- Project switching authorizes normalized mailbox against target-project senders and persists selection per sender; saved choices are revalidated before fallback scanning. Preset-provider app passwords remove whitespace on save/load; custom-provider passwords preserve internal spaces. Blank saved-password submits preserve the stored secret.
- Authorized-sender controls persist only through explicit Add using `authorized_email_address`; Save Email Settings must not add a typed sender. Email booleans use DaisyUI toggle styling with checkbox semantics.
- Email outbound `send_message` sends new SMTP email without reply headers. Optional/default subjects are explicit; blank subjects default conservatively. Runtime config loads one coherent settings snapshot through `SettingsRepo.GetMany` per SMTP-reaching operation.
- Open SMTP cancellation defect `#162`: production SMTP calls block in `smtp.SendMail` without honoring context.
- Email reply headers sanitize printable angle-bracket message IDs, reject injection/control input, bound/fold `References`, and fold `In-Reply-To` within RFC line limits.
- Inbound attachments decode MIME, honor skip settings, byte-sniff/stage through shared ingress, support vision selection, link first-turn executions, queue pending sessions, and include text context. Empty-body messages with attachments are processed; empty-body/no-attachment messages are ignored.
- Receipt insertion is atomic with durable execution or queued-input writes. Existing receipts suppress duplicate work after interruption or IMAP `Seen` failure. Without `Message-ID`, receipts use mailbox `UIDVALIDITY` plus UID; invalid identity remains unread rather than falsely deduplicated.
- Receipt-first polling should fetch lightweight envelope/UID and bounded `Message-ID` metadata before receipt checks, fetch full MIME only for unresolved IDs, canonicalize UID-only fallback to a valid MIME `Message-ID`, replay results in search order, and preserve attachment, retry, durable-handoff, and grouped-acknowledgement semantics. This is distinct from open receipt-row optimization `#529` and implemented grouped acknowledgement `#858`.
- Outbound Email Chat/task replies generate app-owned `Message-ID` headers and persist project-scoped normalized-sender aliases so replies containing only `In-Reply-To` to an app-owned response resolve back to the original session.
