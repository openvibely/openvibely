Provider logic is isolated under `internal/llm` for OpenAI, Anthropic, Ollama, and OpenAI-compatible transports. Routing goes through `internal/service/provider_adapter.go` and shared contracts/normalization/streaming packages.

Normalized requests and selection:
- OpenVibely is converging all model-call behavior on a normalized provider request pipeline. Lifecycle preparation precedes request construction; selected memory/skills, task metadata, goals, follow-up data, attachments, and runtime tools become one `AgentRequest` rather than being reinterpreted by each adapter.
- `AgentRequest.Followup=true` is authoritative even with empty history. OpenAI, OpenAI-compatible, Anthropic, Ollama, and mixtures route zero-history follow-ups through Chat streaming while preserving follow-up prompt and `ChatSystemContext`. Initial worker tasks carry selected-memory context through `ProjectInstructions`; Chat/API follow-ups use `ChatSystemContext`.
- Direct utility calls such as architect, backlog, collision, insights, trend, and upcoming are direct-style model calls and do not run task/chat memory lifecycle unless deliberately redesigned. `OperationDirect` is a lifecycle hook step, not a coding turn; preserve the hook Agent prompt and omit shared coding-agent framing.
- Provider selection uses `LLMConfig.Provider`, `Model`, and `AuthMethod`, not model string alone. Normal task starts choose current `Task.AgentID`, then project default, then global default. Stored per-run/queued model IDs are history/accounting evidence, not immutable rerun assignment.
- Chat uses explicit `agent_id` when supplied; empty/`auto` uses complexity/vision routing, and browser `default` resolves project default before global default. Queued Chat inputs preserve the effective model ID. `Task.AgentDefinitionID` selects persona/system prompt/skills; task `agent_id` selects provider/model. Actual per-run model identity is stored but not shown in task-thread history (`#128`).
- Vision routing uses compact semantic rows with model identity/tier/default/provider/auth metadata and credential-presence flags, hydrating only the selected config. No-image/already-capable paths remain query-free. Secret exclusion, tier/default eligibility, empty-store `ANTHROPIC_API_KEY` fallback, and selected-model delivery are part of the contract.
- Runtime task creation uses compact model rows (`ID`, `Name`, `Provider`, `Model`, `IsDefault`, `AutoStartTasks`) and hydrates full configs only at provider execution. API Chat and shared inbound channel Chat follow the same compact-selection pattern; inbound channel context reuses the compact catalog, and queued inputs retain only the selected ID until promotion.
- System-agent model controls use the existing `agent_configs` catalog rather than changing provider transports or model definitions: the UI submits a selected configuration ID, lifecycle hook lookup hydrates that full config for provider/auth-aware execution, and older Agent rows containing provider-model slugs remain supported through a legacy fallback. Scheduled Skill/Memory maintenance tasks synchronize their `tasks.agent_id` to the system Agent's selected configuration, while empty selection preserves normal project/global inheritance.
- Model names/slugs are trimmed and validated; blank runnable values and case-insensitive duplicate names are rejected. Mixture is a virtual provider with its own stable identifier. CLI auth for OpenAI/Anthropic is retired; migrations normalize legacy rows and adapters reject `auth_method=cli`.

First-party providers:
- OpenAI supports Responses and Completions APIs. Responses `SendAgentic` performs Codex-style client-side history compaction for API-key and OAuth. GPT-6 Astra and GPT-5.6 Sol/Terra/Luna are supported; unknown nonblank first-party selections default to `gpt-5.6-sol`, while blank runnable values remain invalid. Astra supports `low` through `max` reasoning but not `none`, uses its 1.05M context metadata for compaction, and can use provider-native web search. Astra does not support configurable temperature, so its UI control is hidden and browser-form normalization clears submitted or stale values. Fast mode is not persisted/requested (`#295`); GPT-5.6 Cyber/Daybreak aliases remain gaps (`#602`, `#609`), and `gpt-5.3-codex` needs a bounded support audit.
- A bounded model-support audit uses an explicit prior-success cutoff and records only actionable support findings. The latest successful audit cutoff is `2026-08-31` (issue `#974`): Anthropic Fable 5.1/Mythos 5.1 and OpenAI GPT-6 Astra were already supported; voice-only releases remain outside the text/image Task and Chat contract; and Z.AI GLM-5.3-Flash remains tracked by `#911` without duplicate tracking.
- OpenAI GPT-Rosalind Research (`gpt-rosalind-research`), released `2026-09-08` for approved internal life-sciences organizations, is an access-gated reasoning-model support gap: the first-party OpenAI form currently normalizes an unrecognized ID to `gpt-5.6-sol`, preventing eligible accounts from preserving/selecting the exact model. Issue `#1135` tracks bounded first-class support through the existing OpenAI Responses Task/Chat path, without adding a transport, inferring undocumented controls, changing defaults, or broadening OpenAI-compatible/Ollama behavior.
- Responses Lite WebSocket state is conversation-, credential-, and account-scoped rather than global. It serializes compatible turns using `previous_response_id`, reconnects stale sockets once, then falls back to HTTP.
- Anthropic uses `ProviderAnthropic` and `pkg/anthropicclient` for API-key/OAuth calls. Supported IDs include Claude Opus 5, Sonnet 5, Haiku 4.5, Fable 5.1, and Mythos 5.1. Fable/Mythos stay selectable but are not recommended defaults; adaptive thinking is required and HTTP 200 refusals surface as unsuccessful results. Opus 4.1 is retired. OAuth refresh is shared by inference, Analytics, and the lifecycle refresher, while provider-specific refresh failures are classified without exposing response bodies.
- OAuth refresh failures confirmed as permanent, including `invalid_grant`, are represented by durable per-config reauthentication state. The `oauth_needs_reauth` field is persisted by migration 185, prevents repeated refresh attempts, and is cleared atomically by a successful revision-conditional token update. Models cards display `Reconnect Required`; settings/provider/auth changes clear the stale state along with credentials when appropriate.
- `ProviderOpenAICompatible` is a generic Chat Completions path for `/chat/completions`, separate from Ollama. It supports API-key or optional missing auth for local servers, base URL/transport/presets, streaming, provider tool calls/results, usage normalization, and extra header/body JSON. Protected fields such as `model`, `messages`, `stream`, and tools cannot be overridden by extra body values.
- Presets cover hosted gateways and local vLLM/LM Studio/SGLang/LiteLLM-style servers plus Custom OpenAI-Compatible; Ollama remains separate, uses `/api/chat`, defaults to `http://localhost:11434`, and accepts arbitrary exact custom model names. OpenAI-compatible discovery is best-effort through `/models/openai-compatible/available` with credentials in headers, and there is intentionally no manual Discover button. Unverified providers such as xAI, GitHub Copilot, native Bedrock/Gemini, and MiniMax are not surfaced without an explicit decision.
- Z.AI `GLM-5.3-Flash` support is incomplete (`#911`): preset/model fallback, image capability, function calling, 1M context, and required thinking controls are not fully represented. Ollama runtime tools remain unsupported (`#264`). Chat endpoint visibility for compatible/Ollama configs is an open prompt-safe UI gap (`#808`).

Mixtures and OAuth:
- `ProviderMixture` is a virtual `agent_configs` row with `mixture_config_json`. It fans out ordered non-mixture reference calls, appends private outputs only to the aggregator context, and streams only the aggregator's user-visible response. References receive no tools, normal coding prompts, task mutation context, or public output; the aggregator retains normal authorized tools. Compact `mixture_progress` events use the existing live channel.
- `LLMConfig.IsCallableMixtureSlot` rejects recursive, duplicate, missing, retired-CLI, hidden/internal/unknown, and non-callable rows. Mixture CRUD blocks invalid slots and deletion of referenced models; Ollama aggregators receive no inherited runtime tools or textual fallback.
- Model configuration deletion has global downstream impact: single and bulk deletion clear `tasks.agent_id` and historical `executions.agent_config_id` references for affected models. Current confirmation surfaces mixture dependencies and default-model reassignment but not a project-safe, read-only preview of affected tasks, schedules/Automation references, and provenance; suggestion `#1138` tracks this human-control gap.
- OAuth tokens live per `agent_configs` row, preserving independent freshness, rotation, and reauthentication state. `oauth.Manager` reloads the selected config, singleflights by provider/config ID, acquires a durable per-config refresh lease for cross-process coordination, and persists rotated tokens only when provider/auth context and `oauth_config_revision` still match. Provider 401 recovery reloads from DB and may persist rotated tokens; it does not reread disk/keychain/environment material. Built-in callbacks consume pending state once and write only when provider, OAuth method, target, and config revision match. Missing/blank access tokens fail before mutation; zero-row updates fail. Chat model cards expose OAuth status, but Chat readouts do not yet (`#695`). Repair commit `0a83d0b9` fixes manual completion for real provider-denial callbacks containing `error` and `state` but no `code`: it handles the denial before success-code validation, consumes a valid pending flow once, returns the fixed safe denial message, and rejects replay as expired/invalid state. A fresh strict read-only audit then found an Analytics sibling-isolation bug: `refreshAccountSnapshots` marked a shared `provider + OAuthAccountID` key seen before a fetch succeeded, so a first config needing reauthentication or otherwise failing could suppress a healthy sibling's independent fetch and display snapshot. Repair commit `eede5d32` defers failure persistence and account deduplication until a usable cached or successful sibling result, preserving independent credentials and reauthentication state; production-shaped OpenAI/Anthropic regressions cover reconnect-required and refresh-time permanent failures. The exact merged candidate was `acf292c1`, with `eede5d32` as first parent and current `main` as second. A fresh strict read-only audit found a non-forced cooldown-path defect: a recent persisted shared-account failure caused `refreshAccountSnapshots` to mark the grouping key seen and suppress a later healthy sibling. Repair commit `9dc42d5e` scopes failure cooldown to the originating OAuth config in both snapshot selection and traversal, and adds OpenAI/Anthropic coverage for a persisted reconnect-required first config plus healthy sibling under ordinary refresh. A fresh strict read-only audit of exact HEAD `9dc42d5e99ba1706074eb3a68f58c4ba38e560ee` found another material persisted-history bug: when a healthy sibling already has a still-fresh success snapshot while a newer failure snapshot exists for another config sharing the provider/account, the healthy sibling is treated as non-refreshing and marks the shared key seen; snapshot merging then lets the newer failure win, so Analytics can display failure instead of healthy cached account data. Repair commit `b47f844d` makes error-free account views outrank config-scoped failures for the same account while retaining timestamp precedence within the same success/failure class. Its production-shaped OpenAI/Anthropic regression verifies the healthy cached card and limits win without a provider fetch and that both configs retain independent credentials and reauthentication state. Validation passed through a clean committed worktree. A fresh strictly read-only audit of exact HEAD `b47f844d238ab1179be65ceca281a584292c0d3f` found a stale-account-identity race: a rejected revision-conditional account-ID write could leave Analytics using a stale in-memory config, allowing a still-fresh stale token to reach usage fetch and snapshot persistence. Production-shaped regressions cover reconnect and model-edit interleavings after identity resolution for both providers. Build, vet, zero-update template generation, repository and service suites, callback race coverage, focused Analytics regressions, and the CI-style all-package coverage suite passed with only the unchanged `TestValidateRepoPathsProjectionProductionPerformance` timing gate excluded. The worktree was clean. A fresh strict read-only audit of exact HEAD `f7508b68a2713e5ba1e78e9b3663921b9ea8fd22` nevertheless found a material historical-snapshot identity/generation defect: persisted snapshots are not bound to an OAuth config generation. After reconnecting a config from principal A to B, an identity-unavailable path can reuse A's fresh snapshot through `AgentConfigID` fallback, while a known B identity can cause an old A snapshot to be keyed/rendered as B; connected-state checks do not establish snapshot ownership. The next repair must prevent prior-generation snapshots from being reused or attributed to a new principal, with OpenAI and Anthropic regressions for unavailable and changed identities. The audit changed no workspace state and ran no validation commands; separate repair, validation, and another fresh strict read-only audit remain required.
- Analytics account-limit refresh groups and deduplicates fetches by provider account/workspace or organization identity for display and snapshot aggregation only. It never copies access tokens, refresh tokens, expiry, or reauthentication state between configs; account-ID persistence is an isolated revision-conditional field update. Distinct OpenAI principals sharing a ChatGPT workspace and distinct Anthropic principals sharing an organization therefore retain independent credentials, while stable identities can still render one account card.
- A lifecycle-owned OAuth refresh service enumerates refreshable OpenAI and Anthropic OAuth configs independently and runs after successful server startup on a periodic interval. It reuses the provider refresh manager and durable leases, skips configs without credentials or marked for reauthentication, honors cancellation during shutdown, and keeps Analytics account grouping separate from refresh scheduling.

Tools, retries, and streaming:
- Provider-native web search/fetch is provider-executed (`web_search`, versioned Anthropic raw-tool types), not local web tooling. Runtime tools are request-scoped and provider-generic with read/write classification; the web-only `request_user_input` tool follows this registry/payload path rather than using provider-specific or prose-marker fallbacks. Its web-Chat-only restriction must hold at both advertised-definition and execution boundaries: hiding it from task-thread definitions is insufficient while the handler can still accept a provider-emitted call on a web task-thread follow-up. Tool-capable transports are OpenAI API/OAuth, Anthropic API/OAuth, and OpenAI-compatible API-key Chat Completions; unsupported paths receive neither unusable definitions nor marker fallbacks.
- Shared runtime policy owns plan mode, orchestration chat, task follow-ups, defaults/filters, and `SkipDefaultTools`; adapters retain provider schema/naming and local read-only grants. Agent-definition built-in-tool grants also apply at both advertised-definition and execution boundaries: OpenAI, Anthropic, and OpenAI-compatible map local wire tools to Agent permissions, and combine Agent/default suppression with runtime policy without suppressing independently authorized runtime tools. Memory tools are request/tool-profile decisions, not global adapter defaults. Anthropic wire aliases canonical `skills_list` to avoid collisions with `skill_view`/`skill_manage`.
- Optional runtime-tool parameters should use standard schema semantics: include them in `properties`, exclude them from `required`, provide no `default`, and preserve their absence unless the model explicitly sends them. Provider adapters should pass raw JSON arguments through rather than synthesize zero values, strip schema-specific sentinels, or perform string replacement for booleans. Handler omission remains the no-filter/default path, and explicit non-null values retain their meaning.
- A request-scoped guard turns an identical exhausted-empty `list_tasks` retry into a `duplicate_noop` response with guidance; different parameters, mutations, errors, nonempty, or pageable results clear it. `read_file` returns `decimalLineNumber<TAB><source bytes>` so indentation remains exact. Scoped file tools select the longest configured scope prefix and preserve fallback, permissions, traversal, and symlink containment.
- Provider-local file/shell execution is centralized in `pkg/agenttools`; provider packages retain schemas and thin wrappers. Bash timeout policy is explicit: Anthropic defaults to ten minutes only without a positive timeout; OpenAI passes its configured policy.
- External HTTP retry policy is centralized in `internal/httpretry`. Streaming logical-turn retries reconstruct canonical requests, honor cancellation/backoff/Retry-After, and append visible output unless a caller explicitly resets it. Primary client and after-complete deadlines default to ten minutes. Hidden-thinking/tool-argument deltas reset inactivity; known streaming timeout gaps are `#54` and `#68`.
- Service-level Anthropic dispatch in `internal/service/provider_adapter.go` consolidates the shared OAuth/API-key eligibility check, low-level forwarding, and unsupported-auth fallback for `OperationDirect`, `OperationStreaming`, and `OperationTask` in one production path. `req.Operation` remains unchanged, so `internal/llm/anthropic/adapter.go` retains its direct, Chat streaming/history/follow-up, and task behavior; runtime-agent resolution, the `callProviderOnce` boundary, and unknown-operation rejection remain unchanged. Regression coverage exercises all three supported operations, preserves the original work directory and request fields, and proves unsupported auth and unknown operations make no provider call.
- The same service boundary currently repeats Agent-definition preflight work in `openAIProviderAdapter`, `openAICompatibleProviderAdapter`, and `ollamaProviderAdapter`: each resolves plugin runtime state and prepends the persisted Agent definition to both chat and project instruction contexts. The OpenAI-family adapters additionally override the model, while Anthropic performs its injection in a lower-level adapter. Issue `#1158` tracks the smallest safe local consolidation of only this shared preflight, excluding Anthropic injection, transport/operation dispatch, runtime-tool policy, and plugin MCP discovery.
- Service-level provider dispatch preserves normalized chat history for OpenAI, Anthropic, and OpenAI-compatible calls and now applies a provider-aware compaction controller. It estimates current input usage `U` across the complete normalized/provider-visible request, including provider/system prompt context, request-scoped runtime tool definitions, attachments, history, replay, and Agent prompt context; resolves model context window `W`, computes `auto_limit=floor(W*0.90)` and `effective_hard_limit=floor(W*0.95)`, and clamps configured thresholds to the automatic limit. OpenAI Responses and Anthropic native compaction remain first where supported; native summaries are surfaced for checkpoint persistence. When full `U` triggers compaction, native OpenAI requests carry a non-persisted force signal through the normalized request and model config, and OpenAI Responses invokes its existing native `/responses/compact` flow over prior history before appending the pending message or attachments, preserving native-first semantics and leaving the current request content unmodified. OpenAI-compatible requests use proactive token-budgeted local no-tools summarization, while recognized overflow and native unsupported/rejected/invalid/empty/failure cases fall back to bounded local summary without recursive compaction. Durable per-thread checkpoints are stored in `chat_compaction_checkpoints` (migration 181), restored on later turns/reloads, and merged with newer history. A warning-bearing latest-20-turn truncation is reserved for failure of native and local summary strategies, including a recognized context-length failure on the compacted retry. Focused regression coverage proves native OpenAI compaction is forced when non-history model-visible content contributes to `U`; implementation validation passed, and the fresh strictly read-only audit on 2026-09-12 found no material bugs, regressions, or missing requirements.
