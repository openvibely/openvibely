Provider logic is isolated under `internal/llm` for OpenAI, Anthropic, Ollama, and OpenAI-compatible transports. Routing goes through `internal/service/provider_adapter.go` and shared request/normalization/streaming contracts.

Requests and selection:
- OpenVibely is converging model calls on one normalized provider request pipeline. Lifecycle preparation, selected memory/skills, task metadata, goals, follow-up data, attachments, and runtime tools form one `AgentRequest` rather than being reinterpreted per adapter.
- `AgentRequest.Followup=true` is authoritative even with empty history. OpenAI, OpenAI-compatible, Anthropic, Ollama, and mixtures route zero-history follow-ups through Chat streaming while preserving follow-up prompt/context. Initial worker tasks carry memory through `ProjectInstructions`; Chat/API follow-ups use `ChatSystemContext`.
- Direct utility calls such as architect, backlog, collision, Insights, trend, and upcoming are direct-style calls and do not run task/chat memory lifecycle unless redesigned. `OperationDirect` is a lifecycle step, not a coding turn; preserve the hook Agent prompt and omit coding-agent framing.
- Provider selection uses `LLMConfig.Provider`, `Model`, and `AuthMethod`, not model string alone. Normal tasks choose current `Task.AgentID`, then project default, then global default. Stored run/queue model IDs are history/accounting evidence, not immutable rerun assignment.
- Chat honors explicit `agent_id`; empty/`auto` uses complexity/vision routing, and browser `default` resolves project then global default. `Task.AgentDefinitionID` selects persona/system prompt/skills; task `agent_id` selects provider/model. Runtime creation and inbound channels use compact model rows and hydrate full configs only at execution.
- Model names are trimmed and validated; blank runnable values and case-insensitive duplicates are rejected. Mixture is a virtual provider with a stable identifier. CLI auth for OpenAI/Anthropic is retired and rejected.

Supported providers:
- OpenAI supports Responses and Completions, API-key/OAuth, Codex-style history compaction, and provider-native web search. Current supported first-party selections include GPT-6 Astra/Sol/Luna, GPT-5.6 Sol/Terra/Luna, and GPT-5.3-Codex-Spark; unknown nonblank first-party IDs normalize to `gpt-5.6-sol`, while blank values are invalid. Astra supports `low` through `max` reasoning, not `none`, and has no configurable temperature. Durable prior-release coverage cutoff is 2026-08-31. Realtime/full-duplex voice models such as `gpt-live-1` via `v1/live/sessions` are outside the current text/task provider contract and need an explicit product/transport decision before normal model-support work. GPT Image 2.5 Sunburst/Flare support through the OpenAI Responses image-generation tool is a bounded Chat/Task artifact support gap tracked in `#1245`; keep it scoped to durable artifacts/attachments rather than a broad multimodal provider expansion. GPT-6 async function-tool support is narrow: only durable task/chat streaming executions with exact `gpt-6-astra`, `gpt-6-sol`, or `gpt-6-luna`, API-key/OAuth first-party OpenAI transport, and explicitly allowlisted read-only runtime tools may serialize `async: true`; non-GPT-6, non-OpenAI, OpenAI-compatible, mixture, fallback/unsupported transport, default local, side-effecting, and unallowlisted tools remain synchronous. The OpenAI adapter must expire due async rows, seed completed async results into the next Responses request, reclaim/re-execute authorized pending/running read-tool rows, mark no-longer-authorized or scope-mismatched rows stale, terminalize async rows on execution cancellation, cancel matching async tool calls from Automation task-cancellation transactions, and suppress async metadata in mixture aggregators. Documentation must keep the GPT-6 async-tool boundary explicit, especially excluding mixture aggregator/reference calls. Fast mode and some newer/access-gated aliases remain gaps (`#295`, `#602`, `#609`, `#1135`). GPT-6 steering/runtime-tool behavior for `#1202` should fail closed with `AstraSteeringUnavailable` rather than recording delivery/acceptance or consuming steering input after a terminal stream; verify target-branch state before treating branch-local behavior as available.
- Anthropic supports API-key/OAuth through `ProviderAnthropic` and `pkg/anthropicclient`. Current IDs include Claude Opus 5.5, Opus 5, Sonnet 5, Haiku 4.5, Fable 5.1, and Mythos 5.1; Fable/Mythos are selectable but not recommended defaults. Adaptive thinking is required and HTTP 200 refusals are unsuccessful results. Opus 4.1 is retired.
- `ProviderOpenAICompatible` is a generic `/chat/completions` transport, separate from Ollama. It supports API-key or optional missing auth for local servers, base URL/transport presets, streaming, provider tool calls/results, usage normalization, and extra header/body JSON. Protected fields cannot be overridden.
- Presets cover hosted gateways and local vLLM/LM Studio/SGLang/LiteLLM-style servers plus Custom OpenAI-Compatible. Ollama uses `/api/chat`, defaults to `http://localhost:11434`, accepts arbitrary exact custom model names, and does not support runtime tools (`#264`). Discovery is best-effort through `/models/openai-compatible/available` from the Models page. OpenAI-compatible discovery should be bounded with a 5-second budget, race non-OAuth fallback probes, preserve explicit `models_url` as a single probe, propagate request-context cancellation, and abort stale Models-page discovery requests. Models-page discovery cancellation must cover Base URL scheduling, request-identity changes, stale-response fingerprints, provider changes, explicit modal close, backdrop close, opening a new modal, edit-form population, HTMX success close after `#models-container` swaps, pending scheduled discovery timers, and active fetches. A strict read-only audit found no material implementation bugs for `#1263`/PR `#1281` in the inspected implementation, but prior PR head/branch metadata mismatches were outside that implementation audit scope; verify live target-branch/publication state before treating it as shipped. Unverified providers are not surfaced without an explicit decision. Z.AI GLM-5.3-Flash remains incomplete (`#911`).

Mixtures and OAuth:
- `ProviderMixture` fans out ordered non-mixture reference calls and gives private outputs only to the aggregator; only the aggregator response is user-visible and tool-capable. References receive no tools, coding prompts, task mutation context, or public output. CRUD rejects recursive, duplicate, missing, retired, hidden, unknown, and non-callable slots; Ollama aggregators receive no inherited runtime tools or textual fallback.
- Standard OAuth connections are implemented for OpenAI and Anthropic through `oauth_connections` plus an explicit `agent_configs.oauth_connection_id` link. A connection owns access/refresh credentials, expiry, stable account identity, safe provider display name, private strong-principal hash, reauthentication state, revision, and refresh lease state; model rows retain model settings and usage attribution.
- Existing OAuth configurations migrate into private connections with legacy duplicate credential fields cleared. Rows sharing the same provider and exact non-empty rotating refresh token are linked to one deterministic credential owner during migration; matching account IDs, model names, access tokens, display metadata, or provider account identity alone never auto-merge and cross-provider links are rejected.
- New models default to private connections, while sharing requires explicit linking. API-key models and custom OpenAI-compatible OAuth remain independent. Deleting a model preserves a still-referenced connection, deleting a linked connection is blocked, and account disconnect affects all linked models.
- Background refresh enumerates eligible connections once and coordinates by connection ID through singleflight and durable leases. Callback, refresh, reauthentication, account-identity, profile-identity, and Analytics writes require the expected connection revision and, where applicable, that the initiating model still references that connection. Linked callers reload their own model configuration after shared refresh.
- Background Anthropic profile resolution runs under a bounded 10-second per-connection lookup context inside the sequential refresh loop. A timed-out or slow profile lookup is ignored for profile adoption and must not block later OpenAI/Anthropic refreshable connections.
- Analytics rendering rebinds historical snapshots to a currently linked model that still owns the recorded connection generation before display-keying, deduplication, or error association. Legacy snapshots whose `AccountID` is the original model ID are sanitized before that rebind. Latest-snapshot queries partition supersession by provider and explicit `oauth_connection_id` for connection-bound rows while retaining legacy grouping for rows without a connection.
- Fresh migration `187` and existing-database repair migration `190` both consolidate only same-provider/exact-refresh-token duplicate owners. Snapshot migration translates only the removed/private owner's current generation onto the canonical current generation and forces other remapped snapshots to fail-closed revision `-1`, so stale OpenAI or Anthropic snapshot revisions cannot collide with the canonical current revision after credential consolidation. Migration `187` performs this translation before duplicate owners are deleted; migration `190` remains the repair path for databases that already applied the older split migration chain. Migration `193` adds connection-owned safe provider display names plus non-serialized strong-principal hashes and backfills only safe current-revision display names from snapshots, never principal evidence.
- User preference: avoid extra bulk-link confirmations for safe OAuth repair cases. Exact provider plus non-empty refresh-token matches are safe to consolidate automatically. Different refresh tokens are consolidated automatically only after live OAuth/profile resolution provides the same stronger same-user/account principal UUID evidence. Anthropic organization identity, display metadata, model names, provider account identity alone, access tokens, and emails are not safe credential-interchange proofs; ambiguous historical rows require at most one explicit account-level choice rather than per-model edits.
- Successful Anthropic OAuth callback and background refresh resolve current provider profile evidence and persist a safe connection display name immediately, so Edit Model account labels no longer have to wait for an unrelated Analytics refresh. If the provider supplies a strong same-user/account UUID principal hash, same-provider connections with that hash are adopted transactionally; organization-only or cross-user rows remain isolated.
- Models UI direction: standard OAuth account selection lives in Edit Model. The modal's `OAuth Account` dropdown should show the connection-owned safe provider profile display name when present, otherwise a current-revision account snapshot display name, otherwise `Anthropic account` or `OpenAI account`; it must not expose model names, linked-model counts, connection status suffixes, emails, account IDs, raw profile data, principal hashes, or credentials. Model cards should retain a direct OAuth action only for expired, disconnected, or reconnect-required OAuth models; healthy cards remain status-only and do not expose Reconnect or Disconnect account controls. Reconnecting any model should target that model's persisted OAuth connection and repair every model linked to that connection.
- Models page search should match text already visible on model cards. As of GitHub issue `#1239`, cards expose safe endpoint/account details but search omits those fields, so users cannot find configured models by visible server or account context. Automation graph node model selectors have a related but separate gap tracked in `#1251`: they should expose provider and endpoint/account context so recurring task/schedule model choices are distinguishable.

Tools, retries, and compaction:
- Provider-native web search/fetch is provider-executed, not local web tooling. Runtime tools are request-scoped and provider-generic with read/write classification. Tool definitions and execution enforce the same surface/authorization boundary; unsupported transports receive neither unusable definitions nor prose-marker fallbacks. `request_user_input` is web Orchestrate Chat-only.
- Shared runtime policy owns Plan, Orchestrate, task follow-ups, defaults/filters, and `SkipDefaultTools`; adapters own wire schema/naming and local read-only grants. Agent-definition grants are checked at both advertisement and execution. Optional schema parameters belong in `properties`, not `required`, have no synthetic default, and raw JSON arguments pass through.
- Provider-local file/shell execution is centralized in `pkg/agenttools`. Bash timeout policy is explicit: Anthropic defaults to ten minutes only without a positive timeout; OpenAI uses its configured policy. Scoped file tools select the longest configured scope prefix and enforce traversal/symlink containment. `read_file` preserves exact source bytes after a decimal line number and tab.
- External retries are centralized in `internal/httpretry`; streaming retries rebuild canonical requests, honor cancellation/backoff/Retry-After, and preserve visible output unless reset. Primary and after-complete deadlines default to ten minutes. Known streaming timeout gaps are `#54` and `#68`.
- Provider-aware context handling is implemented in `internal/service/provider_adapter.go`. Budgeting resolves plugin/runtime state and Agent model overrides before accounting; shared accounting covers provider-visible instructions, default/runtime tool schemas, attachments, history, native state, pending input, reserved output, and safety margin.
- Final serialized-request preflights exist for OpenAI Responses, Chat Completions/OpenAI-compatible, Anthropic continuation paths, and Ollama dispatch. Ollama uses a conservative enforced 8k fallback for arbitrary models, honors configured `ContextWindow` through `num_ctx`, and aligns reserved output with `num_predict`; `gpt-5.3-codex-spark` maps to a 128k budget.
- Native compaction preserves provider and transport affinity: OpenAI Responses v2 uses the active reusable WebSocket where supported and streamed HTTP `/responses` otherwise, applicable legacy API-key configurations use `/responses/compact`, Anthropic preserves native `context_management` and structurally replayable compaction-block state, OpenAI-compatible and Ollama summaries stay on configured adapters, and Mixture resolves/pins concrete routes before budgeting and immediate continuation.
- Native-compaction capability decisions validate concrete provider, model, authentication method, protocol/transport, and endpoint before consulting the configuration-scoped cache keyed by provider, model, endpoint, transport, authentication method, and account/key identity. Opaque checkpoints persist a hashed compatibility key and are not restored across incompatible configurations.
- Context decision/failure observability is content-free and should include transport, budget components, strategy, externalization, retained/removed history counts, retry-source execution ID, and typed failure category. Immediate and queued failed retries propagate retry-source identity into the normalized request.
- Shared Agent-definition preflight is centralized in the private `prepareAgentRuntimeRequest` helper in `internal/service/provider_adapter.go`. OpenAI, OpenAI-compatible, and Ollama use it for runtime-definition resolution, selected-plugin merge, and injection into both `ChatSystemContext` and `ProjectInstructions`; Anthropic retains lower-level injection ownership (`#1158`). Anthropic service-adapter routing for Direct, Streaming, and Task uses one shared eligibility/forwarding path.
- Provider preflight should carry one request-budget snapshot through unchanged fallback-enabled checks, recomputing only after request-visible mutations such as checkpoint restoration, pending-input externalization, native/local compaction, retry replacement, or last-resort truncation. Fit checks and observability must remain paired with the refreshed request state.
