OpenVibely uses server-rendered HTMX/templ UI with shared SSE live updates. Durable UI rule: SSE announces that something changed; HTMX/server-rendered templ fragments remain authoritative state.

Realtime and rendering:
- Shared `/events/live` multiplexes task, Chat, mixture-progress, and file-change invalidations. Ordinary sidebar streams carry selected `project_id`, retarget on project/navigation changes, and add `task_id` on Task Detail when needed. Typed broadcasters route before fan-out to project/task buckets plus deliberate global subscribers; scoped clients receive only matching events.
- `/events/chat/:exec_id` is the token stream. SQLite is the durable reconnect source and `events.ExecutionStreamHub` carries hot deltas by exact execution ID with bounded subscribers, nonblocking slow-consumer drops, and terminal close. `window._tabVisibility` owns broad visibility and pauses polling while hidden.
- Terminal SSE follows durable writes: completed/cancelled map to `done`, failures to `error`, and missing output is replayed before terminal status. Subscribers are cleaned on cancellation/capacity failure. Periodic/final persistence prevents an older stream snapshot overwriting a newer terminal flush.
- Chat/task-thread streaming batches DOM updates and forces a final flush. Chat reconciles `streaming-message-<exec_id>`; Task Thread appends authoritative fragments. Start/input-applied events must not replace a fresh stream with a reload. Terminal reconciliation uses persisted status/output and preserves queued input/attachment indicators.
- File changes are invalidation/snapshot signals. `diff_snapshot` is metadata-only; browsers refresh authoritative Changes fragments. Changes is lazy unless `tab=changes`. Recoverable merge failures return refreshed fragments with retry guidance; genuine conflicts expose Resolve/Abort and hide ordinary merge actions. Worktree eligibility belongs in `worktree_and_lineage.md`.
- Completed/error bubbles use bounded raw content and one shared scanner/queue per page or fragment for Markdown/code hydration, sanitization, links, copy, pagination, and HTMX preservation. Large code-range work stays asynchronous until the owning render deadline; worker failure renders escaped plaintext.
- Task Detail non-poll thread pages use bounded task prompt and execution previews so the initial first non-follow-up bubble cannot expose the full `tasks.prompt`. The single-execution full-output action remains ownership-checked and lazy; its response carries a stable task-thread execution-bubble marker and after-swap rehydrates the live replacement through the shared assistant renderer.
- Analytics uses a server-rendered dashboard shell with six URL-persisted canonical views: `Overview`, `Outcomes`, `Agents & Models`, `Automations`, `Learning`, and `Usage`; `All Metrics` is intentionally absent. Shared filters and `history.replaceState`/`popstate` restore view state; project-scoped explicit links preserve `project_id`; supporting-record APIs fail closed without project scope; and scope-qualified Learning links preserve `skill_handle`, `skill_scope`, event, and Agent identity. KPI cards, funnel cards, and Chart.js visualizations are display-only: do not render KPI/funnel anchors, add `data-analytics-evidence-link`, or attach chart `onClick` handlers for drill-down/navigation. Tabs, filters, pagination, and explicit table/task/supporting-record links remain the intended Analytics interactions; Agent/Automation dimension changes use explicit filters/selectors and may reload data when the selected dimension changes.
- Dashboard requests include the active `view`; non-selected tabs load lazily; navigating away from Analytics aborts in-flight fetches. Overview avoids hidden evidence-total plus Outcomes-only follow-up-distribution work while preserving visible KPIs and recent rows. Analytics aggregate CTEs use narrow task/execution projections, workflow completion rates count all selected-period terminal invocations, and skill-outcome task evidence uses selected-period terminal counts plus period-aware goal eligibility/achievement. Analytics-specific data/current-state details belong in `usage_analytics.md`; exact-head publication constraints belong in `worktree_and_lineage.md`.

Composer, focus, and navigation:
- The shared composer owns send/queue/steer markup, authoritative OOB state, primary-action states, accepted-submit clearing, and lost-`409` retry; behavior is canonical in `chat_thread_system.md`. It also owns autofocus across full documents, HTMX/lazy content, and history restoration, using cancelable queued settlement and `preventScroll`.
- Focus requests decline when another meaningful control, dialog/menu, unsaved-change confirmation, or intentional history restoration owns interaction. A matching sidebar return is the narrow exception that permits new-composer focus after the `#main-content` swap; ordinary later swaps cannot steal focus. All listeners/timers are abortable and lifecycle-safe.
- Chat and Task Thread share an accessible `Latest message` button, shown only after intentional scroll-up. The keyed `ChatScrollTracker` owns return-to-latest, intent revisions, streaming fences, resize/mutation observation, HTMX/SSE replacement, lazy pagination, and history restoration. The button's wrapper owns centering; the button remains transform-free and pointer-enabled.
- Page titles come from server-rendered `PageTitle` markers. `window.openVibelyNavigate` handles programmatic navigation; history misses request full documents while ordinary HTMX requests remain fragments. Final transcript parsing treats LF/CRLF/bare CR equivalently, escapes raw HTML outside protected code, sanitizes URLs, and keeps malformed/example controls inert.
- Deep breadcrumb selectors are compact, project-scoped, bounded, and section-first rather than globally current-pinned. Search must still constrain results: if the typed query does not match the current task, the current task is omitted rather than pinned. Task selector results use DaisyUI-style grouping labels like task card/dropzone kebab menus: `Running` before `Recent` for empty selectors, and `Running` before other `Matches` for searched selectors. The current task stays selected and first only within its natural section/status bucket, so a running current task appears at the top of `Running` and a non-running current task appears at the top of `Recent`/`Matches` when eligible. Searched results reserve a matching current task within its natural bucket before applying the final bound, so a full running bucket cannot push out the selected non-running match; handler-side `limit+1` has-more trimming also preserves an eligible current task from the extra probe row by replacing the last visible row instead of slicing the current task off. `Recent` is an ordering label, not a fixed date window; it means the newest remaining eligible tasks after running rows, still bounded by the normal result limit. Ordering remains deterministic inside buckets (`updated_at DESC`, `id ASC` after search relevance where applicable, with current first inside its bucket). `from=schedule` requires live schedule membership, not stale task category, and keeps the same eligibility rules within that filter. Product direction: Task selector menus should make running tasks a fast navigation path from authoritative server-rendered status projection; a non-running current task may stay marked/current when eligible but should not hide the running list. Breadcrumb task selector rows remain authoritative server-rendered fragments; while the menu is open, shared `sse-task-event` invalidations debounce and retrigger the selector's existing HTMX `search` request rather than adding a separate live channel. Sidebar live SSE forwards task-goal events through the same browser task event path so goal-met icon changes can invalidate open selector rows. Breadcrumb task result rows show selected check, task status icon, then a truncating title; selector viewport/listbox/option rows must be width-constrained and avoid horizontal scrolling rather than relying only on the text span to truncate. Task breadcrumb switching preserves recognized return origins end to end: `from=schedule` keeps schedule-scoped results, while `from=chat`, `from=alerts`, and `from=automation` preserve return context without narrowing results; Automation origin also carries URL-escaped `automation_id` and `automation_name`, and unknown origins/unrelated query parameters are dropped. Current-state gaps: Review navigation still lacks visible Thread/Reflection links to execution details (`#365`, `#380`), and cancellation hard refresh lacks a matching explicit terminal marker (`#226`).
- Project and Task/Automation selectors share `SearchableSelector` markup/controller. The project trigger remains the compact DaisyUI select with its native arrow; the accessible searchable dialog is a fixed, clamped, direct-child panel with no header/close button. Breadcrumb selector dialogs should horizontally anchor to the opening pointer X so users do not chase menus whose trigger width changes with long names, while vertical placement remains trigger-based and keyboard opens use the caret/trigger fallback. Search is plain text with no custom clear control; local filtering uses direct input/search hooks and toggles both `hidden` and Tailwind `hidden`. Project options use `role=option`/`aria-selected`, preserve current selection when matching, and dispatch the existing hidden-select change.
- Project create/settings HTMX modal hosts must remain body-level siblings outside the sidebar/drawer layout context. Native `dialog` close/DaisyUI transitions can briefly leave the top layer; if the host is inside `#sidebar`/`.drawer-side`, project modals visually shift left during close while Task and Schedule page-mounted dialogs stay centered.

Cards, collections, and board:
- Card lists use `data-card-search` and `window.refreshCardSearches`. Refreshes preserve bounded search/window/anchor/focus state; pagination is silent when exhausted. Collection cards use an accessible loaded-items master checkbox, clear selection on query changes, exclude empty/ineligible cards, and reinitialize after root replacement. Active Agents, Models, Automations, Skills, and Alerts card-browser handlers share `renderCardBrowserPage` for the HTMX/fragment/full-page response shell and pagination headers while page-specific filters, data loading, side data, and templates stay local (`#1262`); a 2026-09-19 audit-only review found no material implementation issues, so verify merge/target-branch state before relying on it as shipped.
- Focusable catalog cards suppress pointer-only focus artifacts with `:focus:not(:focus-visible)` while preserving keyboard `:focus-visible` indicators. Automations and Skills can receive card-level focus during pointer interaction, unlike non-focusable Personality, Channels, Agents, and Models catalog cards, so shared catalog-card styling must handle both shapes without hard-coded theme colors.
- Filters use explicit `aria-expanded`/class state and close on repeat click, outside click, or Escape. HTMX/root replacement aborts requests and cleans timers/observers/listeners, then restores search, viewport, anchor, and valid focus. Sort restores absolute viewport position rather than following a reordered anchor.
- Repository-backed name sorting is case-insensitive with original-name and ID tie-breakers; Automation `updated_desc` uses timestamp then ID. Models/Personalities/Skills/Agents/Alerts/Channels begin with compact projections and lazy authorized detail.
- Automation cards are keyboard-accessible with meaningful names, visible focus, project scope, nested-action isolation, and repeat-safe Enter/Space. Destructive actions use one accessible dialog pattern, duplicate-submit protection, authoritative refresh, and focus restoration only when appropriate. Card action-menu/kebab dropdown shells should converge on a shared primitive while keeping page-specific actions local; verify target-branch state before treating branch-local `#1212` work as resolved. Secrets and sensitive metadata do not appear in compact attributes. Clipboard uses `window.openVibelyCopyText`; toasts use `openvibelyToast` and deduplicate by neutral keys.
- Reusable password-style `SecretInput` controls share `components.SecretInputVisibilityScript()` for reveal/reset behavior; Models and Channels include the shared helper once per page/fragment. The GitHub App private-key textarea remains a page-local masked-textarea variant with separate toggle/reset helpers.
- The Tasks Kanban supports grouped drag/drop, keyboard column controls, optimistic placement, authoritative reconciliation, generation/request fencing, rollback refresh, preserved selection/focus, and portaled Local/GitHub merge submenus. Native browser input is required for behavior evidence; synthetic events are supplemental. Failed merge/fast-forward/rebase/squash/PR actions use swap-safe authoritative refresh and retryable feedback. Board search is still missing (`#938`); Pulse has inconsistent failed-task actions/wording (`#866`).
- Pulse running and active-waiting cards expose an accessible confirmed Stop control only for current-project running, active `pending`, and active `queued` non-Chat cards. The narrow `pulse=1` adapter calls the established project-scoped `POST /tasks/:taskId/cancel` path, returns an authoritative upcoming-container refresh on success, and returns controlled no-swap feedback for stale or rejected cards.
- Pulse blocked work renders persisted `StatusBlocked` chain and swarm dependency tasks in a separate `Waiting for Parent` section with project-scoped non-Chat filtering, deterministic ordering, 200-character previews, compact runtime output, existing navigation, and read-only cards. The visible list is capped at 200 rows while the stat uses aggregate blocked counts when available.
- Task status icons are server-rendered from authoritative projections. `GoalMet` requires completed status plus an achieved persisted goal; merged status wins and goal never masks running/failed/cancelled/blocked states. Failed/cancelled rows are excluded from active dropzones. Task Detail Changes stays contained and Lifecycle owns its scrollport.
- Task status icons use the shared server-rendered `components.TaskStateIcon` templ primitive for task cards and breadcrumb task results. Breadcrumb selector task projections include status/category plus `merge_status` and achieved-goal state so selector rows render merged and goal-met icons consistently with task cards rather than using a running-only spinner or `data-breadcrumb-selector-running` marker. Running task spinners use the shared server-rendered `components.RunningSpinner(extraClass string)` templ primitive where a spinner is still intentional, such as the Pulse `Running Now` header; many other loading indicators still use inline DaisyUI `loading loading-spinner` classes.
- Automation YAML editor/read-only panels share two-space indentation, Shift+Tab dedent, line numbers, syntax highlighting, indentation rails, horizontal scrolling, and no wrapping/folding. Theme rules live in `ui_theming.md`.

Known UI constraints:
- `app_settings.ui.diff_view` is `inline` by default, accepts `split`, and normalizes legacy `unified`; only user toggles persist. Shared task/worktree action descriptors keep surfaces consistent.
- Schedule cards expose a right-click-only context menu for Delete, Pause/Resume, Run Now, and Edit Schedule. The schedule menu shell intentionally mirrors existing task-card dropdown spacing/styling (`menu p-2`, fixed card-menu width, normal `shadow`, and `z-[100]`) rather than using a smaller `menu-sm` variant. Menu actions reuse existing project-owned routes; schedule-page HTMX mutations refresh `#schedule-content` as the authoritative server-rendered state, destructive delete uses the shared accessible confirmation/duplicate-submit pattern, and Edit navigates to the existing Task Detail schedules flow rather than duplicating forms. Agents edit-modal lifecycle hydration fences JSON and hook responses by active agent and modal generation, gates Save until matching hydration completes, and invalidates pending loads on close/reopen (`#1160`).
- The Workers page lacks a per-dedicated-model waiting-work breakdown even though global and project rows expose queue counts; per-model rows show only running/limit/availability (`#1193`).
