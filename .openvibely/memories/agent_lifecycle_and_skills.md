OpenVibely agent and skill behavior is governed by the on-disk agent/skill catalog and lifecycle hooks; source code remains authoritative for exact implementation details.

Agents and skill catalog:
- Protected built-in agents include Skill Curator (`skill_curator`), Memory Curator (`memory_curator`), Goal Agent (`goal`), and Loop Agent (`loop`). Fresh-startup reconciliation must materialize them idempotently from bundled declarations. Protected reconciliation shares declaration mapping, persisted-field repair, and hook create/update behavior; MemoryService owns memory scheduling/legacy cleanup, while AgentLibraryMaintenanceService owns skill/agent roots and skill-library maintenance.
- Goal Agent is bundled under `internal/builtinskills/builtin/agents/goal/`; Loop Agent is a protected after-complete agent enabled only for dynamic-loop tasks. Agents are global/reusable by default; project-scoped agents/skills live under `<project_root>/.openvibely/agents`, global ones under the app/config agents root.
- Per-agent `SKILLS.md` is authoritative for skills, hooks, task loading, tools, enabled state, and declarations. Sync preserves `agent.enabled: false`; absent enabled metadata defaults true; archived generated agents remain disabled. Deleting a filesystem-backed non-protected agent removes its DB row, package directory, and `agents/AGENTS.md` section so sync cannot resurrect it. Protected agents are non-deletable in both UI and backend.
- Project-scoped agent skill routes reject foreign `project_id` before filesystem mutation; omitted scope uses the owning project root. Project Agent lifecycle-hook reads/writes, JSON hydration, and dialog mutations likewise enforce recorded `Agent.ProjectID`; global Agents remain portable and foreign requests return controlled not-found responses. Names are trimmed, blank-looking names are rejected, and enabled/selectable primary agents cannot have normalized case-insensitive duplicates. Disabled/non-primary duplicates remain allowed unless legacy ambiguity persists.
- Standalone skills are packages indexed by `<root>/skills/SKILLS.md` headings with matching `<root>/skills/<handle>/SKILL.md`. An indexed skill without its package body in the running checkout is unusable. Project scope overrides global scope; declaration caches must preserve precedence and restore globals when project declarations disappear. Explicit import/index maintenance is preferred over disk auto-discovery.
- `skill.enabled=false` disables routing, hooks, execution, `skill_view`, and context injection but remains visible to management. Routing reads bounded `SKILL.md` frontmatter; missing/malformed metadata defaults enabled, missing bodies are skipped on route-visible surfaces, and full bodies are reserved for detail/editor paths. Top-level `always_use` is catalog control data, not model-visible skill text.
- Lifecycle model-facing `agent_list` uses a repository-owned compact summary projection with identity/filter fields and SQL-derived ordered skill names; it does not hydrate full prompt/tool/plugin/MCP/permission/model/source JSON. `InspectAgent`, `agent_view`, and configuration paths retain full detail reads.
- Import normalization materializes YAML frontmatter with `name`, `description`, `kind: skill`, and `enabled: true` without clobbering valid fields. Browser dialog-to-declaration conversion is centralized; standalone saves reject agent-root declarations and agent-owned saves validate `agent.key` scope. `skill_import` is a write capability for skill/curation agents, not ordinary turns.
- Bundled GitHub/Native autonomous-SDLC bootstrap skills are disabled by default and startup sync overwrites stale enabled copies. Their prompts remain available for deliberate management; maintained Automation owns its own prompt snapshots. Per-agent materialization uses the Agent's recorded `ProjectID`, including warm-cache refreshes, and must not create a project-B tree under project A.
- Open gaps include duplicated plugin MCP resolution (`#806`), protected-agent plugin-install mutation bypass (`#846`), failed plugin materialization leaving cache directories discoverable as installed (`#937`), and marketplace import accepting manifest-controlled names that can escape the marketplace/plugin storage root and delete or overwrite unrelated plugin data (`#980`). Focused plugin and handler tests cover ordinary marketplace names but not malformed or path-like manifest names.

Project guidance and Skill Curator:
- OpenVibely's required root `AGENTS.md`, `CLAUDE.md`, `PRACTICES.md`, and `guardrails.md` artifacts were removed. Static project guidance belongs in `.openvibely/skills/openvibely_project_guidance/SKILL.md`, indexed by `.openvibely/skills/SKILLS.md`, and selected through top-level `always_use` rather than hardcoded routing.
- Skill Curator observes completed tasks through `observe_task_for_learning` and maintains the library through scheduled `maintain_skill_library`. Cross-agent improvements belong in standalone skills; agent metadata/tools/hooks/attachments remain user-managed and must not be changed by skill maintenance.
- Consolidation/archive requires the full safe package manifest from `skill_view`, including nested support files. If the manifest is unavailable, do not infer contents or archive. Assigned-agent updates are reserved for that agent's role/private workflow. The compact standalone `git_worktree_discipline` body intentionally leaves detailed recovery/orientation in support files. The OpenVibely-specific Go maintenance workflow is a companion to the global `update_go_deps` skill: generic repository dependency maintenance belongs to the global skill, while OpenVibely pins and validation remain project-specific.

Lifecycle contracts:
- Durable lifecycle concepts include `route_task`, `before_run`, `after_complete`, `scheduled`, task-mode bookkeeping, blocking/non-blocking hooks, idempotency/audit rows, recursion prevention, output contracts, and runtime-tool filtering. `route_task` precedes `before_run`; Skill Curator returns skill handles and Memory Curator returns memory handles. Built-in route hooks default non-blocking, but the runner waits for route-slot completion before the main model turn.
- Hook skill resolution is owner-scoped. Effective-mode logic has one primary Agent; multi-agent permission merging is not part of the design. Ordinary tasks may have no primary Agent, while maintenance/system agents are excluded from primary auto-routing.
- Hook declarations may include `payload:` context extras. Missing/empty payload means all slot-produced blocks. `extras.execution_error` reaches ordinary failed after-complete hooks even when undeclared and is absent on success. Explicit Stop/cancel suppresses optional detached hook/model work but still performs terminal bookkeeping, publication, capacity cleanup, and audit/logging. Non-cancel failures, including deadlines, still run detached after-complete hooks.
- Hook and task-mode final status writes use a fresh short-timeout context after model work so cancellation/deadline cannot leave rows `running`. Each hook persists sanitized input JSON and an `input_snapshot` event; the runner exposes durable execution-change notifications mapped to project-scoped `task_lifecycle_execution_changed` SSE events.
- Lifecycle output contracts constrain stored/validated final results, not working notes or tool use. Lifecycle activity is project-scoped and prompt-safe; browser/API ownership and pagination details are canonical in the architecture and realtime topics. Richer prompt-safe trace detail and selected-memory context remain evidence gaps.
- Selected lifecycle handles use catalog-owned `Catalog.EntriesForHandles`, which trims outer whitespace, skips blanks and unknowns, deduplicates the first valid occurrence case-sensitively, and preserves request order. `Catalog.Filter`, selected-skill prompt rendering, Skill Analytics selection events, and learning snapshots map over this projection; route-selection diagnostics and `MergeAlwaysUseIntoSelected` remain separate.

Goal, Loop, and maintenance behavior:
- Goal Agent is a generic detached after-complete evaluator that reconciles transcript evidence with the stored goal, then reloads/publishes current goal state. It must not parse keywords, apply deterministic completion logic, patch transcripts, replace raw output, or gain Goal-specific lifecycle fields without redesign.
- Goal tools such as `get_task_goal`, `send_to_task`, `mark_task_goal_achieved`, and `report_task_goal_blocked` are catalog/UI entries so grants survive saves. `send_message` is also cataloged; runtime availability depends on support/configuration.
- Loop wakeups are lifecycle-only continuations enqueued through durable `thread_inputs`, not direct worker submissions. They are blocked after goal achieved, paused, cleared, blocked, or failed. Lifecycle `send_to_task` rejects stale hook executions, cancelled tasks, and in-process cancellation markers; legitimate follow-up/admission paths clear stale markers.
- Scheduled maintenance is modeled as visible normal scheduled tasks. Fresh installs must idempotently create `System: Memory Consolidation` and `System: Skill Library Maintenance`, including without a default-project repo path. Reconciliation preserves timing, repairs `clear_context_on_start=true`, and must identify ownership beyond title alone; title-only matching can overwrite a user task and remains open as `#694`.
- Hook input and stored-task titles use prompt-safe wording without low-value internal prefixes such as `System:`. Lifecycle editing is for real hook slots, not `task_mode`. Agent dialogs hydrate persisted Advanced values, including unchecked `enabled` and `selectable_as_primary`, before saving.
- Open suggestion `#942` covers explicit per-hook model overrides, which are absent from persistence/save/editor and currently fall back to the hook Agent/project model. `#886` covers exposing routing-critical enabled/selectable/scope state on Agent cards.
- Canonical task-thread runtime and follow-up behavior lives in `chat_thread_system.md`.
