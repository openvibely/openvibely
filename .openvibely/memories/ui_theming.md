OpenVibely has a built-in theme system for application presentation preferences, including native OpenVibely defaults and imported VS Code palettes.

Durable theming contracts:
- `/themes` is the dedicated Themes page and is linked from the main sidebar navigation. It supports both full-page and HTMX fragment rendering, and project switching may preserve `project_id` only for shell consistency; the selected theme is browser/application state, not project configuration. Selecting a theme must update active-card state in place without reordering the catalog/cards, because active-first ordering is disorienting.
- The selectable catalog prepends two native first-party defaults, `OpenVibely Dark` (`openvibely-dark`) and `OpenVibely Light` (`openvibely-light`), before the imported VS Code themes. These are the bundled default/fallback theme IDs and should restore the original pre-VS-Code-theme OpenVibely palettes and styling path, not approximate VS Code/DaisyUI replacements: Dark uses `#191E24` for the page/content canvas, `#1D232A` for sidebar/cards/modals/inputs, and `#15191E` for the original dark base border; Light uses `#F5F5F5` for the page/content/root canvas and `#FAFAFA` for sidebar/cards/modals/inputs. The legacy footer `data-theme` light toggle path should explicitly paint the `html` root, `body`, `.drawer-content`, and `#main-content` with the light canvas so switching from dark cannot leave a black page background behind non-panel content.
- Built-in VS Code themes are imported offline from the open-source `microsoft/vscode` repository pinned at tag `1.130.0`. The reproducible update command is `go run ./internal/themes/cmd/generate`.
- The generated VS Code catalog lives under `internal/themes` and includes all 19 first-party color themes contributed by pinned built-in `theme-*` extensions: Abyss, Dark Modern, Light Modern, Dark (Visual Studio), Dark 2026, Dark High Contrast, Dark+, Kimbie Dark, Light (Visual Studio), Light 2026, Light High Contrast, Light+, Monokai, Monokai Dimmed, Quiet Light, Red, Solarized Dark, Solarized Light, and Tomorrow Night Blue. The full selectable catalog is 21 themes when the two OpenVibely defaults are included.
- Theme JSON includes/inheritance are resolved at generation time. Generated runtime values are sanitized normalized OpenVibely semantic colors, syntax colors, and preview colors; the app must not fetch VS Code/GitHub/Marketplace data at runtime.
- DOM state separates compatibility mode from exact palette: keep `data-theme="light"` or `data-theme="dark"` for DaisyUI/existing selectors and use `data-color-theme="<stable-theme-id>"` for the exact selected palette. High-contrast themes retain high-contrast identity even when their base compatibility mode is light or dark.
- Theme selection is an app/system UI preference, not project configuration. Durable restart persistence belongs in OpenVibely's database/user-settings layer, currently the `app_settings` key `ui.theme`; default when unset is `openvibely-dark`. `localStorage.theme` remains only the same-browser/same-origin mirror and early-apply helper, never the cross-restart or cross-port authority. `data-color-theme="<stable-theme-id>"` mirrors the exact selected ID, while `data-theme="light"` or `data-theme="dark"` remains the DaisyUI/existing-selector compatibility mode. Legacy `localStorage.theme` values of `light` or `dark` are migrated/fallbacked to the OpenVibely Light/Dark defaults; invalid exact IDs safely fall back to those defaults. Browser `localStorage` does not sync across different browsers/profiles, private browsing contexts, cleared site data, or different origins such as a changed localhost port; desktop mode uses an ephemeral server port, so desktop restart persistence needs the database-backed cross-port fallback while still storing only the same stable theme ID rather than raw CSS/computed state. Page loads must not depend on a browser-side preference GET before rendering; full-document server render reads the setting and embeds early theme state so first paint avoids flash. Ordinary HTMX fragments should not re-read `app_settings` for theme/UI preferences on sidebar nav because the already-rendered shell owns visible theme state; HTMX history restores are full-document renders and still receive DB-backed bootstrap state. User theme changes, including footer light/dark mode toggles, update DOM/localStorage immediately and save the stable theme ID to DB through background `POST /ui/preferences`; visible theme changes should not wait for the save response. Regression coverage should preserve DB-backed restart/cross-port persistence and reject falling back to cookies or same-origin `localStorage` as the authority.
- If OpenVibely later moves to a fully separated/static frontend, DB-backed theme persistence can remain authoritative, but the current no-flash bootstrap is server-rendered-specific. A separated frontend needs a read path such as `GET /ui/preferences` or an equivalent app-shell/bootstrap payload; otherwise first paint can only use same-origin `localStorage`/defaults until DB preferences are fetched and reconciled. Preserving first-paint no-flash behavior requires server or native-shell injection of the selected stable theme ID before CSS/layout application.
- The footer sun/moon control is a quick mode switch that toggles between the most recently selected light-side and dark-side themes, treating high-contrast-light as light and high-contrast-dark as dark. In the legacy `data-theme` path, the toggle pill itself must not reuse the dark track in light mode: light mode should render a light track such as `#E8E8E8`, while `[data-theme="dark"] .theme-toggle-pill` keeps the dark `#3a4455` track.
- Footer theme-mode controls can render after the early head script, so runtime theme application must export/rerun a control sync after DOM insertion. Initial sidebar markup should avoid hardcoded dark-mode ARIA/tooltips; `aria-pressed`, `aria-label`, `title`, and tooltip text derive from the current selected light/dark mode.
- Apply theme CSS variables early before paint to avoid theme flash. To avoid response-size regressions, base layout embeds only a compact runtime catalog needed for early application; the full catalog remains available server-side for the Themes page.
- Application and content backgrounds for imported VS Code themes must follow the selected exact VS Code palette, not DaisyUI/default fallbacks. Semantic `contentBg` should prefer VS Code `editor.background`/`window.background` before secondary panel/sidebar surfaces, and app-shell CSS should apply the generated content background to the root/page canvas, `.drawer-content`, and `#main-content`; the Red theme regression is that non-nav content must use its red editor background (`#390000`) instead of generic dark gray (`#252526`).
- Modal surfaces for imported VS Code themes are part of the exact-theme contract: `.modal-box`, nested modal base surfaces/action strips, close-button hover/focus states, and modal backdrop treatment should derive from generated OpenVibely semantic variables such as `--ov-surface-raised`, `--ov-text`, `--ov-border`, `--ov-hover-bg`, and `--ov-focus`, rather than DaisyUI/default light/dark backgrounds.
- Card surfaces and borders for imported VS Code themes are part of the exact-theme contract: `.card`, searchable cards, dropdown card actions, `border-base-300` variants, divider utilities, and directional border utilities should use subtle generated surface/border roles rather than accent/focus/high-contrast borders. Hover border highlights should be reserved for actually clickable/actionable cards and controls; non-clickable cards and inert schedule cells should not gain primary/focus-colored borders just because the mouse is over them.
- Schedule and task-board interaction surfaces for imported VS Code themes are part of the exact-theme contract: schedule grid/timeline accents, today highlights, scheduled/disabled task chips, legend swatches, schedule drag valid/invalid feedback, kanban `.drag-over`, task selected states, category/task dropzones, and legacy shared link/accent tokens such as `--ov-link-color` should consume generated semantic variables such as `--ov-border`, `--ov-link`, `--ov-selection-bg`, `--ov-focus`, `--ov-hover-bg`, and `--ov-diff-delete-bg`, rather than fixed indigo/red/DaisyUI colors. Scheduled task chips should use neutral raised surface/hover roles with a subtle link/accent border, not selection/diff/error backgrounds; Abyss in particular must not produce red schedule task cards. Task dropzone drag feedback should preserve the dashed-outline/dropzone geometry for both valid and invalid targets while allowing the outline color to vary by theme. Regression history/fix from 2026-08-14: an imported-theme transparent-border override for `.category-drop-zone`/`.task-drop-zone` placed after `.drag-over` with equal specificity and `!important` hid the active dashed border; keep the dropzone-specific `.category-drop-zone.drag-over`/`.task-drop-zone.drag-over` override after the transparent baseline so active drag-over wins without changing dropzone geometry.
- Generated semantic variables should be visibly consumed by imported VS Code theme CSS, including status feedback (`info`, `success`, `warning`, `error`), selection, hover, focus, input borders, card borders, modal surfaces, schedule/dropzone interaction states, and diff/review add/modify/delete backgrounds, so UI states follow the exact selected VS Code palette rather than fixed DaisyUI light/dark colors. Native `openvibely-*` defaults should not be caught by the invasive VS Code layout/surface/border override selectors; they should keep the original OpenVibely default nav, card, border, schedule, dropzone, and modal styling behavior. Regression history: broad exact-theme canvas/layout overrides added in `943443ed` became visible as a black/light-canvas bug after native `openvibely-light`/`openvibely-dark` became selectable in `e481e797`; the durable fix direction is to scope invasive exact-theme layout/surface overrides to imported VS Code themes (`[data-color-theme^="vscode-"]`) while native defaults use their original OpenVibely styling path.
- Chat and task-thread surfaces for imported VS Code themes are exact-theme UI, but chat bubbles should preserve the old/native neutral conversation-surface role rather than mechanically using primary/button accent fills. User bubbles and assistant bubbles should use the same subtle generated raised surface/text/border treatment; do not add a separate high-contrast/accent border for user messages. Chat/task-thread input boxes should use the same subtle border treatment as chat bubbles, not a high-contrast input border. Embedded chat code/tool panels should use generated code/surface/border/text roles; chat Markdown borders/tables, stream-thinking text, stream tool toggles/status icons, loading dots, task-result action buttons, selection counter, STT recording feedback, tabs, toggles, and footer theme-toggle controls should use generated link/focus/status/surface/selection variables rather than DaisyUI light/dark or fixed OpenVibely purple/red fallbacks. Keep these selectors scoped to `[data-color-theme^="vscode-"]` so native OpenVibely defaults preserve their original chat-bubble/input/control styling path.
- Button variants for imported VS Code themes are exact-theme UI: primary/accent, secondary/neutral, info/success/warning/error, ghost, link, outline, hover, and focus states should derive from generated semantic variables such as `--ov-button-bg`, `--ov-button-hover-bg`, `--ov-button-secondary-bg`, `--ov-info`, `--ov-success`, `--ov-warning`, `--ov-error`, foreground contrast helpers, `--ov-hover-bg`, `--ov-focus`, and `--ov-selection-bg`, not fixed DaisyUI/native light/dark button colors. Keep the CSS compact rather than large repeated selector matrices because the base layout and downstream pages are size-gated.
- Analytics OAuth account usage meter colors for imported VS Code themes are part of the exact-theme contract: under `[data-color-theme^="vscode-"]`, `--ov-account-limit-track` should derive from the selected theme's generated hover/track role such as `--ov-hover-bg`, and `--ov-account-limit-fill` should derive from the selected theme's generated accent/button role such as `--ov-button-bg`. Native OpenVibely defaults should keep their fixed account-meter colors rather than being caught by broad exact-theme overrides.
- The theme generator and attribution docs should describe semantic fallback/derivation rules for missing VS Code colors: ordered upstream color keys win first, transparent or invalid values are ignored/sanitized, missing roles derive through theme-aware mixes/alpha/best-text helpers, and remaining gaps fall back to bundled light/dark defaults.
- Highlight.js should not load a fixed GitHub Dark stylesheet. Rendered Markdown/code block syntax colors derive from the selected theme through generated CSS variables and must work for initial and HTMX-inserted content.
- For imported VS Code themes, Automation graph and YAML surfaces are exact-theme UI. Live/Edit graph panels, nodes, connectors, arrows, connection handles, state colors, edge/node delete controls, and focus outlines should react to the selected theme through generated surface/border/focus/status variables rather than fixed DaisyUI OKLCH tokens. Automation nodes need visible borders in both Live/preview and Edit modes, and connector lines must contrast with the canvas instead of matching the background. The Automation YAML editor and read-only Live YAML panel are exact-theme code surfaces: panel background/foreground, gutter, line numbers, highlight overlay, caret, YAML keys/values/scalars/comments, diagnostics, indentation dots, and indentation rails should use generated code/syntax/border/focus/error variables such as `--ov-code-*`, `--ov-syntax-*`, `--ov-border-*`, `--ov-focus`, and `--ov-error`. YAML indentation rails should all remain visible by default, and when the editor is focused only the innermost active group rail should switch to the theme focus role; do not recolor every visible rail on focus. Standalone browser fixtures may use safe fallbacks.
