# Consolidated transcript migration

The branch registers one migration: `219_transcript_store.go`. Numbers 217 and 218 are reserved for local main's organizations and task-model-overrides migrations. This change does not merge or modify main. The test fixtures are exact copies from main `b1a8d29ddc98dac2663d49fe6f4cf53810a89da4` and are not registered production migrations.

A fresh database applies the complete transcript schema and conversion in one Goose transaction. Downgrade reverses the stages in dependency order: ranges become owned items, metadata is removed, pending stream text becomes display items, references are materialized, then output/replay/checkpoints return to the pre-transcript representation. Unregistered helper code retains the intermediate SQL because development databases may have applied only some of it.

Before Goose runs, startup identifies old branch schemas using actual tables/columns and active version records. Versions 217–221 from the unpublished branch are completed to the final schema without rebuilding existing transcript rows or changing their sequence IDs. That completion and replacement of the old version records by 219 happen in one transaction. Reopening an adopted database does nothing. Schema/version mismatches fail without relabelling the database. Main's organizations schema distinguishes its 217/218 records from the unpublished branch records; they are not deleted.

No existing user database was opened or modified while implementing this change. As with other migrations, retain a backup before running development builds against valuable data. Applying the consolidated schema is a one-way version-history adoption: an older development binary that expects the five intermediate migration IDs is not a supported downgrade target. Use the consolidated migration's Down path or restore the pre-upgrade backup instead.

Tests cover all five intermediate branch versions, a pre-transcript database, pending Unicode stream output, stable journal sequences, idempotent reopening, malformed-schema rejection, and main 218 → 219 → 218 → 219. Existing reference/range and payload conversion rollback tests retain explicit coverage of intermediate steps without registering them as migrations. The test-only baseline filesystem includes main's files so downgrade to 218 resolves normally before main is merged into this branch.
