# Automation Implementation Status

## Current State

Automation Graphs is implemented as a project-scoped custom automation builder over existing OpenVibely Tasks, Scheduler rows, workers, Native Alerts, GitHub services, queues, and runtime projection. Template, Describe It, Blank, and Chat use the same surfaced graph contract and safety boundaries.

Each Automation has exactly one current saved graph. There is no Automation draft lifecycle, retained version history, superseded graph, version selection, Definition page, execution/history page, invocation page, work-item page, node-resource sidebar, Save journal, failed-Save recovery item, plan revision, or compiler contract version. Internal graph IDs exist only for current runtime identity.

## Save Contract

- New and edited web graphs exist only in browser memory until `Save changes`. Refresh or navigation discards unsaved changes.
- Save validates the complete submitted graph, including every explicitly present browser form overlay, applies real resources immediately, and creates or replaces the current graph under the same Automation identity. Explicit empty Automation/node names and malformed numeric Task priority or Schedule repeat-interval overlays are preserved as invalid input for semantic validation rather than replaced by stale valid values from hidden `candidate_json`. Strict normalization trims non-semantic formatting but does not overwrite `automation_type`, fill explicit empty maintained-node names, derive or overwrite Task/Schedule categories, or add custom Schedule targets from graph topology; explicit invalid values reach validation and fail before effects.
- Save may replace the current graph while Automation work is active. Successful replacement deletes the prior graph and its Automation runtime projection in the same transaction. Failure leaves the current graph and behavior unchanged.
- Template, Describe It, Blank, and Edit are browser-local until `Save changes`. `Use template` loads the maintained candidate into the builder and creates no Automation, Task, or Scheduler row.
- Maintained Native and GitHub registration is a point-in-time setup path, not an upgrade path. First registration copies that release's bundled template and complete valid maintained-node defaults into one saved graph, then overlays exact bound Task/Schedule configuration. Later registration reruns return the existing Automation, graph, bindings, lifecycle, owned Schedules, and runtime projection unchanged even when the bundled template or supplied resources differ. Trusted Edit reconstruction fills only missing canonical keys in older registered snapshots, without overwriting explicit values or mutating storage before `Save changes`; public Save input receives no such repair. Users adopt a newer bundled template only by deleting the old Automation and creating it again. Registration may still remove obsolete noncurrent graphs and exclusively owned Schedules left by pre-contract failed/draft attempts.
- Save writes Automation identity, the complete graph, Task changes, Scheduler rows, bindings, lifecycle-compatible admission state, and replaced-graph cleanup in one SQLite transaction. Replacement allocates a collision-free temporary graph sequence and removes every noncurrent graph before normalizing the new current graph to sequence 1, so databases upgraded with a retained failed draft still Save successfully. Any error rolls back all Save writes, so a first Save creates nothing and an edit leaves its previous graph active.
- Chat uses `plan_automation_save` followed by later-confirmed `save_automation`. Before Save, the displayed plan and private confirmation state expose no Automation/graph identity, URL, runtime resources, or draft terminology. Confirmation consumption and Save commit atomically.
- A rejected browser Save renders a prominent `Save did not apply` message and expands the actionable setup list. For an unready GitHub SDLC graph, the list names connected GitHub authentication, at least one GitHub Authorized User, and either a project GitHub repository URL or a GitHub remote in the project's local checkout; the failed attempt still creates no Automation, Task, or Schedule rows. The maintained GitHub template owns valid defaults for its browser fields (`instructions`, `labels`, `base`, and `draft`) and for its configuration-only downstream Implementation Task (`prompt`, Active `category`, and priority `2`). Save applies strict required-value, type, length, list-size, category/priority, and forbidden `openvibely:` label-prefix validation before any persistence.

## Graph Contract

- Blank is an open custom builder, not a preset assembler. Users can add supported Schedule, Task, Native Alert, GitHub action/gate, and Outcome nodes and connect deterministic supported handoffs.
- A Schedule is a substantive Task plus a Scheduler row targeting that same Task. `Schedule → Task` means scheduled Task A completes before OpenVibely activates distinct follow-up Task B. Custom Schedule handoffs are represented only by graph edges; public candidates containing `target_node_key` are rejected, while trusted reopen removes obsolete topology-derived metadata from older saved graphs.
- Maintained Native and GitHub recurring loops use one Schedule node per substantive scheduled Task, including their built-in Vision Suggestions role. New-template, Chat-template, Describe It canonical-preset, and authoritative Save creation surfaces expose only these two maintained SDLC templates. The internal Vision Driver adapter remains solely so already-saved graphs can still be reconstructed, edited, and run without migration or backfill; `AutomationCompiler.Save` rejects a Vision Driver candidate when no existing project-scoped Automation is found.
- The maintained GitHub SDLC Automation owns complete Offering Manager, finder, Dev Inbox, issue-specific Implementation, and Loop Auditor prompts plus daily discovery, hourly inbox, and weekly auditor cadences. The Implementation node is configuration-only at Save time but carries the canonical prompt, Active category, and priority copied into each later issue-specific Task; because assignment is approval, runtime submits that Task immediately. The maintained Native SDLC Automation likewise owns complete Vision Suggestions, finder, Notification Inbox, and Loop Auditor prompts aligned with the bundled Native bootstrap contract: focused notification-only discovery with stable idempotency, approved-notification inspection and atomic claim/link processing, bounded recovery, and approval-gated audit reporting. Neither template reads or requires its bootstrap skill at runtime. Initial registration hydrates complete canonical configuration plus exact bound Task/Schedule configuration into the point-in-time graph without mutating bound Task prompts; later registration reruns do not rewrite existing snapshots.
- Graph connections leave the source node's unlabeled right output handle and enter the target node's unlabeled left input handle. Missing, reversed, or same-kind ports are rejected through the public Save path. Legacy saved connector metadata is normalized only when reopening an existing saved graph.
- Unsupported handoffs, unsafe configuration, ambiguous task parents, executable cycles, invalid conditions, foreign-project references, and unavailable capabilities fail closed before resource effects.
- The hidden Workflow subsystem is not exposed as an Automation node.

## Runtime And Lifecycle

- Newly created runnable Tasks remain non-admitted Backlog rows inside the Save transaction until the graph, resource membership, configured categories, and topology are ready. New or existing roots that end Save as pending and Active are submitted through the existing worker only after commit, including Backlog-to-Active changes and completed roots reset to pending.
- Saving while paused or archived preserves that lifecycle. It does not enable schedules, resume work, or reacquire active ownership. Pause and Archive atomically demote all current-graph pending Active Tasks, including definition-bound roots, entered downstream children, and activity-created child Tasks, to Backlog. Pause records only activity children that were Active at deactivation, so Resume can restore those exact Tasks once without admitting intentionally Backlog work; Archive discards that admission and remains non-resumable. Ordinary dispatch rechecks current graph lifecycle in the same immediate claim transaction, demotes and rejects a Task when deactivation won the race, and preserves stale replaced-graph domain Tasks as independent work.
- Active root Tasks added or changed from Backlog to Active while paused remain non-admitted until explicit Resume. Downstream task handoffs recheck the current graph and lifecycle in the same transaction: Paused and Archived Automations persist the causal handoff as pending Backlog work without submitting it, Resume derives effective runnable state from the exact current topology, entered transition, or durable paused activity-child admission so Schedule-derived `task`, `github_inbox`, issue-specific, and generic activity-created children are admitted once when eligible, ordinary configured Backlog Tasks remain deferred, and Archived Automations remain non-resumable. Custom Task fan-out treats queued or running children as branch-local contention: each busy branch records its blocked projection and remains unchanged while later independent siblings are still attempted, and the combined completion result continues to report the busy condition.
- Unrelated Automation edits preserve each retained Scheduler row's exact `run_at` and `next_run` when cadence fields are unchanged. Maintained registration reruns leave the saved schedule configuration and configured enabled or disabled intent untouched; lifecycle state keeps paused or archived schedules physically disabled until explicit Resume restores that saved intent.
- Ordinary queued roots atomically claim and retrieve their full authoritative persisted Task plus current Automation context in one SQLite immediate transaction. A queued Task ID is only an admission hint: replacement prompt, selected Agent, topology, and graph identity are loaded at the claim linearization point, so Save and dispatch cannot mix old Task behavior with a replacement graph. Definition-only root provenance creates and terminalizes an execution-scoped work item on the admitted Live graph; prepared Automation dispatches retain their exact immutable envelope.
- Archived Automations retain disabled exclusive schedule provenance using archived owner rows. Archived edits can therefore remove obsolete Scheduler rows, and deleting an archived Automation removes all exclusively owned Scheduler rows while preserving Tasks. Deletion rejects both scheduler in-flight work and ordinary running Task executions linked through exact Automation activity resources; an ordinary execution stops blocking once terminal. An orphaned `running` invocation left after ordinary Task deletion has already cascaded away its dispatch and execution no longer blocks deletion forever.
- Automation GitHub runtime paths use the current project's repository URL when configured and otherwise resolve a GitHub remote from the project's local checkout. This same URL-first/local-remote boundary is used by Save readiness, issue tools, issue-specific Task creation, task-scoped PR open/replace, and external-state refresh, so Save cannot accept a repository that runtime later rejects. Model-supplied repository overrides remain ignored. GitHub Dev Inbox `create_task` validates the exact current execution, discovered issue work item, active graph, and required inbox-to-task-to-PR topology before inserting a Task. Task insertion, goal insertion, and issue-work-item provenance commit atomically under a stable work-item activity claim, so failures leave no unbound Task and concurrent or repeated calls reuse one canonical implementation Task. Compiler-created and issue-specific Tasks retain a durable Automation-origin marker after graph replacement deletes old projection. Migration `124` and the pre-replacement Save correction repair only prior feature-created issue Tasks carrying the exact `work-item:<id>:implementation-task` activity, child-task relation, and Task/legacy-implementation node provenance; unrelated pre-feature and generic `create_task` resources are not inferred or registered. Idle web, queued/channel, and failed-retry Task Thread paths load both the Task and causal Automation context before runtime composition; when replacement has removed that context, the durable marker installs an origin-only fail-closed guard, while already-prepared old bindings are revalidated against the current active graph. Task-bound Discord, Slack, and Telegram `create_task` handlers use the same hardened creation path. Every Automation-bound GitHub write is intercepted before generic runtime fallback and stale origin/binding contexts cannot invoke provider mutations. Issue creation, PR opening, and guarded PR branch replacement additionally require every caller binding to authorize the exact mutation topology, and task-scoped PR mutations must target the causal caller Task. Issue-creation duplicate protection never lists, searches, fetches, or compares existing GitHub issues. It uses a durable local project/repository/normalized-title-fingerprint record with `reserved`, `dispatched`, and `completed` states. Only a definitively pre-dispatch reservation may expire or be released. Once GitHub may have mutated, an ambiguous outcome remains permanently fail-closed. A successful returned issue number and an IDs-only snapshot of the exact OpenVibely projection source are recorded in the claim; the claim stores no GitHub title, body, comment, or instruction content. A completed claim is reusable only by the same project, Task, and complete Automation/graph/source-node binding set, while invocation and execution IDs may change for a legitimate later run. Cross-Automation, replacement-graph, source-node, and Task collisions fail closed without another provider mutation or GitHub lookup. The issue activity, work item, issue transition, and waiting assignment transition are finalized with a bounded context independent of caller cancellation. Same-source same- and later-execution retries idempotently repair any missing projection and return the locally recorded canonical issue only after every stored source binding records its expected issue and assignment transitions. A resource already present on one causal binding is treated as reconciliation evidence and cannot short-circuit completed-claim repair for the remaining bindings. Deleted or incomplete source graphs remain reconciliation errors rather than successful no-ops. Historical claims without trusted projection-source IDs remain fail-closed. Assigned-issue inbox reads remain a separate human-gated flow and are not used for deduplication.
- Native Alert approval never authorizes merge, release, or deployment. GitHub assignment, review, merge, release, and deployment remain human-controlled.
- Runtime state is shown only in the full-width Live graph, whose canvas grows to fill the remaining viewport height. Only Schedule and Task nodes with exact current task bindings navigate, and they open that existing project-scoped Task; nodes without runtime resources are inert. Polling, SSE, visibility, and manual external refreshes each use an independent request source plus one browser request-generation guard, so genuinely overlapping responses can complete out of order without an older response overwriting newer Live state.
- The Automations portfolio reads every saved project Automation rather than a fixed first page, excludes unsaved publication-era draft shells at the repository boundary, and retains deterministic updated-time ordering and browser-side search across all cards. Periodic health reconciliation likewise excludes unsaved shells and traverses every saved Automation in bounded primary-key pages, so health updates cannot leave rows beyond the first 100 permanently stale. Migration `122` deletes Scheduler rows created by failed publication attempts while their exact create-step journal still exists, preserving current and unrelated schedules plus every backing Task. Migration `125` deletes schedules exactly owned by draft-only or noncurrent graphs before removing those identities/graphs, then normalizes the current sequence/state and adds the lifecycle admission store for paused activity-created Tasks. Migration `126` adds the local created-issue number used by Automation issue deduplication; it stores no GitHub title, body, comment, or instruction text. Migration `127` adds the durable mutation state and conservatively marks pre-upgrade numberless claims as dispatched uncertainty rather than reopening them. Migration `128` adds the IDs-only projection-source snapshot for new claims; historical rows remain without inferred provenance and therefore fail closed if projection repair is requested.
