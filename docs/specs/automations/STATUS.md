# Automation Implementation Status

## Current State

Automation Graphs is implemented as a project-scoped custom automation builder over existing OpenVibely Tasks, Scheduler rows, workers, Native Alerts, GitHub services, queues, and runtime projection. Template, Describe It, Blank, and Chat use the same surfaced graph contract and safety boundaries.

Each Automation has exactly one current saved graph. There is no Automation draft lifecycle, retained version history, superseded graph, version selection, Definition page, execution/history page, invocation page, work-item page, node-resource sidebar, Save journal, failed-Save recovery item, plan revision, or compiler contract version. Internal graph IDs exist only for current runtime identity.

## Save Contract

- New and edited web graphs exist only in browser memory until `Save changes`. Refresh or navigation discards unsaved changes.
- Save validates the complete submitted graph, applies real resources immediately, and creates or replaces the current graph under the same Automation identity. Strict normalization trims non-semantic formatting but does not overwrite `automation_type`, fill explicit empty maintained-node names, derive or overwrite Task/Schedule categories, or add custom Schedule targets from graph topology; explicit invalid values reach validation and fail before effects.
- Save may replace the current graph while Automation work is active. Successful replacement deletes the prior graph and its Automation runtime projection in the same transaction. Failure leaves the current graph and behavior unchanged.
- Template, Describe It, Blank, and Edit are browser-local until `Save changes`. `Use template` loads the maintained candidate into the builder and creates no Automation, Task, or Scheduler row.
- Maintained Native and GitHub registration is a point-in-time setup path, not an upgrade path. First registration copies that release's bundled template into one saved graph. Later registration reruns return the existing Automation, graph, bindings, lifecycle, owned Schedules, and runtime projection unchanged even when the bundled template or supplied resources differ. Users adopt a newer bundled template only by deleting the old Automation and creating it again. Registration may still remove obsolete noncurrent graphs and exclusively owned Schedules left by pre-contract failed/draft attempts.
- Save writes Automation identity, the complete graph, Task changes, Scheduler rows, bindings, lifecycle-compatible admission state, and replaced-graph cleanup in one SQLite transaction. Replacement allocates a collision-free temporary graph sequence and removes every noncurrent graph before normalizing the new current graph to sequence 1, so databases upgraded with a retained failed draft still Save successfully. Any error rolls back all Save writes, so a first Save creates nothing and an edit leaves its previous graph active.
- Chat uses `plan_automation_save` followed by later-confirmed `save_automation`. Before Save, the displayed plan and private confirmation state expose no Automation/graph identity, URL, runtime resources, or draft terminology. Confirmation consumption and Save commit atomically.

## Graph Contract

- Blank is an open custom builder, not a preset assembler. Users can add supported Schedule, Task, Native Alert, GitHub action/gate, and Outcome nodes and connect deterministic supported handoffs.
- A Schedule is a substantive Task plus a Scheduler row targeting that same Task. `Schedule → Task` means scheduled Task A completes before OpenVibely activates distinct follow-up Task B. Custom Schedule handoffs are represented only by graph edges; public candidates containing `target_node_key` are rejected, while trusted reopen removes obsolete topology-derived metadata from older saved graphs.
- Maintained Native and GitHub recurring loops use one Schedule node per substantive scheduled Task. Vision Driver also uses one Schedule node rather than a schedule relay linked to a duplicate same-purpose Task.
- The maintained GitHub SDLC Automation owns complete Offering Manager, finder, Dev Inbox, and Loop Auditor prompts plus daily discovery, hourly inbox, and weekly auditor cadences. It does not read or require the bootstrap skill at runtime. Initial registration hydrates the exact bound Task/Schedule configuration into the point-in-time graph without mutating the bound Task prompt; later software releases do not rewrite existing saved Automations.
- Graph connections leave the source node's unlabeled right output handle and enter the target node's unlabeled left input handle. Missing, reversed, or same-kind ports are rejected through the public Save path. Legacy saved connector metadata is normalized only when reopening an existing saved graph.
- Unsupported handoffs, unsafe configuration, ambiguous task parents, executable cycles, invalid conditions, foreign-project references, and unavailable capabilities fail closed before resource effects.
- The hidden Workflow subsystem is not exposed as an Automation node.

## Runtime And Lifecycle

- Newly created runnable Tasks remain non-admitted Backlog rows inside the Save transaction until the graph, resource membership, configured categories, and topology are ready. New or existing roots that end Save as pending and Active are submitted through the existing worker only after commit, including Backlog-to-Active changes and completed roots reset to pending.
- Saving while paused or archived preserves that lifecycle. It does not enable schedules, resume work, or reacquire active ownership. Pause and Archive atomically demote all current-graph pending Active Tasks, including definition-bound roots, entered downstream children, and activity-created child Tasks, to Backlog. Pause records only activity children that were Active at deactivation, so Resume can restore those exact Tasks once without admitting intentionally Backlog work; Archive discards that admission and remains non-resumable. Ordinary dispatch rechecks current graph lifecycle in the same immediate claim transaction, demotes and rejects a Task when deactivation won the race, and preserves stale replaced-graph domain Tasks as independent work.
- Active root Tasks added or changed from Backlog to Active while paused remain non-admitted until explicit Resume. Downstream task handoffs recheck the current graph and lifecycle in the same transaction: Paused and Archived Automations persist the causal handoff as pending Backlog work without submitting it, Resume derives effective runnable state from the exact current topology, entered transition, or durable paused activity-child admission so Schedule-derived `task`, `github_inbox`, issue-specific, and generic activity-created children are admitted once when eligible, ordinary configured Backlog Tasks remain deferred, and Archived Automations remain non-resumable. Custom Task fan-out treats queued or running children as branch-local contention: each busy branch records its blocked projection and remains unchanged while later independent siblings are still attempted, and the combined completion result continues to report the busy condition.
- Unrelated Automation edits preserve each retained Scheduler row's exact `run_at` and `next_run` when cadence fields are unchanged. Maintained registration reruns leave the saved schedule configuration and configured enabled or disabled intent untouched; lifecycle state keeps paused or archived schedules physically disabled until explicit Resume restores that saved intent.
- Ordinary queued roots atomically claim and retrieve their full authoritative persisted Task plus current Automation context in one SQLite immediate transaction. A queued Task ID is only an admission hint: replacement prompt, selected Agent, topology, and graph identity are loaded at the claim linearization point, so Save and dispatch cannot mix old Task behavior with a replacement graph. Definition-only root provenance creates and terminalizes an execution-scoped work item on the admitted Live graph; prepared Automation dispatches retain their exact immutable envelope.
- Archived Automations retain disabled exclusive schedule provenance using archived owner rows. Archived edits can therefore remove obsolete Scheduler rows, and deleting an archived Automation removes all exclusively owned Scheduler rows while preserving Tasks.
- Automation GitHub runtime paths require the current project to have an explicit `repo_url`; Automation issue, task-scoped PR, and external-state refresh resolution never passes `repo_path` or infers a local Git remote. Model-supplied repository overrides are ignored. GitHub Dev Inbox `create_task` validates the exact current execution, discovered issue work item, active graph, and required inbox-to-task-to-PR topology before inserting a Task. Task insertion, goal insertion, and issue-work-item provenance commit atomically under a stable work-item activity claim, so failures leave no unbound Task and concurrent or repeated calls reuse one canonical implementation Task. Compiler-created and issue-specific Tasks retain a durable Automation-origin marker after graph replacement deletes old projection. Migration `124` and the pre-replacement Save correction repair only prior feature-created issue Tasks carrying the exact `work-item:<id>:implementation-task` activity, child-task relation, and Task/legacy-implementation node provenance; unrelated pre-feature and generic `create_task` resources are not inferred or registered. Idle web, queued/channel, and failed-retry Task Thread paths load both the Task and causal Automation context before runtime composition; when replacement has removed that context, the durable marker installs an origin-only fail-closed guard, while already-prepared old bindings are revalidated against the current active graph. Task-bound Discord, Slack, and Telegram `create_task` handlers use the same hardened creation path. Every Automation-bound GitHub write is intercepted before generic runtime fallback and stale origin/binding contexts cannot invoke provider mutations. Issue creation, PR opening, and guarded PR branch replacement additionally require every caller binding to authorize the exact mutation topology, and task-scoped PR mutations must target the causal caller Task. Issue-creation duplicate protection never lists, searches, fetches, or compares existing GitHub issues. It uses a durable local project/repository/normalized-title-fingerprint record containing only the issue number OpenVibely successfully created, with a short local lease so concurrent equivalent runs cannot both create an issue. Assigned-issue inbox reads remain a separate human-gated flow and are not used for deduplication.
- Native Alert approval never authorizes merge, release, or deployment. GitHub assignment, review, merge, release, and deployment remain human-controlled.
- Runtime state is shown only in the full-width Live graph, whose canvas grows to fill the remaining viewport height. Only Schedule and Task nodes with exact current task bindings navigate, and they open that existing project-scoped Task; nodes without runtime resources are inert. Polling, SSE, visibility, and manual external refreshes each use an independent request source plus one browser request-generation guard, so genuinely overlapping responses can complete out of order without an older response overwriting newer Live state.
- The Automations portfolio reads every saved project Automation rather than a fixed first page, excludes unsaved publication-era draft shells at the repository boundary, and retains deterministic updated-time ordering and browser-side search across all cards. Periodic health reconciliation likewise excludes unsaved shells and traverses every saved Automation in bounded primary-key pages, so health updates cannot leave rows beyond the first 100 permanently stale. Migration `122` deletes Scheduler rows created by failed publication attempts while their exact create-step journal still exists, preserving current and unrelated schedules plus every backing Task. Migration `125` deletes schedules exactly owned by draft-only or noncurrent graphs before removing those identities/graphs, then normalizes the current sequence/state and adds the lifecycle admission store for paused activity-created Tasks. Migration `126` adds the local created-issue number used by Automation issue deduplication; it stores no GitHub title, body, comment, or instruction text.
